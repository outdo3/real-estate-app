## 1. 기존 지도 관련 코드 전수 조사

repository 전체를 검색해 지도 관련 파일을 확인했다(추측 없이 코드 직접 읽음).

| 파일 | 역할 | 사용처 |
|---|---|---|
| `src/app/map/page.tsx`(911줄) | `/map` 전용 풀스크린 지도 페이지 | `/map` 라우트 단독 |
| `src/components/MapViewer.tsx` | `Map`+`MapMarker`(기본 핀) 래퍼 컴포넌트 | **어디서도 import되지 않음(dead code)** — grep 결과 자기 자신 정의/export 외 실제 사용 0건 |

### 1-1. `/map` 페이지 구조(코드 직접 확인)

- **SDK 로딩**: `useEffect` 안에서 `document.getElementById('kakao-map-script-main')`로 기존 스크립트 존재 여부를 먼저 확인하고, 없으면 `<script id="kakao-map-script-main" src=".../sdk.js?...&libraries=services,clusterer&autoload=false">`를 직접 주입한다. `window.kakao.maps.load()` 완료를 `setInterval` 폴링(200ms)으로 감지하고, 10초 타임아웃 시 에러 메시지를 표시한다. 스크립트 자체의 `error` 이벤트도 별도로 감지한다(광고차단 확장 등으로 인한 로드 실패 대응).
- **marker 렌더 구조**: `react-kakao-maps-sdk`의 `<CustomOverlayMap>`으로 순수 커스텀 HTML(칩)을 그린다 — `<MapMarker>`(기본 핀)는 쓰지 않는다.
- **compact/detailed 전환**: `DETAIL_ZOOM_LEVEL = 4` 기준으로 카카오맵 레벨이 이 값 이하(확대)면 `detailed`(단지명+가격 카드), 이상(축소)이면 `compact`(가격만 알약 칩)로 전환한다. `CHIP_LAYOUT` 객체에 두 모드의 width/height/gap/clusterRadius가 정의돼 있다.
- **클러스터링**: 카카오 공식 clusterer 라이브러리를 쓰지 않고, `map.getProjection().containerPointFromCoords()`로 마커를 화면 픽셀로 투영한 뒤 `chipLayout.clusterRadius` 이내 마커를 자체 알고리즘으로 그룹화해 정사각형 격자로 살짝 벌려 그린다(숫자 배지 방식이 아님 — 겹친 마커 정보가 안 보인다는 피드백으로 교체된 이력이 코드 주석에 남아 있음).
- **info window/overlay**: 별도 InfoWindow 없이, marker 클릭 시 화면 하단 고정 bottom sheet(`position: fixed; bottom: 60px`)에 선택된 단지의 이름/동/가격 + "상세보기" 버튼 + 광고(`AdContainer`)를 표시한다.
- **marker click 처리**: 1차 클릭 = 선택(하단 카드 노출), 이미 선택된 마커를 다시 클릭 = `/apt/[name]` 상세로 이동(2단계 클릭 — 실수로 바로 이동하지 않도록).
- **zoom/center**: 초기 레벨 4, `onZoomChanged`로 `zoomLevel` state 갱신 → compact/detailed 재계산. 중심은 GPS → 실패 시 IP 기반 위치(`ipinfo.io`) fallback.
- **responsive/mobile height**: 풀스크린(`100vw`/`100vh`, `position: relative` 최상위 div) — 카드 안에 들어가는 형태가 아니라 페이지 전체를 지도가 차지한다. 하단에 자체 바텀네비(`MapBottomNav`, `position: fixed`)가 별도로 떠 있다(Header를 아예 렌더링하지 않는 페이지이기 때문).
- **cleanup/unmount**: `useEffect` cleanup에서 `clearInterval`/`clearTimeout`/이벤트 리스너 해제(`removeListener`)를 전부 수행한다.
- **SDK 중복 로딩 방지**: `document.getElementById(scriptId)` 체크로 방지 — 이 방지 로직이 `KakaoMapEmbed.tsx`와 **완전히 동일한 스크립트 id 문자열(`'kakao-map-script-main'`)** 을 쓰고 있어, 두 컴포넌트가 같은 페이지에 동시에 있어도(현재는 그런 페이지 없음) 중복 주입되지 않는다.

### 1-2. `KakaoMapEmbed.tsx` 구조(코드 직접 확인)

- `address`(문자열) prop을 받아 **Kakao Geocoder로 좌표를 실시간 검색**한 뒤(`addressSearch` → 실패 시 `jibunAddress`로 재시도 → 그래도 실패 시 키워드 검색) 단일 마커(`window.kakao.maps.Marker`, vanilla SDK)를 그린다. `type='roadview'`면 로드뷰(`Roadview`/`RoadviewClient`)로 전환.
- SDK 로딩 로직이 `/map`과 **거의 동일한 패턴**(같은 script id, 같은 폴링+타임아웃+에러 처리 구조)이지만 코드는 별도로 중복 구현돼 있다(공유 헬퍼로 추출되어 있지 않음).
- **좌표를 직접 받는 방식이 아니라 항상 주소 문자열을 지오코딩**한다 — 이미 lat/lng을 알고 있는 경우에도 다시 검색을 태운다는 점에서, B4처럼 이미 확보된 좌표(Presale/ApartmentMaster)를 바로 쓰려는 용도와는 맞지 않는다.

### 1-3. `MapViewer.tsx` 구조(코드 직접 확인)

- `markers: {id, title, lat, lng}[]` prop을 받아 `<Map>`+`<MapMarker>`(카카오 기본 핀 아이콘, 커스텀 스타일 없음)로 렌더링. 검색창 + "내 위치" 버튼 내장.
- **스크립트를 직접 주입하지 않는다** — `useEffect`에서 `window.kakao`가 이미 존재하는지 폴링만 하고, 없으면 무한정 "지도 불러오는 중..."에 머문다(다른 컴포넌트가 먼저 스크립트를 로드해줄 것이라는 전제, 코드 주석에도 "page.tsx에서 로드한 것을 재사용하되"라고 명시돼 있음). **`/presales/[id]`에는 현재 Kakao 스크립트를 로드하는 코드가 어디에도 없으므로, 이 컴포넌트를 그대로 갖다 놓으면 스크립트가 영원히 로드되지 않아 화면이 멈춘다** — 실제로 재사용 불가능한 상태다.
- marker 색상/스타일 구분(분양단지 vs 주변단지) 기능이 없다 — 전부 동일한 기본 핀.

## 2. 기존 MapViewer 재사용 가능성 판단

**최종 평가: B(공통 marker/map core는 재사용 가능하지만 분양 상세용 wrapper/component가 필요)**

- MapViewer.tsx(A안의 후보)는 (1) 스크립트를 자체 로드하지 않아 `/presales/[id]`에서 그대로 쓰면 동작하지 않고, (2) 기본 핀만 지원해 "분양단지=강조/주변단지=neutral" 시각 구분(§8 요구사항)이 불가능하다 — **A(그대로 재사용)는 코드 근거로 기각**한다.
- `/map/page.tsx`(C안이 우려하는 대상)는 재사용하기엔 너무 결합돼 있다 — 풀스크린 레이아웃, 자체 바텀네비, 6개 레이어 토글, 커뮤니티/광고 연동, 자체 클러스터링 알고리즘까지 전부 `/map` 전용으로 얽혀 있어 카드 하나 크기로 축소해 재사용하는 것은 사실상 새로 작성하는 것과 다르지 않다.
- 그러나 **재사용 가능한 "core"는 실제로 존재한다**: (a) `react-kakao-maps-sdk`의 `<Map>`+`<CustomOverlayMap>` 조합(이미 설치된 패키지, `/map`이 실전 검증), (b) `kakao-map-script-main`이라는 공유 script id + 폴링/타임아웃/에러 처리 패턴(`/map`과 `KakaoMapEmbed` 둘 다 동일하게 씀 — 이미 두 곳에서 검증된 관례), (c) `--primary-color`(#03c75a) 강조 + `#94a3b8`/`--border-color` neutral 이라는 기존 색상 구분 관례(`/map`의 `renderMarkerChip`이 이미 "최근 거래 있음(green)/없음(gray)"을 이 조합으로 구분 중).
- 따라서 B4는 **이 core 패턴들을 재사용하는 새 최소 컴포넌트**(가칭 `PresaleMapPreview`)가 필요하다고 판단한다. D(완전 신규, 기존 패턴 무시)는 과하다 — 이미 검증된 SDK 컴포넌트/스크립트 로딩 관례/색상 토큰이 있는데 이를 무시하고 처음부터 만들 이유가 없다.

## 3. Kakao SDK 로딩 전략

- `/presales/[id]`는 현재 Kakao 스크립트를 로드하는 코드가 없다(위치정보 카드는 외부 링크(`<a href="https://map.kakao.com/...">`)만 사용, 임베드 없음).
- B4를 추가하면 새 컴포넌트가 **`KakaoMapEmbed.tsx`/`/map`과 동일한 `kakao-map-script-main` script id**로 스크립트를 확인/주입해야 한다 — 이렇게 하면 사용자가 `/apt/[name]`을 먼저 방문했다가 `/presales/[id]`로 이동해도(또는 그 반대) 중복 스크립트 주입이 애초에 발생하지 않는다(SPA 네비게이션 중 스크립트 태그가 유지되는 한).
- **위험 정리(구현하지 않고 기록만)**:
  - *중복 injection*: script id 체크 패턴을 그대로 재사용하면 이 위험은 기존 두 컴포넌트에서 이미 검증된 방식으로 막을 수 있다.
  - *race condition*: `/map`의 기존 코드도 "스크립트가 이미 있지만 아직 `window.kakao.maps.load()`가 안 끝난 상태"를 폴링으로 처리하고 있어, B4도 같은 폴링 패턴을 그대로 쓰면 된다 — 새로운 위험이 아니라 기존에 이미 두 번 풀어낸 문제다.
  - *hydration 문제*: B4 컴포넌트는 `'use client'` + `useEffect` 안에서만 `window.kakao`를 참조해야 한다(B3의 `nearby-market-section.tsx`가 이미 이 방식으로 SSR/hydration mismatch 없이 동작 중).
  - *client component 요구사항*: Kakao SDK는 `window` 객체가 필요해 서버 컴포넌트로 만들 수 없다 — `presale-detail-client.tsx`가 이미 전체가 `'use client'`이므로 새 지도 컴포넌트도 자연스럽게 그 하위에서 client component로 존재하면 된다(별도 boundary 설계 불필요).

## 4. 데이터 공급 구조 — 실제 API 응답으로 확인

production `/api/presales/479/nearby-market`과 `/api/presales/479/nearby-apartments`를 직접 curl로 호출해 실제 필드를 확인했다(추측 금지).

**`nearby-market`의 `houseTypes[].comparisons[].apartment` 객체(실측)**:
```json
{
  "id": 1, "aptSeq": "26140-1361", "name": "e편한세상송도더퍼스트비치",
  "distanceKm": 0.143, "latitude": 35.0767..., "longitude": 129.0153...,
  "roadAddress": "...", "jibunAddress": "...", "sido": "부산", "sigungu": "서구",
  "buildYear": 2024, "totalHouseholds": 1302, "mainBuildingCount": 11
}
```
`recentMedianPrice`/`differenceAmount`는 이 `apartment` 객체의 형제 필드로 `comparisons[]` 최상위에 있다(`{ apartment, recentTransactions, recentMedianPrice, differenceAmount }`).

**중요한 실측 발견 — nearby-market만으로는 지도에 필요한 5개 후보 전부를 얻지 못하는 경우가 있다**:

| id | `nearbyApartmentCount`(B1 기준 후보 수) | nearby-market의 `comparisons`에 실제로 등장하는 고유 아파트 수 |
|---|---|---|
| 479 | 5 | 5 |
| 755 | 5 | 5 |
| **801** | 5 | **1** |
| **847** | 5 | **1** |
| 630 | 5 | 2 |

`nearby-market`의 `comparisons[]`는 **그 주택형과 ±1㎡ 이내 비교 가능한 거래가 있는 아파트만** 포함한다(B2 정책, 변경 대상 아님) — 비교 가능한 거래가 없는 아파트는 통째로 응답에서 빠지고, 그 아파트의 좌표도 함께 사라진다. 반면 `nearby-apartments`(B1)를 같은 5개 id에 대해 직접 호출하면 **항상 좌표 있는 5개 전부**가 그대로 반환됨을 실측으로 확인했다(예: id=801/847도 B1은 5개 전부의 `lat`/`lng`을 정상 반환).

**결론**: 지도 마커(위치)의 데이터 소스는 **B1(`nearby-apartments`)이 더 적합**하다 — B2(`nearby-market`)의 `comparisons`는 "이 주택형과 비교 가능한 아파트"만 담고 있어 지도의 "주변 아파트가 어디 있는지" 목적과 어긋난다. 반면 클릭 시 보여줄 "최근 거래 대표가격"은 B1에 없고 B2(`comparisons[].recentMedianPrice`, 선택된 주택형 기준)에만 있다 — 즉 **위치는 B1, 가격은 B2**로 역할이 갈린다.

## 5. 신규 API 필요 여부

원칙(가능하면 신규 API 금지)을 따르되, 위 §4의 실측 결과를 근거로 두 가지 현실적 선택지를 정리한다 — 이번 STEP에서는 결정하지 않고 후보만 제시한다.

- **후보 1(신규 API 호출 없음, 권장)**: B3가 이미 호출 중인 `nearby-market` 응답에 **top-level 필드 하나를 additive로 추가**(`nearbyApartments: NearbyApartmentItem[]`) — `route.ts`가 내부적으로 이미 `findNearbyApartments()`를 호출해 `items` 변수에 5개 후보를 갖고 있으므로(§27 실측 근거 코드 위치: `nearby-market/route.ts`의 `const { radiusKm, totalCandidates, items } = await findNearbyApartments(...)`), **새로운 계산·새로운 외부 호출 없이 이미 계산된 값을 응답에 노출만 하면 된다.** B3-FIX가 `supplyArea`를 추가했던 것과 동일한 성격의 additive 변경.
- **후보 2(API 코드 변경 없음, 대신 클라이언트에서 B1 별도 호출)**: 지도 컴포넌트가 `nearby-apartments`(B1)를 별도로 1회 더 호출한다. 이러면 API route 코드를 전혀 안 건드리지만, `nearby-market`이 내부적으로 이미 수행한 `findNearbyApartments()`(DB 반경검색, 문서18 실측 수십~수백ms)를 사실상 중복 실행하게 된다 — MOLIT 외부 호출처럼 비싼 작업은 아니라(문서18 §22) 성능상 치명적이지는 않지만, "이미 계산된 걸 또 계산"하는 비효율은 남는다.

두 후보 모두 **B1/B2의 기존 계산 로직·정책은 전혀 바꾸지 않는다.** 신규 route 생성은 필요 없다.

## 6. 마커 정책

- **분양단지(1개)**: `--primary-color`(#03c75a) 강조. `/map`이 "최근 거래 있음" 아파트에 이미 쓰는 것과 같은 green 토큰이라 새 색상 도입이 아니다.
- **주변단지(최대 5개)**: neutral — `/map`의 "최근 거래 없음" 케이스가 이미 쓰는 `#94a3b8`(회색) + `--border-color` 계열을 재사용 권장. 새 색상 체계를 만들지 않는다.
- 시각적 구분은 marker 모양(분양=별도 아이콘/더 큰 강조 링) + 색상 둘 다로 하는 것을 권장한다 — 색상만으로 구분하면 색약 사용자에게 접근성 문제가 생길 수 있다(§29).

## 8. 마커 클릭 정보

요청안 예시("A아파트 620m · 2021년 준공 · 최근 거래 대표가격 5억 4,100만원")를 §4에서 확인한 실제 필드로 그대로 채울 수 있다: `apartment.name` + `formatDistance(apartment.distanceKm)`(B3가 이미 쓰는 포맷 함수 재사용) + `apartment.buildYear` + (선택된 주택형의) `comparison.recentMedianPrice`(B3가 이미 쓰는 `formatManwon` 재사용).

**주의**: 선택된 주택형에 따라 `recentMedianPrice`가 없는 아파트(§4의 비교 불가 케이스)가 있을 수 있다 — 이 경우 가격 줄은 "이 주택형과 비교 가능한 거래 없음"으로 대체하거나 생략한다(가치판단/추측 금지 원칙 유지).

## 12. 모바일 지도 높이

기존 `/map`은 풀스크린(`100vh`)이라 직접 비교 기준이 되지 못한다. B3 카드 밀도(chip row + 요약 + 카드 3~5개)를 고려하면:

- 220px: 5개 마커+분양단지가 겹쳐 보일 위험(§15 bounds fit과 결합 시 너무 좁아 줌아웃이 과해짐)
- **260px(권장)**: 위치 관계를 식별하기 충분하면서, B3처럼 상세페이지가 이미 긴 상태에서 추가 스크롤 부담을 과도하게 늘리지 않는 절충점
- 280~300px: 위치 체감은 더 좋아지지만, 상세페이지 전체 길이가 유의미하게 늘어남(B3 자체도 카드 최대 5개+더보기로 이미 김)

**추천: 260px**(모바일), PC는 `max-width` 컨테이너 안에서 동일 높이를 유지하고 별도의 큰 지도를 만들지 않는다(요청 원칙 그대로).

## 13. zoom/bounds 정책

adaptive radius(문서16 §6, 1km→2km→3km)로 인해 §27 실측처럼 최단~최장 거리가 **60m~2.38km까지 편차가 매우 크다**(id=847). 고정 zoom을 쓰면:
- 좁은 지역(479: 0.06~0.25km)엔 과도하게 축소된 화면이 되고
- 넓은 지역(847: 0.095~2.38km)엔 마커가 화면 밖으로 잘려나갈 수 있다

**추천: bounds fit**(`kakao.maps.Map`의 `setBounds`/`LatLngBounds` — react-kakao-maps-sdk가 감싸는 원본 SDK 기능, 신규 패키지 아님). 분양단지 좌표 + 주변단지 좌표 전부를 포함하는 `LatLngBounds`를 계산해 지도가 자동으로 모든 마커를 한 화면에 담도록 한다 — radius 기반 고정 zoom(§15 후보 중 "radius 기반 zoom")은 §27 실측 편차를 고려하면 매 사례마다 다른 zoom 값을 하드코딩해야 해서 비현실적이다.

## 14. 좌표 없는 Presale

production 실측(id=173, id=164) 확인: `nearby-market` 응답이 `locationAvailable: false`를 정확히 반환한다. B3가 이미 이 필드로 "정확한 위치정보가 없어 주변 단지를 비교할 수 없습니다."를 표시하는 것과 동일하게, 지도 섹션도 **같은 조건으로 숨기고 동일한 톤의 안내 문구**("정확한 위치정보가 없어 지도를 표시할 수 없습니다.")를 쓸 것을 권장한다 — B3/위치정보 카드와 표현이 어긋나지 않는다. 임의 좌표 생성 금지 원칙(문서10/16에서 이미 여러 번 재확인) 그대로 유지.

## 15. 주변단지 좌표 부족

§4에서 이미 실측으로 확인한 대로, **B1(`nearby-apartments`)이 반환하는 5개 후보는 전부 좌표를 보유한다**(`findNearbyApartments`가 애초에 `ApartmentMaster.latitude/longitude not null` 조건으로만 검색하기 때문 — 문서17에서 이미 확정된 정책). 따라서 "주변단지 중 일부만 좌표 있음" 문제는 B1 기준으로는 발생하지 않는다.

다만 §4에서 발견한 대로, **B3 카드(현재 nearby-market 기반)와 지도가 B1을 직접 쓴다면 표시 개수가 다를 수 있다** — B3 카드는 "선택된 주택형과 비교 가능한 아파트만"(최대 5개, 종종 더 적음 — 예: id=801은 1개) 보여주지만, 지도는 B1 기준 "반경 내 후보 5개 전부"를 보여줄 수 있어 **지도에는 마커가 5개인데 B3 카드는 1개만 있는 상황이 실제로 발생**한다(id=801, 847 실측 확인). 이는 버그가 아니라 두 섹션의 정의가 다르기 때문(지도="주변에 물리적으로 존재하는 단지", B3 카드="가격 비교가 가능한 단지")이며, 이 차이를 감추지 말고 필요하면 지도 쪽에 "이 중 일부는 이 주택형과 비교 가능한 거래가 없을 수 있습니다" 같은 보조 설명을 고려할 수 있다(문구 확정은 구현 STEP에서).

## 16. 지도 데이터 로딩 타이밍

B3(`nearby-market`)는 cold 시 최대 4~5초 이상 걸릴 수 있음을 이번 세션 중 production에서 실측했다(INFRA I1 조사 시 `/api/presales/479/nearby-market` 4.93초 관측). 후보 비교:

| 후보 | 평가 |
|---|---|
| A. Presale 좌표만 먼저 지도 표시 → nearby 완료 후 marker 추가 | 분양단지 마커는 즉시 뜨고(Presale 데이터는 상세페이지 최초 로드에 이미 있음, 추가 fetch 불필요), 주변단지 마커만 데이터 도착 후 순차 추가 — **가장 자연스러운 progressive rendering**이며 §5 후보 1(additive 필드)과도 잘 맞는다(같은 응답 안에서 지도용 좌표 배열만 추가되므로, presale 좌표는 이미 페이지가 갖고 있고 주변 좌표만 이 응답을 기다리면 됨) |
| B. nearby-market 완료 후 지도 전체 렌더 | 구현은 가장 단순하지만 cold 시 사용자가 5초 가까이 빈 지도(또는 로딩 상태)를 봐야 함 |
| C. B1을 별도 호출 | §5 후보 2와 동일한 구조 — B1은 DB 전용이라 B2보다 훨씬 빠를 가능성이 높아(문서18 §22: DB 반경검색 40~412ms vs MOLIT 포함 전체 2.2~6.1초) **A안을 "B1으로 주변 마커를 먼저 채우고, 가격 정보는 nearby-market 도착 후 채우는" 방식으로 구체화하면 오히려 가장 빠른 체감 속도를 만들 수 있다** |

**중복 API 호출 회피 원칙과 체감 속도를 모두 고려하면**, §5 후보 1(nearby-market에 additive 필드 추가) 채택 시 A안이 자연스럽게 따라온다 — 새 호출 없이 같은 응답 안에서 "좌표(빠르게 쓸 수 있는 값)"와 "가격(조금 늦게 확정되는 값)"을 구조적으로 분리할 수 있기 때문이다. 이번 STEP에서 실제 구현은 하지 않는다.

## 17. API 호출 추가 여부

§5/§16 논의를 종합하면 **원칙적으로 신규 API 호출 없이 구현 가능**하다고 판단한다:
- 위치(마커): B3가 이미 호출 중인 `nearby-market` 응답에 additive 필드 하나만 추가(§5 후보 1) — 이러면 지도 전용 API 호출이 0이 된다.
- 가격(클릭 정보): 같은 응답의 `comparisons[].recentMedianPrice` 재사용.

이 additive 필드 추가 자체가 이번 STEP(조사/설계 전용)에서 허용된 "API 변경"은 아니므로 실제로 구현하지는 않았다 — 위 판단은 **B4 구현 STEP에서 채택 가능한 설계 방향**으로만 제시한다.

## 18. 성능 영향 분석

- **Kakao SDK 다운로드/초기화**: `/apt/[name]`에서 이미 상시 발생 중인 비용과 동일한 성격(신규 부담 아님) — 다만 `/presales/[id]`는 지금까지 이 비용이 전혀 없었던 페이지라, B4 추가는 이 페이지 기준으로는 **순수 추가 비용**이다.
- **marker 6개(분양1+주변5) + CustomOverlay**: `/map`이 실전에서 수십 개 이상의 클러스터 마커를 문제없이 렌더링 중이므로, 6개는 성능상 미미한 수준으로 판단한다.
- **모바일 LTE/5G 체감**: B3의 cold API(4~5초, 위 실측)와 Kakao SDK 다운로드(별도 네트워크 요청)가 동시에 발생하면 상세페이지 진입 초반 몇 초간 "여러 개가 동시에 로딩 중"인 상태가 체감될 수 있다. §16의 progressive rendering(분양단지 마커부터 즉시 표시)이 이 체감을 완화하는 방향이다.

## 19. Lazy load 필요성

이 프로젝트에는 `IntersectionObserver` 기존 사용 사례가 없다(전수 검색 결과 0건) — 새로 도입한다면 이 프로젝트 최초의 lazy-render 패턴이 된다. 다만 이는 "새로운 과도한 abstraction"이 아니라 **브라우저 네이티브 API**(신규 package 불필요)이므로 요청안의 "과도한 abstraction 회피" 원칙에 저촉되지 않는다.

**권장**: 지도 섹션이 viewport 근처(예: `rootMargin: '200px'`)에 왔을 때만 Kakao SDK를 로드하고 지도를 렌더링한다 — 지도가 상세페이지 중간(§10)에 위치해 있어 사용자가 스크롤하지 않으면 애초에 보이지 않는 콘텐츠이기 때문에, 즉시 로드는 §18의 초반 로딩 부담을 사용자 상당수(스크롤 안 하는 사용자)에게 불필요하게 지우는 셈이다.

## 20. 지도 실패 UX

`/map`과 `KakaoMapEmbed`가 이미 확립한 패턴(스크립트 `error` 이벤트 감지 + 폴링 타임아웃 10초 + 명확한 에러 메시지)을 그대로 재사용할 것을 권장한다. B4는 상세페이지의 **부분 섹션**이므로, `/map`처럼 전체 화면을 에러로 덮지 않고 **그 섹션만 fallback**한다:

```
지도를 불러오지 못했습니다.
[카카오맵에서 보기]  ← 기존 위치정보 카드의 외부 링크와 같은 URL 재사용
```

전체 상세페이지(청약일정/주택형/B3 카드 등)는 이 실패와 무관하게 정상 동작해야 한다 — B3가 이미 이 원칙(섹션별 독립 에러 처리)을 따르고 있어 일관된다.

## 21. 카카오맵 외부 링크 유지 여부

**유지를 권장한다.** 임베드 지도는 "위치 체감"용이고, 카카오맵 앱/웹의 **길찾기, 실제 거리뷰 탐색, 대중교통 경로, 즐겨찾기 저장** 등은 이 프로젝트가 재구현하지 않는(할 이유도 없는) 기능이다. `/apt/[name]`도 `KakaoMapEmbed`(임베드)와 별개로 카카오맵 외부 연동을 유지하고 있어(코드 확인), 이 프로젝트의 기존 일관된 패턴이기도 하다.

## 22. 사용자 가치 검증

핵심 질문: "B3 카드만 볼 때보다 위치·주변 비교단지 관계를 더 빠르게 이해할 수 있는가?"

- **거리 체감**: B3 카드는 "143m", "1.5km" 같은 텍스트만 제공한다 — 숫자만으로는 "가까운 편인지, 걸어갈 거리인지"를 직관적으로 알기 어렵다. 지도는 이 격차를 실제로 메운다.
- **방향/위치 체감**: 텍스트 거리(예: "252m")는 방향 정보가 전혀 없다 — 지도만이 제공 가능한 값이다.
- **지역경계 체감**: id=801처럼 "가장 가까운 단지가 실제로는 다른 행정구역(문서19 §16에서 확인된 사례)"인 경우, 텍스트로는 "남구 최근접"이라고만 표현되지만 지도는 이 경계 관계를 시각적으로 즉시 보여준다.
- **주변 밀집도**: id=479(0.06~0.25km, 5개 밀집) vs id=847(0.095~2.38km, 넓게 분산)의 차이는 텍스트 거리 목록만으로는 감지하기 어렵지만 지도는 한눈에 보여준다.
- **신축단지 위치**: 준공연도는 이미 카드에 텍스트로 있지만, "신축단지가 분양지 근처에 몰려있는지, 흩어져 있는지"는 지도가 더 잘 전달한다.

**결론**: 단순 시각적 장식이 아니라, 위 5개 관점 중 특히 "거리/방향 체감"과 "지역경계 체감"은 텍스트만으로는 구조적으로 전달 불가능한 정보다 — **지도 추가는 사용자 가치가 있다고 판단한다.**

## 23. B4 V1 최소 범위 제안

- 분양단지 marker 1개(강조, `--primary-color`)
- 주변단지 marker 최대 5개(neutral, B1 기준 — §4/§15)
- bounds fit(고정 zoom 아님, §13)
- marker 클릭 시 단지명/거리/준공연도/대표가격(선택된 주택형 기준, §8)
- 카카오맵 "크게 보기"(외부 링크, §21)

- lazy load(viewport 근접 시, §19)
- 실패 시 섹션 단위 fallback(§20)

**과도해서 V2로 미루는 항목**: 지도↔B3 카드 상호 연동(§9의 D 채택), 레이어 토글(`/map`의 6개 카테고리 개념은 B4에 불필요 — 분양+주변 단일 목적), 클러스터링(마커 최대 6개뿐이라 `/map` 수준의 클러스터링 알고리즘은 불필요 — 겹치면 bounds fit이 자연히 완화).

## 24. B4 분리 필요성

**분리하지 않는다(단일 STEP 권장).** §23의 V1 범위 자체가 이미 "지도 기본 렌더+marker"만으로 구성돼 있고(B4-2에 해당할 카드 연동은 처음부터 V2로 미뤘다), B1/B2가 이미 필요한 데이터를 대부분 제공하므로(§4/§17) 신규 백엔드 작업이 크지 않다. B4-1/B4-2로 나눌 만큼 작업이 크지 않다고 판단한다.

## 26. 모바일 UX 리스크

- 260px 높이(§12) 안에서 bounds fit이 6개 마커+말풍선 라벨(§7)을 전부 겹치지 않게 배치하지 못할 가능성(특히 id=479처럼 60m~252m 사이에 5개가 몰린 경우) — `/map`의 클러스터링 알고리즘을 그대로 가져오기엔 과하지만(§23), 최소한의 겹침 방지 로직(예: 라벨 생략 후 marker만)은 필요할 수 있다.
- 지도 섹션과 B3 chip 가로 스크롤이 인접해 있으면, 지도 위에서 세로 스크롤을 시도하다 지도 자체의 드래그(팬) 제스처와 충돌할 잠재적 위험 — `/map`은 풀스크린이라 이 문제가 없었지만 B4는 카드 안에 들어간 지도라 처음 겪는 상황이다. 실제 모바일 실기기 검증이 필요한 항목으로 기록한다.

## 27. 접근성 리스크

지도만으로 정보를 전달하면 screen reader 사용자가 소외된다. **B3 카드가 이미 위치·거리·준공연도 정보를 텍스트로 제공**하고 있으므로(§4의 `apartment.name`/`distanceKm`/`buildYear`가 이미 B3 카드에 노출 중), 지도가 추가해도 핵심 정보 자체가 지도에만 갇히는 상황은 원천적으로 발생하지 않는다 — 지도는 "이미 텍스트로 존재하는 정보의 시각적 보강"이라는 위치다. `role="img"` + `aria-label`(예: "분양단지와 주변 아파트 5곳의 위치를 보여주는 지도")을 지도 컨테이너에 부여할 것을 권장한다(구현 시).

## 30. 최종 판단

### 판단: **B. 지도 기능 가치 있음. 다만 기존 MapViewer 재사용보다 최소 신규 wrapper 필요.**

**근거**:
1. §2에서 확인한 대로 MapViewer.tsx는 스크립트를 자체 로드하지 않아(`/presales/[id]`에 스크립트 로더가 전혀 없음) 그대로 두면 동작하지 않고, 커스텀 마커 색상도 지원하지 않는다 — A(그대로 재사용)는 코드 근거로 기각된다.
2. 그러나 `react-kakao-maps-sdk`(이미 설치된 패키지)의 `<Map>`+`<CustomOverlayMap>`, `kakao-map-script-main` 공유 스크립트 로딩 관례(2곳에서 이미 검증), `--primary-color`/neutral 색상 조합(`/map`이 이미 검증)이라는 **재사용 가능한 core**가 실제로 존재해, 완전 신규(D)로 갈 이유는 없다.
3. §4/§15에서 실측으로 확인한 대로, 데이터는 **B1(위치)+B2(가격)를 조합**하면 신규 API 없이(또는 최소 additive 필드만으로) 충분하다 — 이는 §22 사용자 가치 평가(거리/방향/지역경계 체감을 텍스트가 구조적으로 줄 수 없다는 점)와 결합해, "가치는 있지만 새 API/스키마까지는 필요 없는" B4 V1 범위(§23)를 명확히 그릴 수 있게 한다.
4. §26/§27에서 정리한 모바일 겹침·제스처 충돌 리스크는 실제 구현·실기기 검증이 필요한 수준이지, 기능 자체를 보류할 만큼 크지 않다고 판단한다.
