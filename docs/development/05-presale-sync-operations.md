**초기 동기화 기본값**: `mode: 'initial'`이고 `fromDate`를 지정하지 않으면 **최근 3년**(`DEFAULT_INITIAL_YEARS = 3`)을 자동 적용하도록 구현했다(§C 코드 참고). 실제 전체 백필(1,046건)은 이번 STEP에서 실행하지 않았다(§26 금지사항) — `MAX_SYNC_LIMIT=200` 제약상 관리자가 6회 정도 나눠 클릭해야 완료된다는 점도 문서화해둔다.

## C. 증분 동기화 정책

### 수정일 필드 존재 여부

청약홈 Detail API 응답 49개 필드를 다시 확인한 결과, **수정일/변경일/업데이트시각을 나타내는 필드는 없다.** 모든 필드가 "모집공고일", "접수기간", "발표일" 등 공고 자체의 일정 정보이지, "이 레코드가 마지막으로 언제 바뀌었는지"를 알려주는 메타데이터는 제공되지 않는다.

### 채택한 증분 기준: "최근 모집공고일 재조회"

수정일 필드가 없으므로, 사용자가 제시한 후보 중 **"최근 모집공고일 기준 재조회"**를 채택했다. `RCRIT_PBLANC_DE >= (오늘 - N일)` 조건으로 매번 그 범위의 공고를 통째로 다시 가져와 `houseManageNo` 기준 upsert한다 — 동일 공고를 다시 조회해도 P2-B의 upsert 구조로 중복 생성되지 않음을 이번 STEP에서 실측 재확인했다(§K).

이 방식이 "진행 중 공고를 계속 갱신"하는 요구도 자동으로 만족한다: 모집공고일이 최근 N일 안에 있는 공고는 접수/발표 일정이 진행되는 동안 매번 증분 윈도우에 다시 포함되어 upsert되므로, 접수기간(`RCEPT_BGNDE/ENDDE`)이나 당첨자 발표일 등의 최신 값이 반영된다(청약홈이 값을 사후 수정하는 경우에도 다음 증분 실행에서 갱신됨).

### 권장 기본값

| 항목 | 기본값 | 근거 |
|---|---|---|
| `mode: 'incremental'`의 기본 윈도우 | **최근 90일**(`DEFAULT_INCREMENTAL_DAYS = 90`) | §A 실측: 90일 이내 80건 — 관리자 버튼 1회 클릭(limit 200 이내)으로 여유 있게 전체를 커버 가능. 모집공고~접수~발표~계약까지 전체 사이클이 보통 몇 주~두 달 안에 끝나므로, 90일이면 "최근에 시작해 아직 진행 중인" 공고를 놓치지 않는다 |
| 관리자가 직접 조정 | 가능(`fromDate`/`toDate`/`limit`을 API/UI에서 지정 가능) | 사용자가 예시로 든 "매일 60~90일 재조회"를 그대로 채택하되, 고정 숫자로 못박지 않고 조정 가능하게 구현했다 |

"오래된 공고는 매일 재조회하지 않는다"는 원칙은 `fromDate` 하한을 두는 것 자체로 자연히 만족된다(90일보다 오래된 공고는 증분 동기화 범위에 아예 들어오지 않음). 다만 이번 STEP은 **수동 트리거만 구현**했으므로 "매일"이라는 주기 자체는 아직 실현되지 않는다 — 자동화(cron)는 §L의 다음 단계로 남긴다.

## D. API 호출량 분석

data.go.kr(공공데이터포털) 호출은 Detail(페이지당 최대 50건) + 공고 1건당 Mdl 1회 구조다. 실측으로 확인된 계산식: `Detail 호출 = ceil(N / 50)`, `Mdl 호출 = N`(N=처리 대상 공고 수).

| 시나리오 | N | Detail 호출 | Mdl 호출 | data.go.kr 호출 합계 | Kakao 지오코딩 호출(대략) |
|---|---|---|---|---|---|
| 100건 sync | 100 | 2 | 100 | **102** | ≈100(주소 있는 건마다 1~4회, 대부분 1회에 성공) |
| 500건 sync | 500 | 10 | 500 | **510** | ≈500 |
| 1,000건 sync | 1,000 | 20 | 1,000 | **1,020** | ≈1,000 |
| 초기 범위(최근 3년, 1,046건) | 1,046 | 21 | 1,046 | **1,067** | ≈1,046 |
| 일일 증분(최근 90일, 80건) | 80 | 2 | 80 | **82** | ≈80(신규만 해당, 기존 갱신 건도 매번 재지오코딩은 하지만 이미 좌표가 있으면 실패해도 기존값 보존이라 실질 낭비는 재호출 비용뿐) |

**한도 대비 안전성 판단**: 공공데이터포털의 정확한 일일 호출 한도(활용신청 승인 등급에 따라 다름, 보통 개발계정 1,000~10,000회/일 수준으로 알려져 있음)는 이번 조사에서 data.go.kr 마이페이지를 직접 확인하지 않아 **정확한 수치를 알 수 없다** — 추측으로 단정하지 않는다. 다만 위 표의 "일일 증분(82회/일)" 규모는 일반적인 공공데이터포털 개발계정 한도 대비 여유가 크다고 판단된다. 초기 백필(1,067회)이나 그 이상 범위는 하루 한도에 걸릴 가능성이 있으므로, **실제 초기 백필 전에 반드시 data.go.kr 마이페이지에서 이 서비스키의 실제 일일 한도를 확인할 것을 권고**한다. 새로운 유료 API는 추가하지 않았다.

## E. 지오코딩 fallback

### 설계 및 실측 검증

P2-B 테스트에서 실패했던 3개 주소(시흥거모/용인반도체클러스터/세종우미린)를 그대로 사용해 4단계 fallback을 설계·검증했다.

```
1차: 원본 HSSPLY_ADRES 그대로
2차: 괄호(및 안의 설명) 제거
   예) "...5204-1번지 일원(행정중심복합도시 5-2생활권 S1BL)" → "...5204-1번지 일원"
3차: "일원" 제거
   예) "...번지 일원 시흥거모 공공주택지구..." → "...번지 시흥거모 공공주택지구..."
4차: 시/도+시/군/구+읍/면/동까지만(번지·지구·블록명은 버림) — 가장 거친 근사치
   토큰을 앞에서부터 훑어 "시/도/군/구" 접미사인 동안 포함시키고, "읍/면/동" 접미사를
   만나면 그것까지 포함한 뒤 멈춘다(정규식 기반, 하드코딩된 지역명 목록에 의존하지 않음).
```

3개 주소 전부 **4차(시/도+시/군/구+읍/면/동)에서 실제로 성공**함을 라이브 Kakao 호출로 확인했다.

| 원본 주소 | 1~3차 결과 | 4차 결과(성공) |
|---|---|---|
| 경기도 시흥시 거모동, 군자동 일원 시흥거모 공공주택지구 내 A-5블록 | 전부 실패(0건) | `경기도 시흥시 거모동` → 성공 |
| 경기도 용인시 처인구 원삼면 용인 반도체 클러스터 일반산업단지 D1-1BL | 전부 실패(0건, "일원" 자체가 원문에 없어 3차는 2차와 동일) | `경기도 용인시 처인구 원삼면` → 성공 |
| 세종특별자치시 다솜동 5204-1번지 일원(행정중심복합도시 5-2생활권 S1BL) | 2차/3차도 실패(0건 — 번지 자체가 Kakao DB에 없는 것으로 추정) | `세종특별자치시 다솜동` → 성공 |

### 검증 규칙(§8 요구사항 반영)

- 각 단계에서 Kakao가 결과를 주더라도, 응답의 `address.region_1depth_name`(시/도)이 해당 공고의 `SUBSCRPT_AREA_CODE_NM`(Detail API의 공급지역 시/도, 이미 별도 필드로 저장돼 있음)과 일치하는지 검증한다 — **불일치하면 그 결과는 버리고 다음 단계로 넘어간다.** 시/도 단위 비교인 이유는 `subscriptionAreaName` 자체가 시/도 단위까지만 세분화돼 있기 때문(P2-A 확인).
- 문자열을 과도하게 삭제하지 않았다 — 정규식은 "주소 접미사(시/도/군/구/읍/면/동) 패턴이 이어지는 동안만 유지하고, 처음으로 그 패턴에 맞지 않는 토큰(번지, 지구명 등)을 만나면 즉시 중단"하는 방식이라, 임의 길이만큼 잘라내는 것이 아니라 주소의 행정구역 계층 구조를 따라간다.
- 4단계 모두 실패하거나 검증에 실패하면 `latitude`/`longitude`는 `null`로 유지된다 — 지역 중심 좌표나 임의 좌표를 생성하지 않는다.

### 실제 운영 테스트 결과(§J) — ⚠️ 아래 수치는 검수 전 1차 구현 기준, 최신 결과는 §N 참고

25건 실제 동기화에서 지오코딩 응답 자체는 25/25(100%) 얻었고, 그중 6건이 4단계까지 내려가 fallback으로 해결됐다. 다만 이후 검수(§N)에서 **4차(시/도+시/군/구+읍/면/동) 결과는 행정구역 대표 좌표일 뿐 실제 사업지 좌표로 볼 수 없다는 지적에 따라 저장 기준을 강화**했고, 그 결과 이 6건은 좌표를 저장하지 않는(`area_only`) 범주로 재분류되어 `null`로 정정됐다 — **최종적으로 좌표가 저장된 것은 25건 중 19건(76%)** 이다(§N). "100% 성공"은 응답을 얻은 비율이었을 뿐 "정확한 사업지 좌표를 저장한 비율"이 아니었다는 것이 이번 검수의 핵심 결론이다.

## F. 관리자 수동 동기화

### 조사 결과

기존 관리자 구조(`src/lib/auth-helpers.ts`의 `requireAdmin()`, `src/app/api/admin/users/[id]/ban/route.ts` 같은 액션형 API 패턴, `src/app/admin/dashboard/page.tsx`의 카드 그리드 UI)를 그대로 재사용할 수 있음을 확인했다. 새로운 인증 체계나 UI 프레임워크를 도입하지 않았다.

### 구현

- **API**: `POST /api/admin/presales/sync`(`src/app/api/admin/presales/sync/route.ts`) — `requireAdmin()`으로 서버 사이드 인증(관리자가 아니면 401/403). 요청 바디로 `mode`/`fromDate`/`toDate`/`limit`/`dryRun`을 받아 `syncApplyhomeListings()`를 호출하고 결과를 그대로 반환한다.
- **UI**: `src/app/admin/dashboard/page.tsx`에 "📦 분양정보(청약홈) 수동 동기화" 카드를 추가했다 — 모드 선택(증분/초기), 최대 건수 입력(1~200), dry run 체크박스, 실행 버튼. 실행 후 시작/종료 시각, 조회 대상 건수(matchCount)/처리 건수(fetched), 신규/업데이트/실패/건너뜀 건수, 주택형 upsert/Mdl 실패 건수, 지오코딩 성공(fallback 포함)/실패 건수를 카드 안에 표시한다.

## G. Batch 보호장치

기존 관리자 대시보드에는 이런 "대량 작업" 보호장치 선례가 없어서(강퇴 토글처럼 1건 단위 액션만 있었음), 이번 STEP에서 다음 방식을 새로 설계했다.

- **하드 캡(`MAX_SYNC_LIMIT = 200`)**: `syncApplyhomeListings()` 내부에서 요청된 `limit`이 얼마든 `Math.min(limit, 200)`으로 강제 클램프한다. 관리자 UI/API 요청 바디에 아무리 큰 값을 넣어도 서비스 레이어에서 최종적으로 잘린다 — **API route가 아니라 서비스 함수 자체가 이 상한을 강제**하므로, 향후 이 함수를 호출하는 새 진입점(cron 등)이 생기더라도 우회되지 않는다.
- **명시적 scope(날짜 범위)**: `mode`+`fromDate`/`toDate`로 항상 명시적인 기간 범위 안에서만 동작한다. "범위 없이 전부"를 의미하는 옵션은 만들지 않았다.
- **dryRun**: 실제로 DB에 쓰지 않고 신규/업데이트 예상 건수만 미리 계산하는 모드를 제공해, 관리자가 실행 전 영향 범위를 가늠할 수 있게 했다.
- **UI 단의 max 속성**: `<input type="number" max={200}>`으로도 200을 넘는 값을 입력하기 어렵게 했다(다만 이건 UX 편의일 뿐 실제 방어선은 서버의 `MAX_SYNC_LIMIT`).

## H. 실패 처리

### 오류 유형 구분

- **아이템 단위 오류**(계속 진행): 공고 하나를 upsert하다 발생하는 예외(예: 특정 값 파싱 실패, 일시적 Mdl 호출 오류)는 그 아이템의 `for` 루프 반복 안에서 `try/catch`로 감싼다. 실패해도 `failed` 카운트만 늘고 `items[]`에 오류 메시지가 기록되며, 나머지 공고 처리는 그대로 계속된다. 실패는 기존 `logServerError()`(`ErrorLog` 재사용, 새 Model 미생성)로도 남긴다.
- **전체 중단(fatal) 오류**: Detail 목록 자체를 가져오는 fetch가 실패하거나(네트워크 오류, API 키 미설정, HTTP 오류 응답), 함수 진입 전체를 감싸는 바깥쪽 `try/catch`에서 잡히는 예외는 즉시 결과에 `error` 필드를 채워 반환한다 — 이 경우는 개별 공고 몇 건이 아니라 애초에 "무엇을 처리해야 할지" 자체를 알 수 없는 상황이라 계속 진행이 의미가 없다.

### 실증

25건 실제 동기화 2회 모두 `failed: 0`이었다 — 정상 데이터에서는 실패가 발생하지 않음을 확인했을 뿐, 실제 예외 상황(예: 존재하지 않는 필드 참조, DB 제약 위반)을 인위적으로 주입해 재현하지는 않았다. 다만 코드 구조상(각 아이템이 독립된 `try/catch` 블록 안에 있음) 한 건의 실패가 나머지에 영향을 주지 않는다는 것은 리뷰로 확인된 사실이다.

## I. Mdl 실패 처리

`syncHouseTypeDetails()`는 P2-B 때부터 이미 예외를 던지지 않고 `{upserted, prices, failed}` 형태로 결과를 반환하도록 설계되어 있었다 — 이번 P2-C에서는 `failed: boolean` 플래그를 추가해 "정상적으로 빈 배열을 받은 경우"(주택형 데이터가 실제로 없는 공고)와 "호출 자체가 실패한 경우"를 구분할 수 있게 했다.

- Mdl 조회/저장이 실패해도 **이미 upsert된 Presale(부모 공고) 행은 그대로 유지된다** — Presale upsert가 먼저 커밋되고, 그다음에 Mdl 동기화를 시도하는 순서이기 때문에 구조적으로 분리돼 있다.
- 실패한 공고는 `mdlFailedCount`에 집계되고, 개별 `items[].mdlFailed`로도 표시된다.
- "나중에 재시도 가능"하다는 요구사항은, 동일 공고를 포함하는 범위로 증분/초기 동기화를 다시 실행하면 `houseManageNo` upsert 덕분에 Presale은 그대로 두고 Mdl만 자연스럽게 재시도되는 구조로 이미 만족된다 — Mdl 전용 재시도 API를 별도로 만들지는 않았다(불필요한 복잡도 추가로 판단).

이번 25건 테스트에서는 `mdlFailedCount: 0`으로, 실제 Mdl 실패를 재현하지는 못했다(§H와 동일한 한계).

## L. 자동화 전 남은 과제

이번 STEP에서 의도적으로 구현하지 않은 것들 — P2-C 검수 후 별도 단계에서 결정한다.

- **초기 백필(최근 3년, 1,046건) 실행**: `MAX_SYNC_LIMIT=200` 제약상 관리자가 여러 번(약 6회) 나눠 클릭해야 한다 — 이 반복을 자동화(예: "다음 페이지" 버튼, 또는 서버 측에서 200건씩 순차 처리하는 별도 배치 엔드포인트)할지는 향후 결정 사항.
- **data.go.kr 실제 일일 한도 확인**: §D에서 언급한 대로, 초기 백필을 실행하기 전에 이 서비스키의 정확한 한도를 data.go.kr 마이페이지에서 확인할 것을 권고한다.
- **연속 실패 시 회로차단기(circuit breaker)**: 현재는 아이템 단위 실패가 나머지 처리를 막지 않지만, "동일 원인으로 N건 연속 실패" 같은 상황을 감지해 조기 중단하는 로직은 없다 — 실제 장애 패턴을 관찰한 뒤 필요성을 판단하는 것이 합리적이라고 보고 이번엔 구현하지 않았다.
- **오래된 좌표 재검증**: 이번 지오코딩 검증(시/도 일치)은 신규/갱신 시점에만 적용된다. 이미 저장된(과거에 다른 로직으로 저장됐을 수 있는) 좌표를 일괄 재검증하는 배치는 없다.

## N. 지오코딩 정확도 검수 보완 (2026-08-12)

### 문제 제기와 재분석

기존 4단계 fallback 중 **4차(시/도+시/군/구+읍/면/동까지만)** 를 다시 분석했다. 1~3차는 원본 주소의 번지(지번)를 그대로 유지한 채 괄호/"일원" 같은 부연 텍스트만 제거하는 것이라, Kakao가 매칭에 성공하면 여전히 **그 필지의 정확한 좌표**다. 반면 4차는 번지를 완전히 버리고 "시/도+시/군/구+읍/면/동"만 질의하므로, Kakao가 돌려주는 좌표는 **그 읍/면/동의 대표(중심) 좌표**이지 실제 분양 사업지의 좌표가 아니다 — 시/도(심지어 시/군/구까지) 일치 검증을 통과해도 "정확한 사업지 좌표"라고 단정할 근거가 되지 못한다는 지적은 타당했다.

### 정확도 우선 원칙 반영

**"좌표 없음보다 잘못된 좌표가 더 위험하다"** 는 원칙에 따라 fallback 결과를 세 등급으로 재분류했다.

| 등급 | 해당 단계 | 저장 여부 | 근거 |
|---|---|---|---|
| `exact` | 1차(원본 그대로) | **저장** | 번지 단위 매칭 |
| `normalized` | 2차(괄호 제거)/3차("일원" 제거) | **저장** | 번지는 그대로 유지, 부연 텍스트만 제거 |
| `area_only` | 4차(시/도+시/군/구+읍/면/동) | **저장하지 않음**(null 유지) | 행정구역 대표 좌표일 뿐, 사업지 좌표가 아님 |

100% 성공률을 목표로 하지 않는다 — `area_only`는 통계에는 남기되(§O), `latitude`/`longitude`에는 절대 쓰지 않는다. 임의의 행정구역 중심 좌표를 실제 사업지 좌표처럼 저장하지 않는다는 원칙을 코드 레벨에서 강제했다.

### 주소 일치 검증 강화

기존에는 Kakao 응답의 `region_1depth_name`(시/도)만 비교했다. 다음과 같이 강화했다.

- 원본 `HSSPLY_ADRES`에서 "시/도 + 시/군/구"를 직접 추출하는 `extractExpectedSidoSigungu()`를 새로 추가했다(정규식 기반 — 토큰이 시/도/군/구 접미사인 동안 누적하고 읍/면/동을 만나면 멈춘다).
- Kakao 응답의 `region_1depth_name`(시/도)뿐 아니라 `region_2depth_name`(시/군/구)까지 비교한다 — **원본 주소에 시/군/구 정보가 있으면 시/도만 같아서는 성공으로 인정하지 않는다**(예: 같은 "경기도"의 다른 시/군/구로 잘못 매칭된 경우를 걸러낸다).
- 세종특별자치시처럼 시/군/구 세분화가 없는 경우(Kakao `region_2depth_name`이 빈 문자열)에는 시/도 일치만으로 충분하도록 예외 처리했다(원본 주소 자체에 시/군/구 정보가 없으므로).

### 광범위 fallback 처리

`extractCoarseAddress()`를 수정해, **읍/면/동 수준에 끝내 도달하지 못하면(즉 시/도 또는 시/군/구까지만 남는 경우) 아예 4차 fallback 후보를 만들지 않는다** — "세종특별자치시"나 "경기도 용인시 처인구"처럼 사업 위치를 전혀 특정할 수 없는 수준의 질의는 시도조차 하지 않는다(기존 코드는 이 가드가 없어 이론상 시/도 단독까지 축약될 수 있었다).

### 기존 25건 재검증 결과

`scripts/reverify_presale_geocode.ts`(신규, 일회성 검증 스크립트 — Detail/Mdl은 재호출하지 않고 저장된 `locationAddress`로 Kakao 지오코딩만 다시 실행)로 기존 25건 전체를 새 기준으로 재검증했다.

### API 호출한도 — 재확인

초기 3년 백필(약 1,046개 공고, 예상 약 1,067회 API 호출)은 이번에도 실행하지 않았다. §D에 기록한 대로, **실제 data.go.kr 일일 트래픽 한도는 사용자가 마이페이지에서 직접 확인한 뒤 백필 실행 여부를 결정한다** — 추측으로 한도를 단정하지 않는다.

### 관리자 UI 런타임 검증 — 추후 항목으로 유지

관리자 로그인 세션이 없어 실제 버튼 클릭까지는 이번에도 확인하지 못했다. 이는 P2-C 완료를 막는 blocker로 보지 않으며, **향후 운영 UI 검수 항목**으로 남긴다. 인증 우회는 하지 않았다 — API 자체의 인증 차단(§J, `401` 확인)만으로 서버 측 보호는 검증됐다.

## O. 지오코딩 통계 구분 (재설계)

기존 "성공/실패" 2분류 대신, 새 DB 컬럼 추가 없이 **sync 결과(`CheongyakSyncResult`)와 로그 수준에서만** 다음 4개 범주로 구분하도록 재설계했다.

| 범주 | 의미 | `latitude`/`longitude` 저장 |
|---|---|---|
| `geocodeExact` | 원본 주소 그대로 매칭 성공 | 저장 |
| `geocodeNormalized` | 괄호/"일원" 제거 후 매칭 성공(번지 유지) | 저장 |
| `geocodeAreaOnly` | 시/도+시/군/구+읍/면/동까지만 매칭 성공 | **저장하지 않음**(기존 값 보존 또는 null 유지) |
| `geocodeFailed` | 어떤 단계에서도 신뢰 가능한 결과를 얻지 못함(지역 불일치 포함) | 기존 값 보존 또는 null 유지 |

관리자 대시보드의 동기화 결과 표시도 이 4개 범주로 갱신했다(`src/app/admin/dashboard/page.tsx`).

## P. P2-C 최종 승인 (2026-08-12)

### 지오코딩 최종 정책

| 범주 | 조건 | 처리 |
|---|---|---|
| `exact` | 원본 주소 그대로 지오코딩 성공 | 신뢰 가능한 좌표로 저장 |
| `normalized` | 괄호/"일원" 등 최소 정규화 후 성공, 번지 등 핵심 위치정보 유지 + 시/도+시/군/구 검증 통과 | 저장 |
| `area_only` | 읍/면/동 등 광범위 행정구역 수준에서만 성공 | 실제 사업지 좌표로 볼 수 없어 저장하지 않음 — `latitude`/`longitude`는 `null` 유지 |
| `failed` | 지오코딩 실패(모든 단계 실패 또는 지역 불일치) | `latitude`/`longitude`는 `null` 유지 |

원칙: **"좌표 없음보다 잘못된 좌표가 더 위험하다."** 100% 지오코딩 성공률을 목표로 하지 않는다. 이 정책을 최종 확정한다.

### 25건 최종 결과

| 구분 | 건수 |
|---|---|
| 신뢰 가능한 좌표(`exact`+`normalized`) | **19건** |
| `area_only`로 판정되어 `null` 처리 | **6건** |

위 6건(시흥거모 A-5블록, 용인반도체클러스터 동일하이빌 파크밸리, 세종 우미 린 센터파크, 아산테크노밸리 더원 7차, 수원당수지구 A5블록 신혼희망타운, 업성 푸르지오 레이크시티 2단지)은 실제 사업지 좌표로 사용하지 않는다.

### normalized — 현재 미사용, 로직은 유지

25건 표본에서 `normalized`(2·3차 성공) 사례는 **0건**이었다. 대부분 1차(`exact`) 또는 4차(`area_only`)로 갈렸다. 더 큰 표본에서는 발생할 수 있으므로(괄호/"일원" 텍스트가 있으면서도 번지가 살아있는 주소는 충분히 존재할 수 있음), 현재 사용되지 않는다는 이유로 이 로직을 삭제하지 않는다.

### 관리자 UI 런타임 검증 — 완료 blocker 아님

관리자 로그인 세션이 없어 실제 버튼 클릭 테스트는 이번 STEP에서도 수행하지 못했다. 이는 P2-C 완료를 막는 blocker로 보지 않는다. 향후 관리자 운영 UI를 검수할 때 실제 로그인 상태에서 "분양정보 동기화" 버튼 클릭 → 결과 카드 렌더링을 확인할 것을 다음 항목으로 남긴다.

### API 호출 한도 — 백필 미실행 유지

초기 최근 3년 백필(약 1,046개 공고, 예상 약 1,067 API 호출)은 이번 STEP에서도 실행하지 않았다. 실제 data.go.kr 일일 트래픽 한도는 이집 계정 마이페이지에서 사용자가 직접 확인한 뒤, 백필 실행 여부를 결정한다.

### P2-C 최종 승인

위 정책과 결과를 최종 승인한다. PRESALE P2-C(분양 데이터 운영·동기화 체계 구축)를 완료로 처리한다.
