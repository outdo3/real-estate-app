## 0. 이 문서의 성격 — 먼저 분명히

**이 환경에는 브라우저·실기기·에뮬레이터가 없다.** 그래서 §2~§12의 실기기 절차
(Android Chrome에서 화면을 열고 탭하는 검증)는 **수행하지 못했다.** 하지 않은 QA를
PASS로 적지 않는다.

대신 브라우저 없이 실제로 확인 가능한 것을 프로덕션에 HTTP로 검증했고, 그 과정에서
**재현되는 성능 문제 한 건**을 찾았다. 나머지는 사용자가 실기기로 실행할 체크리스트로
정리했다.

| 구분 | 상태 |
|---|---|
| 서버 응답·메타데이터·공유 링크 복원·위생 점검 | **검증 완료** (아래 §2) |
| 화면 렌더·터치·키보드·모달·지도·PWA 설치 | **미검증 — DEVICE QA REQUIRED** |
| 재현된 버그 | **1건** (성능, §3) |

## 1. 검증에 쓴 방법

프로덕션에 대한 읽기 전용 HTTP 요청(`curl`)과 서버 렌더링된 HTML/JSON 검사.
쓰기 없음, 설정 변경 없음, 코드 변경 없음.

## 2. 브라우저 없이 검증된 것

### 2.1 커뮤니티 비로그인 접근 (§2 일부)

```
GET /community                     200   TTFB 148ms
GET /api/community/posts?page=1    200   success:true, total:0
```

목록 페이지와 목록 API 모두 **쿠키 없이** 200을 돌려준다 — 읽기에 인증을 요구하지
않는다는 계약이 프로덕션에서 성립한다.

> **QA 진행에 영향을 주는 발견: 게시글이 0건이다.**
> 그래서 §2의 4~11번(상세 진입, 본문·댓글 열람, 댓글 placeholder, 댓글 액션 로그인
> 모달)은 **테스트할 콘텐츠 자체가 없다.** 실기기 QA 전에 로그인해서 글을 1~2개
> 작성해야 그 흐름을 밟을 수 있다. 목록은 지금 빈 상태 화면을 보여준다.

### 2.2 비교 공유 링크 복원 (§6의 핵심)

공유 링크를 서버가 실제로 되살리는지 확인했다. 하필 **이름 충돌 쌍**으로 테스트했다.

```
GET /stats/compare?a=26230-149&b=26230-1810
  <title>대원아파트 vs 대원 | 이집</title>
  canonical  https://e-jip.com/stats/compare?a=26230-149&b=26230-1810
  og:url     https://e-jip.com/stats/compare?a=26230-149&b=26230-1810

GET /stats/compare?a=26140-15&b=26140-63
  <title>문화 vs 문화 | 이집</title>
```

- 정규화 이름이 같은 두 단지(`대원아파트` / `대원`)를 **aptSeq로 정확히 구분**해 복원한다.
- `26140-15`와 `26140-63`은 둘 다 이름이 "문화"다(동대신동3가 / 토성동2가). 제목이
  "문화 vs 문화"로 나오는 것이 **정상**이며, 이름만으로는 절대 구분할 수 없었다는
  증거이기도 하다.
- canonical과 og:url이 공유 URL과 동일하고, 퍼센트 인코딩된 한글이 없다.

즉 `COMPARE_SHARE_URL_COMPACT_FIX_V1`과 `SCORE_CANONICAL_APTSEQ_RESOLUTION_FIX_V1`의
결과가 프로덕션에서 확인됐다. **카카오톡 말풍선 자체는 실기기 확인이 필요하다.**

### 2.3 출시 위생 (§11 주변)

```
robots.txt        Sitemap: https://e-jip.com/sitemap.xml
sitemap.xml       36 URL,  서울 URL 0건
IndexNow 키 파일  200
```

실행·로그인 유지는 실기기 항목이다(§9).

## 3. 재현된 버그 — P1 (성능)

### 증상

`최근 12개월` + `부산광역시 전체` 조합의 실거래 피드가 **22~25초** 걸린다.

```
GET /api/stats/feed?sidoCode=26&period=12m&offset=0&limit=50

  1차 측정   25.46s
  직후 2회    0.93s / 0.85s      ← 캐시 적중
  수 분 후    22.39s             ← 다시 느려짐
```

일회성 콜드 스타트가 아니다. **반복 재현된다** — §12 기준("3s+ 반복되면 P1")에 해당한다.

### 기본 진입 경로는 정상

```
GET /api/stats/feed?sidoCode=26&period=7d    1.71s (첫 호출) → 0.27s
GET /api/stats/feed?lawdCd=26140&period=7d   1.37s
GET /api/stats/feed?sidoCode=26&period=1m    1.80s → 0.17s
GET /api/stats/feed?sidoCode=26&period=3m    0.19s
GET /api/stats/dashboard?sidoCode=26         2.42s
GET /api/apt/…/score?aptSeq=26140-1356       0.82s
GET /api/community/posts?page=1              0.24s
```

`TransactionFeedView`의 기본 기간은 `7d`다. 그래서 **첫 진입은 1.7초 안에 끝난다.**
문제는 사용자가 기간 칩에서 `최근 12개월`을 직접 누르고, 지역이 부산 전체일 때다.

### 근본 원인

`src/app/api/stats/feed/route.ts`

```ts
const cacheKey = `stats-feed-sido:${sidoCodeParam}:${months.join(',')}`;
const cached = await getOrSetCache(cacheKey, 5 * 60 * 1000, async () => { … });
```

- 캐시 TTL이 **5분**이고, `dynamic = 'force-dynamic'` + 인메모리 캐시라
  **serverless 인스턴스마다 따로** 유지된다.
- 그 키가 커버해야 하는 작업량: 16개 구·군 × 12개월 × (매매+전월세) =
  **약 384회 MOLIT 배치 조회**.

따라서 5분이 지나거나 새 인스턴스에 붙은 **첫 사용자가 매번 22~25초를 부담한다.**

### 이번 STEP에서 고치지 않은 이유

가능한 수정안이 전부 승인이 필요한 영역이다.

| 안 | 문제 |
|---|---|
| TTL 상향 | 실거래 데이터의 **신선도 정책** 결정이다(최대 N분 과거 데이터를 보여주게 됨) |
| cron 사전 예열 | 신규 cron = 인프라 추가, 이번 STEP의 "새 기능 추가 금지"에 해당 |
| 부산 전체에서 12개월 옵션 제한 | 사용자 선택지를 제거하는 제품 결정 |

§13의 "DB/infra/승인 필요 사항은 STOP하고 보고"에 따라 **측정만 하고 변경하지 않았다.**

### 완화되어 있는 점

직전 `STATS_LOADING_STATE_UX_FIX_V1` 덕분에, 그 22초 동안 화면은
**"실거래 데이터를 확인하고 있어요"**를 보여준다. 예전 코드라면 같은 상황에서
"기간 내 실거래가 없어요"가 떠서 고장으로 보였을 것이다. 느린 것과 고장난 것의 차이는
확보돼 있다.

## 5. 네이버 로그인 — 별도 상태 (§10)

이번 QA에서 **변경하지 않았다.** 직전 감사(`NAVER_OAUTH_CALLBACK_FAILURE_AUDIT_V1`)의
결론이 그대로 유효하다.

```
[next-auth][error][OAUTH_CALLBACK_ERROR]  State cookie was missing.  providerId: 'naver'
```

- 서버는 세 프로바이더 모두에게 `__Secure-next-auth.state`를 **동일하게** 발급한다(확인됨)
- Google·Kakao는 같은 모바일 Chrome에서 PASS → 공용 쿠키 인프라 문제가 아니다
- 남은 판별: **데스크톱 Chrome에서 네이버 로그인이 되는지**
  - 실패 → 자격증명 계열 / 성공 → 모바일 브라우저 컨텍스트 전환(네이버 앱 핸드오프)
- `sameSite` / provider 설정 / client secret / callback URL은 **승인 없이 바꾸지 않는다**

검수 대기와 이 오류는 **같은 문제로 단정하지 않는다** — 검수 상태라면 네이버 자체
화면에서 막혀 우리 콜백에 도달하지 못한다.

## 8. Soft launch 권고

**조건부 진행 가능.**

- 기본 진입 경로(홈·목록·상세·기본 기간 통계·지도 문서 응답)는 서버 측에서 정상이고
  응답이 빠르다.
- 성능 P1은 **사용자가 가장 넓은 기간을 직접 선택했을 때만** 발생하고, 그동안 화면은
  로딩 상태를 정직하게 보여준다 — 고장으로 보이지는 않는다.
- 다만 §4 체크리스트 중 **A·B·C·E·F는 출시 전에 실기기로 한 번은 밟아야 한다.**
  특히 지도/로드뷰(카카오 도메인 등록 의존)와 카카오 공유는 서버에서 검증할 수 없다.
