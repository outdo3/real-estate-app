## 3. 현재 cancellation 아키텍처

**DB 컬럼** (`prisma/schema.prisma:1256-1258`, `apartment_trade_histories`)

```prisma
dealCanceled Boolean @default(false) @map("deal_canceled")
cancelDate   String? @map("cancel_date")   // raw 해제사유발생일
registryDate String? @map("registry_date") // raw 등기일자
```

자연키: `@@unique([groupKeyStr, dealAmount, dealDate, floor, occurrenceIndex])`.
가격/일자 정정은 **새 row**로 나타나고, 자연키 밖 3개 필드만 upsert하는 설계다.

**write 정책** (`scripts/write-policy-logic.ts:31-45`) — 5분기:

| 분류 | 조건 | 동작 |
| --- | --- | --- |
| `insert` | 매칭 없음 + aptSeq 있음 | INSERT |
| `reviewRequired` | 매칭 없음 + aptSeq 없음 | **쓰지 않음** (name+dong으로 canonical identity 생성 금지) |
| `conflict` | 자연키 같은데 aptName/dong 다름 | **쓰지 않음**, 셀 전체를 `INVALID`로 |
| `updateFalseToTrue` | false → true | UPDATE (유일하게 승인된 UPDATE) |
| `updateTrueToFalseSkipped` | true → false | **차단** (source의 "취소 해제" 의미가 미검증) |

flip write는 `dealCanceled: true`를 **하드코딩**하므로 구조적으로 단방향이다
(`resync-cancellation-v2.ts:193-202`, `sale-sync-core.ts:213-224`).

**DELETE 경로 없음** — repo 전체에 `apartmentTradeHistory.delete/deleteMany` 부재.

**단 하나의 역전 위험**: `scripts/backfill-trade-history.ts:191-201`의 legacy upsert는
`dealCanceled: row.dealCanceled`를 무조건 덮어써서 true→false 역전이 가능하다.
CLI 전용이고 cron에 연결돼 있지 않지만, **이미 보정된 구간에 재실행하면 안 된다.**

**해석 (핵심 질문에 대한 답):**

1. **필드는 2006년 응답에도 존재한다** — 즉 "API가 옛날 월을 지원하지 않는다"가 아니다.
2. **값이 채워지는 것은 2020-03 관측치부터다.** 2020년 이전 표본 **1,948건 중 취소 0건**,
   2020년 이후는 약 4~7%. 0/1,948 vs ~5%는 우연으로 설명되지 않는다.
   (국토부 계약해제 공개 제도가 2020-02 시행된 것과 일치한다.)
3. **취소는 소급 반영된다** — 202106 거래에 `cdealDay 22.11.02`(17개월 뒤)가 붙어 있다.
   즉 과거 월을 오늘 재조회하면 **그 이후에 발생한 취소가 반영된 상태로** 돌아온다.

**따라서: 2006년 거래를 오늘 다시 조회하면 취소 여부를 확인할 수 없다.**
누락이 아니라 **원천에 데이터가 존재하지 않는다.** 이 구간은 어떤 방법으로도 검증 불가다.

## 6. 취소 지연(lag) 분포 — 진행 중인 신뢰 저하

검증된 C구간의 취소 4,727건에 대해 `cancelDate - dealDate` 실측:

| p50 | p75 | p90 | p95 | p99 | max |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 0.7개월 | 1.8개월 | 3.1개월 | 4.4개월 | 11.8개월 | 20.6개월 |

- 거래일로부터 **3개월 뒤에 취소된 비율: 10.5%**
- 6개월 초과: 3.0% / 12개월 초과: 0.9%

**일일 sale cron의 overlap은 3개월이다** (`shared.ts:110`, 주석은 "취소 반영 지연 p90").
p90=3.1개월이므로 상수 자체는 근거가 있으나, **나머지 10.5%는 어떤 정기 작업으로도
다시 확인되지 않는다.** 부산 월평균 취소 약 197건 기준 **월 ~21건, 연 ~250건**이
"취소됐지만 DB에는 유효로 남는" 상태로 누적된다.

이것이 이번 감사에서 발견한 **유일한 진행 중(active) 신뢰 문제**다.

## 7. 추가 발견 — pagination cap으로 인한 실거래 8,446건 누락

`DATA_FRESHNESS_AUTOMATION_V1 Phase 1`에서 지적된 "sale fetcher에 pagination 검증 부재"의
실제 피해를 원천 `totalCount`와 대조해 확정했다. 행 수가 **정확히 1000**인 셀 23개 전부:

| 구간 | 셀 | 누락 rows |
| --- | ---: | ---: |
| A (2006-01~2020-01) | 12 | 2,848 |
| B (2020-02~2024-08) | 11 | 5,598 |
| **합계** | **23** | **8,446** |

최악 사례 `26350/202010`: DB 1,000건 / 원천 **2,442건 → 1,442건(59%) 누락**.
그 외 `26350/202006` 924건, `26350/201911` 891건, `26230/202011` 633건 누락 등.

**중요:** A구간은 취소 검증은 불가능하지만 **거래 자체는 복구 가능하다.**
2020-06~11 부산 급등기가 대량 포함돼 있어 최고가/통계 정확도에 직접 영향이 있다.
Phase 1.5에서 만든 paginated fetcher가 이미 이 문제를 해결하므로, 23셀만 재수집하면 된다.

## 8. record-high 계산과 현재 안전성

**`getRecordHighRowsFromDb`** (`src/lib/trade-history-read.ts:754-813`)
- `deal_canceled = false`, `deal_type='sale'` 필터 있음 ✅
- 범위: **rolling 24개월** — `candidateFromDate()` = 오늘 −24개월 (`:562-565`)
- 그룹: `group_key` = identity + **정확한 전용면적** + dealType
- 신고가 판정은 strict `>`, 창 내 첫 거래는 신고가가 될 수 없음(`prior_high_amount IS NOT NULL`)

**안전성 판정:** 2026-09-03 기준 rolling 창은 **2024-09-03 ~ 오늘**이고,
SAFE 구간은 **2024-09 ~ 2026-08**이다. 즉 **현재 record-high는 검증된 구간만 읽는다.**
창의 시작점은 앞으로 전진하므로 검증구간 밖으로 나가지 않는다 → **구조적으로 안전.**

**단, 두 가지 단서:**
1. §6의 10.5% lag 누락분이 창 안에 누적된다. 취소 거래는 가격이 높은 쪽에 치우치는
   경향(자전거래/업계약)이 있어, 이 기능에는 방향성 있는 악영향이다:
   - 잘못 남은 고가 취소건이 `prior_high`를 부풀려 **진짜 신고가를 숨기거나**,
   - 그 취소건 자체가 **가짜 신고가로 표시**된다.
2. `price-rankings/route.ts:66-80`의 고지 주석은 **"24개월 중 최근 13개월만 검증됨"**
   이라고 적혀 있으나 이는 **2026-08-31 V2 resync(24개월 전체) 이후 낡은 서술**이다.
   실측상 24개월 전 구간에 취소가 존재한다. 주석이 현실보다 비관적이다.

**`getAllTimeHigh`** (`trade-history-read.ts:110-122`)
- 날짜 상한/하한 **없음 — 저장된 전 이력(2006~) 스캔**. 유일한 진짜 all-time 계산.
- **`src/`에 호출부 0건** (`scripts/qa-trade-history.ts`에서만 사용) → 현재 노출되는 화면 없음.
- 자체 docstring이 "검증 안 된 구간에 '역대' 표현 금지, 호출부 책임"이라고 명시.
- **잠재적 지뢰**: 누군가 import하는 순간 §4에 의해 검증 불가능한 all-time 주장이 생긴다.

## 10. 검증 전략 옵션 A–D

| | 내용 | 셀 | 예상 flip | 얻는 것 | 위험 |
| --- | --- | ---: | ---: | --- | --- |
| **A** | 현행 유지 | 0 | 0 | 없음 | §6 오염이 연 ~250건 누적 |
| **B** | **capped 23셀 재수집** (Phase 1.5 paginated fetcher) | 23 | – | **실거래 8,446건 복구** | 낮음 (INSERT 위주) |
| **C** | **취소 lag 커버리지 확대** (3개월 → 12개월 재확인) | 208/일 | 월 ~21 | §6 진행형 오염 차단 | 중 (cron 시간예산) |
| **D** | B구간 취소 resync (2020-02~2024-08) | 880 | 7천~1.2만 | 2020년 이후 최고가 주장 가능 | 중 (대량 UPDATE) |

**권장 순서: B → C → D.**
- **B가 최우선** — 셀 23개, 실측 fetch 3초, 누락 8,446건 복구. 투입 대비 효과가 압도적이고
  A구간(검증 불가 구간)에서도 **거래 데이터는** 복구된다.
- **C가 그다음** — 유일하게 *현재 진행 중인* 신뢰 저하를 막는다. 과거 정리보다 우선한다.
- **D는 선택** — 지금 어떤 화면도 이 구간을 읽지 않으므로(§8) 즉시 버그를 고치는 게 아니라
  "2020년 이후" 주장을 **가능하게** 만드는 투자다.
- **A(2006-01~2020-01) 취소 resync는 어떤 옵션에도 넣지 않는다** — §4에 의해 무의미하다.

### C의 구현 제약 (실측 기반)

`maxDuration = 60`, TimeBudget 50s (`sale-sync-core.ts:56`), 현재 overlap 3개월 → 약 64셀/일.
MOLIT fetch는 실측 **평균 119ms/셀**(중앙값 106ms)로 병목이 아니며, 비용은 DB측이다.
overlap을 단순히 12로 올리면 208셀/일이 되어 50s 예산을 초과할 가능성이 크다.
Hobby 플랜 cron 2개가 모두 사용 중이므로 신규 cron도 불가.

→ 권장 설계: **기존 sale cron 안에서 "최근 3개월 매일 + 나머지 4~12개월을 요일별로 순환"**.
`districtOffset`/`districtLimit` 청크 기능이 이미 있으므로 동일 패턴을 월 축으로 확장한다.
이 설계는 **본 STEP의 범위가 아니며 별도 승인이 필요하다.**

- 총 소요는 DB가 지배한다(기존 row 조회 172,383건 + UPDATE 약 9,000건 + INSERT 5,598건).
  **추정 10~20분** — 측정이 아니라 추정이며, dry-run으로 먼저 확인해야 한다.
- Supabase egress: B구간 기존 row 조회는 좁은 select 9컬럼 × 172,383행 ≈ **20MB 수준**.
  현재 문제(월 GB 단위)에 비해 무시할 수준. **DB 용량은 증가한다** — 8,446 INSERT × 569 B/row
  ≈ **4.8MB**. 이미 free 한도 초과 상태(548MB/500MB)이므로 Pro 전환 전이라면 고지 필요.
- Vercel: 위 작업은 60초 함수에 들어가지 않는다. **감독 하의 로컬 CLI 단계 실행**이 전제다.

## 13. 멱등성

`createMany({ skipDuplicates: true })` + 자연키 unique index로 INSERT는 멱등.
flip은 `dealCanceled: true` 하드코딩이라 재실행해도 같은 상태로 수렴한다(단방향).
V2 24개월 작업에서 apply 후 재실행 시 `insert 0 / flip 0`이 관측된 전례가 있다.
**단 `occurrenceIndex`가 MOLIT 응답 순서에서 파생되므로**, 절단됐던 셀을 완전본으로 다시
읽으면 인덱스 배정이 달라져 **중복 INSERT가 발생할 수 있다** — 23셀 작업의 최대 위험이며
반드시 dry-run에서 먼저 확인해야 한다.

## 14. NEEDS_REVIEW 정책

`reviewRequired`(aptSeq 없음)와 `conflict`(aptName/dong 불일치)는 **쓰지 않고 계수만** 한다.
`conflicts > 0`이면 셀은 `INVALID`, 런 전체 verdict는 `cellFailed===0 && cellInvalid===0`일 때만 SAFE.
현행 유지를 권장한다. 다만 `updateTrueToFalseSkipped`가 `unchanged`에 합산돼
**리뷰 대상으로 드러나지 않는 점**은 개선 여지다(별도 카운터 권장).
