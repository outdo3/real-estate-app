## 0. 결론 요약

**판정: READY_FOR_REPAIR_APPROVAL**

1. **상한선 327행 → 확정 21행.** 기존 추정치(`형제 전원 취소 그룹`의 `siblings-1` 합계, 315→324→327로 증가 중)는 **약 15배 과대추정**이었다. 1,118개 셀을 전수로 원천 대조한 결과 실제 과다 취소는 **21행**이다.
2. **모호한 행이 사실상 없다.** 7,929개 그룹 전부가 확정 분류됐다 — `SOURCE_UNAVAILABLE` 0, `GROUP_ABSENT_IN_SOURCE` 0, `DB_UNDER_CANCELED` 0. 원천 셀 1,118개가 **전부 COMPLETE**로 읽혔다(직전 STEP의 페이징 수정 덕분에 원천을 자르지 않고 읽을 수 있었다).

4. **21행 전부 최근 12개월 안에 있다**(가장 오래된 것이 2025-10). 래칫은 sync/recheck가 실제로 도는 창(현재월~12개월 전)에서만 누적된다 — 그보다 오래된 셀은 재조회되지 않아 물들지 않는다. 연도별 상한선에서 2020~2021이 컸던 것(180행)은 **전부 진짜 이중 취소**였다.
5. **집계 영향은 미미하지만 단지 단위 영향은 크다.** 전체 활성 거래 +0.0025%에 불과하지만, **21행 중 10행이 해당 단지의 "최근 실거래"를 바꾸고**, 2행이 신고가를 바꾸며, **래미안포레스티지2단지는 활성 거래가 0건 → 1건**이 된다(현재 거래가 하나도 없는 것처럼 보인다).
6. **repair와 재발방지는 분리해야 한다.** 21행을 고쳐도 `classifyRow`의 단방향 래칫이 남아 있으면 다시 쌓인다. 둘 다 별도 승인 대상이다.

## 1. Root cause 재구성

### 코드 (확정)

| 단계 | 파일:라인 | 동작 |
|---|---|---|
| 1 | `scripts/trade-history-logic.ts:149-151` | `occurrenceIndex`를 **MOLIT 응답 등장 순서**로 부여 |
| 2 | `src/lib/sync/sale-sync-core.ts:182` | 자연키 = `group_key + 금액 + 계약일 + 층 + occurrenceIndex` |
| 3 | `scripts/write-policy-logic.ts:58-59` | `!match.dealCanceled && fresh.dealCanceled` → `updateFalseToTrue` (**쓴다**) |
| 4 | `scripts/write-policy-logic.ts:61-62` | `match.dealCanceled && !fresh.dealCanceled` → `updateTrueToFalseSkipped` (**되돌리지 않는다**) |

MOLIT은 같은 occurrence 그룹(동일 단지·금액·계약일·층) 안에서 행의 순서를 **호출마다 보장하지 않는다**. 그래서 `occurrenceIndex`는 불안정한 식별자다.

### 메커니즘

```
원천(항상):   [ 유효, 취소(해제일 D) ]     ← 취소는 언제나 1건

sync T1: 응답 순서가 [취소, 유효] → occ0 이 fresh.canceled=true 와 매칭 → occ0 flip (cancel_date=D)
sync T2: 응답 순서가 [유효, 취소] → occ1 이 fresh.canceled=true 와 매칭 → occ1 flip (cancel_date=D)
         동시에 occ0 은 fresh.canceled=false 와 만나지만 4번 규칙이 되돌리기를 차단

DB 결과:  [ 취소(D), 취소(D) ]           ← 유효 거래 1건이 영구히 취소로 표시됨
```

되돌리기가 막혀 있으므로 그룹은 **단조적으로** 전부 취소로 물든다. sync를 다시 돌려도 치유되지 않는다(직전 audit의 dry-run에서 `wouldFlipCanceled=0 unchanged=259`로 확인됨).

### 데이터가 이 메커니즘을 확인한다

21개 확정 그룹 **전부**에서 형제들의 `cancel_date`가 **동일**하다. 예:

```
보수3차봄여름가을겨울  원천 취소 1건(해제일 26.09.02)
                      DB  occ0 취소 26.09.02 · occ1 취소 26.09.02   ← 같은 해제일이 복사됨
```

진짜 이중 취소라면 서로 다른 해제 사건이므로 해제일이 갈리는 것이 자연스럽다. 실제로 전원취소 그룹 266개 중 **해제일이 2개 이상인 157개 그룹은 단 하나도 과다 취소가 아니었다**(전부 `CONFIRMED_CANCEL`).

## 2. Canonical transaction identity

취소 판정에 쓰는 매칭 규칙을 명시한다. **이름/동 fuzzy 매칭, first-match 금지.**

occurrence 그룹 키 (`trade-history-logic.ts`의 `occurrenceGroupKey`와 동일):

```
group_key (= identityKey::areaKey::dealType, identityKey = "id:{aptSeq}")
  | deal_amount      (만원 정수)
  | deal_date        (YYYY-MM-DD)
  | floor            (정수)
```

**그룹 안에서는 개별 행을 서로 구분할 수 없다** — `occurrenceIndex`를 빼면 모든 식별 필드가 동일하기 때문이다. 이것이 결함의 근원이자, repair 설계의 출발점이다.

따라서 판정은 **행 단위가 아니라 그룹 단위 취소 "개수"로만** 한다(순서 무관):

```
원천 그룹의 취소 수 N  vs  DB 그룹의 취소 수 K
K > N  →  (K - N)행이 과다 취소
```

`aptSeq`는 모든 대상 행에 존재한다(null 0건) — name+dong fallback 식별은 쓰이지 않았다.

## 7. Repair rule (deterministic)

다음을 **전부** 만족하는 행만 복구한다:

1. occurrence 그룹(§2 정의)이 원천에 존재하고, 원천 셀 status가 `COMPLETE` 또는 `EMPTY_VALID`다.
2. 그룹의 **형제 수가 원천과 일치**한다(다르면 결함 B 영역 → 제외).
3. **DB 취소 수 K > 원천 취소 수 N**이다.
4. 대상 행이 현재 `deal_canceled = true`이고 **`registry_date IS NULL`**이다.
5. 그룹당 정확히 `K - N`행만 복구한다. 형제가 서로 구분되지 않으므로 `occurrence_index` **내림차순**(동률이면 `id` 내림차순)으로 결정적으로 고른다.

복구 내용: `deal_canceled = false`, `cancel_date = NULL`. **그 외 어떤 필드도 건드리지 않는다**(자연키·금액·면적·등기일·occurrence_index 전부 불변).

AMBIGUOUS / SIBLING_COUNT_MISMATCH / 원천 미확인은 **전부 제외**한다.

## 8. Repair script 제안 (미실행)

`scripts/repair-cancel-ratchet-defect-a.PROPOSAL.ts` — **승인 대기**. 파일명에 `.PROPOSAL.`이 있는 동안 apply하지 않는다.

안전장치:

| # | 장치 |
|---|---|
| 1 | 기본이 dry-run. apply는 `--apply` **와** `APPROVE_CANCEL_RATCHET_REPAIR=1` 둘 다 필요 |
| 2 | **id 목록을 신뢰하지 않는다** — apply 시점에 원천을 다시 읽어 그룹 단위로 재판정하고, 그때도 과다 취소인 행만 쓴다 |
| 3 | 원천 셀이 COMPLETE가 아니면 그 셀 전체 skip("못 읽음"을 "취소 아님"으로 해석하지 않음) |
| 4 | `--expect=21` assertion — 대상 수가 다르면 **쓰기 전에** 중단 |
| 5 | `WHERE id IN (...) AND deal_canceled = true AND registry_date IS NULL` — 이미 복구된 행은 0 rows → **멱등** |
| 6 | 배치 트랜잭션. rows-affected가 예상과 다르면 롤백 후 즉시 중단 |
| 7 | 스냅샷 파일을 먼저 쓰지 않으면 apply를 시작하지 않는다 |
| 8 | broad UPDATE 없음 — 항상 명시적 id 목록 |

동등한 SQL(감사용, 실행하지 않음):

```sql
-- 21개 id는 원천 재대조로 산출된 값이며, 실행 전에 반드시 재검증한다.
```

## 9. 스냅샷 · 롤백

apply 전에 `tmp/cancel-ratchet-repair-snapshot-<ts>.json`으로 저장:

`id · deal_canceled · cancel_date · registry_date · updated_at · lawd_cd · deal_ymd · apt_seq · apt_name · deal_date · deal_amount · floor · occurrence_index`

롤백(제안, 실행하지 않음) — 스냅샷의 원본 값을 행 단위로 되돌린다:

```sql
-- 스냅샷 JSON의 각 행에 대해 (예시: id 949472, cancel_date '26.09.02')
UPDATE apartment_trade_histories
   SET deal_canceled = true, cancel_date = '26.09.02'
 WHERE id = 949472 AND deal_canceled = false;
```

21행뿐이므로 전량 복원이 즉시 가능하다. 자연키를 건드리지 않으므로 롤백이 다른 행에 영향을 주지 않는다.

## 10. 배치 정책

**권장: 단일 트랜잭션 한 번(21행) 또는 배치 25 (= 사실상 1배치).**

근거: 대상이 21행뿐이고, 자연키·인덱스를 건드리지 않는 2개 컬럼 UPDATE다. 잠금 시간이 밀리초 단위라 배치를 쪼갤 이득이 없고, 오히려 중간 상태(일부만 복구)를 만들 위험이 커진다. 스크립트는 `--batch=25`가 기본이라 한 배치로 끝난다.

## 12. 재발 방지 (코드 수정 — 이번 STEP에서 하지 않음)

**data repair와 ingest prevention은 별개이며 둘 다 필요하다.** 21행을 고쳐도 `classifyRow`가 그대로면 다시 쌓인다(상한선이 315 → 324 → 327로 계속 늘어난 것이 증거다).

최소 수정 제안 — **행 단위 취소 매칭을 그룹 단위 취소 개수 정합으로 바꾼다**:

```
현재: 행마다 naturalKey(occurrenceIndex 포함)로 매칭 → false→true만 허용
제안: occurrence 그룹마다 "원천 취소 수 N"을 구하고, DB 그룹의 취소 수를 N에 맞춘다
      (부족하면 취소로, 많으면 유효로 — 순서에 의존하지 않으므로 flapping이 없다)
```

- `occurrenceIndex`를 식별자로 쓰는 구조 자체는 유지해도 된다(자연키 안정성 때문). 바뀌는 것은 **취소 플래그를 정하는 방법**뿐이다.
- 이 변경은 write policy 변경이므로 **별도 승인 대상**이다. `write-policy-logic.ts`는 순수 함수라 테스트로 고정하기 쉽다.
- 서울/경기 확장 **전에** 반드시 끝내야 한다 — 고치지 않고 적재하면 같은 오류를 새 지역에 복제한다(`SEOUL_GYEONGGI_EXPANSION_DATA_AUDIT_V1` §28 STEP 0).

## 14. 알려진 한계

- 판정은 **2026-09-16 시점의 원천**과의 대조다. MOLIT이 이후 정정/회수하면 결과가 달라질 수 있어, repair script는 apply 시점에 원천을 **다시** 읽도록 설계했다.
- 그룹 안에서 어느 행이 "원래 유효했던 행"인지는 원천이 알려주지 않는다(형제가 구분 불가). `occurrence_index` 내림차순은 결정적 선택일 뿐 "원본 복원"은 아니다 — 다만 형제의 모든 식별 필드가 동일하므로 결과 상태는 동등하다.

- 오피스텔·분양권·빌라는 범위 밖이다.
