## 1. 기존 생활편의 코드 재조사

- **SDK/REST**: 화면에는 **Kakao Maps JS SDK**(client-side, `KakaoPlaces.tsx`
  가 `window.kakao.maps.services.Places/Geocoder`)를 사용. 이번 STEP의
  카테고리 검증(§4)만 별도로 **Kakao Local REST API**(read-only, 서버가
  아니라 조사용 임시 스크립트)로 확인 — 실제 화면 동작 방식은 그대로.
- **병원(HP8) 호출 구조**: `NeighborhoodInfoPanel.tsx`,
  `<KakaoPlaces categories={['HP8']} keywords={['공원']} limit={4}/>` —
  병원 카테고리 검색과 공원 키워드 검색을 **한 컴포넌트 호출에서 병합**해
  "🏥 병원·공원" 카드 하나로 보여줌(기존 그대로, 미변경).
- **공원 keyword 구조**: 전용 카테고리 코드가 없어 `keywordSearch('공원', ...)`
  로 검색 후 이름에 `아파트/빌라/화장실/맨션/타워`가 포함된 결과만 제외
  (기존 그대로, 미변경).
- **radius**: 카테고리 검색 1,500m, 키워드 검색 5,000m(코드 상수, 기존 그대로).
- **최대 결과 수**: `limit` prop(카드별로 다름, 기존 병원·공원/교통=4, 학교=5).
- **거리 계산**: Kakao 응답의 `distance`(직선거리) 그대로 사용, 도보(분속
  80m)/차량(분속 500m) 환산은 `formatEta()`(기존 그대로, 미변경).
- **정렬 기준**: `sort: SortBy.DISTANCE`(카카오 API 옵션), 병합 후에도
  `Number(a.distance) - Number(b.distance)`로 재정렬(기존 그대로).
- **중복 제거**: 같은 호출 내에서 카카오 장소 `id` 기준 dedupe(기존 그대로,
  미변경) — 이번에 추가한 4개 카테고리는 각각 **독립적인 단일 카테고리
  호출**이라 이 dedupe 로직이 새로 걸릴 일 자체가 없음(§11).
- **loading/error/empty state**: `KakaoPlaces.tsx` 내부에서 공통 처리
  (`loading`/`error` state), 결과 0건과 API 실패가 지금까지 구분되지
  않던 것을 이번 STEP에서 문구만 최소 개선(§14).
- **확장 abstraction 존재 여부**: **이미 존재함.** `KakaoPlaces`는
  `categories: KakaoCategoryCode[]`를 배열로 받아 카테고리를 몇 개든
  조합할 수 있게 설계돼 있었다 — 단지 `KakaoCategoryCode` 유니온 타입에
  새 코드가 없어서 못 쓰고 있었을 뿐(§4). 새 abstraction을 만들 필요가
  없었다.

## 2. 카테고리 최종 범위

기존 유지: 병원 · 공원. 신규: 대형마트 · 편의점 · 약국 · 어린이집·유치원.
정확히 6개 — 백화점/쇼핑몰/전통시장/체육시설/문화시설/관공서/학원가/카페/
음식점은 추가하지 않았다.

## 3. Kakao category code 검증(REST API 실측, read-only)

이 프로젝트가 이미 다른 곳(`geocode-apt.ts`)에서 쓰는 것과 동일한
`NEXT_PUBLIC_KAKAO_MAP_API_KEY` + `KA`/`Origin` 헤더 조합으로 Kakao Local
REST API(`/v2/local/search/category.json`)를 직접 호출해(DB/코드 변경
없음) `category_group_name` 필드를 확인했다:

| 카테고리 | 예상 코드 | 실제 확인 결과(`category_group_name`) |
|---|---|---|
| 대형마트 | `MT1` | **"대형마트"** — 일치 |
| 편의점 | `CS2` | **"편의점"** — 일치 |
| 약국 | `PM9` | **"약국"** — 일치 |
| 어린이집/유치원 | `PS3` | **"어린이집,유치원"** — Kakao 공식 명칭 자체가 둘을 묶어서 부름(§5) |

임의 코드를 쓰지 않았다 — 4개 전부 API 응답으로 재확인 후 사용.

## 4. PS3 의미 확인 — "어린이집·유치원"으로 UI 표기 확정

REST API 응답의 `category_group_name`이 이미 `"어린이집,유치원"`이고,
실측(§7~§9의 5개 단지)에서도 실제로 어린이집과 유치원이 섞여 나왔다
(예: 엘지메트로시티3 결과에 "LG메트로시티유치원(182m, cat=…유아교육 >
유치원)"이 다른 어린이집들 사이에 섞여 포함). 그래서 UI 라벨을
**"어린이집·유치원"**으로 확정했다(§5 지시대로 "어린이집"이라고만 단정하지
않음) — `NeighborhoodInfoPanel.tsx` 카드 제목, `KakaoPlaces.tsx`의
`CATEGORY_ICON`은 라벨과 무관하게 아이콘만 담당.

## 5. 대형마트(MT1) 정확도 실측

부산 5개 단지(§7 표 참고)에서 MT1 카테고리 검색 결과에 **이마트/롯데마트/
메가마트/홈플러스/하나로마트/GS더프레시** 등 실제 마트·대형슈퍼 브랜드만
나왔고, 동네 슈퍼·편의점·소형 식자재마트 오탐은 없었다. 다만 결과 구성이
"대형마트"(메가마트/롯데마트 같은 대형 매장)와 "슈퍼마켓 > 대형슈퍼"(GS더
프레시/홈플러스익스프레스 같은 준대형 체인)가 섞여서 나온다 — 이는
**카카오 자체 분류 체계상 MT1 그룹에 원래 포함되는 하위 카테고리**이지
문자열 오탐이 아니다(§3에서 확인한 대로 `category_group_name` 자체가
공식적으로 "대형마트"). 임의 필터를 추가하지 않았다(지시 §6 준수) —
결과가 정확하므로 그대로 사용.

## 6. 공원 검색 정확도 재확인(변경 없음)

5개 단지 표본에서 기존과 동일한 패턴의 결과를 확인: 실제 공원(예:
"용호공원", "대신공원") 외에 "OO공원 주차장", "OO체육공원 풋살장/테니스장/
축구장", "나무공원빌딩"(건물명 우연 포함), "공원빌라"(기존 필터로 이미
제외됨) 등이 섞여 있다. `아파트/빌라/화장실/맨션/타워` 필터는 "공원빌라",
"화장실" 계열은 걸러내지만 "주차장/풋살장/체육공원" 계열은 걸러내지
못한다 — **이건 기존부터 있던 특성이며 이번 STEP에서 손대지 않았다**
(지시 §7·§24: 큰 검색 로직 변경 금지, 공원/병원 회귀만 확인). 필터
추가는 하지 않음.

## 8. 대형마트 실측(§20 항목)

§7 표 참고. 5개 단지 전부 반경 내 결과 존재(최소 2건~최대 9건), 오탐 없음.

## 9. 편의점 실측(§21 항목)

5개 단지 전부 반경 1,500m 내 **10건 이상**(카카오 API 최대 사이즈로 절단)
검색됨 — 실제로 매우 조밀하다는 지시의 우려가 실측으로 확인됐다. UI에서는
`limit=2`(가장 가까운 2곳만)로 제한해 과도한 나열을 막았다.

## 10. 약국 실측(§22 항목)

5개 단지 전부 반경 내 다수(10건 이상) 존재, 전부 "OO약국" 형태로 오탐 없음.
결과 좌표가 병원(의원) 근처에 몰려 있어(약국은 통상 병원 인근에 입지)
지리적으로는 겹쳐 보이지만, **병원과는 다른 개별 장소**이며 "약이 가까운가"
라는 실제 다른 질문에 답하는 정보라 병원과 별도로 둘 가치가 있다고 판단.

## 11. 어린이집·유치원 실측(§23 항목)

§4에서 이미 확인. 5개 단지 결과 예: 엘지메트로시티3에서 "LG메트로시티
어린이집"과 "LG메트로시티유치원"이 함께 검색됨 — 라벨 "어린이집·유치원"이
실제 결과 구성과 일치함을 재확인.

## 12. 공원/병원 회귀

`git diff`로 재확인: `NeighborhoodInfoPanel.tsx`의 기존 교통·병원·공원
블록은 **한 글자도 수정되지 않았다**(diff에 등장하지 않음, 새 카드 4개만
추가). `KakaoPlaces.tsx`의 기존 로직(검색/정렬/중복제거/학교·지하철
배지)도 그대로이며, 유일한 공통 변경은 §14의 empty state 문구 한 줄뿐
(모든 카테고리에 동일하게 적용되는 개선이라 회귀가 아님).

## 13. empty state 정책

기존 "주변에 해당 인프라가 없습니다." → **"검색 반경 내 정보가 없습니다."**
로 변경(`KakaoPlaces.tsx` 135행 부근, 6개 카테고리 전체 공통 적용).
"정보 준비중" 문구는 쓰지 않았다(지시 §14 준수) — 검색은 실제로 실행됐고
결과가 없는 것이지 "아직 조사 전"이 아니기 때문.

## 14. API 실패 UX

기존에도 **위치를 못 찾은 경우**("위치를 찾을 수 없어…")와 **API 키
없음**("지도 API 키가 설정되지 않았습니다")은 이미 별도 문구로 분리돼
있었다(재확인). 다만 카테고리/키워드 검색 자체의 상태값(`status`)이
`ZERO_RESULT`(진짜 0건)인지 `ERROR`(카카오 쪽 오류)인지는 **여전히
구분되지 않는다**(`searchOneCategory`/`searchOneKeyword`가 OK가
아니면 전부 빈 배열로 합쳐버림) — 검토는 했으나, 이 부분을 분리하려면
검색 함수들의 반환 타입 자체를 바꿔야 해 기존 6개 호출부(학교/지하철/
병원공원 포함) 전체에 영향이 미친다. "최소 변경" 원칙에 따라 **이번
STEP에서는 보류**하고 한계로 기록한다(§17).

## 15. 호출 수 측정

- **기존**: "교통·편의시설" 탭 클릭 시 카드 2개 → Kakao 검색 **2회**
  (SW8+키워드 2개 합쳐 1회 호출 묶음, HP8+키워드 1개 합쳐 1회 호출 묶음
  — 정확히는 `categorySearch`+`keywordSearch`가 각각 별도 API 콜이라
  내부적으로는 SW8 1콜+KTX 1콜+기차역 1콜=3콜, HP8 1콜+공원 1콜=2콜,
  총 **5콜**이 이미 있었음. "카드 단위" 기준으로는 2개).
- **수정 후**: 같은 탭 클릭 시 카드 6개 → 기존 5콜 + 신규 4콜(MT1/CS2/
  PM9/PS3 각 1콜) = **총 9콜**. 카드 단위로는 2개 → 6개(3배).
- **증가율**: 카드 기준 3배, 실제 API 콜 기준 약 1.8배(5→9).

## 16. lazy load 여부 — 재확인 결과: **이미 존재함**

`apt-client.tsx`의 `infraTab` state 기본값은 `'환경'`이다(§ UI-C 문서39
에서 이미 확인, 재검증). 즉 `NeighborhoodInfoPanel`(교통·생활편의를
담당)은 **사용자가 "교통·편의시설" 탭을 직접 클릭하기 전까지 아예
mount되지 않는다** — 페이지 최초 로드 시 신규 4개 카테고리 호출은
**0건**이다. 새로운 lazy-load 인프라를 만들 필요가 없었다(§18의 A/B
선택지 중 **A. 지금 단순 확장**을 선택 — 이미 tab 기반 lazy가 있으므로).

## 17. Kakao quota/비용 영향

- 이 프로젝트는 이미 Kakao Maps JS SDK를 지도(`/map`), 자동완성
  (`ApartmentAutocomplete`), 학교(`SchoolDistrictPanel`) 등 여러 곳에서
  광범위하게 쓰고 있어 **새 외부 유료 API를 도입하지 않았다**(원칙8
  준수) — 기존 앱키 쿼터 안에서의 호출 패턴 변화일 뿐.
- §15의 카드 기준 3배 증가는 **탭을 실제로 연 사용자에게만** 발생하고
  페이지뷰 전체에 걸리지 않는다(§16) — 트래픽 대비 실질 증가폭은
  "교통·편의시설 탭 클릭률" × 1.8배 수준으로 제한적이라고 판단.
- 절대적인 쿼터 한도(일일 호출 수 등)는 Kakao 콘솔의 앱별 설정값이라
  이 STEP의 코드/문서 조사만으로는 확인할 수 없다 — 웹조사는 지시대로
  하지 않았고, "기존 대비 몇 배"까지만 계산해 기록한다(§17 지시와 일치).

## 18. 대표 테스트 결과 요약 — 도심/주거/외곽

§7 표 참고. 도심(대신푸르지오1차)·주거(명륜아이파크1단지)·대형마트
인접(엘지메트로시티3)·소규모(남성한빛가든, 대가하이츠) 5개 유형 모두

## 19. UI 구조 — 선택한 방식: **C. 기존 tab 구조 확장**

기존 "교통·편의시설" 탭 안의 `repeat(auto-fit, minmax(260px,1fr))` 그리드에
카드 4개만 추가했다(새 탭, 새 chip, 새 대형 카드 시스템 없음). 이미 학교/
교통/병원·공원이 같은 카드 스타일(`cardStyle` 상수)을 쓰고 있어 **시각적
일관성이 그대로 유지**된다 — 가장 작은 변경이라고 판단한 근거.

## 20. 모바일 우선 검토 — 근사 검증(도구 제약, 명시)

`grid-template-columns: repeat(auto-fit, minmax(260px, 1fr))`는 CSS
계산상 **390px 미만 폭에서는 260px 카드 2개가 들어갈 수 없어(260×2 +
gap > 390) 자동으로 1열로 쌓인다** — 이건 별도 미디어쿼리 없이 CSS
`auto-fit`의 산술적 성질로 보장되는 동작이다. **다만 이번 세션은 로컬
개발 서버(포트 3211, 카카오 콘솔에 등록된 도메인이 아님)에서 Kakao Maps
JS SDK 로드 자체가 401/차단되어(§21) 실제 6개 카드에 데이터가 채워진
상태의 좁은 뷰포트 스크린샷은 확보하지 못했다** — 카드 레이아웃(제목/
아이콘/그리드 줄바꿈)은 데스크톱 폭에서 스크린샷으로 확인했고 CSS 구조는
기존 학교/교통 카드와 완전히 동일한 패턴을 재사용했으므로 모바일에서도
동일하게 동작할 것으로 판단하나, **실제 데이터가 채워진 모바일 화면은
production 배포 후 재확인이 필요하다**(정직하게 한계로 기록, 지어내지
않음).

## 21. 로컬 검증 제약(투명하게 기록)

로컬 dev 서버(포트 3211)로 실제 페이지를 열어 확인을 시도했으나,
`performance.getEntriesByType('resource')`로 확인한 결과 `dapi.kakao.com/
v2/maps/sdk.js` 요청이 `transferSize:0`/`responseStatus:0`로 사실상
실패하고, 같은 세션의 지오코딩 호출도 `401`을 반환했다 — **Kakao 앱키가
등록된 도메인이 아닌 로컬 포트에서는 SDK 자체가 초기화되지 않는
환경 제약**으로 판단된다(기존 병원·공원·교통 카드도 동일하게 "검색
중입니다..."에서 멈춰 있어, 이번에 추가한 코드 때문이 아니라 로컬
환경 자체의 문제임을 확인). 이 문제로:
- **데이터 정확도**는 Kakao Local **REST API**(다른 도메인 제약이
  없는 서버간 호출, `geocode-apt.ts`와 동일한 인증 헤더 재사용)로
  대체 검증했다(§3, §5~§11) — read-only, DB/코드 변경 없음.
- **실제 화면 렌더링**(로딩→데이터 표시 전환, 최종 카드 모양)은 이번
  세션에서 확인하지 못했다 — production 배포(사용자 승인 후) 또는
  카카오 콘솔에 등록된 도메인에서의 재확인이 필요하다.

## 최종 판단

APT DETAIL UI-C2는 생활편의를 병원·공원 2종에서 대형마트/편의점/약국/
어린이집·유치원 포함 6종으로 확장했다. 기존 Kakao Local 카테고리 검색
구조(`KakaoPlaces` 컴포넌트의 배열 기반 카테고리 설계)를 그대로 재사용해
새 카드 4개만 추가했고, 기존 교통·병원·공원 로직은 한 글자도 건드리지
않았다(diff로 재확인). 4개 신규 카테고리 코드는 REST API로 직접
재검증했고(임의 코드 사용 없음), PS3는 Kakao 공식 명칭이 "어린이집,
유치원"임을 확인해 UI 라벨을 정확히 맞췄다. 이미 존재하던 tab 기반
lazy load 덕분에 페이지 최초 로딩에는 영향이 없다. 새 API/package/DB/
schema는 만들지 않았다.

DB/schema/migration은 변경하지 않았고 commit/push 하지 않았다.

사용자 모바일 검수 전까지 UI-C2를 최종 완료 처리하지 않는다.
