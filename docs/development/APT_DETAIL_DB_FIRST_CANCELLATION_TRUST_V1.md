# APT DETAIL — DB-FIRST / CANCELLATION TRUST V1 (P0)

> **Production write 없음 / schema 변경 없음 / migration 없음.**
> 선행: `APT_DETAIL_UNIT_TRADE_FILTER_BUG_V1.md` (평형 선택 자체는 그 STEP에서 수정됨)

## 1. 두 개의 결함

### 1.1 소스 분기 — 지도와 상세가 서로 다른 거래를 보여줬다

같은 플랫폼·같은 단지·같은 시각:

| 화면 | 라우트 | 소스 | 26140-1164의 2026-09-05 129.7178㎡ 6.65억 |
|---|---|---|---|
| 지도 | `/api/transactions` | **DB-first** (`queryTrades`) | **있음** |
| 상세 | `/api/apt/[name]` | **MOLIT 라이브** (`fetchMolitMonthCached`) | **없음** |

상세 응답은 `monthsRequested=12 / monthsSucceeded=12 / partial=false / apiError=null`
— 실패를 숨긴 게 아니라 MOLIT가 그 시점에 그 행을 돌려주지 않았다. 실측상 이건 단발
사고가 아니다: **2026-09-05 계약 건들이 여러 단지에서 동시에** 빠져 있었다
(대신롯데캐슬 129.7178㎡ 6.65억, 대신해모로센트럴 76.5236㎡ 5.8억 등).

`apartment_trade_histories`는 append-only로 축적된 신뢰 소스이고 지도·통계·리포트가
이미 그것을 쓴다. 상세페이지만 더 약한 소스를 보고 있었다.

### 1.2 취소 거래가 활성 화면에 그대로 들어갔다

상세페이지는 `dealCanceled`를 **한 번도 필터하지 않았다.** 지도(`/map`)는 예전부터
취소 건을 제외했는데 상세만 포함해, 취소된 거래가 최근 실거래·타임라인·최고/최저·
건수에 그대로 반영될 수 있었다.

## 2. 새 소스 계약

```
/api/apt/[name]  type=apt (매매)
  1. canonical aptSeq 확정        ← 확정 못 하면 DB 경로를 쓰지 않는다
  2. queryTrades({ aptSeq, from, includeCanceled: false })   ← PRIMARY
  3. DB 0건이면 MOLIT 결과 유지                               ← SECONDARY
```

핵심은 **지도가 쓰는 것과 동일한 `queryTrades`를 재사용**한다는 점이다. 새 쿼리를
만들지 않았으므로 "지도와 상세가 같은 활성 거래 집합에서 나온다"가 구조적으로 보장된다.

### 2.1 identity — 이름으로 재식별하지 않는다

`resolveDetailAptSeq()`:

1. URL이 `aptSeq`를 줬으면 그것을 쓴다(지도/검색이 canonical identity를 들고 온 경우).
2. 아니면 `ApartmentMaster`를 **lawdCd(+dong)로 좁힌 뒤** 정규화 이름이 **정확히 하나**
   일치할 때만 채택한다.
3. 후보가 2건 이상이거나 0건이면 **null** — DB 경로를 포기하고 기존 MOLIT 경로로 간다.

`statistics-pyeong-resolver.ts`의 `findSingleMatch`와 같은 원칙이다. 다른 단지 거래를
보여주느니 기존 동작을 유지하는 편이 안전하다.

### 2.2 MOLIT의 남은 역할 (§9 — 지우지 않았다)

MOLIT 라이브는 **여전히 필요하며** 다음 경우에 쓰인다:

| 상황 | 경로 |
|---|---|
| 전월세(`type=rent`) | **MOLIT 전용** — `apartment_trade_histories`는 sale 전용이다 |
| DB 커버리지 없는 지역(부산 외) | MOLIT 폴백 |
| aptSeq를 단일하게 확정 못 함 | MOLIT 폴백 |
| DB 조회 자체가 실패 | MOLIT 결과 유지(실패를 "거래 없음"으로 위장하지 않는다) |

**MOLIT가 유효한 DB 거래를 덮는 경로는 없다.** 폴백은 DB가 0건일 때만 일어나므로
DB가 가릴 데이터가 애초에 존재하지 않는다.

### 2.3 §10 — DATA PRESENT와 COVERAGE VERIFIED의 분리

응답에 `tradeDataSource: 'DB' | 'MOLIT'`와 `canceledExcluded: true`를 추가했다.

DB에서 읽었으면 MOLIT 월별 성공/실패는 이 목록의 완전성과 무관하므로
`partial`/`failedMonths`/`apiError`를 승격하지 않는다 — 실제로 거래를 확보했는데
"MOLIT 몇 월이 실패했다"는 이유로 화면이 불완전하다고 말하면 거짓이 된다.
반대로 DB 커버리지가 없으면 MOLIT 경로의 기존 completeness 표현이 그대로 유지된다.

## 3. 취소 규칙 (§5)

- DB 경로: `queryTrades({ includeCanceled: false })` — 애초에 조회하지 않는다.
- MOLIT 경로: `excludeCanceled()`로 응답 조립 직전에 제거한다.

두 경로 모두 활성 거래만 내보내므로 최근 실거래·타임라인·건수·최고/최저·차트·
전세가율이 전부 자동으로 취소 건에서 자유로워진다(각 위젯을 따로 고치지 않았다 —
소스가 하나이기 때문).

**DB의 취소 이력은 삭제하지 않는다.** 화면에서 제외할 뿐이다. 별도의 취소 이력
표시 UI는 현재 존재하지 않으므로 보존할 대상도 없었다.

## 5. 알려진 한계

- **전월세는 여전히 MOLIT 라이브**다. `apartment_trade_histories`가 sale 전용이라
  전세가율/갭 지표의 rent 쪽은 이 STEP의 신뢰 개선을 받지 못한다.
- **DB 커버리지가 없는 지역(부산 외)은 그대로 MOLIT**다. 기존 동작이 유지될 뿐
  개선되지는 않는다.
- MOLIT가 왜 2026-09-05 건들을 빠뜨렸는지는 **규명하지 않았다.** 이 STEP은 상세가
  더 신뢰할 수 있는 소스를 보게 만든 것이고, MOLIT 자체의 누락 원인은 별건이다.
  다만 sync가 이미 그 행들을 확보해 뒀기 때문에 화면에는 영향이 없다.
- 칩 라벨 충돌(`59.8826`/`59.8839`가 둘 다 `전용 59.88㎡`로 표시)은 이전 STEP에서와
  동일하게 남아 있다 — 선택·필터는 정확히 분리되며 표시만 같다.
