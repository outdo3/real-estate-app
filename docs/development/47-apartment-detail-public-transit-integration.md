# STEP 47 — APT DETAIL UI-C3-3: 대중교통 통합 + 버스 노선정보 연결

상태: **구현 완료 / 사용자 승인 대기(commit/push 없음)**

성격: 이미 production 배포된 UI-C3-2(TAGO 버스정류소 연동, STEP 45)를
폐기하거나 다시 만드는 작업이 아니다. 확보된 TAGO 데이터를 기반으로
(1) 지하철+버스를 "대중교통"으로, KTX/기차를 "광역교통"으로 IA를
재구성하고 (2) "정류장 개수" 대신 "운행 노선번호"를 보여주도록
버스 카드를 개선하며 (3) 노선번호 연결이 안전하게 가능한지 조사 후
조건을 만족하는 경우에만 최소 구현한다.

## 0. 기존 문제 (사용자 판단)

STEP 45가 구현한 "500m 이내 정류장 40곳"은 API 데이터로는 유효하지만
사용자가 아파트를 판단하는 화면 정보로는 가치가 낮다는 지적. 반면
"어떤 버스를 탈 수 있는가"(노선번호)는 실제 의사결정에 직접 도움이
되는 정보다. 또한 지하철(일상 대중교통)과 KTX(가끔 이용하는 광역교통)
가 하나의 카드에 섞여 있어 의미가 흐려진다는 지적.

## 2. TAGO 노선 API 조사 (추측 없이 실제 호출로 검증)

공식 문서(data.go.kr/data/15098534)에서 같은 서비스
(`BusSttnInfoInqireService`) 안에 "정류소별경유노선 목록조회" 오퍼레이션이
존재한다는 사실만 확인되고 상세 스펙(파라미터명 등)은 문서에 없어,
실제 서비스키로 직접 호출해 스펙을 확정했다.

**오퍼레이션**: `getSttnThrghRouteList`
**Endpoint**: `https://apis.data.go.kr/1613000/BusSttnInfoInqireService/getSttnThrghRouteList`
**파라미터**: `serviceKey`(필수), `cityCode`(필수), `nodeid`(필수),
`pageNo`/`numOfRows`/`_type`(선택)

**핵심 발견 — 파라미터명 대소문자 함정**: 요청 파라미터명이 반드시
소문자 `nodeid`여야 한다. 흔한 TAGO 문서 표기 관례대로 camelCase
`nodeId`로 보내면 TAGO가 그 파라미터를 인식하지 못하고 **조용히
무시**한 채 `resultCode: "00"`(정상)과 함께 해당 `cityCode`(부산)
전체 노선 목록(302개)을 돌려준다 — 에러가 전혀 없어 실수로 놓치기
쉽다. 실제로 서로 다른 두 정류장(nodeid만 다름)에 `nodeId`로 호출해
완전히 동일한 302개 응답을 받는 것으로 이 문제를 재현·확인했고,
`nodeid`(소문자)로 바꾸자 정류장마다 다른(2개/6개/14개 등) 결과를
받는 것으로 검증했다. **"다른 정류장의 노선을 대신 표시"하는 사고를
막은 핵심 지점**이다.

**응답 필드**: `routeid`(노선ID), `routeno`(노선번호 — "11"처럼 숫자형과
"A01"/"180(아침)"처럼 문자형이 섞여 온다), `routetp`(버스 유형: 일반버스/
마을버스 등 실측 확인), `startnodenm`/`endnodenm`(기점/종점명).

## 3. 노선 API 조사 항목 (§6 답변)

1. 현재 `DATA_GO_KR_API_KEY`로 호출 가능한가 → **예**(같은 서비스,
   추가 활용신청 없이 즉시 호출 성공 확인).
2. 별도 활용신청 필요한가 → **아니오**.
3. 사용 operation → `getSttnThrghRouteList`.
4. 부산 cityCode=21 지원하는가 → **예**(실측 다수 정류장에서 확인).
5. nodeid/nodeno 입력 가능한가 → `nodeid` 입력, `nodeno`는 사용하지
   않음(정류소 조회 응답의 `nodeid`를 그대로 사용).
6. 특정 정류장 경유 노선 목록 획득 가능한가 → **예**, 정류장마다
   다른 목록 확인(§2의 대소문자 검증 포함).
7. 노선번호 field → `routeno`.
8. 노선 ID field → `routeid`.
9. 버스 유형 field → `routetp`("일반버스"/"마을버스" 실측 확인).
10. 호출량/응답속도 → 단건 응답 수백ms~1초대. 짧은 간격 연속 호출 시
    STEP45와 동일한 data.go.kr 레이트리밋 성격의 timeout/비정상 응답을
    재현(§7 참고).
11. 정류장 1개당 API 몇 회 필요한가 → 1회(`getCrdntPrxmtSttnList` 1회
    + 이번에 추가한 `getSttnThrghRouteList` 1회 = 총 2회/페이지 방문).
12. 현재 UI 진입 시 호출량 과도 증가 여부 → 아니오, 가장 가까운
    정류장 1곳의 노선만 조회(§9 지시대로, 40여 개 정류장 전체 조회
    안 함).

## 5. 서버 구조 변경

`src/app/api/transit/bus-stops/route.ts`:

- 신규 `fetchTagoRoutesOnce`/`fetchTagoRoutes`(고정 1회 400ms 재시도,
  STEP45와 동일 패턴) 추가.
- `nearestBusStop`에 `routes: { routeNo: string; routeType: string }[]
  | null` 필드 추가. `routes === null`은 "조회 실패", `routes === []`는
  "조회 성공했지만 경유 노선 없음"으로 명확히 구분(§4 empty/error 분리
  원칙).
- **캐싱을 정류소 위치 캐시와 분리했다.** 처음에는 기존 6시간 캐시
  콜백 안에서 노선까지 함께 조회해 하나의 캐시 값으로 묶었는데, 실측
  중 노선 조회가 일시적으로 실패하면 그 실패(`routes: null`)가
  정류소 위치 캐시(6시간) 안에 통째로 박제되어 **TAGO가 정상 복구된
  뒤에도 캐시가 만료될 때까지 계속 `null`을 돌려주는 버그**를 실제로
  재현했다(테스트 중 특정 정류장 2곳에서 발생, 서버 로그로 원인 확인).
  이를 고쳐 노선 조회를 `bus-routes:{cityCode}:{stopId}` 키로 별도
  캐시하도록 분리했다 — `getOrSetCache`는 fetcher가 throw하면 아무것도
  캐시하지 않으므로(server-cache.ts 참고), 노선 조회 실패는 캐시되지
  않고 다음 요청에서 자연히 재시도된다(재배포 없이 자연 복구 확인).
- `DATA_GO_KR_API_KEY`는 기존과 동일하게 서버에서만 사용, 새 환경변수
  없음.

## 6. 버스 UI 변경 (`BusAccessCard.tsx`)

- "가까운 정류장" → "가장 가까운 정류장"으로 라벨 변경, 거리/도보시간
  형식은 유지.
- **"500m 이내 N곳" 문구를 화면에서 제거했다**(§1/§4 지시). API 응답의
  `busStopCountWithin300m`/`busStopCountWithin500m` 필드 자체는 삭제하지
  않고 그대로 유지 — 향후 교통점수/이집 브리핑용으로 보존.
- "운행 노선" 섹션 추가: 노선번호를 숫자 우선 정렬 후 " · "로 연결,
  최대 4개까지 표시하고 나머지는 "외 N개"로 축약
  (예: `11 · 96 · 103 · 167 외 4개`).
- `routes === null`(조회 실패): 조용히 생략 — 잘못된 값을 보여주지
  않는다. `routes.length === 0`(경유 노선 없음, 실측으로 실재 확인 —
  §8 명륜아이파크1단지): "경유 노선 정보가 없습니다." 표시.

## 7. 호출 최적화 (§9)

가장 가까운 정류장 1곳의 노선만 조회한다. 주변 정류장 전체(단지당
많으면 40곳 이상)의 노선을 조회하지 않는다. "전체 노선 보기" 등의
추가 기능은 이번 STEP 범위 밖으로 남겼다(§9 "과도한 기능 확장 금지"
지시 준수).

## 10. KTX/광역교통 분리 (`NeighborhoodInfoPanel.tsx`)

기존 하나의 "🚇 교통 (지하철·KTX)" 카드를 두 카드로 분리했다:

- **🚇 대중교통**: 지하철(`KakaoPlaces categories={['SW8']}`, keywords
  없음) + 버스(`BusAccessCard`)를 한 카드 안에 하위 섹션 두 개로 배치.
- **🚄 광역교통**: KTX/기차(`KakaoPlaces categories={[]} keywords={['KTX',
  '기차역']}`)만 별도 카드로 분리.

**설계 선택(§3)**: 옵션 A(컨테이너만 통합, 컴포넌트는 그대로 유지)를
선택했다 — `KakaoPlaces`/`BusAccessCard` 컴포넌트 자체는 무수정, 상위
`NeighborhoodInfoPanel.tsx`에서 배치만 재구성했다. 회귀 위험이 가장
낮고(컴포넌트 내부 로직 변경 없음), "대중교통"이라는 하나의 의미
단위로 보이는 목표도 달성한다.

기존 KTX 필터(폐역 제외 `isClosedStation`, KTX특송퀵서비스 등 오탐
제거 `isRailwayStation`)는 `KakaoPlaces.tsx` 내부 로직이라 전혀 건드리지
않았다 — §10 지시대로 훼손 없음.

지하철만 단독으로 호출해도(`categories={['SW8']}`, keywords 생략)
`isSubwayOnly` 판정(`categoriesKey === 'SW8' && keywords.length === 0`)이
그대로 참이 되어 기존 "초역세권" 배지 로직에 영향 없음을 코드로
확인하고 브라우저로도 재확인했다(§9).

## 11. 부산진화물역 등 비여객역 조사 (§11)

Kakao Local API로 실측 확인한 결과, **화물전용역과 여객역의
`category_name`이 완전히 동일하다**:

```
가야화물역:   교통,수송 > 기차,철도 > 기차역   (여객역과 동일)
부산진화물역: 교통,수송 > 기차,철도 > 기차역   (여객역과 동일)
부산역(KTX): 교통,수송 > 기차,철도 > 기차역 > KTX,SRT정차역
부전역(KTX): 교통,수송 > 기차,철도 > 기차역 > KTX정차역
범일역(폐역): 교통,수송 > 기차,철도 > 기차역 > 폐역
```

Kakao가 명시적으로 구분해 주는 값은 "폐역"(이미 필터링 중, §10 훼손
없음)과 "KTX,SRT정차역"/"KTX정차역" 접미사뿐이다. **화물전용 여부를
구분하는 공식 category 값은 존재하지 않는다** — "부산진화물역"이라는
이름 문자열 자체에만 신호가 있고, 이는 사용자가 명시적으로 금지한
"특정 역 이름 하드코딩"에 해당한다. 안전한 일반 규칙(category/공식
데이터 기반)을 찾지 못했으므로 **이번 STEP에서는 필터를 추가하지
않았다** — §11 지시("안전한 일반 규칙을 만들 수 없다면 임의 필터를
추가하지 말고 조사 결과만 보고")를 그대로 따랐다. 브라우저 실측(§9)
으로 "부산진화물역"이 광역교통 카드에 그대로 노출됨을 확인했다.

## 12. 공항 / 출퇴근 시간

이번 STEP에서 구현하지 않았다(§12, §13 지시). "광역교통" 카드 구조
자체는 KTX/기차 항목을 배열처럼 추가하는 형태라 향후 "✈️ 공항" 항목을
같은 카드 안에 추가하는 확장이 구조적으로 가능하다(별도 컴포넌트를
새로 만들 필요 없이 KTX 항목과 같은 패턴으로 카드에 줄 하나 추가하는
정도).

향후 "아파트 → 가까운 지하철/버스 → 주요 업무지역 → 예상 통근시간"
기능과 연결할 때, 이번 STEP에서 확보한 `nearestBusStop`(정류장 좌표·
노선)과 지하철 카드의 역명이 출발점 데이터로 재사용 가능하다 — 단
실제 경로 탐색 API는 이번 STEP에서 추가하지 않았다.

## 16. 알려진 한계

1. 명륜아이파크1단지처럼 TAGO에 정류장은 등록돼 있지만 경유 노선이
   0건으로 등록된 경우가 있다 — 정류장 자체의 존재/거리 데이터는
   정확하나 노선 데이터베이스 등록 완성도는 정류장마다 다르다(§8).
2. 노선 조회가 정류소 조회에 추가되면서 data.go.kr 레이트리밋에 걸릴
   가능성이 다소 늘었다 — 캐시 분리(§5)로 실패가 영구화되지 않도록는
   고쳤지만, 근본 원인(게이트웨이 정책)은 STEP45와 마찬가지로 문서화돼
   있지 않다.
3. 부산진화물역 등 비여객역이 광역교통에 그대로 노출된다 — 안전한
   일반 필터 규칙이 없어 의도적으로 손대지 않았다(§11).
4. 모바일 뷰포트(360/375/390px) 실측은 브라우저 자동화 도구의 리사이즈
   미반영으로 하지 못했다(§9) — **사용자 모바일 실기기 검수 필요**.
5. 빠른 단지검색/StickyPriceBar/하단 nav는 직접 클릭 재현을 하지
   않았다(§13).
6. 행정구역 경계 인근 citycode 중복 집계(STEP45에서 이미 기록)는
   이번 STEP에서 다시 손대지 않았다 — 화면에서 300/500m 카운트 자체를
   제거했으므로 사용자 화면 영향은 없고, 내부 데이터(향후 점수체계용)
   에는 여전히 남아있는 한계다.
