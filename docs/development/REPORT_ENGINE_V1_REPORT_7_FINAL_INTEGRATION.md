# E-JIP REPORT ENGINE — REPORT-7 (최종 통합 / 진입 UX / 릴리스 QA)

> **Production write 없음 / schema 변경 없음 / migration 없음 / 신규 의존성 없음.**
> 선행: REPORT-1~6.

## 1. 문제

리포트 엔진은 완성돼 있었지만 **제품 안에서 리포트로 들어갈 길이 없었다.**
URL을 직접 알아야만 볼 수 있는 상태였다. REPORT-7은 그 진입 경로를 연결한다.

## 2. route 모양의 단일 정의

진입 CTA와 공유 canonical URL이 각자 문자열을 조립하면 언젠가 갈라지고, 갈라지는
순간 **공유 링크가 다른 리포트를 가리킨다.** 그래서 `src/lib/report/report-links.ts`
하나가 모든 리포트 경로를 정의하고, REPORT-6의 `reportCanonicalPath()`도 이 함수들에
위임한다(테스트로 동일성 고정).

```ts
cityReportHref()                    // /report/city/busan
districtReportHref(lawdCd)          // null 가능
dongReportHref(lawdCd, dong)        // null 가능
aptReportHref(aptSeq)               // null 가능
compareReportHref(a, b)             // 둘 다 있어야 하고 a!==b
dailyReportHref('YYYY-MM-DD')       // 형식이 맞아야 함
```

**핵심 계약: canonical identity가 없으면 `null`.** 호출부는 null이면 CTA 자체를
렌더하지 않는다 — 이름으로 지어낸 경로로 사용자를 보내느니 진입점을 만들지 않는다(§4).

## 3. 진입점

| 화면 | CTA | 조건 |
|---|---|---|
| 단지 상세 | `이 단지 한장 리포트` | canonical aptSeq 확정 시에만 |
| 지도(선택 단지 카드) | `한장 리포트` | marker에 aptSeq가 있을 때만 |
| 단지 비교(CompareV2) | `비교 리포트 보기` | 두 슬롯 모두 aptSeq identity일 때만 |
| 통계(지역) | `{구/동} 한장 브리핑` | 부산 현행 16개 코드일 때만 |
| MY | `한장 리포트 보기` | 항상(허브로 가는 정적 링크) |
| 허브 `/report` | 부산 브리핑 / 오늘 새로 확인된 실거래 / 16개 구 | — |

### 3.1 단지 상세 (§2)

기존 `NextActionSection`(DECISION_JOURNEY_V1)에 `REPORT` 액션을 추가했다. 페이지마다
CTA를 새로 만들지 않고 이미 있는 액션 블록을 쓰므로:

- 버튼 디자인 언어가 자동으로 일치한다(§15)
- 클릭 트래킹(`next_action_click`)이 그대로 붙는다
- 위치가 히어로 바로 아래 액션 영역이라 §2의 배치 요구를 만족한다

`NEXT_ACTION_TYPES`에 `'REPORT'`를 추가했다. 이 배열이 analytics actionType 검증의
**단일 출처**이며 DB enum이 아니다(schema 무관). 타입 검사기가
`admin-analytics/query.ts`의 라벨 맵 누락을 즉시 잡아줬다.

리포트가 primary가 되면서 `지도에서 위치 보기`는 secondary로 내려간다(primary 1개 규칙).
aptSeq가 없으면 리포트 CTA가 없고 지도가 다시 primary가 된다.

### 3.2 비교 (§3)

`/stats/compare`의 canonical UI는 **CompareV2**다(5개까지 비교하는 옛 `CompareView`는
다른 slug에서만 쓰인다). CTA는 CompareV2에만 붙였다 — 5곳 비교 화면에 "2곳 리포트"
버튼을 두면 어느 2곳인지 오해를 준다.

두 슬롯이 모두 `identity.kind === 'aptSeq'`로 해석됐을 때만 링크가 만들어진다.
이름으로만 잡힌 단지가 섞이면 `compareReportHref`가 null을 주고 CTA가 사라진다.

### 3.3 지역 (§4)

통계 화면의 `RegionContext`가 canonical `lawdCd`/`dong`을 이미 들고 있을 때만 노출한다.
추가로 **`isBusanCurrentLawdCd` 가드**를 건다 — 리포트는 부산 16개 구·군만 다루므로
서울/대구를 선택한 상태에서 브리핑을 권하지 않는다. 동이 선택돼 있으면 동 브리핑,
아니면 구 브리핑으로 간다.

지도에서 좌표만 있고 lawdCd가 없는 상태에는 CTA를 만들지 않는다. **지오코딩을 새로
돌려서까지 버튼을 그리지 않는다**(§4 — 취약성을 늘리지 않는다).

### 3.4 지도 (§5)

선택된 단지 카드에서는 **단지 리포트가 지역 브리핑보다 우선**이라는 §5 규칙에 따라
`한장 리포트` 보조 버튼 하나만 추가했다. 팝업을 더 무겁게 만들지 않는다.

## 4. 일별 리포트 진입 (§6)

기존에 `/stats/feed`("실거래 · 지역별 실거래 피드")가 있지만 이건 **기간 기준 지역
거래 피드**이지 관찰일 기준이 아니다. REPORT-5의 "새로 확인된" 의미와 다르므로
그 화면의 문구를 바꾸는 것은 틀린 정렬이다.

그래서 §6의 지침대로 **새 내비게이션 페이지를 만들지 않고** 허브에 자리를 줬다.
날짜는 `todayKst()`(REPORT-5의 단일 helper)를 그대로 쓴다.

문구는 `오늘 새로 확인된 실거래` + 부제 "이집이 오늘 새로 확인한 거래입니다 ·
계약일은 각 거래에 따로 표시됩니다" — "오늘 계약된"으로 읽힐 여지를 남기지 않는다.

## 5. 허브 결정 (§8/§23)

**REPORT HUB: IMPLEMENTED** (`/report`)

이유: 부산 전체 브리핑과 일별 리포트는 **자연스러운 진입 화면이 아예 없었다.**
나머지 리포트는 각자 맥락 화면(상세/비교/통계)에서 들어가지만, 이 둘은 갈 곳이
없어 URL을 아는 사람만 볼 수 있었다.

무거운 대시보드가 아니다 — **서버 컴포넌트**이고(클라이언트 JS 경계 없음) 구성은:

1. 바로 보기: 부산 한장 브리핑 / 오늘 새로 확인된 실거래
2. 지역 브리핑: `BUSAN_DISTRICTS`(검증된 16개 코드)에서 그대로 나온 칩 16개
3. 단지·비교 리포트는 **어디서 여는지 안내만** 한다

3번이 중요하다. 허브에서 단지를 이름으로 고르게 하면 그게 곧 이름 기반 식별이 된다.
canonical aptSeq는 지도/검색/상세를 거쳐야 확정되므로 그 진입 화면으로 보낸다.
