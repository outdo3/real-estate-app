## 1. 현행 집계 경로

| | 화면(`/api/stats/concentration` → ConcentrationView · VolumeChartCard 거래 많은 단지) | 브리핑(`readRegionReport` → `representativeComplexes`) |

| 기간 | 선택 기간(계약일) — 이전 STEP에서 일치 확인 | 같은 기간 |
| 읽는 순서 | `ORDER BY deal_date, id` | — |
| dedupe | **`dedupeTrades`: (단지 identity + 면적 + 유형, 금액, 계약일, 층)이 같으면 첫 행만 남김** | 없음 |

차이는 두 가지다. ① 4필드가 같은 행을 1건으로 접는다. ② 접을 때 **취소 여부를 보지 않고 id가 작은 행**을 남기고, 그 뒤 취소를 뺀다 — 남은 행이 취소면 그 거래는 0이 된다.

참고: 같은 화면의 거래량 요약(dashboard)은 dedupe 없이 유효 행을 센다 — 화면 안에서도 요약과 단지 목록의 기준이 달랐다.

## 3. 원천 재확인 — DB ingest 중복은 없다

30일(32셀)·3개월(64셀) 전부 원천 페이지 완주(비완전 셀 0). 같아 보이는 그룹 전체에서 **DB 행 수 > 원천 행 수인 경우 0** — DB가 원천을 중복 적재한 사례가 없다. DB 행은 자연키(+occurrenceIndex)로 원천 기록과 1:1이다.

## 4. 거래 identity

- DB 저장 필드(단지·면적·금액·계약일·층)만으로는 **같은 층 다른 세대**를 구분할 수 없다. 원천에도 호수가 없다.
- 원천이 주는 더 강한 필드: `aptDong`(건물 동 — 부산 데이터에서 대부분 공란), `dealingGbn`(중개/직거래), `slerGbn`/`buyerGbn`(개인/법인), `rgstDate`(등기일), `cdealType`/`cdealDay`(해제). 거래 일련번호 같은 공식 고유 식별자는 **없다**.
- 따라서 공식 identity는 "원천이 발행한 기록 하나"이고, DB에서는 자연키 + occurrenceIndex(원천 내 순번)로 그 기록에 대응한다. **4필드는 거래 identity가 아니다** — 같은 날 같은 층 같은 금액의 서로 다른 세대 거래가 원천에 실재한다(대운).

## 8. 취소 작업과의 관계

- false-cancel 28행은 두 경로 모두에서 유효 거래를 0으로 만든다(30일 12건). **집계 규칙과 무관** — repair가 해결한다. 새 insert 경로 수정(`03abea9`) 이후 새로 생기지 않는다(cron 검증 대기).
- 화면 dedupe는 취소 형제 그룹에서 **순서에 따라** 결과가 바뀐다(id가 작은 행 = 먼저 적재된 행이 취소면 0). 취소 정확도와 별개로 화면 규칙 자체가 결정적이지 않다.
- 결함 B 행은 두 경로 모두 과대 계산한다(삭제 경로 없음).

## 9. 제품 의미

"거래 많은 단지 N건" = **선택 기간에 실제로 유효한 매매 계약 기록 수.** 공식 원천(국토교통부 실거래 공개)이 발행한 유효 기록 하나가 한 건이다. DB 행 수나 필드 조합 dedupe 수가 목적이 아니다.

## 10. 권고 — B. CANONICAL TRANSACTION COUNT

| 안 | 판단 |
|---|---|
| A. RAW VALID ROW COUNT | 현재 데이터에서는 B와 같은 숫자다(DB 행 ↔ 원천 기록 1:1, ingest 중복 0). 다만 "DB 행"이 정의가 되면 적재 결함이 규칙이 된다 |
| **B. CANONICAL TRANSACTION COUNT** | **채택.** 정의 = 원천 유효 기록 수, 구현 = 취소 제외 DB 행을 **DB id(=원천 기록 1:1) 기준**으로 센다. 내용 필드로 접지 않는다 |
| C. 현행 화면 4필드 dedupe | **기각.** 원천 실재 거래를 지우고(대운 −30), 취소 형제에서 순서 의존적으로 유효 거래를 잃는다 |

구현상 B = 브리핑의 현행 계산과 동일. **화면을 브리핑 쪽으로 맞춘다**(반대로 맞추면 틀린 숫자에 맞추는 것).

## 11. 화면/브리핑 일치 계획 (이번 STEP 구현 없음)

1. 공용 순수 함수 `countValidTradesByComplex(rows)` — 취소 제외 → 단지 identity(aptSeq, 없으면 이름+동)별 개수. 브리핑 `representativeComplexes`와 화면 `buildConcentrationRanking`의 개수 계산이 이것을 쓴다.
2. concentration DB 경로(부산): 매매 행에 `dedupeTrades`를 걸지 않는다(DB id가 고유). 취소는 **먼저** 뺀다. 직전 기간 개수도 같은 함수.
3. MOLIT live 경로(비부산 — 현재 stats 게이트로 닫힘)의 `dedupeTrades`는 "같은 달을 두 번 받은 경우" 방지용이므로 그 용도로만 남기고, 키에 occurrence 순번(원천 내 순서)을 넣어 원천 기록을 접지 않게 하는 것은 별도 판단.
4. 실거래 피드(`/api/stats/feed`)도 같은 `dedupeTrades`를 쓴다 — 피드 건수·목록도 같은 이유로 과소일 수 있어 같은 STEP에서 함께 본다.
5. 테스트: 대운 패턴(층당 3건 동일 행) 46 유지 · 취소 형제에서 id 순서와 무관하게 유효 1건 · 기간별(7d/15d/30d/3m) 같은 함수 · 요약 거래건수 = 단지 합계와 같은 기준.
6. Production QA: 이 감사 스크립트를 다시 돌려 화면 = 브리핑 = 원천(데이터 결함 제외) 확인.
