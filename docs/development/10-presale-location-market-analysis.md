## 1. 현재 데이터 구조 조사 — 8개 질문에 대한 답

`prisma/schema.prisma` 전체와 관련 서비스/API 코드를 직접 읽어 확인했다.

**1) Apartment에 어떤 식별자가 있는가?**
`id`(자동증가 PK), `@@unique([name, dong])`. 외부 API(MOLIT/Kakao) 식별자와 연결되는 별도 컬럼은 없다.

**2) Apartment에 주소가 있는가?**
없다. `name`/`dong`/`lawdCd`/`jibun`(지번, 선택)만 있다 — 도로명주소·지번주소 풀 텍스트 컬럼 자체가 없다.

**3) Apartment에 latitude/longitude가 있는가?**
**없다.** schema 주석에 명시된 대로 이 모델은 "실거래가처럼 실시간 API가 있는 데이터가 아니라 `scripts/crawl_facilities.py`가 오프라인으로 채우는 단지 커뮤니티 시설 정보"(건축물대장 표제부 캐시)이며, 좌표 필드 자체가 존재하지 않는다.

**4) 실거래 데이터는 DB 저장형인가, 실시간 API 호출형인가?**
**실시간 API 호출형이다.** `src/lib/api-molit.ts`의 `fetchMolitData({ lawdCd, dealYmd, type })`가 매 요청마다 국토부 실거래 API(`apis.data.go.kr/1613000/...`)를 직접 호출한다. `Transaction`/`TradeHistory` 모델은 schema 주석에 "라이브 앱에서는 사용하지 않음"(구 시드/오프라인 스크립트용)이라고 명시돼 있고, 실제로 라이브 API 라우트 어디에서도 이 두 모델을 조회하지 않음을 확인했다.

**5) 아파트와 실거래를 연결하는 key는 무엇인가?**
현재 코드(`api/apt/[name]/route.ts`)는 **`lawdCd`(법정동코드 5자리) + 단지명 문자열 유사매칭(공백 제거, "아파트" 접미사 제거 후 부분일치) + `dong`(있으면 정확 일치)**으로 연결한다. 안정적인 외부 식별자로 연결하지 않는다.
그런데 이번 조사에서 실제 MOLIT 원본 XML을 직접 파싱해 확인한 결과, **국토부 API 자체는 `aptSeq`(예: `"11560-7"`, `"26140-1361"`)라는 단지 고유번호를 제공하고 있었다** — 이 프로젝트의 `api-molit.ts`는 현재 이 필드를 추출하지 않고 있다(문자열 이름 매칭에만 의존). 이는 이번 STEP에서 코드로 반영하지 않지만(§22 금지 항목), 향후 이름 매칭보다 훨씬 안정적인 연결 키가 될 수 있는 후보로 기록해둔다.

**6) 법정동코드는 어디에서 얻는가?**
세 경로가 확인된다.
- `src/lib/geocode-apt.ts`(`geocodeApartmentName`): 아파트명 → Kakao 키워드검색(좌표) → Kakao `coord2regioncode`(좌표→행정동)로 lawdCd 역산.
- `prisma.apartment` 캐시 조회(이전에 lawdCd/dong이 저장된 적 있으면 재사용).
- `src/lib/region-utils.ts`: `REGCODE_PROXY`(`grpc-proxy-server-mkvo6j4wsq-du.a.run.app`, 이 프로젝트 소유가 아닌 외부 프록시 서비스로 보임)로 시/도·시/군/구 이름 ↔ lawdCd 상호 변환. Kakao와 무관한 별도 외부 의존성이다.

**7) 아파트 목록을 특정 지역 기준으로 가져오는 기존 로직이 있는가?**
직접적인 "지역별 아파트 마스터 목록" 조회는 없다. 대신 `/api/transactions`(지도 페이지가 사용)가 `lawdCd` 기준으로 MOLIT 실거래를 가져온 뒤 **단지명+동 기준으로 그룹핑**해 사실상의 "그 지역에 실거래가 있는 단지 목록"을 즉석에서 만들어낸다(§7 상세).

**8) 현재 지도에 아파트 마커를 표시할 때 데이터는 어디서 오는가?**
`src/app/map/page.tsx`의 `fetchAptMarkers()` → `/api/transactions?type=apt&lawdCd=...&months=12` 호출 → 응답의 각 거래건을 **Kakao 키워드검색(`"${dong} ${name}"`)으로 서버 라우트(`api/transactions/route.ts`)가 실시간 좌표 보강** → 좌표가 확보된 건만 마커로 렌더링. 이 좌표는 DB에 저장되지 않고 매 요청마다(서버 인스턴스 생존 기간 동안의 in-memory `Map` 캐시만) 재조회된다.

**결론(§1)**: 이 앱에는 "좌표로 아파트를 찾을 수 있는 로컬 마스터 DB"가 없다. 대신 "MOLIT 실거래(이름+동) → Kakao 키워드검색으로 좌표 실시간 보강"이라는, 이미 실제로 동작 중인 패턴이 `/api/transactions`와 `api/apt/[name]`에 존재한다 — 이번 조사는 이 기존 패턴을 분양 위치 기준으로 재사용할 수 있는지를 핵심적으로 검증했다.

## 4. Kakao Local API 반경검색 실제 호출 검증

### 4-1. 기존 사용 현황(신규 키 발급 불필요 확인)

이 프로젝트는 이미 `NEXT_PUBLIC_KAKAO_MAP_API_KEY` 하나로 다음을 전부 수행 중이다(신규 API 키 발급 불필요, `.env.local`에 이미 설정 확인 — 값은 출력하지 않음):
- 주소 검색(`/v2/local/search/address.json`) — `cheongyakService.ts`의 분양 지오코딩
- 키워드 검색(`/v2/local/search/keyword.json`) — `api/transactions/route.ts`, `geocode-apt.ts`
- **카테고리 검색 + radius 파라미터**(`/v2/local/search/category.json?...&radius=...&sort=distance`) — `src/lib/ai-search.ts`(초등학교, `radius=500`), `src/app/api/school/stats/route.ts`(학원, `radius=3000`)
- 좌표→행정구역(`/v2/local/geo/coord2regioncode.json`) — `geocode-apt.ts`

즉 **radius 기반 검색은 이미 이 프로젝트의 검증된 기존 패턴**이며(서버 라우트에서 JS 키를 `KA`/`Origin` 헤더 우회로 REST 호출하는 방식까지 이미 확립돼 있음), 이번 조사를 위해 새로 발급받거나 새로 도입한 API/패키지는 없다.

### 4-2. 실제 소량 호출 검증(2026-08-13 실행, 결과 확인 후 스크립트는 삭제함)

Presale 4건의 실제 좌표로 `keyword.json?query=아파트&x=...&y=...&radius=...&sort=distance`를 직접 호출했다.

`total_count`는 radius가 커질수록 실제로 증가해(radius 파라미터가 실제로 작동함을 확인), 서버 측 REST 호출로 실제 동작함을 확인했다.

**중요한 한계 발견**: Kakao 키워드검색(`sort=distance`)의 `pageable_count`(실제로 페이지네이션해서 가져올 수 있는 건수)는 `total_count`보다 훨씬 작다(예: 서울 2000m에서 total_count=1172인데 pageable_count=16). 3페이지(최대 45건)까지 모두 가져와도 실제 확보되는 원본 문서 수는 위치에 따라 16~23건 수준에 머물렀다(§6에서 재확인) — **"반경을 2km로 넓혀도 API가 실제로 돌려주는 결과 개수 자체가 늘어나지 않는" Kakao API 자체의 상한**이 존재함을 실측으로 확인했다. 이는 신뢰도 있는 전수 "주변 아파트 목록"을 만들 때 넓은 반경에서는 결과 누락 가능성이 있다는 의미다.

### 4-3. 아파트 전용 카테고리 코드는 없음(실측 확인)

Kakao Local의 공식 카테고리 그룹 코드(`MT1`/`CS2`/`PS3`/`SC4`/`AC5`/`PK6`/`OL7`/`SW8`/`BK9`/`CT1`/`AG2`/`PO3`/`AT4`/`AD5`/`FD6`/`CE7`/`HP8`/`PM9`) 중 "아파트"에 해당하는 코드는 없다(`AD5`는 숙박/모텔·호텔이며 아파트가 아님을 실제로 `category_group_code=AD5`로 호출해 확인 — 결과는 전부 모텔/호텔이었다). 따라서 이 앱의 `KakaoPlaces.tsx`가 병원/학교/지하철 등에 쓰는 것과 같은 방식의 "카테고리 코드 기반 정밀 검색"은 아파트에는 적용할 수 없고, **키워드검색("아파트") + 응답의 `category_name`(예: `"부동산 > 주거시설 > 아파트"`) 문자열 필터링**으로만 아파트를 걸러낼 수 있다.

## 5. Kakao 검색 결과를 "아파트 마스터"로 쓸 수 있는가

### 5-1. Kakao 응답 필드(실측)

키워드검색 응답 문서(`documents[]`)에 실제로 존재하는 필드: `place_name`(장소명), `address_name`/`road_address_name`(지번/도로명주소), `x`/`y`(좌표), `id`(Kakao Place ID), `category_name`(카테고리 경로 문자열), `category_group_code`(공식 그룹코드, 아파트는 빈 문자열), `distance`(중심좌표 기준 거리, m).

### 5-2. Kakao ↔ MOLIT 이름 매칭 실측 검증

### 5-3. 추가 발견 — MOLIT의 `aptSeq`(단지 고유번호)

§1-5에서 언급한 대로, MOLIT 원본 XML에는 이 앱이 현재 사용하지 않는 **`aptSeq`**(예: `"26140-1361"`) 필드가 있다. 이는 이름 매칭보다 신뢹할 수 있는 연결키가 될 잠재력이 있으나, Kakao 응답에는 이 값이 없어(Kakao Place ID와 무관) **Kakao↔MOLIT 연결에는 여전히 이름 매칭이 필요**하다. `aptSeq`는 "같은 이름의 다른 단지"를 MOLIT 내부에서 구분하는 데는 쓸 수 있지만, Kakao 검색 결과와의 연결 문제 자체를 해결하지는 못한다.

**결론(§5)**: Kakao 검색 결과는 부동산 "마스터 DB"로 쓰기엔 정확한 신원 식별자가 없어(Place ID는 MOLIT와 무관) 완전히 신뢰할 수 없지만, "이 지점 주변에 물리적으로 존재하는 아파트 후보 목록"을 얻는 용도로는 실사용 가능한 수준이다. 다만 이 목록을 MOLIT 실거래와 연결할 때는 항상 "매칭 실패/모호 가능성"을 사용자에게 숨기지 않는 설계가 필요하다.

## 7. MOLIT 실거래 연결 구조 재확인

`fetchMolitData({ lawdCd, dealYmd, type: 'apt' })` → `RTMSDataSvcAptTradeDev` 엔드포인트, 파라미터 `LAWD_CD`(5자리)+`DEAL_YMD`(YYYYMM). 실제 원본 XML 필드 전체를 이번 조사에서 직접 확인했다(예시: 서울 영등포구 삼환아파트 거래 1건):

```xml
<aptDong/><aptNm>삼환</aptNm><aptSeq>11560-7</aptSeq><bonbun>0076</bonbun><bubun>0001</bubun>
<buildYear>1999</buildYear><buyerGbn>개인</buyerGbn><dealAmount>147,000</dealAmount>
<dealDay>26</dealDay><dealMonth>6</dealMonth><dealYear>2026</dealYear><dealingGbn>중개거래</dealingGbn>
<estateAgentSggNm>서울 영등포구</estateAgentSggNm><excluUseAr>59.91</excluUseAr><floor>5</floor>
<jibun>76-1</jibun><landCd>1</landCd><roadNm>영중로</roadNm>...<sggCd>11560</sggCd>
<umdCd>10900</umdCd><umdNm>영등포동8가</umdNm>
```

핵심 필드: `aptNm`(단지명), `aptSeq`(단지 고유번호, §5-3), `excluUseAr`(**전용면적**, ㎡), `dealAmount`(거래금액, 만원), `floor`(층), `buildYear`(건축년도), `dealYear/Month/Day`(계약일), `jibun`(지번), `umdNm`(법정동명), `sggCd`(=lawdCd). **좌표 필드는 없다.** `api-molit.ts`가 이미 이 필드들을 정상적으로 파싱하고 있음을 원본 XML 대조로 확인했다(§4의 `item.아파트 || item.aptNm || ...` fallback 체인 중 `aptNm`이 실제 사용되는 필드임을 확인).

| 단계 | 평가 | 근거 |
|---|---|---|
| Presale → 분양 좌표 | **부분 가능(69.6%)** | §2 |
| 분양 좌표 → 주변 아파트 후보(Kakao 반경검색) | **가능(제약 있음)** | §4 — 단, Kakao 자체 결과 상한(pageable_count) 때문에 넓은 반경에서 일부 후보 누락 가능 |

## 11. 거리 계산 가능성

이 프로젝트 코드베이스 전체를 검색한 결과 **Haversine이나 기존 거리 계산 함수는 존재하지 않는다**(신규 검색 결과 0건). Kakao API 응답이 자체적으로 `distance`(정수, m)를 반환하므로 반경검색 결과에 한해서는 별도 거리 계산 없이 Kakao 값을 그대로 쓸 수 있다. 다만 "이미 확보한 두 좌표(분양 vs 특정 아파트) 간 거리"를 앱 내부에서 직접 계산해야 하는 경우(예: DB에 저장된 두 좌표 비교)에는 Haversine 공식을 새로 구현해야 한다 — 표준 공식이라 구현 자체의 리스크는 낮지만, **이번 STEP에서는 구현하지 않고 향후 구현 후보로만 기록**한다(§22).

## 13. 분양가 ↔ 실거래 단순 비교의 위험

실측/코드 확인 결과 다음 문제들이 실제로 존재한다.

- **면적 개념 불일치**(§14에서 상세) — `supplyArea`(공급면적)와 MOLIT `excluUseAr`(전용면적)는 다른 개념. 단순 비교 시 같은 평형인데 면적 수치가 달라 사용자가 오인할 수 있음.
- **신축 분양가 vs 구축 실거래가** — 부산 서구 사례(§9)처럼 분양 당시와 준공 후 실거래 시점 사이에 몇 년의 시차가 있어, 그 사이의 시세 변동(상승/하락)을 반영하지 못하면 "분양가가 비쌌다/쌌다"는 결론이 왜곡됨.
- **`topAmount`의 의미** — 07 문서(§I-2)에서 이미 확정한 대로 이는 "최고 분양가(상한액)"이지 평균가·확정가가 아니다. 실거래 평균/중앙값과 직접 비교하면 항상 분양가가 더 비싸 보이는 구조적 편향이 생긴다.
- **단일 실거래의 대표성 부족** — 한 단지의 특정 층·특정 시점 거래 1건은 그 단지 시세를 대표하지 못한다(로열층/저층, 급매/직거래 여부 등에 따라 편차가 큼).
- **거래시점/입주시점 불일치** — 분양은 계약~입주까지 수년이 걸리는 반면, 비교 대상 실거래는 "오늘 기준 최근"일 수 있어 시점 기준이 다르다.
- **옵션/발코니 확장비** — `topAmount`에 확장비가 포함됐는지 여부가 API 문서/기존 조사에서 확인되지 않는다(확인 필요 사항으로 남김, 임의 가정 금지).

## 14. 면적 비교 가능성 — 실측으로 확정

이번 조사의 핵심 발견 중 하나다. `PresaleHouseTypeDetail` 15개 행을 `supplyArea`와 `houseTy` 앞자리 숫자로 직접 대조했다.

| 공고 | houseTy(앞자리) | supplyArea | 차이 |
|---|---|---|---|
| 성남복정2 A1블록 | 55.97 | 83.6488 | +27.68 |
| 시흥거모 A-5블록 | 55.00 | 82.2068 | +27.21 |
| 더샵 신길센트럴시티 | 51.9981 | 73.9159 | +21.92 |
| 더샵 신길센트럴시티 | 59.9973 | 84.6386 | +24.64 |

`houseTy`의 앞자리 숫자(예: `"059.9973A"` → 59.9973)는 **일관되게 `supplyArea`보다 약 21~28㎡ 작다** — 이는 한국 아파트의 "전용면적/공급면적" 통상 비율(공급면적 ≈ 전용면적 + 주거공용면적)과 정확히 일치하는 패턴이며, 국민평형 표기 관례("전용 59㎡", "전용 84㎡")와도 맞아떨어진다.

**결론**: `houseTy` 앞자리 숫자가 **전용면적**, `supplyArea`(`SUPLY_AR`)가 **공급면적**을 의미한다는 것을 실측으로 확인했다. MOLIT의 `excluUseAr`는 명확히 "전용면적"이므로,
- **`supplyArea` ↔ MOLIT `excluUseAr` 직접 비교는 틀린 비교다**(공급면적 vs 전용면적 — 다른 개념).
- **`houseTy` 앞자리 숫자 ↔ MOLIT `excluUseAr`는 같은 개념(전용면적)으로 비교 가능할 가능성이 높다.**

다만 이는 이번 STEP에서 처음 실측 확인한 것으로, 09 문서(P2-D3)에서는 `houseTy`를 "타입 접미사(A/B 등)만 추출"하는 용도로만 썼고 앞자리 숫자를 전용면적으로 공식 채택한 적은 없다 — **공식 API 문서에 "HOUSE_TY 앞자리=전용면적"이라는 명시적 정의가 있는지는 이번 조사에서 재확인하지 못했다**(정황 증거는 강하나 공식 문서 대조는 못함 — "확인 필요"로 남긴다). parser/schema 변경은 하지 않는다(§22).

## 15. 안전한 가격 비교 단계(LEVEL) 평가

| LEVEL | 정의 | 현재 데이터로 가능? |
|---|---|---|
| 1 | 같은 지역(시/도) 최근 실거래 참고 | **가능** — `subscriptionAreaName` + lawdCd 매핑(`region-utils.ts`) |
| 2 | 주변 아파트(반경) 최근 실거래 | **부분 가능** — 좌표 69.6% + Kakao 상한(§12) + 이름매칭 79%(§5-2) 누적 손실 감안 시 "참고용"으로만 가능 |
| 3 | 유사 면적 주변 아파트 실거래 | **조건부 가능** — §14 발견(`houseTy` 앞자리=전용면적 추정)을 전제로 하면 가능하나, 이 전제 자체가 "확인 필요" 상태 |
| 4 | 연식/거리/면적 종합 비교 | **불가(현재 범위 밖)** — 신축 분양 vs 구축의 연식 차이를 정량 보정하는 로직이 없고, 이번 STEP에서 설계도 하지 않음 |
| 5 | 이집 자체 가격 경쟁력 점수 | **불가** — 추천/점수 알고리즘 없음, 요청 범위(§22)에서도 명시적으로 금지 |

**억지로 LEVEL 5까지 가능하다고 말하지 않는다.** 현재 실측 근거로 안전하게 주장할 수 있는 최대 수준은 **LEVEL 2(주변 실거래, 참고용 명시 필요)**이며, LEVEL 3은 §14의 "확인 필요" 전제가 검증돼야 승격 가능하다.

## 16. 사용자 화면 문구 정책 제안

정확도 수준에 따라 라벨을 구분해야 한다는 원칙(요청안 §16, P2-D1 §4 결정)을 이번 실측 결과에 맞춰 구체화한다.

| 상황 | 권장 문구 | 근거 |
|---|---|---|
| 좌표 있음 + 반경 내 Kakao 후보 확보 + MOLIT 이름매칭 성공 | "반경 OOm 내 아파트 실거래" | 실제 거리 기반(§4) |
| 좌표 있음 + 반경 내 후보는 있으나 MOLIT 매칭 실패/모호 | 해당 단지는 목록에서 제외(억지 표시 금지) | §5-2 매칭 실패 사례 존재 |
| 좌표 없음(318건) | "이 지역 최근 실거래"(시/도 또는 시/군/구 명시) — **"주변"이라는 단어 사용 금지** | P2-D1 §4 기존 결정과 동일 원칙 |
| 유사 전용면적 조건까지 만족(§14 전제 확인 후) | "비슷한 면적(전용 OO㎡ 대)의 최근 실거래" | §14, 단 전제 검증 후 |
| 그 외 모든 근사 상황 | "참고용 지역 시세"(정확한 위치 비교가 아님을 명시) | §16 원칙 |

"주변 시세"라는 표현은 실제 반경 기반 결과에만 쓰고, 그 외에는 절대 쓰지 않는 것을 권고한다(요청안 원칙 그대로 재확인).

## 18. 행정구역 개편 문제 재확인

06 문서가 기록한 "인천광역시 서구 → 검단구/서해구" 지오코딩 불일치 사례를 이번 조사에서도 재확인했다(코드는 수정하지 않음, `cheongyakService.ts`의 `validateRegion` 로직 그대로). 이런 사례는:
- **좌표 확보 자체를 막는다**(P2-C 정책상 지역 불일치 시 좌표 저장 거부 → §2의 318건 중 상당수가 이 패턴으로 추정).
- 주변 아파트 검색 단계에서도 동일한 문제가 재현될 수 있다 — 과거 주소 기준으로 표기된 Presale 주소와, 현재 행정구역 기준으로 응답하는 Kakao 결과 간 지역명 불일치가 반경검색 자체는 막지 않지만(반경검색은 좌표 기준이라 행정구역명과 무관), **법정동 텍스트 기반 보조 검증 로직을 추가한다면 동일한 문제가 재발할 것**으로 예상된다. 이번 STEP에서 해결하지 않는다(§22).

## 19. API 호출량/트래픽 구조 비교

| 방식 | 장점 | 단점 | API 호출량(추정) | 속도 | 전국 확장성 | 데이터 신선도 |
|---|---|---|---|---|---|---|
| A. 매 요청 실시간 호출(현재 `/api/transactions`, `api/apt/[name]` 방식) | 구현 최소, 항상 최신 | 상세페이지 방문마다 Kakao(반경 1회 + 매칭 대상 수만큼 이름 매칭 시도) + MOLIT(월별 호출) 다회 발생 | 분양 1건 상세 진입당 Kakao 수~수십 회 + MOLIT 수~십수 회(반경 내 후보 수에 비례) | 느림(순차/병렬에 따라 다름, 현재 코드는 이미 `Promise.all` 병렬화 패턴 사용 중) | 전국 확장 시 트래픽 선형 증가, 인기 분양 상세는 반복 호출 부담 큼 | 항상 최신 |
| B. 서버 인메모리 캐시(현재 `getOrSetCache`, `Map` 캐시 이미 존재) | 코드 추가 거의 불필요(기존 패턴 재사용) | **서버리스(Vercel) 환경에서는 인스턴스 재시작/다른 인스턴스 라우팅 시 캐시가 사라짐** — 이 프로젝트가 실제로 Vercel에 배포돼 있어(메모리 기록 확인) 이 한계가 실사용에 그대로 적용될 가능성이 높음 | A와 유사(캐시 미스 시) | 캐시 히트 시 빠름 | 캐시 크기 무관하게 개선 안 됨(인스턴스별 분리) | 캐시 TTL 동안 약간 낡을 수 있음 |
| C. DB 캐시(Presale별 주변 아파트/실거래 요약을 DB에 저장) | 인스턴스 무관하게 공유, 응답 빠름 | 갱신 정책 필요(언제 재계산할지), schema 변경 필요(이번 STEP 금지) | 최초 계산 시에만 발생, 이후 0 | 빠름(DB 조회만) | 좋음 | 갱신 주기에 의존(실시간 아님) |
| D. Apartment 마스터 DB 구축(좌표 enrichment) | 반경검색 자체를 Kakao 실시간 호출 없이 DB 쿼리로 대체 가능 | 전국 enrichment 비용 매우 큼(§20), 이번 STEP 금지 | 최초 구축 시 대량, 이후 신규 단지만 | 빠름 | 가장 좋음(구축 후) | 신규 단지 추가 주기에 의존 |
| E. 정기 enrichment(배치) | D의 부담을 분산 | 스케줄러(cron) 인프라 필요 — 이 프로젝트는 아직 cron을 구현한 적 없음(05/06 문서에서 명시적으로 "cron 미구현") | 배치 주기당 대량, 실시간 0 | 빠름(조회 시) | 좋음 | 배치 주기 지연 |

**평가**: 현재 이 앱의 실사용 배포 환경(Vercel, 서버리스)을 고려하면 B(인메모리 캐시)의 효과는 제한적이다. 분양 상세페이지 하나에 "주변 아파트+실거래"를 실제로 붙인다면, C(DB 캐시, 예: presale별 요약을 별도 테이블에 주기적으로 채워 넣는 방식)가 현재 구조에서 가장 현실적인 절충안으로 보이나, 이는 schema 변경이 필요해 이번 STEP 범위 밖이며 P2-D4 구현 시 별도로 설계해야 한다.

## 20. 이집 장기 데이터 구조와의 관계

현재 확인된 사실을 근거로:
- `Property` 모델(오피스텔/생숙/재개발용, `lat`/`lng` 필드 보유)이 이미 존재하지만 비어 있고 좌표를 채우는 로직도 없다(§6).
- `Apartment` 모델은 좌표가 없어 이 역할을 할 수 없다(§6).

**설계 후보(제시만, 구현하지 않음)**: 분양 전용의 별도 "주변 아파트 캐시 테이블"을 새로 만들기보다, 이미 존재하는 `Property`(카테고리 확장이 쉬운 구조, `PropertyCategory` enum에 `APT`가 이미 정의돼 있음 — 현재는 미사용)를 아파트 마스터로 확장하는 방향이 스키마 중복을 피할 수 있는 후보로 보인다. 다만 이는 실거래/분양/재개발/학군/커뮤니티를 연결하는 장기 구조 설계가 선행돼야 하는 큰 결정이라, 이번 STEP에서는 후보로만 기록하고 실제 schema 변경은 하지 않는다.

## 21. P2-D4 구현 범위 제안

이번 조사 결과를 근거로, 요청안이 예시한 분리(B/C/D/E)를 실제 데이터/API 제약에 맞춰 다음과 같이 제안한다.

- **P2-D4-B (위치/지도)**: 좌표 있는 728건에 한해 `MapViewer.tsx`(Kakao SDK) 기반 인터랙티브 지도를 상세페이지에 실제로 임베드. 좌표 없는 318건은 기존 위치 카드(P2-D3) 유지. — 기존 `/map` 인프라 재사용 가능성 높음(07 문서 §J-3과 동일 결론 재확인).
- **P2-D4-C (주변 아파트 후보, LEVEL 1~2)**: Kakao 반경검색(§4) + 이름 정규화 매칭(§5-2, 접미사 제거 규칙)으로 "주변 아파트 실거래 참고" 기능을 좌표 있는 건에 한해 제공. 매칭 실패/모호 사례는 노출하지 않음(§5-2/§16). API 호출 비용 문제(§19)를 이 단계에서 캐시 전략과 함께 반드시 설계.
- **P2-D4-D (면적 조건 정밀화, LEVEL 3)**: §14의 "houseTy 앞자리=전용면적" 가설을 공식 API 문서 또는 추가 표본으로 검증한 뒤 착수(현재는 "확인 필요" 상태이므로 P2-D4-C보다 먼저 하지 않는다).
- P2-D4-E(연식/거리 종합, LEVEL 4) 이상은 이번 제안에 포함하지 않는다 — 데이터/설계 근거가 부족하다(§15).

불필요하게 단계를 늘리지 않기 위해, 요청안의 4단계(B/C/D/E) 대신 **3단계(B/C/D)**로 압축 제안한다.

## 최종 검수 결정 (2026-08-13)

PRESALE P2-D4-A(분양 위치·주변 아파트·실거래 연결 가능성 조사)를 최종 승인한다. 최종 판단 **B(부분적으로 가능하지만 추가 데이터/Apartment Master 구축이 필요)**를 그대로 확정한다. 이번 STEP에서는 실제 주변 아파트/실거래 비교 기능을 구현하지 않는다.

### 1. Apartment Master 부족 — 확정

현재 구조만으로는 전국 단위의 신뢰 가능한 "주변 아파트 + 실거래 비교" 기능을 구현하기에 Apartment Master가 부족하다.

- `Apartment` 모델: 좌표 없음(필드 자체가 없음), 실제 20건뿐, 전국 마스터가 아님(§6).
- `Property` 모델: 좌표 필드(`lat`/`lng`)는 있으나 실제 데이터 **0건**(§6).

둘 다 전국 아파트 마스터 역할을 할 수 없다는 것을 최종 확정한다.

### 2. Kakao 반경검색의 위치 — 후보 탐색용으로만 사용

Kakao 반경검색(§4)은 주변 후보 탐색에는 유용하지만, **아파트 마스터 자체로 사용하지 않는다.** 일부 지역(서울·부산 남구 표본, §12)에서는 `pageable_count`/결과 상한 때문에 500m→1km→2km로 반경을 넓혀도 후보 수가 충분히 증가하지 않는 사례를 실측으로 확인했다 — 따라서 Kakao 검색 결과만으로 전국 주변 아파트 목록을 구성하지 않는다.

### 3. 부산 서구 실측 결과 — 부분 가능성의 근거이자 한계

부산 서구 표본(id=479)에서 Kakao 반경 1km 후보 14곳, MOLIT 실거래 918건(12개월) 대비 **이름 정규화("아파트" 접미사 제거)만으로 약 79%(14건 중 11건) 매칭**된 실측 결과(§5-2)를 그대로 기록한다. 이 결과는 부분 구현 가능성을 보여주지만, 약 21% 수준의 미매칭/모호 사례가 존재하므로 **전국 서비스의 최종 연결 방식으로 채택하지 않는다.**

### 4. `aptSeq` — 중요 발견, 아직 PK로 확정하지 않음

MOLIT 원본에 `aptSeq`(단지 고유번호, 예: `"26140-1361"`)라는 후보가 존재함을 중요 발견사항으로 기록한다(§1-5, §5-3, §7). 향후 Apartment Master 설계 시 다음을 반드시 검증한다.

- `aptSeq`의 안정성(동일 단지가 시점에 따라 값이 바뀌지 않는지)
- 지역 간 유일성(전국 범위에서 값 충돌이 없는지)
- 거래월에 따른 유지 여부(재건축/리모델링 등으로 값이 갱신되는지)
- 동일 단지명/동명 충돌 해결 가능성(§5-2에서 관측된 "송도혜성주상복합빌딩아파트" 같은 모호 사례를 `aptSeq`가 실제로 해소하는지)
- 다른 데이터 소스(Kakao Place ID, Property 모델 등)와의 연결 가능성

현재 단계에서 `aptSeq`를 무조건 최종 PK로 확정하지 않는다. 이 검증은 **향후 Apartment Master 설계 STEP(MASTER M1)**에서 수행한다.

### 5. 면적 비교 정책 — 확정

`PresaleHouseTypeDetail.supplyArea` ≠ `houseTy` 앞자리 숫자(§14 실측 확인)이며, MOLIT `excluUseAr`는 전용면적이다(§7). 따라서:

- 향후 분양가↔실거래 비교에서 **`supplyArea`를 MOLIT `excluUseAr`와 직접 비교하지 않는다.**
- `houseTy` 앞자리 숫자가 전용면적을 의미하는지는 **공식 API 문서를 통해 다시 확인한 뒤 사용한다.**
- 공식 확인 전까지 이 값을 "전용면적 확정값"으로 취급하지 않는다(§14의 "확인 필요" 상태를 그대로 유지).

### 6. P2-D4 진행 순서 변경

P2-D4의 다음 구현 단계는 당장 진행하지 않는다. 다음 순서로 변경한다.

1. P2-D4-A 조사 완료(이번 STEP)
2. Apartment Master 조사/설계
3. Apartment Master 구축
