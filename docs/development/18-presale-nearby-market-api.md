# 이집 분양 주변 실거래 비교 API — P2-D4-B2

작성일: 2026-08-13
성격: P2-D4-B1(주변 ApartmentMaster 검색)에 이어, "주변 아파트 → aptSeq → MOLIT 실거래 연결 → 유사 전용면적 비교 → 가격차이 계산"까지 구현했다. Prisma schema/migration 변경 없음.

**상태: P2-D4-B2 완료(사용자 최종 승인).** 이 문서는 "BLOCKER 발생(§3) → 추가 법령 조사(P2-D4-B2-FIX) → 조건부 정책 승인(판단 B) → 가격비교 구현 완성(P2-D4-B2-CONTINUE)"의 전체 히스토리를 그대로 보존한다 — **§3의 BLOCKED 기록은 삭제하지 않는다.** 아래 "최종 승인 정책"이 이 문서 전체(§3~마지막)의 내용을 무효화하지 않으며, 오히려 그 조사 과정 전체가 최종 정책의 근거다.

## 최종 승인 정책 (2026-08-13, 사용자 승인)

1. `houseTy` 숫자부를 비교용 전용면적으로 사용하는 정책 승인.
2. 근거: 「주택공급에 관한 규칙」 제21조제5항(국가법령정보센터 원문 확인, §"houseTy 추가 검증") + 기존 실측(문서16 §8, 55개 표본) + `PresaleHouseTypeDetail` 5,395건 전수 정합성(파싱 성공 100%, exclusiveArea<supplyArea 100%, §"P2-D4-B2-CONTINUE").
3. **청약홈 API 기술문서에 HOUSE_TY의 직접 정의가 없다는 한계는 계속 문서에 남긴다** — 판단 B(조건부 사용)이지 판단 A(공식 확정)가 아니다.
4. `supplyArea`는 이번 실거래 면적 비교 계산에 사용하지 않는다(기존 상세 UI 표시 용도로만 유지).
5. 유사면적 비교 범위 ±1㎡(경계값 포함) 유지.
6. `ApartmentMaster` ↔ MOLIT 연결은 `aptSeq` 정확 일치만 사용, 단지명 문자열 매칭 fallback 금지.
7. 실거래 조회 6개월→12개월→24개월 fallback 유지, 판단 기준은 "Presale 주택형과 ±1㎡ 이내 비교 가능한 거래 존재 여부"(단순 거래 존재 아님).
8. 최근 비교거래 최대 3건, `recentMedianPrice`(중앙값), `differenceAmount = presaleTopAmount - recentMedianPrice`(만원, 부호 있는 객관적 숫자) 유지.
9. `differenceRate`는 현재 버전에서 계속 제외.
10. 가치판단(저렴/비쌈/고평가/저평가/적정가/투자추천 등) 필드·문구는 생성하지 않는다.
11. 대형 평형(104㎡ 이상)의 낮은 비교 coverage는 데이터 오류가 아니라 현재 시장 데이터의 한계로 문서에 유지한다.
12. 실제 모집공고 PDF 30개 표본 직접 대조 미완료 사실도 한계로 계속 유지한다.
13. `topAmount` null / parser 실패 경로는 현재 실데이터에 사례가 없어 라이브 검증은 못했으나, nullable-safe 코드 검토(§"P2-D4-B2-CONTINUE" 단위테스트) 결과로 승인한다.

## 3. houseTy 공식 의미 확인 — BLOCKER 조사 결과

### 3-1. 조사 경로

1. `data.go.kr`의 "한국부동산원_청약홈 분양정보 조회 서비스" 공식 API 페이지(`https://www.data.go.kr/data/15098547/openapi.do`)를 확인했다 — 페이지 자체에는 필드별 상세 설명이 없고, 한국부동산원(REB) 기술문서로 안내하는 링크가 있었다.
2. 그 링크(`https://www.reb.or.kr/reb/na/ntt/selectNttInfo.do?mi=10251&bbsId=1268&nttSn=79889`)에서 **"[기술문서] 청약홈 분양정보 조회 서비스(26.01.29 수정)"** 공식 문서(.docx, 58페이지)를 실제로 찾았다.
3. 브라우저로 문서 뷰어를 열어 "HOUSE_TY"를 문서 내 검색, **26페이지 "c) 응답 메시지 명세" 표에서 해당 행을 직접 확인했다**:

| 항목명(영문) | 항목명(국문) | 항목크기 | 항목구분 | 샘플데이터 | 항목설명 |
|---|---|---|---|---|---|
| house_ty | 주택형 | 17 | 0 | 058.8500A | 주택형 |
| suply_ar | 공급면적 | 17 | 0 | 80.3800 | 공급면적 |

4. **"항목설명" 열이 모든 필드에서 "항목명(국문)"을 그대로 반복하는 형식임을 같은 페이지의 다른 행(`house_manage_no`→"주택관리번호", `pblanc_no`→"공고번호")으로 교차 확인했다** — 즉 이 공식 문서의 "항목설명"은 의미를 풀어 설명하는 필드가 아니라 국문 필드명을 한 번 더 적은 것뿐이다.

### 3-2. 결론

**공식 문서(한국부동산원 청약홈 API 기술문서, 26페이지)에 `house_ty`가 "전용면적 기반 코드"라거나 숫자 부분이 전용면적을 의미한다는 명시적 정의가 없다.** 공식 문서가 제공하는 정보는 "필드명=주택형, 크기=17자, 샘플=058.8500A"뿐이며, `data.go.kr`의 파일데이터 메타데이터(문서16 조사 시점)도 `house_ty`를 "내용_내용"(일반 텍스트) 유형으로 분류할 뿐 "수량_면적"(면적) 유형으로 분류하지 않는다는 점(공급면적 `suply_ar`은 명시적으로 면적 유형) — 두 개의 독립적인 공식 소스가 같은 결론(명시적 정의 없음)을 가리킨다.

**판정: 공식 확인 실패.** 문서16의 55개 표본 실측(강한 정황 증거, §3-3)에도 불구하고, 요청안 §3의 명시적 지침("공식 확인 실패 시: 가격차이 계산 구현을 중단하고 B2를 BLOCKED로 보고한다. 추측으로 진행 금지")에 따라 **유사 전용면적 비교·가격차이 계산 구현을 중단했다.**

### 3-3. 참고 — 기존 실측 정황(참고용, 공식 근거 아님)

문서16 §8이 8개 Presale·55개 주택형에서 `houseTy` 앞자리와 `supplyArea`를 대조해 일관된 패턴(면적이 클수록 차이도 커짐, 국민평형 표기와 일치)을 확인한 바 있다. 이는 여전히 유효한 관찰이지만, **정황 증거는 공식 정의를 대체하지 않는다**는 원칙을 그대로 지켰다.

## 5. fetchMolitData 확장 (BLOCKER와 무관 — 구현함)

`src/lib/api-molit.ts`에 **optional 필드 2종을 추가**했다(기존 필드 이름/타입/순서는 전혀 변경하지 않음):

- `aptSeq: string | null` — MOLIT 원본 `item.aptSeq`를 `String()`으로만 감싸 그대로 보존(숫자 변환 없음, identifier 안전 원칙).
- `excluUseArea: number | null` — MOLIT 원본 전용면적(`excluUseAr`)을 숫자로 파싱. **주의**: 이 필드는 MOLIT 자체 공식 필드(전용면적임이 명확)이며 §3의 BLOCKER(청약홈 `houseTy`)와는 무관하다 — B2는 이 필드를 표시용으로만 쓰고, Presale 어떤 필드와도 비교하지 않는다.
- `dealDate: string`("YYYY-MM-DD") — 기존에 `info` 문자열 내부에만 있던 값을 별도 필드로 노출(정렬/식별용).
- `floorRaw: string | number | null` — 층수 원본.

기존 consumer(`/api/apt/[name]`, `/api/transactions`, `/api/school/apartments`, admin dashboard)는 이 필드들을 읽지 않으므로 영향이 없다 — `tsc --noEmit` 오류 0, 기존 라우트 재테스트(§16)로 재확인했다.

## 7. MOLIT 조회 전략 — 구현함

### 7-1. distinct sggCd 기준 배치 조회

Presale 자체의 sggCd 하나가 아니라, **B1이 찾은 반경 내 후보(최대 5개)가 실제로 속한 distinct sggCd 전부**를 조회 대상으로 삼는다(§10). 실측(§13)으로 남구 분양(id=801)이 `[26290, 26500]` 두 지역코드로 정상 배치 조회됨을 확인했다.

### 7-2. 아파트 개수와 무관한 호출 수

같은 sggCd+월 조합은 **한 번만** 호출한다(아파트 5개 각각 호출하지 않음, §31). 예: 남구 3개+수영구 2개 후보라면 매 월 남구 1회+수영구 1회만 호출 — 응답을 aptSeq로 필터링해 5개 후보 모두에 나눠 쓴다.

### 7-3. 캐시 재사용

신규 캐시 시스템을 만들지 않았다. 기존 `getOrSetCache`(in-memory, TTL 3600초)를 **`/api/apt/[name]`과 완전히 동일한 키 형식**(`molit:apt:{sggCd}:{dealYmd}`)으로 그대로 재사용했다 — 이 프로젝트의 다른 실거래 조회 기능과 캐시가 자연스럽게 공유된다. 서버리스 환경에서 hit율이 보장되지 않는다는 기존 한계(문서16 §23)는 그대로 유지된다 — 이번 STEP은 이를 성능 최적화로만 취급하고 정확성에 의존하지 않는다.

---

## 8. 6→12→24개월 fallback — 구현함

`MONTH_PHASES = [6, 12, 24]`. 매 phase마다 **이전에 조회하지 않은 신규 월만** 추가로 fetch한다(이미 조회한 월 재호출 없음). "충분" 판정 기준: **반경 내 후보(aptSeq 보유) 전원이 최소 1건 이상의 실거래를 확보하면** 그 phase에서 멈춘다 — 원래 설계(§10)가 언급한 "유사면적 최대 3건"은 §3 BLOCKER로 인해 면적 필터링 자체가 없으므로, "거래 존재 여부"로 단순화했다.

---

## 9. 유사 전용면적 정책 / 사용자 면적 표현 — 구현하지 않음

§3 BLOCKER로 인해 `isSimilarExclusiveArea()` 같은 helper, `±1㎡` 허용범위 적용, "비슷한 전용면적" 표현 모두 이번 B2 코드에 없다. `recentTransactions`는 해당 단지의 **면적 필터링 없는** 최근 실거래 원본이다.

---

## 10. 최근 거래 최대 3건 / 정렬 — 구현함(면적 무관 버전)

각 주변 아파트(`aptSeq` 기준)에 대해 연결된 실거래를 `dealDate` 내림차순 정렬 후 최대 3건 반환한다. 각 거래는 `dealAmount`(만원)/`dealDate`/`excluUseArea`(참고용, 필터링에는 쓰지 않음)/`floor`를 포함한다.

---

## 11. median / differenceAmount / differenceRate — 구현하지 않음

§3 BLOCKER로 인해 `recentMedianPrice`, `differenceAmount`, `differenceRate`, `expensive`/`cheap` 등 어떤 형태의 가격 비교·판정 필드도 API 응답에 없다. `topAmount`(만원 단위, 문서03 §G에서 이미 확정된 정책)조차 이번 응답에서 읽지 않는다 — 비교 대상이 없어 필요가 없다.

### 공식 문서 확인 결과 — 새로 발견한 핵심 근거

법제처 국가법령정보센터(`law.go.kr`, 정부 1차 공식 소스)에서 **「주택공급에 관한 규칙」 제21조(입주자모집 공고)를 브라우저로 직접 열람**해 원문을 확인했다(시행 2026. 6. 15., 국토교통부령 제1592호 — 현행).

- **제21조제3항제8호**: 입주자모집공고에 "호당 또는 세대당 주택공급면적 및 대지면적"을 포함해야 한다.
- **제21조제5항**(원문 그대로 인용): "제3항제8호에 따라 공동주택의 공급면적을 세대별로 표시하는 경우에는 주거의 용도로만 쓰이는 면적(이하 "주거전용면적"이라 한다)으로 표시하여야 한다. 다만, 주거전용면적 외에 다음 각 호의 공용면적을 별도로 표시할 수 있다.
  1. 주거공용면적: 계단, 복도, 현관 등 공동주택의 지상층에 있는 공용면적
  2. 그 밖의 공용면적: 주거공용면적을 제외한 지하층, 관리사무소, 노인정 등 공용면적"

**의미**: 대한민국 법령상, 아파트 분양 시 "호당/세대당 주택공급면적"(=업계 관행상 "주택형" 표기, 예: "084.9700A")을 표시할 때는 **법적으로 주거전용면적(전용면적) 기준으로 표시해야 하며**, 공급면적(전용면적+공용면적)은 별도로 "추가 표시 가능한" 부가 정보일 뿐이다. 이는 청약홈 API 기술문서(§3, 26페이지)에는 없는 내용이지만, **그 API가 서비스하는 원본 데이터(입주자모집공고) 자체를 규율하는 상위 법령**이다.

독립적인 3개 소스가 동일한 결론("주택형 표기방식이 전용면적+주거공용면적 방식에서 주거전용면적 단독 표시로 변경됨", 시행 2009. 4. 1.)을 일관되게 확인해줬다(qnaqc.co.kr 블로그, nepla.ai 법령 아카이브, 일반 검색 결과 종합) — 그리고 이번에 **law.go.kr 원문을 직접 열람해 현재도 유효한 조항임을 1차 소스로 재확인**했다.

### 실제 교차검증 — 시도했으나 기술적 제약으로 미완료

10개 이상 공고·30개 이상 주택형 직접 대조(§3~5)를 시도했다. 실제 입주자모집공고 PDF(예: 철산역자이 정정공고, 2025000429)를 확보했으나:

- `pdftotext`(poppler-utils)로 텍스트 추출 시도 → **한글이 전혀 추출되지 않음**(임베디드 폰트 인코딩 문제로 추정, `-layout`/`-raw` 옵션 모두 동일).
- Chrome 브라우저로 PDF를 열어 자동화 도구로 검색·스크롤 시도 → **PDF 뷰어가 브라우저 내부(internal) URL로 처리돼 자동화 도구가 상호작용 불가**(REB 문서뷰어와 달리 이 PDF는 Chrome 자체 내장 뷰어를 사용).
- `pdfinfo`, OCR 도구 등 대체 수단은 이번 환경에 설치돼 있지 않음.

**따라서 "HOUSE_TY numeric ↔ 실제 공고문 전용면적 표"의 숫자 단위 직접 대조(§4~5가 요청한 30개 표본, 오차 범위 실측)는 이번 STEP에서 완료하지 못했다.** 이는 새로 발견한 사실이 아니라 기존 실측(문서16 §8, 55개 표본, 55/55 일관된 패턴)을 재확인하지 못했다는 뜻이며, 기존 실측 결과 자체를 부정하는 근거는 발견되지 않았다.

`src/lib/presale-house-type.ts`(신규)에 런타임 helper로만 구현했다 — **`PresaleHouseTypeDetail.houseTy`/`supplyArea` DB 원본은 전혀 건드리지 않았고, 신규 DB 컬럼도 만들지 않았다.**

- `isSimilarExclusiveArea(a, b, tolerance=1)`: `Math.abs(a-b) <= tolerance` — 경계값(±1㎡ 정확히)도 포함(inclusive), 단위테스트로 확인(§아래).
- `medianPrice(amounts)`: 1건=그 값, 2건=평균, 3건=정렬 후 가운데 값.

### 6→12→24개월 fallback 조건 강화 (§17 핵심 수정)

이전 STEP(BLOCKED 이전 버전)은 "해당 아파트에 거래가 1건이라도 있으면 충분"으로 판단했다. 이번에는 **"이 Presale의 주택형 중 하나와라도 ±1㎡ 이내로 비교 가능한 거래가 있는가"**로 기준을 강화했다 — 59㎡ 분양인데 주변 아파트에 84㎡ 거래만 있는 경우를 "충분"으로 조기 종료하지 않기 위함이다. 실제로 강서구(847) 표본에서 이 변경으로 종료 시점이 6개월→24개월로 늘어남을 확인했다(§실측 표 참고) — 요청안이 우려한 시나리오가 실제로 발생했고, 강화된 로직이 이를 올바르게 처리함을 확인했다.

### 호출량 폭증 방지 확인

주택형이 여러 개(예: id=479는 12개)라도 MOLIT 호출은 여전히 **distinct sggCd × 개월 수**에만 비례한다 — 원본 거래를 sggCd+월 단위로 한 번만 가져와 메모리에서 모든 주택형에 재사용하는 구조(§7의 기존 설계)를 그대로 유지했고, 주택형별 개별 호출 코드는 추가하지 않았다.

### B3 전달 사항 (갱신)

1. `comparisonAvailable`이 `true`인 주택형만 비교 UI를 그려야 한다. `false`(이번 실데이터에는 없지만 코드상 존재)는 "비교 정보 없음" 처리.
2. `comparisons`가 빈 배열인 주택형(예: 630의 나머지 10개 대형 평형)은 "주변에 비교 가능한 최근 실거래가 없습니다" 안내만 하고 임의 추정치를 만들지 않는다.
3. **"전용면적(추정)"을 매 카드마다 반복 노출하지 않는다**(요청 §20) — "비슷한 전용면적"을 기본 표현으로 쓰고, 법령 근거는 별도 정보/도움말 영역에 한 번만 배치한다.
4. `differenceAmount`는 부호 있는 숫자 그대로 노출하고, "높습니다/낮습니다" 같은 방향 표현만 부가하되 "비싸다/싸다/고평가/저평가" 같은 가치판단 단어는 쓰지 않는다.
5. 노후 단지와 신축 분양 간 큰 차액 사례(§수동검산 표)가 실제로 존재하므로, 비교 카드마다 연식(`buildYear`, B1이 이미 제공)을 함께 보여주고 면책 문구(문서16 §22)를 반드시 포함해야 한다.
