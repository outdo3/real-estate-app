# STEP R2 — Redevelopment Data Validation

상태: **실물 검증 완료 — DB/schema/migration/UI 변경 없음**

## 목적

R1에서 후보로 지목한 "국토부 전국 도시정비사업 통합 데이터"의 실제
CSV 전체(1,566건)를 확보해 전국 커버리지·부산 포함 여부·부산
서구 존재 여부를 실물 기준으로 확정하고, 부산광역시 정비사업 API
(R1 후보 C)와 이름 기준으로 대조해 R1에서 미확정으로 남긴 "부산
서구 데이터 누락" 문제의 실제 원인을 재검증한다. 사업유형/진행단계
표준화 가능성과 지오코딩·폴리곤 전략을 설계 수준에서 정리하고,
R3(Master DB 설계) 착수 가능 여부를 판단한다.

## 부산 API 서구 누락 원인

**핵심 정정: R1의 결론("부산 API가 서구를 누락하고 있다", 판정 C)은
틀렸다.** 실제로는 판정 **B**(서구 사업은 있지만 텍스트 형식
때문에 못 찾음)에 해당한다.

R1에서는 부산 API 원문 343건 전체를 대상으로 `"서구"`라는
문자열을 raw grep했고 0건이었다(이 사실 자체는 R2에서도 재확인—
지금도 0건). 하지만 R2에서 국토부가 확정한 서구 20개 구역명을
기준으로 부산 API의 `areaName`을 정규화(공백 제거, "재개발/
재건축/구역" 등 접미사 제거)해 대조하자 **7건이 정확히 일치**했다:

```text
국토부[동대신1]   <-> 부산API[동대신1 재건축]   location="구덕로296번길 40-1(동대신동2가)"
국토부[동대신2]   <-> 부산API[동대신2 재개발]   location="보수대로173, 3층(동대신동 1가)"
국토부[부민2]     <-> 부산API[부민2 재개발]     location="해돋이로269번길4, 이약국3층(아미동2가)"
국토부[부민3]     <-> 부산API[부민3 재개발]     location="부용로26번길 18, 1층(부용동2가)"
국토부[서대신4]   <-> 부산API[서대신4 재개발]   location="대영로45번길20, 3층(서대신동2가)"
국토부[서대신5]   <-> 부산API[서대신5 재개발]   location="대영로84, 3층(동대신동1가)"
국토부[서대신6]   <-> 부산API[서대신6 재개발]   location="서대신동2가 414-1일원"
```

부산 API에는 `서대신7 재개발`(location="서대신동1가 212일원",
step="이전고시")도 존재 — 국토부 서구 목록에는 없는 항목이라
부산 API에만 있는 사례(반대 방향 존재).

**원인 확정**: 부산 API의 `location`/`areaName` 필드는 **구
단위(예: "서구") 지명을 거의 쓰지 않고, 법정동 단위(예:
"서대신동", "동대신동", "아미동", "부용동") 지명만 쓴다.**
구 이름 자체가 응답 어디에도 나타나지 않는 구조라, "서구"라는
문자열로 검색하면 실제로는 존재하는 서구 사업을 전부 놓친다.
이건 부산 API의 **데이터 자체 누락이 아니라, R1이 사용한 검증
방법(구 이름 문자열 검색)의 한계**였다.

다만 국토부 서구 20건 중 13건(남부민1/2, 동대신4/5/6/7/8/9/10,
동대신1(주거환경개선 쪽), 부용1, 아미1, 아미3)은 이번 정규화
매칭으로도 부산 API에서 대응 항목을 찾지 못했다 — 이 13건은
전부 국토부 기준 **"2)정비구역지정"(가장 초기 단계) + "5)주거환경개선"
+ 세대수 0**인 항목들이다. 초기 단계라 아직 조합/추진위 사무실이
없어 부산시 운영형 시스템(부산 API는 필드 구성상 "조합 운영현황"에
가까운 성격 — `businessEntities`/`telNo`/`guildMemNum` 등 운영
주체 정보 중심)에 개별 등록되지 않았을 가능성이 있다 — 이건
추정이며 R2에서 확정하지 못했다.

## 국토부 vs 부산 overlap

이름 정규화(공백 제거, "제" 제거, "재개발/재건축/정비사업/정비구역/
구역/지구/사업" 등 접미사 제거) 기준, **부산 전체**(서구만이 아닌
227건 전부) 대조:

```text
국토부 부산 총 건수(정규화 후 distinct): 209
부산 API 총 건수(정규화 후 distinct):     323
정규화 후 정확 일치:                       129
국토부만 존재:                              80
부산API만 존재:                            194
```

**주의**: 이 매칭은 "정규화 후 문자열 완전 일치"만 본 것이라,
번호가 우연히 같은 서로 다른 사업을 같은 사업으로 오판할 위험이
있다(아래 "대표 샘플 수동 검증"에서 실제 이런 사례를 발견함).
production 매칭 로직으로 그대로 쓸 수 없다 — R3에서 별도로
설계·검증 필요.

나타난다. 우연 4연속이라기엔 패턴이 뚜렷하다.

**가능한 설명(확정 아님, R3에서 재검토 필요)**:
1. 같은 구역이 처음엔 "주거환경개선구역"으로 지정됐다가 나중에
   "재개발/재건축구역"으로 전환됐는데, 국토부 데이터(연간 갱신)가
   최초 지정 시점 스냅샷에 머물러 있고 부산 API(포털 명시
   "실시간")는 최신 상태를 반영하고 있을 가능성.
2. 이름이 같은 서로 다른 두 사업(동명이인)일 가능성 — 정규화
   매칭의 한계로 오판했을 가능성.

어느 쪽이든 결론은 같다: **"진행 단계"라는 관점에서는 국토부
데이터를 그대로 믿을 수 없고, 부산처럼 갱신이 빠른 지역 소스가
있다면 그쪽을 우선해야 한다.**

## 부산 사업유형 추정 결과

부산 API에는 공식 유형 필드가 없어 `areaName` 접미사로 추정
(R1과 동일 방식, 343건 전수 재확인):

```text
재개발: 171건 / 재건축: 67건 / 가로주택정비: 56건 / 소규모재건축: 49건
```

**중요 발견**: 국토부 5개 유형 코드 어디에도 "가로주택정비"·
"소규모재건축"에 대응하는 코드가 없다. 이는 데이터 누락이
아니라 **법적 근거 자체가 다르기 때문**으로 판단된다 — 국토부
"전국 도시정비사업 통합 데이터"는 페이지 설명상 명시적으로
"도시 및 주거환경정비법"(도시정비법)에 근거한 사업만 다루고,
가로주택정비·소규모재건축은 별도 법률인 "빈집 및 소규모주택
정비에 관한 특례법"(소규모주택정비법) 소관이라 **국토부 이
데이터셋의 정의상 범위 밖**이다. 부산 API의 343건 중
105건(56+49, 약 31%)이 이 카테고리라 — **국토부 데이터를
Master로 쓰면 소규모주택정비법 사업 전체가 구조적으로 빠진다.**

## schema review 필요 여부

**SCHEMA_REVIEW_REQUIRED.** 근거:

1. `추진위원회 구성`처럼 실사용 빈도가 높은 단계가 Prisma enum에
   아예 없다(정비구역지정과 조합설립인가 사이 공백).
2. `RELOCATION_DEMOLITION`(이주철거)은 국토부·부산 둘 다 현재
   관측값에 없는 단계다 — 실제로 쓰이지 않는 값을 enum에 갖고
   있는 셈(향후 다른 지자체 데이터에 등장할 수도 있어 삭제를
   권하는 것은 아니다).
3. **완공(준공)·취소(해제)·해산(조합해산) 상태를 나타낼 값이
   전혀 없다** — 실제 데이터에 이미 상당수(부산 API 343건 중
   준공/해제/조합해산 합쳐 상당 비율) 존재하는데 현재 스키마로는
   표현이 안 된다.
4. 사업유형(REDEVELOPMENT/RECONSTRUCTION 등) 자체는 Prisma
   `RedevelopmentProject` 모델에 필드가 없다(스키마에 유형 구분
   필드 자체가 없음 — 이번 STEP에서 확인만 하고 추가하지 않음).

이번 STEP에서 enum이나 스키마를 변경하지 않았다 — 위 표는 R3에서
스키마를 다시 설계할 때 참고할 실측 근거로만 남긴다.

## 주소 품질

- **국토부**: 주소 필드 자체가 없음(시도/시군구까지만) —
  지오코딩 입력값으로 쓸 수 없음. 시군구 중심점 정도의 매우
  거친 근사 좌표만 가능(정확한 위치 아님).
- **부산 API**: `location` 필드 78%(268/343)에 값 존재. 그 중
  "구/군 포함"+"도로명 포함" 형태(구 이름 있든 없든 도로명이
  있으면 지오코딩 시도 가능)가 148+64=212건(약 62%), "동명만"
  56건(16%, 동 중심점 수준까지만 가능), null 75건(22%, 지오코딩
  불가). **단, `location`이 사업장 현장 주소가 아니라 조합
  사무실 주소인 사례가 섞여 있다는 R1 지적이 이번 수동 검증
  샘플에서도 재확인됨**(예: 문현6구역 location="남구 수영로
  26(문현동, 문현대림시티프라자 상가 208호)" — 상가 208호는
  사무실이지 정비구역 현장이 아닐 가능성이 높음). 지오코딩에
  성공해도 결과 좌표가 정비구역 자체 위치가 아닐 위험을 안고
  있다.

## 기존 Kakao geocoding 재사용 가능 여부

**재사용 가능성 높음, 새 연동 불필요.** 코드 조사 결과:

- **클라이언트**: `window.kakao.maps.services.Geocoder().addressSearch()`
  — `BusAccessCard.tsx`, `KakaoPlaces.tsx`, `ApartmentQuickSearch.tsx`,
  `KakaoMapEmbed.tsx` 4곳에서 이미 사용 중인 표준 패턴.
- **서버(REST)**: `https://dapi.kakao.com/v2/local/search/address.json`
  — `cheongyakService.ts`, `api/school/stats/route.ts`에서 이미
  사용 중. `NEXT_PUBLIC_KAKAO_MAP_API_KEY`(JavaScript 키)를
  `Authorization: KakaoAK` 헤더로 쓰되, REST 호출 시 401을 막기
  위해 `KA`/`Origin` 헤더를 함께 보내는 이 프로젝트의 기존
  우회 패턴(`src/lib/geocode-apt.ts`에 이미 문서화됨)을 그대로
  재사용하면 된다.
- 호출량 리스크: 정량 확인은 못했으나(이번 STEP 범위 밖), 이미
  여러 기능이 상시 호출 중인 동일 API라 재개발 배치 지오코딩
  (최대 수백~수천 건, 1회성/저빈도 배치) 추가가 기존 사용
  패턴을 크게 벗어나지 않을 것으로 판단.

## 추천 geocoding 전략(설계만)

```text
1. 부산 API location 필드를 1차 입력으로 사용(원본 주소 정규화:
   층/호수/상가명 등 건물 상세 정보 제거 시도)
2. 기존 Kakao Local 주소검색(REST, search/address.json) 호출
3. 성공하면 lat/lng 저장 + "지오코딩 신뢰도: 주소기반" 표시
4. 실패하면 areaName에서 추출한 동 이름으로 재시도(동 중심점 수준)
   → 성공 시 "지오코딩 신뢰도: 동단위 근사" 표시
5. 그래도 실패하면 UNRESOLVED로 남기고 사람 검수 대상으로 분리
6. location이 조합 사무실 주소로 의심되는 경우(예: "OO호",
   "상가" 등 건물 상세 포함) 별도 플래그를 둬서 신뢰도를
   낮게 표시(사람 검수 우선순위 상향)
```

## polygon 전략

이번 STEP에서 확정하지 못함(구현 금지 범위이기도 함). 조사한
후보:

- **VWorld(공간정보 오픈플랫폼, vworld.kr)**: 국토교통부 산하,
  900종 이상의 행정공간정보(도시계획정보 등)를 WMS/WFS로 제공.
  "정비구역 경계"를 명시적으로 이름 붙인 개별 레이어가 있는지는
  이번 STEP에서 확정하지 못함 — 도시계획정보 범주 안에 있을
  가능성이 높으나 정확한 레이어명 확인은 R3 이후 별도 조사 필요.
- **부산광역시 자체 GIS/도시계획 공간정보**: 존재 가능성 있으나
  이번 STEP에서 조사하지 않음.
- **지자체 정비구역 SHP**: data.go.kr에 개별 지자체 단위로
  간헐적으로 올라오는 경우가 있음(R1에서 본 "부산광역시_동구_
  도시정비 사업 현황" 같은 fileData류) — 전국 통합 Master는
  아니고 지자체별로 흩어져 있음.

결론: **전국 통합 polygon Master는 이번 STEP에서 확인하지
못했다** — 있다면 VWorld 쪽일 가능성이 높지만 확정 못함, R3
이후 별도 조사 과제로 남긴다.

## 데이터 freshness 전략(설계만)

두 소스의 갱신 주기가 이질적이므로(국토부 연간 vs 부산 "실시간"
표방) 각 레코드에 다음 메타 정보를 함께 저장하는 것을 권장(스키마
반영은 하지 않음, R3에서 판단):

```text
sourceUpdatedAt   : 원본 소스가 이 레코드를 마지막으로 갱신한 시점
                    (국토부는 파일 등록일, 부산은 API 응답에 없어
                    수집 시점으로 대체할 수밖에 없음)
collectedAt       : 이집이 이 레코드를 실제로 수집한 시점
sourceOfTruth     : 이 레코드의 각 필드가 어느 소스에서 왔는지
                    (존재/유형은 국토부, 단계/세대수는 부산 API 등
                    필드 단위로 다를 수 있음 — 위 source priority 참고)
```
