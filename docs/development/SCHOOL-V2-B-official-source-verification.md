**3) 필드 레벨 스키마 — 여전히 NOT_CONFIRMED(단정 금지)**

"학생 진로 현황" 카테고리의 상세 명세 페이지(요청 파라미터/응답

않았을 가능성이 높다**(구조적 추정, "11월 공시"라는 사용자 확인

**2025년 11월에 공시된 자료**일 것으로 추정된다. 단, 공시월 자체가
이번 조사(§1-4-1)에서 인코딩 문제로 자체 확증하지 못했으므로 이
추정은 사용자가 화면에서 직접 확인한 "11월"에 의존한 조건부 결론이다
— 실제 키 발급 후 API 응답의 "기준연도/공시차수" 필드로 재확인

"연구자(기관)가 학술연구 목적으로 자료를 요청하면 심사 절차를 거쳐
제공"하는 서비스로 확인됐다 — **상업적 서비스인 이집이 EDSS 경로로
3년 이전 자료를 받는 것은 사실상 어렵다고 봐야 한다**(연구 목적
한정, 심사 필요). 13-다도 학교알리미 전체 공시 제도의 일부이므로
동일한 3년 제한이 적용될 것으로 추정(개별 재확인은 안 했으나, 이
규정이 항목별 예외를 둔다는 근거도 발견되지 않음).

**6) Open API vs 파일데이터(§요청7)**

"학생 진로 현황"만을 별도로 다루는 data.go.kr 파일 데이터셋(예:
"학교알리미\_진로현황" 같은 이름)은 이번 검색에서 **찾지 못했다** —
즉 이 항목은 (a) OpenAPI "학생 진로 현황" 카테고리를 통해서만
받거나, (b) 포괄 파일 `15090212`(학교별 공시정보)/`15014351`
(공개용데이터) 안에 다른 항목들과 함께 컬럼으로 섞여 들어있을
가능성이 있다 — 파일을 직접 열어보지 않는 한 후자는 확정 불가.
독립된 전용 파일 dataset은 없는 것으로 잠정 결론.

**7) 이용허락조건(§요청8) — LEGAL_REVIEW_REQUIRED(추론, 미확정)**

"학생 진로 현황"이 학교알리미 OpenAPI의 한 카테고리라면, data.go.kr에
등록된 **동일 API 상품(`15098092`, 제3유형: 출처표시+변경금지)**의
라이선스를 그대로 상속할 가능성이 높다 — data.go.kr은 통상 API
상품 단위로 라이선스를 표시하고 오퍼레이션별로 따로 명시하지 않기
때문이다. **다만 이는 추론이며, "학생 진로 현황" 오퍼레이션 자체의
개별 라이선스 문구를 직접 확인하지는 못했다.** §1-2와 동일하게
파일 경로(제1유형)로 우회 가능한지, 또는 진로 데이터가 애초에 파일
경로에 포함되지 않는다면(§1-4-6) 이 우회가 불가능한지가 실제 착수
전 반드시 확인돼야 하는 지점이다.

**8) 최종 분류**

| 구분 | 분류 |
|---|---|
| 공식 공시항목 존재 | **CONFIRMED** |
| OpenAPI 카테고리 존재 | **AVAILABLE_API**(카테고리 레벨) |
| 필드 레벨 응답 스키마 | **NOT_CONFIRMED**(실제 키 발급 후 호출 필요) |
| 이용허락조건 | **LEGAL_REVIEW_REQUIRED**(제3유형 상속 추정, 미확정) |
| 3년 이전 자료(EDSS 경로) | **NOT_AVAILABLE**(상업 서비스 기준 사실상 불가) |

**총평**: "NOT_CONFIRMED"로 방치하지 않고 **"AVAILABLE_API(카테고리) +
LEGAL_REVIEW_REQUIRED + 필드 스키마 미확정"**으로 정정한다. 이전
버전의 "학교알리미에 진로 관련 API가 있는지조차 불확실하다"는 판단은
**오류였다** — 실제로는 명확한 카테고리가 존재한다. 다만 이를 즉시
기능화할 수 있다는 뜻은 아니다: 필드 스키마와 라이선스 두 gate가
아직 남아있다.

**[2026-08-23 SCHOOL V2-C2B/C2C 재조사로 추가 정정 — append, 위 §1-4는
원문 그대로 보존]** 위 §1-4의 "AVAILABLE_API(카테고리)" 판단은 이후
SCHOOL V2-C2B(`docs/education/SCHOOL_V2_C2B_SCHOOLINFO_SOURCE_AUDIT.md`
§10)에서 학교알리미가 공식 배포하는 OpenAPI 전체 35개 카테고리 명세서
(`OpenAPI_Output.xlsx`)를 직접 파싱해 재확인한 결과 **오판으로
확인되었다** — "진로/진학/졸업" 관련 시트는 35개 중 0건이다. SCHOOL
V2-C2C(`docs/education/SCHOOL_V2_C2C_GRADUATE_OUTCOME_AUDIT.md`)에서
실제 API 제공목록 화면(학사/학생·재정/시설/설비·보건/복지 3개 탭,
총 34개 오퍼레이션)을 직접 순회해 동일 결론을 재확인했다: **13-다(졸업생의
진로 현황)는 OpenAPI 오퍼레이션으로 존재하지 않는다.** §1-4가 근거로
삼았던 "OpenAPI 카테고리 메뉴(`/ng/go/pnnggo_a01_l2.do`)에 '학생 진로
현황'이 명시적으로 포함돼 있음을 확인"이라는 §1-4-2의 기술은, 실제로는
사람이 보는 웹 공시항목 메뉴(13-다 디스클로저 페이지 링크)를 API
오퍼레이션 목록으로 오인한 것으로 추정된다 — 화면에 공시되는 항목과
OpenAPI로 자동 수집 가능한 항목은 서로 다른 집합이라는 점이 이번
재조사로 명확해졌다. 대신 13-다는 **로그인 불필요한 별도 웹 페이지**
(`Pneiss_b01_s0.do?SHL_IDF_CD={school-uuid}&GS_HANGMOK_CD=06`)로 실제
데이터가 확인되며, 공식 "엑셀다운로드" 버튼도 존재한다(단, 조사 시점에
서버가 503을 반환 — SCHOOL V2-C2C §2 참고). 상세 스키마/라이선스/자동화
분류는 V2-C2C 문서를 참고할 것.

### 1-5. NEIS vs 학교알리미 역할 분리(제안)

V1 audit(§8/§9)에서 이미 확인된 대로 NEIS `schoolInfo`는 학교
정체성(이름/코드/주소/설립구분/남녀공학/학교급)만 제공하고 학생수·
학급수·교원·진학·급식은 없다. 이번 조사로 확인된 학교알리미 카테고리와
겹치지 않는다(중복 필드가 발견되지 않음) — 아래 역할 분리가 실제
필드 기준으로도 타당해 보인다(최종 확정은 학교알리미 필드 레벨 확인
후):

| 영역 | source |
|---|---|
| 학교 identity/주소/설립구분/남녀공학/학교급 | **NEIS**(이미 연동됨) |
| 학생/학급/교원/시설/급식/공시통계 | **학교알리미**(신규, §1-3) |

### 1-6. schoolCode 매핑 가능성 — **[2026-08-21 SCHOOL V2-C2B RESUME 실측으로 확정]** CONFIRMED: 별도 코드 체계, 직접 매핑 불가

사용자가 발급받은 실제 인증키로 `openApi.do`를 호출해 확정했다(방법론은
`scripts/education/c2b-verify-schoolinfo-api.ts` 참고, 결과 원본은
CHANGELOG 참고).

- 학교알리미 자체 식별자는 **`SCHUL_CODE`**("정보공시 학교코드", 공식
  개발자 가이드 `OpenAPI_Output.xlsx`에 명시된 필드명)이고, 값 형식은
  `"S020001449"` 같은 **영숫자 코드**다. NEIS `SD_SCHUL_CODE`(예:
  `"7171046"`, 순수 숫자)와 **자릿수·형식이 다르고, 같은 학교(부산 서구
  구덕초등학교)를 나란히 조회해도 값이 전혀 겹치지 않는다** — 이전 버전의
  "추정은 되나 확정 못함"은 **틀렸다**로 정정한다. 두 코드 체계는
  독립적이고, **NEIS ↔ 학교알리미 간 코드 기반 직접 조인은 불가능**하다.
- 안전한 crosswalk 키는 **(학교명, 시·군·구) 조합**이다. 부산 16개
  구·군의 NEIS 적재 초등학교 305건 전부가 학교알리미 2025년 공시자료에서
  이 조합으로 100% 매칭됐다(스크립트 §3 출력 참고). 다만 이것만으로도
  완전히 안전하지는 않다 — 강서구 안에서만도 "송정초등학교"와
  "대저중앙초등학교"가 **같은 구·군 안에서조차 이름이 중복되면서
  `SCHUL_CODE`가 서로 다른 두 레코드**로 존재함을 실측으로 확인했다
  (분교/폐교 후 재개교 등 이력성 중복으로 추정되나 원인은 확정하지
  않는다). 즉 **학교명 단독 매칭은 물론, (학교명, 구·군) 매칭조차
  100% 유일성을 보장하지 않는다** — 실제 ingestion 시 `BNHH_YN`(분교여부)
  이나 주소 등 3차 disambiguator를 함께 봐야 한다.
- 별도로 실측된 동명이교 사례: "송정초등학교"는 해운대구(송정동,
  `SCHUL_CODE=S020001666`)와 강서구(송정동, `SCHUL_CODE=S020001278`)에
  각각 존재 — 부산 664개 NEIS 적재 학교 전체를 조사한 결과 이 1건이
  유일한 구·군 간 동명이교였다(§25 CHANGELOG 참고).
- **부산 coverage 재확인(§1-7 UNKNOWN 해소)**: 학교알리미 2025년
  공시자료의 부산 16개 구·군 초등학교(317건, distinct 학교명+구군
  기준)가 NEIS 적재본(305건)을 전부 포함하고, 추가로 12건이 더
  있었다 — 이름으로 볼 때(눌차/덕도/삼광/세산초등학교 = 강서구
  가덕도 권역, 좌성/좌천초등학교 = 기장군, 위봉초등학교 = 해운대구,
  감정초등학교 = 사하구, 서곡/회동초등학교 = 동래구, 가산/주원초등학교 =
  부산진구) 분교이거나 NEIS 적재본에서 별도 사유로 빠진 소규모 학교로
  추정되나, 개별 원인은 확정하지 않았다.

### 1-7. 부산 coverage — 구조적으로는 전국 의무공시, 실측 미확인

학교알리미는 「교육관련기관의 정보공개에 관한 특례법」에 따라 **전국
모든 초·중·고·특수학교가 매년 1회 이상 공시할 법적 의무**가 있는
제도다(공식 설명 명시). 구조적으로 부산 667개교(NEIS 실측치, V1 §5)도
포함될 것으로 강하게 추정되나, **이번 조사에서 학교알리미 데이터를
실제로 내려받아 부산 표본 수를 세어보지는 않았다** — NEIS 667과의
직접 비교는 실제 데이터 확보 후 확인 필요(V1 §25에서 이미 unresolved로
표시된 항목, 이번 STEP에서도 미해소).

**[2026-08-21 SCHOOL V2-C2B RESUME — 초등학교 한정으로 해소]** 부산
16개 구·군 초등학교(schulKndCode=02)에 한해 실제로 세어봤다 — 317건
확인, NEIS 적재본 305건을 전부 포함(§1-6). 중/고/특수학교는 이번
STEP에서 조회하지 않아 여전히 미해소.

### 1-8. 실제 호출 방식(2026-08-21 실측, apiKey는 기록하지 않음)

- **Endpoint**: `http://www.schoolinfo.go.kr/openApi.do`(HTTP만 실측 —
  HTTPS 동작 여부는 별도 확인 필요)
- **필수 파라미터(실제 에러 메시지로 하나씩 확인)**: `apiKey` →
  `apiType` → `pbanYr`(공시년도, 최근 3년만 허용 — 2026-08-21 기준
  2024~2026 성공, 2023 이하는 `"오픈API는 최근 3년동안의 데이터만
  제공합니다."`) → `schulKndCode`(02=초, 03=중, 04=고 등, 미확정
  전체 코드표) → `sidoCode` → `sggCode`
- **`sidoCode`/`sggCode` 실제 형식 — 이 프로젝트가 이미 쓰는 MOLIT
  법정동코드(lawdCd)와 동일**: `sidoCode=26`(2자리), `sggCode=26140`
  (5자리, 서구) 조합으로 실제 성공 확인. NEIS의 3자리 교육청코드
  (`C10`)나 schoolinfo.go.kr 웹페이지 내부 검색 AJAX가 쓰는 10자리
  법정동코드(`2600000000`/`2614000000`, `selectSchoolListLocation.do`
  전용)는 **둘 다 `openApi.do`에서는 통하지 않는다** — 형식은
  받아들여지지만(에러 없음) 실제 데이터와 매칭되지 않아 항상
  `"해당 시도 및 시군구에 데이터가 존재하지 않습니다."`를 반환한다.
  이 프로젝트는 MOLIT 실거래/건축물대장 조회에 이미 5자리 lawdCd를
  전역적으로 쓰고 있어(`src/lib/api-molit.ts` 등), **schoolinfo API
  연동 시 새 코드표를 만들 필요 없이 기존 lawdCd를 그대로 재사용할 수
  있다.**
- **응답 wrapper**: `{"resultCode": "success"|"fail", "resultMsg": string, "list"?: object[]}`
  — NEIS의 `{schoolInfo: [{head:[...]},{row:[...]}]}` 중첩 구조와
  다른, 평평한 배열이다.
- **(참고, 이번 STEP 범위 밖)** 학교기본정보(`apiType=0`) 응답에
  `LTTUD`/`LGTUD`(위도/경도) 필드가 실제로 채워져 있음을 확인했다
  (예: 구덕초등학교 `35.1204504376, 129.0125451943`). SCHOOL V2-C5
  거리/접근성 감사(`SCHOOL-V2-C5-distance-accessibility-audit.md`
  §4)에서 "School 자체 공식 좌표 소스가 없다(UNKNOWN)"고 남겼던 항목에
  대한 유력한 후보다 — 단 이번 STEP은 학생/학급수 검증이 목적이라
  좌표 필드의 정확도(주소 대표점인지 건물 중심인지 등)는 검증하지
  않았고, ingestion도 하지 않았다. C5-B(좌표 provenance 채우기)
  착수 시 최우선 확인 대상으로 남긴다.

### 4-2. 중학교 배정권역

data.go.kr 표준데이터는 초등 전용이지만, **학구도안내서비스는
"학교군"(중학교 배정 단위의 통상 명칭) 항목을 명시**하고 있어 중학교
배정권역도 이 서비스를 통해 얻을 수 있을 것으로 보인다 — 단, 필드
레벨/파일 다운로드 실제 확인은 하지 않았다(UNKNOWN 수준 확정).

### 4-3. 결론

통학구역/배정권역은 스크래핑 없이 **공식 GIS 서비스 + 공공데이터포털
표준데이터 조합으로 확보 가능성이 높다** — SCHOOL V2-C(거리/경로
정확도) 이전에 별도로 다룰 가치가 있는 예상보다 좋은 source. 다만
라이선스·정확한 필드는 미확정이라 TIER 2로 분류(§7).

### TIER 분류

**TIER 1 — 반드시 연동**
- 어린이집 전국 정보 API(`15101155`) — 전국통합·라이선스 제한없음·
  좌표/유형/정원현원 모두 확인, 마찰 가장 적음
- 유치원 통합현황 파일데이터(`15037485`) — 라이선스 제한없음, 학급수/
  원아수/교직원현황 확인됨
- 학교알리미 학생/학급/교원 공시자료 — V1에서 식별된 최대 gap(NOT_FOUND
  대부분)을 메우는 유일한 source, 단 **라이선스 재확인(제1유형 경로
  선택) 선행 필요**

**TIER 2 — 있으면 강력**
- 학구도안내서비스(통학구역/배정권역) — 예상보다 잘 갖춰진 공식 GIS,
  SCHOOL V2-C보다 먼저 검토 가치 있음
- 유치원알리미 OpenAPI 나머지 항목(통학차량/방과후 등, 상업이용 가능
  오퍼레이션만 선별)

## 10. 비용

공식 문서로 확인된 범위만:

- 학교알리미/유치원알리미/어린이집/통학구역/학원/도서관 API 전부
  **가격 정보가 명시적으로 "무료"라고 확인된 곳은 어린이집 API 뿐**
  (`15101155`, "비용무료" 명시).
- 나머지는 공공데이터포털의 일반 원칙("공공데이터는 원칙적으로 무료")을
  따를 것으로 추정되나, 개별 페이지에서 명시적 가격 문구가 확인되지
  않은 곳은 추정하지 않는다.
- 트래픽 제한: 구체적 수치가 명시된 곳은 도서관 정보나루뿐(개발계정
  1,000). 나머지는 "기관 정책에 따라 상이" 수준의 정성적 언급만 있음.

## 12. MVP 범위 제안(갱신)

이번 조사 결과를 반영해 사용자 제안 구조(§요청24)를 다음과 같이
구체화한다(확정 아님, 다음 STEP 논의용):

- **SCHOOL V2-B1**: 학교알리미 학생/학급/교원 — **단, 착수 전 라이선스
  재확인(제1유형 경로 확정) 및 실제 키 발급 후 schoolCode 매핑 여부
  확인이 선행 조건**. "학생 진로 현황"(13-다, §1-4)은 OpenAPI 카테고리
  존재 자체는 확인됐으나 필드 스키마·라이선스가 여전히 미확정이라
  이번 단계 범위에서는 제외하고, 실제 키 발급 후 필드 확인이 끝난
  뒤 별도로 기능화 여부를 재판단한다(NOT_CONFIRMED 방치가 아니라
  "확인 완료 전 보류").
- **SCHOOL V2-B2**: 유치원(통합현황 파일, 라이선스 제한없음 확인된
  경로 우선) + 어린이집(전국 API) core. 두 source 모두 이번 조사에서
  가장 마찰이 적은 것으로 확인됨 — **B1보다 먼저 착수해도 되는 순서로
  재배치 제안**.
- **SCHOOL V2-C**: 거리/경로 정확도(기존 계획 유지) — 단, 통학구역
  실제 배정 여부(§4)를 먼저 반영하는 편이 "학교까지 거리"보다 부모
  의사결정에 더 직접적일 수 있어 순서 재검토 여지 있음.
- **SCHOOL V2-D**: 부모 의사결정 UX(기존 계획 유지).
- (신규) **SCHOOL V2-E**: 통학구역/배정권역(§4) — 예상보다 잘 갖춰진
  공식 GIS source가 확인되어 별도 STEP으로 승격 제안.

## 14. SCHOOL V2-C 설계 참고용 메모(schema/migration 아님)

다음 STEP(SCHOOL V2-C: Education Data Architecture & Ingestion Design)
설계 시 참고할 사항만 기록한다 — **실제 schema/migration은 여전히
금지 범위**이며 이 메모는 설계 착수 시 고려할 후보 목록일 뿐이다.

- "졸업생의 진로 현황"(13-다)은 **temporal school statistic**(학교당
  1개 값이 아니라 "학교 × 공시연도"별로 매년 갱신되는 시계열 값)
  후보로 반영 필요 — 학생수/학급수(§1-3)와 마찬가지로 "현재 값"만
  저장하면 안 되고, 공시연도/공시차수를 키의 일부로 설계해야 매년
  11월(추정) 갱신 시 과거 값을 덮어쓰지 않고 추이를 보존할 수 있다.
  학교알리미가 최근 3년치만 제공한다는 제약(§1-4-5)도 ingestion
  주기/보관 정책 설계에 반영 필요.
- 필드 스키마가 아직 NOT_CONFIRMED이므로, V2-C 설계 단계에서도 이
  항목의 정확한 컬럼 구조는 실제 API 키 발급 후 확정하는 것을
  선행 조건으로 남겨두는 편이 안전하다(추정 스키마로 먼저 설계하지
  않는다).
