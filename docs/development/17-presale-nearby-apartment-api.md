## 1. 목적

MASTER M4-B(부산 ApartmentMaster 3,402건)와 P2-D4-B 조사(문서 16)의 설계를 실제 서버 API로 구현한다. 목표는 단 하나 — **분양(Presale) 1건의 좌표를 기준으로, 신뢰 가능한 좌표를 가진 ApartmentMaster 중 실제로 가까운 단지를 정확하게 찾아 반환**하는 것이다.

---

## 2. API 설계

### 경로

```
GET /api/presales/[id]/nearby-apartments
```

기존 `GET /api/presales/[id]`(문서 09 P2-D3)와 `POST /api/community/posts/[id]/comments`(중첩 하위 리소스 패턴)를 그대로 따른 경로다 — 이 프로젝트에 이미 확립된 `[id]/{하위리소스}` 컨벤션과 일치해 별도 근거 검토 없이 채택했다.

### 처리 흐름

1. `id` 파싱 — 정수가 아니거나 0 이하면 `400`.
2. `Presale.findUnique`로 조회 — 없으면 `404`(기존 `/api/presales/[id]`와 동일한 메시지·상태코드 재사용).
3. `latitude`/`longitude`가 없으면 `200` + `locationAvailable: false` + `items: []`(§6).
4. 최대 반경(3km)을 위경도 범위로 환산한 bounding box로 `ApartmentMaster`를 1차 필터링(§9).
5. `@turf/turf`의 `distance()`로 정밀 거리 계산(§5 요청, 신규 패키지 설치 없음 — `src/app/api/school/apartments/route.ts`가 이미 쓰던 `import { point, distance } from '@turf/turf'` 그대로 재사용).
6. Adaptive radius(§4)로 최종 반경 결정 → 거리순 정렬 → 최대 5개 반환.

MOLIT 호출은 전혀 없다 — Prisma 쿼리 + 순수 메모리 연산만 수행한다.

---

## 3. 검색 대상

`ApartmentMaster`만 사용한다. `Apartment`(좌표 필드 없음)·`Property`(빈 테이블)는 쿼리하지 않는다(요청 원칙, 코드에도 해당 모델 import 없음). `latitude`/`longitude`가 `not null`인 row만 거리 계산 대상으로 삼는다 — 좌표 재지오코딩, 자동 보정, 행정구역 대표좌표 대체는 코드 어디에도 없다.

---

## 4. Adaptive Radius (문서 16 §6~7 채택)

```
RADIUS_STEPS_KM = [1, 1.5, 2, 3]
MIN_CANDIDATES = 5
MAX_ITEMS = 5
```

1km부터 시작해 후보(정밀 거리 계산 기준) 5개 이상이면 그 반경에서 멈춘다. 5개 미만이면 다음 단계로 확장하고, **3km에 도달하면 후보 수와 무관하게 멈춘다**(행정구역을 채우기 위해 반경을 더 넓히지 않음). 최종 반환은 선택된 반경 내 후보를 거리 오름차순(동률은 `id` 오름차순으로 deterministic하게)으로 정렬한 뒤 상위 5개만 자른다 — "먼저 5개를 잘라낸 뒤 정렬"이 아니라 "반경 내 전체를 정확히 계산한 뒤 정렬·절단"하는 순서를 그대로 지켰다.

---

## 5. 정렬 정책

이번 B1에는 실거래 정보가 없으므로 **거리 오름차순 단독**을 사용한다(문서 16의 "최근거래 우선→거리순" 중 1순위 조건은 B2에서 실거래 데이터가 들어온 뒤 추가한다). 정렬 로직은 `items`를 만드는 마지막 단계에서만 적용되도록 분리해뒀다 — B2에서 실거래 존재 여부를 필터/정렬에 추가하더라도 이 파일의 반경 계산·bounding box 로직은 건드릴 필요가 없다.

## 6. 응답 구조 (실제 코드 기준)

```jsonc
{
  "success": true,
  "data": {
    "presaleId": 479,
    "locationAvailable": true,
    "radiusKm": 1,
    "totalCandidates": 31,
    "items": [
      {
        "id": 9,
        "aptSeq": "26140-1353",
        "name": "비스타동원더비치테라스",
        "distanceKm": 0.06,
        "latitude": 35.075074,
        "longitude": 129.014693,
        "roadAddress": "부산광역시 서구 암남공원로 16 (암남동)",
        "jibunAddress": "부산광역시 서구 암남동 771번지",
        "sido": "부산",
        "sigungu": "서구",
        "sggCd": "26140",
        "umdCd": "12400",
        "buildYear": 2023,
        "totalHouseholds": 295,
        "mainBuildingCount": 7
      }
    ]
  }
}
```

필드는 전부 `ApartmentMaster` 실제 컬럼명을 그대로 썼다(`prisma/schema.prisma` §192 직접 확인). 요청안 예시의 `apartmentName`/`address`/`householdCount`/`buildingCount`는 실제 schema에 없는 이름이라 채택하지 않고, 실제 필드명(`name`/`roadAddress`+`jibunAddress`/`totalHouseholds`/`mainBuildingCount`)을 그대로 노출했다 — 존재하지 않는 필드를 상상해서 만들지 않는다는 원칙을 지켰다.

`buildYear`/`totalHouseholds`/`mainBuildingCount`/`roadAddress`/`jibunAddress`는 건축물대장 enrichment 확보율(문서 15 §AA-7, 약 25~41%)에 따라 `null`일 수 있다 — **누락됐다고 해서 해당 아파트 자체를 목록에서 제외하지 않는다**(§7에서 실측 확인).

## 7. 지역경계 처리 — 실제 검증 결과

요청안이 "이번 STEP의 핵심 테스트"로 지정한 항목이다. 코드에는 `sigungu`/`sggCd` 기준 필터가 **전혀 없다** — bounding box와 `distance()`만으로 후보를 정한다.

| 1 | 더비치푸르지오써밋 | 남구(26290) | 0.182km |
| 2 | 아침햇살 | 남구(26290) | 0.244km |

## 8. B2를 위한 지역코드 보존

`items`의 각 원소가 자체 `sggCd`/`sigungu`/`umdCd`를 원본 그대로 포함한다(§6). B2가 이 필드들을 그대로 읽어 "이 5개 후보가 속한 distinct sggCd" 집합을 얻을 수 있다 — 예를 들어 §7 사례라면 B2는 `[26290, 26500]` 두 지역코드로 MOLIT를 조회해야 함을 바로 알 수 있다. 별도의 집계 필드를 추가하지 않고 원본 필드만으로 충분한 구조로 최소화했다.

## 9. 좌표 품질 원칙 준수

- 좌표 없는 `ApartmentMaster`는 `latitude: { not: ... }` 조건 없이도 자연히 제외된다 — bounding box 쿼리 자체가 `latitude`/`longitude` 범위 조건이라 `null`인 row는 매칭되지 않는다.
- 부산 외 좌표를 생성하는 로직 없음(좌표는 M4-B가 이미 저장해둔 값만 읽음).
- 행정구역 대표좌표 생성 없음, Kakao 재지오코딩 없음, 좌표 자동 보정 없음 — 코드 전체에 외부 API 호출이 없다(§2).

## 10. 성능

### bounding box prefilter

premature한 공간 DB/schema 도입 없이(요청 원칙), 최대 반경(3km)을 위경도 델타로 환산해 Prisma `where` 절에 그대로 넣는 방식만 사용했다(`latDelta = 3 / 111`, `lngDelta = 3 / (111 * cos(lat))`). 신규 컬럼·인덱스·PostGIS 없이 기존 `Float` 컬럼에 대한 범위 쿼리만으로 구현했다.

### 실측 응답시간(10개 테스트 Presale, 2라운드 반복)

| 항목 | 값 |
|---|---|
| 평균 | 90.8ms |
| 최소 | 37ms |
| 최대 | 254ms(콜드 스타트 1회) |

문서 16 §22가 우려했던 "캐시 미스 시 2.2~6.1초"는 **B2(MOLIT 실거래 호출)의 문제이지 B1의 문제가 아님을 이번 실측으로 확인했다** — B1은 MOLIT를 전혀 호출하지 않으므로 100ms 안팎으로 충분히 빠르다. 별도 캐시 계층은 B1 단계에서 불필요하다고 판단한다.

## 12. 반경 동작 검증

- **1km에서 5개 이상 → 유지**: 479/630/706/737/755/801/1040(7건) 전부 1km에서 확정.
- **radius 확장**: 847(강서구)이 1km→1.5km→2km→3km까지 전부 시도된 뒤 3km에서 확정(§11).

## 14. duplicate 검증

8개 좌표 보유 테스트 Presale의 전체 응답(총 40개 item)에서 **응답 내부 `id` 중복 0건, `aptSeq` 중복 0건**을 확인했다(§6 필드가 곧 M4-B가 이미 보증한 `aptSeq` unique 제약을 그대로 반영). 동일 좌표라는 이유로 서로 다른 `aptSeq`를 병합하는 로직은 코드에 없다 — M4-B가 이미 전역 좌표 중복을 정리해뒀으므로(문서 15 §AA-7) B1은 identity 판단을 추가로 하지 않고 그 결과를 그대로 신뢰한다.

2. adaptive radius(§4)·정렬(§5)·지역경계 무시 정책(§3, §7)이 실제 API 호출(10개 표본)로 설계대로 정확히 동작함을 확인했고, 특히 §7의 실제 지역경계 사례(남구→수영구)로 핵심 요구사항을 실증했다.
3. 좌표 없음(§13)·optional enrichment 누락(§6)·duplicate 없음(§14) 등 엣지케이스가 전부 안전하게 처리된다.
4. 응답시간(§10, 평균 90.8ms)이 매우 빠르고, 기존 기능(§16)에 영향이 없다.
5. B2가 필요로 하는 지역코드(§8)가 응답에 이미 포함돼 있어, B2 구현 시 이 API를 그대로 재사용하며 확장할 수 있는 구조다.

P2-D4-B2, B3, B4, M4-C, 재개발, 커뮤니티, 전국 확장으로 자동 진행하지 않는다. 검수를 기다린다.
