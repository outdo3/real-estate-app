## 0. 먼저 — 이 STEP을 촉발한 전제가 틀렸다

직전 STEP(`APT_DETAIL_DEFAULT_ALL_TRUST_FIX_V1`)의 보고서와 문서에 이렇게 적혀 있었다:

> 리포트는 249m, ApartmentScoreCard는 341m — 두 화면의 숫자가 다를 수 있다.

**이것은 사실이 아니었다.** `341m`은 해당 단지의 실제 저장값이 아니라, 직전 STEP **지시문에 예시로 등장한 숫자**였다. 작성자가 그 숫자를 실측 before 값처럼 옮겨 적었고, 거기서 "출처가 달라 화면이 어긋난다"는 결론까지 끌어냈다.

실제 값은 이렇다:

| 26290-2625 대연롯데캐슬레전드1단지 | 값 |
|---|---|
| DB에 저장된 Kakao 거리 | **249m** |
| NEIS 좌표로 계산한 거리 | **249m** |
| 두 출처가 가리키는 학교 | **둘 다 연포초등학교** |

즉 **불일치 자체가 없었다.** 직전 STEP이 바꾼 것은 "이름이 생겼다"뿐이고 숫자는 처음부터 같았다.

해당 문서와 CHANGELOG의 잘못된 서술은 이 STEP에서 정정했다.

## 1. 그럼에도 감사할 가치가 있었다

전제는 틀렸지만, 전수 대조를 하니 **진짜 문제 두 가지**가 드러났다. 아래는 전부 실측이다.

### 전수 대조 (아파트 3,401건 · NEIS 초등학교 305곳)

| 구간 | 건수 | 비율 |
|---|---|---|
| 두 값 모두 존재 | 3,381 | — |
| ├ 정확히 일치(0m) | 1,514 | 44.8% |
| ├ 5m 이내 | 1,846 | 54.6% |
| ├ 6~25m | 0 | 0.0% |
| └ **25m 초과** | **21** | **0.6%** |
| Kakao null(1km 밖) | 20 | — |
| NEIS 후보 없음 | 0 | — |

**99.4%가 5m 이내로 일치한다.** 6~25m 구간이 0건이라는 점이 중요하다 — 분포가 "거의 같음"과 "완전히 다름"으로 깔끔하게 갈린다. 즉 두 출처는 같은 것을 재고 있고, 어긋나는 경우는 **측정 오차가 아니라 아예 다른 학교를 골랐기 때문**이다.

## 2. 두 거리의 의미 — 같다

| | ScoreCard 경로 | 리포트 경로 |
|---|---|---|
| 출처 | `ApartmentLocationFeature.nearestElementaryDistanceM` | `School`(NEIS) + haversine |
| 수집 | Kakao `categorySearch('SC4', lat, lng, 1000)` | DB 직접 조회 |
| 학교 좌표 | Kakao POI 좌표 | `OFFICIAL_POINT` |
| 아파트 좌표 | `ApartmentLocationFeature.latitude/longitude` | **같은 값** |
| 거리 의미 | **직선거리**(Kakao가 x/y 기준으로 돌려주는 m) | **직선거리**(haversine) |
| 학교 이름 | **없음**(컬럼 자체가 없다) | 있음 |

**도보 거리 대 직선 거리의 문제가 아니다.** 둘 다 직선거리이고, 아파트 좌표도 같은 값을 쓴다. 감사 스크립트에서 Kakao가 돌려준 `distance`와 그 POI 좌표로 직접 계산한 haversine이 m 단위까지 일치함을 확인했다(249m = 249m).

## 3. 진짜 문제 ① — Kakao 검색이 더 가까운 초등학교를 놓친다 (21건, 0.6%)

`categorySearch('SC4', …, 1000)`는 `size=15` **단일 페이지**다. SC4는 초·중·고·대를 **전부 포함하는** 학교 카테고리라, 1km 안에 다른 학교가 많으면 진짜 최근접 초등학교가 상위 15건 밖으로 밀린다. 그 뒤 `filterElementary`가 이름으로 거르지만, **이미 잘려 나간 학교는 복구되지 않는다.**

실측 사례(전부 Kakao 쪽이 **더 멀게** 나온다 — 더 가까운 학교를 놓쳤다는 뜻):

| aptSeq | Kakao | NEIS | 차이 |
|---|---|---|---|
| 26200-22 | 376m | 신선초등학교 **59m** | 317m |
| 26530-104 | 513m | 괘법초등학교 **130m** | 383m |
| 26530-1121 | 553m | 괘법초등학교 **178m** | 375m |
| 26200-20 | 356m | 신선초등학교 **133m** | 223m |
| 26200-21 | 419m | 신선초등학교 **294m** | 125m |
| 26200-75 | 447m | 봉삼초등학교 **254m** | 193m |
| 26530-105 | — | — | **429m (최대)** |

21건 전부 같은 방향이다. 무작위 오차가 아니라 **구조적 누락**이다.

> 참고: 이 저장소는 **해수욕장** 수집에서 정확히 같은 문제를 이미 겪었고, `keywordSearchNearestMatch`로 페이지를 넘겨가며 첫 일치를 찾는 방식으로 고쳤다(`kakao.ts` 주석에 경위가 남아 있다). **학교 경로에는 그 처리가 적용되지 않았다.**

## 4. 진짜 문제 ② — 1km 밖은 "없음"이 된다 (20건)

Kakao 검색 반경이 1,000m라, 가장 가까운 초등학교가 그보다 멀면 `nearestElementaryDistanceM = null`이 된다. NEIS로는 전부 찾힌다.

```
26350-2335 : 좌산초등학교 1359m   (Kakao null)
26350-295  : 송정초등학교 1422m   (Kakao null)
26350-204  : 좌산초등학교 1407m   (Kakao null)
26350-2304 : 송정초등학교 1108m   (Kakao null)
26290-15   : 대남초등학교 1052m   (Kakao null)
```

`null`은 "학교가 없다"가 아니라 **"1km 안에서 못 찾았다"**이다. 그런데 Score는 이 null을 `treatCompleteNullAsWorst: true`로 **최악값 취급**한다 — 결과적으로는 "멀다"와 방향이 같아 크게 틀리진 않지만, 의미가 다른 상태를 같은 값으로 눌러 담고 있다.

## 5. Score 영향 (§4) — **바꾸지 않았다**

`nearestElementaryDistanceM`은 점수에 **두 경로로** 들어간다:

1. `categories/school-access.ts` — `SCHOOL_ACCESS_SUBWEIGHTS` 가중치의 **percentile 하위지표**(`lowerIsBetter`). peer pool 내 **상대 순위**라, 한 단지 값이 바뀌면 **그 pool의 다른 단지 percentile도 함께 움직인다.**
2. `school-distance-band.ts` — 절대 band(200/400/650/933).

### 출처를 바꾸면 band가 실제로 옮겨간다

| 사례 | Kakao | band | NEIS | band |
|---|---|---|---|---|
| 26200-22 | 376m | `CLOSE` | 59m | **`VERY_CLOSE`** |
| 26530-104 | 513m | `NORMAL` | 130m | **`VERY_CLOSE`** |

이건 표시 문제가 아니라 **점수 이동**이다. 게다가 band 임계값 자체가 *Kakao 분포*에 앵커링돼 있다 — 주석에 "반경 1000m 검색이라 933m를 넘는 값은 실측 표본에 없었다"고 적혀 있는데, NEIS는 1,052~1,422m를 만들어낸다. 출처를 바꾸면 **임계 근거까지 다시 세워야 한다.**

영향 범위: 직접 영향 **41건**(21 + 20, 전체의 1.2%). 다만 percentile이 상대 순위라 **같은 peer pool의 다른 단지들도 간접 영향**을 받는다.

→ **AGENTS.md와 §4에 따라 여기서 멈춘다.** 수집기·feature 값·임계값·점수 로직 **어느 것도 건드리지 않았다.** 승인과 정식 영향 분석이 필요하다.

## 6. 이 STEP에서 실제로 바꾼 것 — 의미 라벨 하나

값은 그대로 두고, **의미를 명시**했다.

`ApartmentScoreCard`는 이미 "가까운 초등학교 **직선거리** 249m"라고 쓰고 있었다. 리포트는 라벨 없이 "연포초등학교 · 249m"였다. 같은 의미의 값에 한쪽만 라벨이 붙어 있으면, 라벨 없는 쪽이 도보 거리로 읽힐 수 있다.

```
지하철   : 못골역 342m            →  못골역 · 직선 342m
초등학교 : 연포초등학교 · 249m     →  연포초등학교 · 직선 249m
```

지하철 행도 같은 표의 같은 성격(Kakao 직선거리)이라 함께 맞췄다 — 한 행만 고치면 표 안에서 새 불일치가 생긴다.

**숫자는 한 건도 바뀌지 않았다. Score도 바뀌지 않았다.**

## 7. 정합성 판정 (§5)

| 항목 | 결과 |
|---|---|
| 같은 학교를 가리키는가 | 99.4%는 YES. 0.6%(21건)는 NO — **Kakao 쪽이 틀렸다** |
| 이름 + 거리 같은 레코드인가 | 리포트는 YES(구조적으로 보장, 테스트로 고정) |
| 의미 라벨 | 이제 두 화면 모두 **직선** 명시 |
| 서로 모순되는 무라벨 거리 | 해소 |
| 남은 차이 | 21건 이상치 + 20건 1km 밖 — **Score 경로의 데이터 품질 결함**이며 표시 문제가 아니다 |

리포트가 더 정확한 값을 보여주는 셈이다. 그렇다고 Score를 조용히 맞추지는 않는다 — 그게 §4가 금지하는 일이다.

## 9. 남은 한계 / 다음 STEP 후보

1. **Kakao SC4 15건 잘림** — 21건(0.6%)에서 더 가까운 초등학교를 놓친다. 고치려면 `keywordSearchNearestMatch`처럼 페이지를 넘기거나, 아예 NEIS School 테이블로 전환. **둘 다 Score를 움직인다 → 승인 필요.**
