# STEP 1.5-B — 관리자 API 상태 표시 신뢰성 정비

작성일: 2026-08-12

## 문제

STEP 1 정밀진단(`01-current-system-audit.md`, N/R섹션)에서 관리자 대시보드의 "공공 API & 데이터 파이프라인 상태" 카드가 청약홈·건축물대장 항목을 **실제 호출 검증 없이 `DATA_GO_KR_API_KEY` 환경변수 존재 여부만으로 "정상(API 키 설정됨)" 또는 "오류(API 키 미설정)"로 표시**하고 있다는 문제가 지적됐다. "API 키가 있다"는 사실은 "설정값이 존재한다"만을 의미할 뿐 "실제로 그 API가 정상 동작한다"를 의미하지 않으며, 반대로 "키가 없다"고 해서 곧바로 "오류"인 것도 아니다(아직 연동을 시작하지 않은 상태일 수 있음). 관리자가 이 문구만 보고 청약홈/건축물대장 파이프라인이 실제로 살아있다고 오인할 수 있는 구조였다.

## 기존 상태 판단 방식

`src/app/api/admin/dashboard/route.ts`의 `checkPipelineHealth()`는 3개 항목을 점검한다.

| 항목 | 기존 판정 방식 |
|---|---|
| 국토부 실거래가(MOLIT) | **실제 라이브 호출** — 부산 서구(`lawdCd=26140`) 기준으로 `fetchMolitData()`를 실제로 호출해 응답을 확인 후 `정상`/`오류` 판정 |
| 청약홈 분양정보 | `!!process.env.DATA_GO_KR_API_KEY`만 확인 → `true`면 "정상(API 키 설정됨)", `false`면 "오류(API 키 미설정)" |
| 건축물대장 | 청약홈과 동일한 방식으로 같은 환경변수(`DATA_GO_KR_API_KEY`)만 확인 → `정상`/`오류` |

즉 MOLIT만 실제 검증이었고, 나머지 둘은 "키 존재"를 "정상 동작"으로 잘못 등치시키고 있었다. 게다가 관리자 화면(`src/app/admin/dashboard/page.tsx`)의 스타일 결정 로직(`p.status.startsWith('정상') ? 초록 : 빨강`)은 **"정상"으로 시작하지 않는 모든 문자열을 빨간색(오류)으로 렌더링**했다 — 즉 상태 문구를 "미연동"처럼 중립적인 표현으로만 바꿔도, 아직 실패가 아닌 "구현 예정" 상태가 시각적으로는 장애처럼 보이는 문제가 있었다. 이번 작업에서 문구뿐 아니라 이 스타일 분기도 함께 손봤다(아래 "수정 내용" 참고).

## 외부 데이터 소스별 현재 상태

조사 범위: 관리자 화면(`src/app/admin/**`) 전체에서 "상태"/"정상"/"파이프라인"/API 키 관련 표시를 검색. 관리자 화면에 실제로 상태 표시 UI가 존재하는 것은 대시보드의 "공공 API & 데이터 파이프라인 상태" 카드 하나뿐이며, 여기 표시되는 항목은 MOLIT/청약홈/건축물대장 3개뿐이다. NEIS, Kakao, Gemini는 관리자 화면 어디에도 상태 표시 UI 자체가 없다(점검할 표시 자체가 없으므로 이번 작업에서 다룰 대상이 아님 — 아래 "확인이 필요한 기능"에 별도 기재).

| 소스 | 분류 | 근거 |
|---|---|---|
| 국토부 실거래가(MOLIT) | **A. 실제 연동 및 동작 확인 가능** | `checkPipelineHealth()`가 매 5분 캐시 주기로 실제 라이브 호출을 수행해 응답을 직접 확인함(`src/lib/api-molit.ts`). 지도/통계/단지상세 등 앱 전반에서도 실사용 확인됨(STEP 1 감사 F섹션). |
| 건축물대장 | **B. 연동 코드는 존재, 이 헬스체크 자체는 검증 안 함(단 기능 자체는 다른 경로에서 실사용 확인됨)** | `src/lib/apt-building-info.ts`의 `fetchBuildingRegistryInfo()`가 `src/app/api/apt/[name]/info/route.ts`, `src/lib/ai-search.ts`, `src/services/publicDataService.ts` 3곳에서 실제로 호출됨(코드로 확인). 다만 관리자 대시보드의 이 항목 자체는 라이브 호출을 하지 않고 키 존재만 확인하므로, "이 헬스체크가 정상을 보장한다"고는 말할 수 없음. |
| 청약홈 분양정보 | **C. 구조/함수만 준비, 호출 경로 없음** | `src/services/cheongyakService.ts`의 `syncApplyhomeListings()`를 호출하는 크론/스크립트/관리자 액션/API route가 전체 코드베이스에 전무함(재확인 완료 — 정의부 외 참조 0건). `Presale` 테이블은 항상 비어 있을 것으로 추정됨(STEP 1 감사 K섹션). 파일 자체 주석에도 "엔드포인트/필드명을 라이브로 검증하지 못했다"고 명시되어 있음. |
| NEIS(학교정보) | 해당 없음(관리자 상태 표시 UI 자체가 없음) | `/school`, `/api/school*`에서 실사용 중(STEP 1.5-A에서 확인)이나, 관리자 대시보드에는 이 항목이 아예 존재하지 않음. |
| Kakao(지도/장소검색) | 해당 없음(관리자 상태 표시 UI 자체가 없음) | 지도/AI검색/학군 등 앱 전반에서 실사용 중이나 관리자 화면에 상태 카드 없음. |
| Gemini | 해당 없음(관리자 상태 표시 UI 자체가 없음) | AI검색에서 실사용 중이나 관리자 화면에 상태 카드 없음. |

## 수정 내용

### `src/app/api/admin/dashboard/route.ts`
- MOLIT 항목 로직은 이미 실제 라이브 검증이었으므로 **변경하지 않음**.
- 청약홈: `cheongyakConfigured`(키 존재 여부)로 `정상`/`오류`를 판정하던 로직을 제거하고, 키 존재 여부와 무관하게 **"미연동"**으로 표시하도록 변경. 키가 있을 때는 "미연동(API 키만 설정됨)", 없을 때는 "미연동(API 키 미설정)"으로 세분화 — 실패가 아니라 "아직 연결되지 않음"을 정확히 전달.
- 건축물대장: 동일하게 "정상"/"오류" 이분법을 제거하고, 실제 검증 방식(키 존재만 확인)에 맞는 **"설정됨"**으로 표시. 다른 코드 경로에서 실사용이 확인된 사실을 괄호로 병기("설정됨(실사용 확인, 상태 점검 미구현)")해, 실제로는 동작하는 기능임을 숨기지 않으면서도 이 헬스체크 자체가 그것을 검증하지 않는다는 점을 함께 드러냄.
- 이번 작업에서 **새로운 외부 API 호출을 추가하지 않았다** — 청약홈/건축물대장 모두 기존과 동일하게 환경변수만 확인하며, 대시보드 로딩 시 추가 네트워크 호출은 발생하지 않는다(MOLIT의 5분 캐시 라이브 호출도 기존 그대로).

### `src/app/admin/dashboard/page.tsx`, `page.module.css`
- 상태 문구가 "정상"으로 시작하지 않으면 무조건 빨간색(오류)으로 표시되던 이분법을 `pipelineStatusClass()` 헬퍼 함수로 교체: `정상`→초록(`pipelineStatusOk`), `오류`→빨강(`pipelineStatusError`), 그 외("미연동", "설정됨" 등)→회색 중립(`pipelineStatusNeutral`, 신규 CSS 클래스, `var(--text-muted)` 사용). 레이아웃 구조는 변경하지 않음(기존 `pipelineRow`/`pipelineStatus*` 한 줄 표시 방식 그대로, 색상 분기만 3단계로 확장).

## 상태 표시 기준

이번 작업에서 실제로 사용한 5단계 기준(코드 주석에도 반영):

| 상태 | 의미 | 적용 예 |
|---|---|---|
| 정상 | 실제 호출 및 정상 동작을 이 헬스체크가 직접 확인함 | MOLIT |
| 설정됨 | API 키 등 설정값은 존재. 이 헬스체크 자체는 라이브 호출로 검증하지 않음(단, 다른 코드 경로의 실사용 여부는 별도 확인 가능) | 건축물대장 |
| 미연동 | 코드/함수는 준비되어 있으나 이를 호출하는 경로(크론/스크립트/관리자 액션 등)가 아직 없음 | 청약홈 |
| 확인 필요 | 코드만으로 실제 운영 상태를 확정할 수 없음 | (이번 조사 대상 3개 항목 중 해당 없음 — 아래 "확인이 필요한 기능" 참고) |
| 오류 | 실제 호출을 시도했고 실패가 확인됨 | MOLIT가 실패할 경우(로직 자체는 기존과 동일) |

## 개발 중/미연동으로 분류한 기능

- **청약홈 분양정보** — `syncApplyhomeListings()` 함수와 `Presale` 스키마, `GET /api/presales`는 모두 존재하나 실제로 데이터를 채우는 호출 경로가 없음. STEP 1.5-B 작업 원칙에 따라 **삭제하지 않았고**, 코드/스키마는 그대로 유지함.

## 실제 정상 확인 가능한 기능

- **국토부 실거래가(MOLIT)** — 관리자 대시보드가 매 5분 실제로 라이브 호출해 응답을 검증함. 지도/통계/단지상세 등에서도 광범위하게 실사용 확인됨.

## 확인이 필요한 기능

- **건축물대장** — 기능 자체는 다른 코드 경로(단지 상세페이지, AI 조건검색)에서 실사용이 코드로 확인되지만, 관리자 대시보드 카드 자체는 라이브 호출을 하지 않으므로 "이 순간 정상 동작 중"인지는 이 헬스체크만으로는 확정할 수 없다. 실제 운영 중 정상 동작 여부를 더 확실히 하려면 별도의 헬스체크(예: 최근 성공 호출 시각 기록)가 필요하다 — 아래 "향후 Health Check 설계 필요사항" 참고.
- **NEIS / Kakao / Gemini** — 관리자 화면에 상태 표시 UI 자체가 없어 "잘못 표시되고 있는지" 여부를 이번 STEP에서 평가할 대상이 아니었다. 각각 다른 화면(학군/지도/AI검색)에서의 실사용 여부는 STEP 1 감사 및 STEP 1.5-A에서 이미 별도로 확인됨.

## 실제 오류가 확인된 기능

- 없음. 이번 조사에서 "구현되어 있어야 하는데 실제로 실패하는" 사례는 발견되지 않았다. MOLIT 헬스체크 로직 자체가 실패를 감지하면 기존과 동일하게 "오류"로 표시된다(로직 변경 없음).

## 테스트 결과

- **TypeScript**: `npx tsc --noEmit` — 오류 없음.
- **lint**: `npx eslint`(변경된 `.ts`/`.tsx` 파일 대상) — 오류/경고 없음. `page.module.css`는 ESLint 대상 파일 타입이 아니라 "설정 없음" 경고만 출력됨(정상, 코드 문제 아님).
- **build**: `npx next build` — 성공. `/admin/dashboard`, `/api/admin/dashboard` 라우트 정상 포함.
- **관리자 화면 런타임 확인**: 로컬 개발 서버(http://localhost:3000)에서 인증 없이 접근을 시도한 결과, `GET /admin/dashboard`는 HTTP 307(리다이렉트, 기존과 동일한 인증 가드 동작), `GET /api/admin/dashboard`는 `{"success":false,"error":"로그인이 필요합니다."}`로 응답함 — **관리자 인증이 필요해 실제 카카오/네이버 로그인 세션 없이는 파이프라인 상태 카드의 실제 렌더링 결과(문구/색상)까지는 확인하지 못했다.** 인증을 우회하거나 임시로 관리자 권한을 부여하는 방식은 사용하지 않았다(요청 지침에 따름). 대신 코드 리뷰로 응답 JSON 값(`status` 문자열)과 `pipelineStatusClass()` 분기 로직을 직접 확인해 의도한 대로 동작함을 검증했다.

## 최종 검수 결과 (2026-08-12)

사용자 검수에서 전체 방향은 승인됐으나, 건축물대장의 화면 표시 문구 **"설정됨(실사용 확인, 상태 점검 미구현)"이 관리자 UI에 노출하기에는 너무 길고 개발자 중심 표현**이라는 피드백을 받아 화면 문구만 아래와 같이 단순화했다. 분류 기준·판정 로직·문서상의 분석 내용은 변경하지 않았다.

**최종 화면 표시 문구 3종**

| 항목 | 화면 표시 문구 |
|---|---|
| 국토부 실거래가(MOLIT) | 정상 / 오류 (실제 라이브 호출 결과에 따름, 변경 없음) |
| 청약홈 분양정보 | 미연동(API 키만 설정됨) / 미연동(API 키 미설정) (변경 없음) |
| 건축물대장 | **설정됨** (API 키가 없을 때는 기존과 동일하게 "미설정(API 키 없음)") |

**중요**: "설정됨"은 실제 API 호출 성공(health check)을 의미하지 않는다 — 이 문서 상단의 분석대로, 건축물대장은 환경변수(`DATA_GO_KR_API_KEY`) 존재 여부만 확인한 결과이며, 실제 라이브 검증은 이 헬스체크가 아니라 `/api/apt/[name]/info` 등 다른 사용자 화면 경로에서 이뤄진다는 사실은 위 "외부 데이터 소스별 현재 상태"·"확인이 필요한 기능" 섹션에 그대로 유지한다. 화면 문구를 짧게 줄인 이유는 UI 가독성 때문이며, 그 배경 근거는 이 문서에 기록하는 것으로 대체한다.

**관리자 로그인 상태의 실제 UI 검증**: 이번 STEP의 필수 완료조건에서 제외됨(사용자 지시). 실제 카카오/네이버 관리자 계정으로 로그인해 대시보드 카드가 위 3개 문구와 의도한 색상(정상=초록/미연동·설정됨=회색/오류=빨강)으로 정확히 렌더링되는지 눈으로 확인하는 절차는 **향후 관리자 UI 검수 항목으로 이월**한다.

## 향후 Health Check 설계 필요사항

이번 STEP 범위 밖으로 남겨둔, 더 신뢰도 높은 상태 표시를 위한 후보(구현하지 않음, 목록만 기록):

- 청약홈/건축물대장도 MOLIT처럼 "마지막 성공 호출 시각"을 기록해두면 "설정됨"보다 더 정확한 "정상" 판정이 가능하다. 다만 이번 STEP의 제약(관리자 페이지 로딩마다 새 외부 API 호출 금지)상, 이는 페이지 로딩과 무관한 별도의 주기적 백그라운드 체크(예: 크론) 또는 실제 사용 시점에 성공/실패를 로깅하는 방식이 필요하며, 그 설계는 이번 STEP에서 하지 않는다.
- 청약홈은 애초에 실제 연동(엔드포인트/필드명 검증)이 되어 있지 않으므로, 상태 체크 설계 이전에 STEP 1 감사에서 이미 지적된 "라이브 검증되지 않은 스텁"이라는 전제부터 해소해야 한다(재개발/분양 데이터 연동은 이번 STEP 금지 범위).
- NEIS/Kakao/Gemini도 실사용 중인 외부 의존성이므로, 향후 관리자 대시보드에 상태 카드를 추가할지 여부는 별도 논의가 필요하다(이번 STEP에서는 대시보드에 새 카드를 추가하지 않았다 — 대규모 관리자 UI 개편 금지 원칙에 따름).
