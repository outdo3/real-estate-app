## C. 사용자 핵심 니즈

분양 서비스에서 사용자가 실제로 알고 싶어 하는 것은 결국 다음 3가지로 수렴한다.

1. **"어디에, 언제, 얼마에"** — 지역/일정/가격을 목록만 보고 빠르게 스캔할 수 있어야 한다.
2. **"나도 청약할 수 있나/아직 유효한 공고인가"** — 접수 상태(예정/중/마감)를 즉시 알아야 한다. 단, 실측 결과(§F) 현재 1,046건 중 **접수마감(closed) 1,039건(99.3%), 접수예정(upcoming) 7건, 접수중(ongoing) 0건**이다 — 이는 3년치 과거 이력 백필의 자연스러운 결과다. 즉 이 서비스는 "지금 청약 가능한 공고를 찾는 화면"이자 동시에 **"과거 분양가 추이를 조사하는 아카이브"**로서의 성격이 훨씬 크다는 점을 목록/상태 설계에 반영해야 한다(§F, §L 연결).
3. **"이 가격이 괜찮은 건가"** — 분양가 하나만으로는 판단이 안 되고, 이집이 이미 보유한 실거래 데이터와 비교될 때 가치가 생긴다(§K, §L).

### D-2. 지도 위치 가능 여부 표시

좌표 신뢰 가능 여부(69.6%)를 카드에 작은 아이콘/여부로만 표시하고(예: 📍 있음/없음), 좌표 없는 카드를 목록에서 제외하지 않는다(§12 원칙 — 목록에서는 정상 노출).

### D-3. 모바일 카드 레이아웃 방향

세로 스택형 카드(제목 → 상태배지+지역 한 줄 → 가격 → 세대수/입주예정 한 줄) — 이 프로젝트가 이미 `/map`의 marker chip이나 `/apt` 목록류에서 쓰는 "한 줄에 압축 정보 2~3개" 패턴과 톤을 맞춘다. 정보 5~6개를 초과해 카드 높이가 늘어나지 않도록 한다.

### E-2. 지역 필터 세분화의 한계

`subscriptionAreaName`은 시/도 단위까지만 제공된다(02 문서 §L 재확인). 시/군/구 단위 필터가 필요하면 `locationAddress` 텍스트 파싱이 추가로 필요하다 — 이번 STEP에서는 시/도 단위 필터를 1차 구현 범위로 제안하고, 시/군/구 세분화는 별도 파싱 로직이 필요한 확장 과제로 분리한다(이 STEP에서 구현하지 않음).

## F. 분양 상태 계산 정책

### F-1. 기존 로직 재확인

`computePresaleStatus()`(`cheongyakService.ts`)가 이미 다음 4개 상태를 계산한다: `upcoming`(접수예정) / `ongoing`(접수중) / `closed`(접수마감) / `unsold`(REMAIN 유형 전용, 이번 1,046건에는 REMAIN 유형이 없어 실질 미해당).

### F-2. 실측 분포(2026-08-12 기준)

| 상태 | 건수 | 비율 |
|---|---|---|
| 접수예정(upcoming) | 7건 | 0.7% |
| 접수중(ongoing) | 0건 | 0% |

## I. 가격 표시 정책

### I-1. 단위 변환 규칙

`topAmount`/`minPrice`/`maxPrice`는 DB에 **만원 단위 정수**로 저장돼 있다(예: `79831`). 화면 표시는 억/만원 단위로 가공하되, **DB 원본은 절대 변환하지 않는다**(요청안 그대로 채택).

```
79831(만원) → 7억 9,831만원
```

변환 로직 예시(설계만, 구현 안 함):
- 억 단위 = `Math.floor(만원값 / 10000)`
- 나머지 만원 = `만원값 % 10000`
- 나머지가 0이면 "N억"만, 아니면 "N억 M만원"

### I-2. 최고가 의미 명시

`topAmount`는 "평균가"나 "최저가"가 아니라 **해당 주택형의 최고 분양가(상한액)**이다(02/03 문서에서 언론 보도 교차검증으로 확정된 사실). UI에서 단순히 "분양가: 7억9,831만원"이라고만 쓰면 사용자가 확정가/평균가로 오인할 위험이 있다 — "최고 7억9,831만원" 또는 "분양가(상한) 7억9,831만원"처럼 상한액이라는 의미를 라벨에 포함할 것을 권고한다.

### I-3. 가격 없는 경우

현재 1,046건 전체가 `minPrice`/`maxPrice`를 갖고 있어(100%) 이번 데이터셋에서는 "가격 미공개" 케이스가 실제로 발생하지 않는다. 다만 향후 증분 동기화로 신규 공고가 들어오면(모집공고 초기 단계에서 가격 미정인 경우, 02 문서 §M에서 가능성 언급) 발생할 수 있으므로, **"가격 미공개"로 명확히 표시하고 0원으로 표시하지 않는 방어 로직을 설계 단계에서부터 포함**한다(요청안 그대로 채택).

## K. 주변 아파트/실거래 연결 가능성

### K-1. 조사 결과 — 정직한 한계 기록

이 앱의 실거래/아파트 관련 모델을 확인했다.

- `Transaction`(오늘의 상위 거래 랭킹용, `lat`/`lng` optional이지만 범용 좌표 인덱스 조회용이 아님)

- 실제 MOLIT 실거래는 `src/lib/api-molit.ts`를 통해 **`lawdCd`(법정동코드) 기준 실시간 API 호출**로 가져오는 구조이지, 좌표 반경으로 조회 가능한 로컬 마스터 테이블이 아니다.

**결론**: 이 앱에는 "좌표 반경 N km 내 아파트를 찾는" 마스터 DB가 없다. 따라서 요청안이 예로 든 "주변 기존 아파트 / 최근 실거래 / 평당가 비교"를 **좌표 기반 정밀 반경 검색으로는 구현할 수 없다**(§13 요청 원칙대로 억지 매칭하지 않는다).

### K-2. 현재 가능한 대안(제한적)

- 분양 공고의 `locationAddress`/`subscriptionAreaName`에서 지역을 얻어, 같은 지역(`lawdCd` 단위)의 MOLIT 실거래를 **실시간 API 호출로 별도 조회**하는 방식은 기존 `api-molit.ts` 인프라로 가능하다 — 다만 이는 "정확히 이 분양 현장 주변"이 아니라 "같은 시/군/구의 최근 실거래"라는, 훨씬 넓은 범위의 근사치다.
- `locationAddress` → `lawdCd` 변환은 이 앱이 이미 아파트 상세페이지에서 쓰고 있는 Kakao 지오코딩 fallback 패턴(주소 → 좌표 → 행정구역)을 재사용할 수 있어 보인다(기억 메모: apt 상세 lawdCd 폴백 로직 기존 존재) — 다만 이번 STEP에서 실제로 재사용 가능한지 코드까지 확인하지는 않았다(범위 밖).

### K-3. P2-D2 이후 가능성 평가

"주변 아파트 정밀 비교"는 좌표 인덱스 마스터 DB가 먼저 구축돼야 하는 기능이라 **현재 범위에서는 P2-D4의 목표를 "동일 시/군/구 단위의 최근 실거래 요약"으로 낮춰 잡는 것을 권고**한다. 좌표 반경 기반 정밀 비교는 MASTER DB 작업(이번 STEP 금지 항목)이 선행돼야 하는 별도 과제로 명확히 분리한다.

## M. 커뮤니티 확장 구조 고려

### M-1. 기존 패턴 확인

`Post` 모델은 이미 `aptName`(String?, 자유 텍스트, 정확 일치 필터)이라는 **FK 없는 느슨한 태그 방식**으로 단지 상세페이지와 연동돼 있다(`@@index([aptName, createdAt])`). 이 프로젝트는 이미 이런 "느슨한 텍스트 태그" 패턴을 실제로 쓰고 있다.

### M-2. 분양 연동 방향 제안(설계만, 구현하지 않음)

- `Post`와 유사하게 향후 `presaleId`(또는 `houseManageNo`) 느슨한 태그 필드를 추가하는 방향이 기존 관례와 일관성 있다. 다만 `aptName`은 자유 텍스트인 반면 분양은 이미 안정적인 정수 PK(`Presale.id`)가 있으므로, FK 강제(`@relation`)도 고려할 수 있다 — 최종 방식은 커뮤니티 기능을 실제로 만드는 시점에 결정.
- 이번 STEP에서 schema를 변경하지 않는다(§24 금지 항목).

## N. SEO 구조 설계

### N-1. URL 후보 평가

`/presales/[id]`(숫자 PK) vs `/presales/[slug]`(이름 기반).

**권고: `/presales/[id]`(숫자 PK) 우선.** 이유:
- `Presale.id`는 항상 유일하고 안정적인 autoincrement PK다.
- 이 프로젝트는 과거 `/apt/[name]`에서 **이름 기반 라우팅 때문에 겪은 실제 버그**가 있다(같은 브랜드명이 다른 동에 있는 단지가 병합되는 문제, 이후 동 이름을 필수 구분자로 추가해 해결 — 기존 세션 기록). 분양명은 `"OO아파트 A1블록 신혼희망타운(본청약)"`처럼 이미 충분히 길고 구체적이라 아파트명보다는 충돌 가능성이 낮아 보이지만, 굳이 같은 위험을 다시 감수할 이유가 없다.
- `houseManageNo`(청약홈 고유 관리번호, unique 제약 있음)를 URL에 노출하는 대안도 있으나, 외부 식별자를 그대로 노출하는 것보다 내부 PK가 더 짧고 단순하다.
- SEO 친화적인 이름을 원한다면 `/presales/[id]-[slug]`(id는 유지하되 slug는 표시/가독성용, 실제 조회는 id로만) 형태를 절충안으로 고려할 수 있다 — 이번 STEP에서 확정하지 않는다.

### N-2. 메타데이터 후보

기존 `apt/[name]/page.tsx`의 `generateMetadata()` + `buildOpenGraph()`(`src/config/site.ts`) 패턴을 그대로 재사용 가능.

```

description: "${houseName}(${subscriptionAreaName}) 분양가 ${minPrice}~${maxPrice}만원, 청약 접수 ${receiptStartDate}~${receiptEndDate}. 주택형별 상세 정보를 확인하세요."
```

실제 DB 데이터 기반으로 생성 가능(요청안 원칙 그대로 — 지어낸 문구 없이 실 데이터로 채움).

### N-3. 확인 사항

| 항목 | 상태 |

## R. 단계별 구현 계획

요청안의 4단계 분리(P2-D2 목록+필터+상태 / P2-D3 상세+주택형+일정+가격 / P2-D4 지도+주변 연결 / P2-D5 SEO+공유+완성도)를 현재 코드 기준으로 평가했다.

**결론: 이 분리는 적절하며, 그대로 채택할 것을 권고한다.** 근거:
- P2-D2(목록)는 API가 이미 존재(`GET /api/presales`)해 프론트만 새로 만들면 되는 가장 낮은 리스크의 시작점이다.
- P2-D3(상세)는 신규 API 라우트(`/api/presales/[id]`)가 필요하지만, `PresaleHouseTypeDetail` 조회를 포함해도 Prisma 관계(`presale.houseTypeDetails`)가 이미 schema에 정의돼 있어 구현이 단순하다.

- P2-D5(SEO+공유)를 마지막에 두는 것도 타당하다 — sitemap/구조화 데이터는 실제 페이지(P2-D3)가 먼저 있어야 의미가 있다.

**추가 제안(선택 사항)**: P2-D2 착수 전에, `/redevelopment`의 기존 "분양·청약" 탭을 어떻게 처리할지 결정이 필요하다 — (a) 그 탭 안에 목록을 임베드할지, (b) 별도 `/presales` 라우트를 새로 만들고 그 탭은 링크만 걸지. 기존 bottom nav 진입점("재개발·분양")이 이미 `/redevelopment`를 가리키고 있으므로, 사용자 동선을 새로 만들지 않으려면 (b) + 탭에서 링크 연결이 더 안전해 보인다 — 다만 이는 P2-D2 착수 시 결정할 사항이며 이번 STEP에서 확정하지 않는다.

1. 분양 관련 **사용자 화면은 현재 전혀 없다**(API/데이터/관리자 도구만 존재).

## 최종 검수 결정 (2026-08-12)

PRESALE P2-D1(분양 서비스 UI/UX 구조 조사 및 설계)를 최종 승인한다. 아직 P2-D2 구현은 시작하지 않는다.

### 1. 상세 URL 최종 결정

`/presales/[id]`(`Presale.id`, DB Primary Key 기반)로 확정한다(§N-1의 권고안 그대로 채택). 분양명 자체를 unique 식별자로 사용하지 않는다 — `/apt/[name]`에서 겪었던 이름 기반 라우팅 충돌을 반복하지 않는다.

향후 SEO 필요성이 충분해지면 `/presales/[id]-[slug]` 형태로 확장할 수 있으나(§N-1에서 절충안으로 이미 언급), 이번 단계에서는 구현하지 않는다.

### 2. /redevelopment 분양 탭 정책

`/redevelopment`의 "분양·청약" 탭은 삭제하지 않는다. 향후 독립 분양 서비스의 중심은 `/presales`로 하고, `/redevelopment`의 분양·청약 탭은 향후 `/presales`로 연결되는 **진입점** 역할을 하도록 한다(§R "추가 제안"에서 검토한 (b)안 — 별도 라우트 + 탭에서 링크 연결 — 을 최종 채택). 이번 단계에서는 실제 UI를 수정하지 않는다.

### 3. 분양 상태 정책 최종 확정

기존 4분류(`upcoming`/`ongoing`/`closed`/`unsold`) 상태 계산(`computePresaleStatus()`)을 P2-D2 기본안으로 유지한다(§F 결론 그대로). 실제 3년 데이터의 약 99.3%가 접수마감 상태이므로 이번 단계에서 불필요한 상태 세분화를 하지 않는다.

다만 `upcoming`/`ongoing`/`closed`/`unsold` 같은 내부 코드명이 그대로 사용자에게 노출되지 않도록, P2-D2에서 "접수예정/접수중/접수마감/무순위" 같은 한국어 라벨로 매핑해 표시하는지 확인한다(이번 STEP에서는 라벨 매핑 존재 여부만 P2-D2 체크리스트로 남기고, 구현하지 않는다).

향후 실제 신규/진행 공고(현재 7건/0건)의 사용성이 축적되면 상태 세분화를 재검토한다.

### 4. 주변 아파트 정책 최종 확정

`Apartment` 모델에는 좌표 기반 단지 레지스트리가 없음을 이번 STEP에서 확인했다(§K-1). 이 한계가 해소되기 전까지, 시/군/구 단위로 근사한 데이터를 **"주변 아파트"라고 표현하지 않는다** — §K-2에서 제안한 "동일 시/군/구 최근 실거래 요약"은 라벨을 "주변 아파트"가 아니라 그 자체로 정확하게("이 지역 최근 실거래" 등) 표기해야 한다.

P2-D2/P2-D3에서는 정밀 주변 아파트 기능을 구현하지 않는다. 향후 MASTER DB 구축 후 "분양좌표 → 반경검색 → 기존 아파트 → 최근 실거래 → 분양가 비교" 순서로 구현하는 방향을 후보로 기록한다(§K-3, §21 금지 항목이므로 이번 STEP·P2-D2/D3 어디에서도 착수하지 않음).

### 5. 현재 가능한 지역 비교 — 향후 차별화 후보로 유지

MASTER DB 없이도 현재 분양 데이터 자체로 가능한 "같은 지역 분양 비교"(같은 지역 최근 분양, 같은 지역 주택형별 분양가, 최근 3년 분양가 흐름, §L-1)는 향후 차별화 기능 후보로 유지한다. 이를 위 §4의 "주변 아파트"(정밀 반경 비교)와 혼동하지 않는다 — 전자는 분양 데이터 내부 비교, 후자는 분양과 기존 아파트 실거래를 좌표로 연결하는 별개 기능이다.

### 6. 분양 아카이브 가치 — 데이터 자산으로 정의

현재 최근 3년 분양 데이터 1,046건(99.3% 접수마감)을 단순 종료 데이터로 보지 않는다. 향후 "최근 3년 분양가 아카이브"로 활용할 수 있는 데이터 자산으로 정의한다(§L-1에서 이미 "오히려 강점"으로 평가한 바 있음). MASTER DB/실거래 연결 후 "과거 분양가 vs 현재 실거래" 분석으로 확장 가능성을 기록해둔다. 이번 단계에서 구현하지 않는다.

### 7. P2-D 구현 순서 최종 확정

§R의 평가를 그대로 최종 확정한다.

- **P2-D2**: 분양 목록 + 기본 필터 + 상태
- **P2-D3**: 분양 상세 + 일정 + 주택형 + 가격
- **P2-D4**: 지도 + 위치정보(정밀 주변 아파트는 MASTER DB 이후로 이관, §4)
- **P2-D5**: SEO + 공유 + 모바일/PC 완성도 정리

이 순서로 진행한다.
