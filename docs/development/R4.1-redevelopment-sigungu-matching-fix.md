# STEP R4.1 — 부산 시군구 해석 보정 + Redevelopment 실제 병합 품질 확정

상태: **완료 — schema/migration 무변경, production migration/ingestion 미실행**

## 문제

R4 실물 파일럿에서 merged(MOLIT+BUSAN 양쪽 연결) 프로젝트가 1,904개 중 **2건**에
그쳤다. 원인은 매칭 confidence 로직이 아니라, 부산 343건 중 location 텍스트에
"OO구"/"OO군" 리터럴 문자열이 있는 경우만 sigungu를 해석했기 때문(148/343, 43%) —
"서대신4"처럼 R3A가 가장 깨끗한 EXACT 사례로 꼽은 건조차 부산 쪽 location
("대영로45번길20, 3층(서대신동2가)")에 "서구"라는 문자열 자체가 없어 sigungu가
"미상"으로 떨어지고, sido+sigungu 인덱스로 후보를 조회하는 매칭 로직 자체가
작동할 기회를 얻지 못했다.

## 원인 재확인

R4 doc "신규 발견 2"에서 이미 진단한 그대로였다 — 재조사하지 않고 그 결론을
그대로 가져와 해결책만 구현했다.

## api/properties/route.ts 변경 이유 확인

`git diff`로 재확인: R4 schema가 `RedevelopmentProject.lawdCd` 필드를 완전히
제거했고(R3B 설계 — 국토부/부산 원본 모두 lawdCd 없이 sido/sigungu 텍스트만
제공), 이 필드를 참조하던 REDEVELOPMENT 분기 쿼리(`where: { lawdCd }`)가 새
Prisma 타입에서 컴파일 자체가 안 되기 때문에 sido/sigungu 쿼리 파라미터로 바꾼
것이었다. **판정: A(필수 변경) — 유지.** OFFICETEL/LIVING_STAY 분기(Property
모델)는 완전히 무관, 이 분기를 호출하는 프론트엔드도 없음(`/map`은 "준비 중"
안내만 표시) — 기존 apartment/property API 회귀 위험 없음.

## resolver 설계

새 DB enum을 추가하지 않고, `src/lib/redevelopment/sigunguResolver.ts` 안에서만
쓰는 내부 분류로 우선순위를 뒀다(섹션 8/12 요구사항):

```text
1. EXPLICIT      location 텍스트에 명시된 "OO구"/"OO군" 리터럴(R4와 동일, 148/343)
2. DONG_NAME      location 텍스트의 법정동명 → REGCODE_PROXY 공식 매핑
3. ROAD_ADDRESS   도로명만 있는 경우 → Kakao 주소 검색(좌표 아니라 sigungu만 사용)
4. PROJECT_NAME   areaName(사업명)에서 구역번호/접미사를 뗀 나머지가 공식
                  법정동명과 "정확히" 일치할 때만(fuzzy 매칭 금지)
5. UNRESOLVED     위 4개 전부 실패 — 억지로 채우지 않음
```

## 동→구군 공식 mapping 소스

**새 외부 API를 추가하지 않았다.** 이 프로젝트가 이미 `src/lib/region-utils.ts`
에서 쓰고 있는 `REGCODE_PROXY`(`grpc-proxy-server-mkvo6j4wsq-du.a.run.app/v1/regcodes`,
공식 법정동코드 조회 서비스)를 그대로 재사용했다(섹션 7 지시대로 먼저 검색해서
찾음). `regcode_pattern=26*`(부산광역시 전체) 단일 호출로 254개 법정동을
한 번에 받아 인메모리 인덱스를 만든다 — 구별로 나눠 부르지 않아 quota 부담이
없다.

실측 확인 몇 가지(하드코딩 전에 공식 데이터로 검증, 섹션 6 지시):

```text
부산광역시 서구 동대신동1가/2가/3가
부산광역시 서구 서대신동1가/2가/3가
부산광역시 서구 부민동1가/2가/3가
부산광역시 서구 아미동1가/2가
부산광역시 서구 남부민동
```

동명이인 실측 확인(추측 방지 근거): **"송정동"은 해운대구와 강서구 양쪽에
공식적으로 존재**(REGCODE_PROXY 실측) — resolver는 이런 경우 sigungu 후보가
2개 이상 나오면 추측하지 않고 UNRESOLVED로 남긴다(테스트로 고정).

## 도로명-only 처리

location 텍스트가 도로명뿐이고(예: "구서중앙로 20") 위 1~2단계로 못 푼
레코드만 Kakao 주소 검색(`/v2/local/search/address.json`, 기존
`cheongyakService.ts`의 KA/Origin 헤더 패턴 재사용)에 태웠다. **실물 데이터
343건 기준 실제 호출 47건**(전체의 14%) — quota 걱정 없는 규모다.

목적은 **좌표 확정이 아니라 sigungu 복원**이다(섹션 9) — `region_2depth_name`만
뽑아 쓰고 좌표(lat/lng)는 어디에도 저장하지 않는다.

**조합사무실 주소 오인 방지(섹션 9/13, 실제 데이터로 결정)**: ROAD_ADDRESS로
sigungu를 얻은 47건 중 `classifyLocationText()`가 office 의심 패턴(층/호/상가
등)과 동시에 검출한 건이 **26건(55%)**이었다 — R3A의 "지오코딩 성공의 82%가
사무실 의심"과 같은 방향의 결론. 이 26건은 `safeForMatching=false`로 표시해
sigungu를 알아도 자동 매칭 key로 쓰지 않고(Project.sigungu에 반영하지 않고
"미상"으로 유지), 나머지 21건(office 패턴 없음)만 매칭에 사용했다.

## PROJECT_NAME 추론의 한계(정직하게 기록)

"명서1"(R3A/R2 문서에 기록된 실제 사례, 동래구 소재)은 실제 법정동명이
"명장동"이라 "명서"+"동"="명서동"이 레지스트리에 없어 **의도적으로
UNRESOLVED**로 남는다 — fuzzy 매칭을 걸었다면 잘못된 다른 동에 배정될
위험이 있어, 틀리게 채우기보다 모른다고 두는 쪽을 선택했다(단위 테스트로
회귀 고정).

## 매칭 알고리즘 자체의 보완 — 접미사 비교 문제(실물 데이터로 발견)

sigungu를 고쳐도 "서대신4"가 여전히 병합되지 않는 것을 실제로 확인했다 —
부산 API의 실제 `areaName`은 **"서대신4 재개발"**(유형 접미사 포함)이었다
(R3A 문서의 "서대신4" 예시는 접미사 없는 축약 표기였을 뿐, 실제 원본과
다름). `normalizedName`은 저장 목적상 접미사를 보존하므로("거제2 재개발"
"거제2 재건축" 오매칭 방지, R3B 정책 그대로 유지) 국토부의 "서대신4"(접미사
없음)와 문자열이 달라 EXACT/유사도 비교 모두 실패했다.

**해결**: `matching.ts`의 `computeMatchConfidence()`에서만 쓰는 비교 전용
`stripTypeSuffixForComparison()`(R3A 원래 파일럿의 접미사 목록 재사용)을
추가했다. **DB에 저장되는 `normalizedName` 자체는 이 함수를 거치지 않는다**
— 오매칭 방지는 여전히 별도 `businessType` 필드 비교가 담당한다(접미사를
떼서 이름이 같아져도 businessType이 다르면 여전히 LOW로 강등 — "거제2
재개발 vs 재건축" 회귀 테스트로 고정, 실물 데이터에서도 "대연3"이 실제로
REDEVELOPMENT/RECONSTRUCTION 두 개로 정확히 분리 유지됨을 확인).

## location classification 배선(섹션 23-25)

`classifyLocationText()`를 `ingestRecord()`의 canonical 재계산 단계에
연결했다. 한 Project에 연결된 SourceRecord들의 rawLocation을 전부 분류한
뒤 PROJECT_SITE > APPROXIMATE > OFFICE > UNKNOWN 우선순위로 가장 유용한
신호를 `Project.locationType`/`locationConfidence`에 반영한다. **좌표(lat/lng)는
채우지 않았고 `geocodeStatus`는 항상 `NOT_ATTEMPTED`로 정직하게 남긴다**(섹션
24 — 343건 전체 지오코딩 금지, office 의심 좌표를 PROJECT_SITE로 저장하지
않음).
