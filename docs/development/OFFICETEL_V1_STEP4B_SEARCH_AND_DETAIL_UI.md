## 1. 기존 검색 아키텍처 감사와 확장 방식

`/api/search`를 호출하는 컴포넌트는 `ApartmentAutocomplete.tsx` **하나**이고, 홈·지도·통계·상세 빠른검색이 그것을 공유한다. 그래서 확장 지점은 명확했다.

**아파트 검색을 대체하지 않았다.** 응답에 `officetels` 키를 **추가**만 했고, 기존 `regions`/`apartments` 계산 경로는 한 줄도 바꾸지 않았다. 오피스텔 쿼리는 실패해도 `catch`로 빈 배열이 되어 아파트/지역 결과를 죽이지 않는다.

### `includeOfficetel` opt-in으로 둔 이유

오피스텔 결과를 무조건 섞으면, 그것을 처리하지 않는 소비처(지도·통계·상세 빠른검색)가 오피스텔 항목을 아파트 분기로 흘려보내 **잘못된 이동**을 만든다. 그래서 기본값 `false`이고, 켠 쪽(홈 검색)만 책임지고 처리한다. 기존 경로는 코드·동작 모두 무변경이다.

AI 검색은 범위 밖이라 건드리지 않았다.

## 2. 검색 read path

`src/lib/officetel/search-read.ts` — 실제 저장된 master 값만으로 검색한다: 표시명 / 법정동 / 지번 / 도로명주소. 좌표·거래 데이터는 쓰지 않는다.

티어 랭킹(`search-contract.ts`, 순수): 이름 완전일치 → 접두 → 부분 → 주소. 동률은 결정적으로 깬다. `officetel_masters`는 5,056행이라 `take` 없이 받아 랭킹 후 상위 8건만 응답한다(아파트 검색이 `take:50`에서 exact match를 잘라먹던 문제를 반복하지 않는다).

"온천동 153"처럼 **여러 토큰으로 주소를 치는 습관**을 지원한다 — 토큰 전부가 어딘가 걸려야 한다(AND of ORs).

**identity 계약**: 결과는 언제나 `officetelId` + `canonicalKey`를 함께 들고 간다. 이동은 `/officetel/{id}`로만 하고 이름으로 하지 않는다. 아파트가 하던 "이동 전 실거래 연결 확인"은 오피스텔에 필요 없다 — 그것은 이름 기반 재식별의 안전장치였고, 오피스텔은 이미 정확한 id를 갖고 있다.

## 3. 빈 이름 정책

표시명이 빈 master 390건(7.71%)은 `officetelFallbackDisplayName()`이 **`전포동 897-0 오피스텔`** 형태로 부른다. 저장된 주소 성분만 조합하며 **DB에 쓰지 않는다**(표시 전용). identity는 언제나 그 아래의 id/키다.

실측 확인: id 2296 → `온천동 153-8 오피스텔`, API `master.name`은 `null` 그대로.

## 4. 라우트

`/officetel/[id]` (별도 라우트). 아파트 상세는 식별자가 **이름**이라 오피스텔을 얹으면 곧바로 identity 모호성이 생긴다(동명 충돌 4.47% 실측).

초기 렌더는 서버에서 STEP 4A의 `getOfficetelDetail()`을 그대로 호출(HTTP 왕복 절약, API와 같은 함수라 계약이 갈라지지 않음). 거래 목록/탭/면적 전환은 클라이언트가 STEP 4A API를 호출한다.

딥링크·새로고침 실측: `/officetel/2243`, `/officetel/2296`, `/officetel/OFFI:26350:우동:1435-3:_` 전부 200. 없는 id는 404 + 전용 not-found 화면.

## 5. 시각 구분 (§4)

공통 e-jip 시각 시스템을 쓰되 **teal 강조**만 오피스텔에 배정했다: 배지 · 활성 탭 · 선택 칩 · 섹션 액센트 선. 페이지 전체를 물들이지 않고, 아파트 green(`--primary-color`)은 전혀 건드리지 않았다.

**색에만 의존하지 않는다** — 검색 결과와 상세 헤더 모두 `오피스텔` 텍스트 배지를 항상 함께 보여준다.

## 6. 정보 우선순위 (§8)

아파트 순서를 베끼지 않았다. 오피스텔은 장기 보유·임대수익 관점이라 거래가 먼저다:

`거래 요약 → 매매/전세/월세 → 전용면적 → 추이 → 건물 정보 → 주차·규모 → 데이터 안내`

## 8. QA에서 발견해 고친 실제 결함 3건

이 STEP의 가장 중요한 산출물은 UI가 아니라 아래 세 가지다.

### (1) Supabase 커넥션 풀 고갈 — STEP 4A에서 들어온 결함

상세 페이지를 연속으로 열자 `FATAL: (EMAXCONNSESSION) max clients reached — pool_size: 15`로 **모든 상세가 500**이 됐다. 원인은 STEP 4A의 `loadSummary()`가 count/findFirst **9개를 동시에** 던진 것. serverless에서는 동시 요청 두세 개만으로 풀이 마른다.

→ 집계와 최신 1건을 `LEFT JOIN LATERAL`로 합쳐 **데이터셋당 SQL 1개**로 축약(9 → 2). 같은 인덱스를 그대로 타므로 비용은 늘지 않았다.

### (2) 전세 탭이 잘못 비어 보이는 문제

RENT 응답 한 페이지를 받아 화면에서 전세/월세로 가르고 있었다. 최근 20건이 전부 월세인 단지(id 1323)에서 **전세 77건이 있는데도 "전세 거래 없음"** 이 떴다.

→ 분리는 페이지네이션 **이전**에 해야 한다. STEP 4A API에 `rentType=jeonse|wolse`를 추가하고 서버가 가르게 했다.

### (3) 탭 전환 시 페이지 전체가 빈 화면이 되는 크래시

탭을 바꾸면 새 fetch가 끝나기 전에 한 번 더 렌더되는데, 그때 **이전 탭의 행**이 새 탭 렌더러로 들어갔다. 매매 행에는 `deposit`이 없으므로 `won(undefined)` → `undefined.toLocaleString()` 예외 → React가 트리를 통째로 버려 **첫 탭 클릭에 화면이 사라졌다.**

→ 응답을 만든 **쿼리 키와 함께** 보관하고, 키가 다른 응답은 아예 그리지 않는다(로딩으로 취급). 추가로 `won()`이 숫자가 아니면 던지지 않고 `정보 없음`을 반환하도록 방어했다.

## 10. 최근 본 항목 — 이번 STEP에서 연기

`RecentView` 모델은 `lawdCd`/`dong`/`name`이 필수이고 `@@unique([userId, lawdCd, dong, name])`이며 **propertyType 필드가 없다**. localStorage 쪽(`ejip:recentApartments`)도 `name|dong`을 키로 쓴다.

오피스텔을 넣으려면 스키마 변경(타입 컬럼 추가 + unique 재정의)과 기존 행의 타입 해석이 필요한데, 이는 이번 STEP이 금지한 DB 변경이고 §21이 말한 "위험한 마이그레이션"에 해당한다. **연기하고 보고한다.** 빈 이름 master와 한 주소 복수 master 때문에 `name|dong` 키는 오피스텔에서 충돌하기도 한다.

## 11. 지도 / 로드뷰

**구현하지 않았다.** master 좌표 보유율 0.00%라 보여줄 것이 없고, 지도를 띄우려고 느슨하게 지오코딩하지 않았다. 빈/가짜 지도 카드도 만들지 않았다. 상세는 카드 단위 섹션 구조라, 좌표가 생기면 카드 하나를 추가하는 것으로 지도 ↔ 로드뷰 전환을 넣을 수 있다.
