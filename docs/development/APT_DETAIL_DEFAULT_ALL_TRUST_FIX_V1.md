## 1. 무엇이 잘못됐나

핵심은 "전체인데 84㎡가 보인다"가 아니었다. 실제 프로덕션 동작은 이랬다:

```
상세 진입 → 84㎡가 자동 선택됨
         → 헤더는 "최근 실거래가"      ← 단지 전체의 최신 거래로 읽힌다
         → 값은 84㎡의 최신 거래        ← 실제로는 한 평형의 최신 거래
```

다른 평형에 **더 최근 거래가 있어도 그게 가려졌다.** 라벨과 값이 어긋나므로 UI 선호 문제가 아니라 신뢰 문제다.

### 프로덕션 데이터로 재현

실제 API 응답(대연롯데캐슬레전드1단지, 거래 920건 · 전용면적 9종)으로 두 정책을 비교했다:

| | 가격 | 계약일 | 전용면적 |
|---|---|---|---|
| **예전**(84㎡ 자동 선택) | 8억 | 2026-08-25 | 84.98㎡ |
| **지금**(전체) | 8억 9,000만 | **2026-09-03** | 100.95㎡ |

예전 화면은 **9일 더 최근인 100.95㎡ 거래를 가리고** 84㎡ 거래를 "최근 실거래가"라고 보여줬다. 금액 차이는 9,000만원이다.

(비교군: 해운대두산위브더제니스는 두 정책의 결과가 같았다 — 84㎡ 밴드 거래가 실제로 최신이었던 경우다. 즉 이 버그는 **단지마다 조용히 나타났다 사라졌다** 했고, 그래서 더 잡기 어려웠다.)

## 2. 근본 원인

`src/lib/trade-area-selection.ts`의 `pickDefaultTradeArea`:

```
STANDARD_AREA_MIN = 84
STANDARD_AREA_MAX = 85
→ 84~85㎡ 구간 거래가 하나라도 있으면 그 구간을 우선 선택
```

`apt-client.tsx`가 거래를 받아온 직후 이 함수로 평형을 **자동 선택**하고 있었다. 84㎡는 "가장 흔한 평형"이라는 뜻이지 "가장 최근 거래된 평형"이 아니다. 그런데 그 옆 라벨은 전 평형을 뜻하는 "최근 실거래가"였다.

## 3. 고친 방식 — 한 줄도 새로 만들지 않았다

**자동 선택 호출을 없앤 것이 전부다.** 파생 로직은 이미 올바르게 짜여 있었다:

```
selectedTradeArea === '전체'
  → areaMatchesSelection이 전부 통과
  → API가 이미 tradeDate 내림차순 정렬(route.ts:204)
  → filteredTrades[0] = 모든 평형을 통틀어 가장 최근의 유효 거래
  → renderHeroAreaLabel(heroTrade.area) = 그 거래의 실제 평형
```

즉 `전체`로 두기만 하면 §2가 요구하는 동작이 그대로 나온다. 취소 거래 제외·canonical aptSeq·DB-first 소스는 전부 API 쪽에 있어 손대지 않았다.

## 5. 전체 모드 차트 (§6)

전체가 기본 상태가 되면서 차트가 비어 있으면 안 된다. 그런데 **서로 다른 면적의 거래를 하나의 절대가격 선으로 이으면 존재하지 않는 가격 변동을 그려낸다** — 59㎡ 거래와 129㎡ 거래를 연결하면 그건 시세가 아니라 착시다.

그래서 `buildUnitTrendSeries`가 면적마다 **독립된 선**을 만든다.

- 그룹 기준: `parseFloat` 후 소수 4자리까지의 **정확한 전용면적**. `84.7855m²`와 `84.7855`처럼 표기만 다른 건 한 그룹, `84.7855`와 `84.9950`처럼 **다른 면적은 절대 합치지 않는다**(Unit Master 보호).
- 가독성 규칙(결정적): 거래 건수 내림차순 → 같으면 면적 오름차순 → 상위 5개. 같은 입력이면 언제나 같은 결과.
- 빠진 평형은 **지어내거나 뭉뚱그리지 않고** 개수만 알린 뒤 "평형을 선택하면 볼 수 있다"고 안내한다.
- 매매만 쓴다. 전세까지 겹치면 선이 두 배가 되고, 애초에 매매가와 전세가는 같은 절대 축에서 비교할 값이 아니다.

**기존 선택-평형 경로는 한 줄도 건드리지 않았다.** 전체 모드는 별도 렌더 경로라 크로스헤어 히트테스트·거래량 막대·매매/전세 토글이 그대로 남아 있다.

### 실제 데이터 확인 (대연롯데캐슬레전드1단지)

```
입력 거래 920건 → 시리즈 5개 / 생략 4개 / 포인트 737개
  39.70㎡ 82건 · 59.94㎡ 144건 · 84.95㎡ 221건 · 84.98㎡ 193건 · 100.95㎡ 97건
면적 혼합 포인트: 0
```

`84.95`와 `84.98`이 **서로 다른 선으로 유지**된다 — 반올림으로 합치지 않는다.

## 6. 리포트 초등학교 이름 (§7)

### 근본 원인

리포트는 `ApartmentLocationFeature.nearestElementaryDistanceM`만 들고 있었다. 그 테이블에는 **학교 이름 컬럼이 없다** — 수집기(`collectors/location.ts`)가 Kakao 응답에서 거리만 저장했기 때문이다. 지하철은 `nearestSubwayName`이 있어 `해운대역 320m`으로 나오는데, 초등학교는 이름이 없어 `341m`만 나왔다.

### 스키마 변경 없이 해결

`School` 테이블(NEIS 원천)이 이미 있고 조회해 보니 조건이 충분했다:

```
초등학교 305곳 · 전부 active · 전부 좌표 보유 · 전부 OFFICIAL_POINT · 전부 COMPLETE · 전부 부산
```

그래서 **읽기 전용 조회**로 이름과 거리를 함께 얻는다. 마이그레이션도, 컬럼 추가도, 백필도 없다.

### 출처를 섞지 않는다

NEIS 이름에 Kakao 거리를 붙이지 않는다. 두 출처가 **서로 다른 학교를 가리킬 수 있어** "OO초등학교 · (다른 학교까지의) 341m"라는 거짓 조합이 만들어질 수 있다. 이름을 쓸 때는 거리도 같은 행에서 계산한다.

좌표가 없거나 후보가 없으면 이름을 추측하지 않고 `학교 정보 확인 불가`를 표시한다.

### 결과 (실측)

```
이전 : 초등학교  249m
지금 : 초등학교  연포초등학교 · 직선 249m
```

**즉 이 단지에서 바뀐 것은 "이름이 생겼다"뿐이고 숫자는 그대로다.**

### ⚠️ 정정 (SCHOOL_DISTANCE_SOURCE_RECONCILIATION_V1, 2026-09-11)

이 문서는 처음 작성될 때 위 "이전" 값을 **`341m`으로 잘못 적었고**, 그에 근거해 "리포트 249m vs ScoreCard 341m으로 두 화면이 어긋난다"고 서술했다. **둘 다 사실이 아니다.**

- `341m`은 이 단지의 실제 저장값이 아니라 직전 STEP 지시문에 예시로 등장한 숫자였다. 작성자가 그것을 실측값처럼 옮겨 적었다.
- 이 단지(26290-2625)의 실제 저장값은 **249m**이고, NEIS 계산값도 **249m**이며, 두 출처가 가리키는 학교도 **같은 연포초등학교**다.

전수 대조(3,381건) 결과 두 출처는 **99.4%가 5m 이내로 일치**한다. 즉 "출처가 달라 화면이 어긋난다"는 서술 자체가 성립하지 않았다. 실제로 존재하는 차이와 그 영향은 `SCHOOL_DISTANCE_SOURCE_RECONCILIATION_V1.md`에 정리했다.

## 9. 모바일 QA — 구조 분석

브라우저 확장이 이 세션에서 승인되지 않아 **렌더링이 아니라 CSS/DOM 구조 분석**이다.

- Hero 라벨은 문자열 길이만 바뀐다(`최근 실거래가` → `선택 평형 최근 실거래가`, 6→11자). 부모가 `flexWrap: 'wrap'`이라 360px에서도 줄바꿈으로 흡수된다.
- 전체 모드 차트는 기존 클래스(`.chart`/`.legend`/`.notice`)를 그대로 쓴다. `.legend`는 `flex-wrap: wrap`이라 평형 5개 범례가 360px에서 2~3줄로 접힌다.
- 리포트 초등학교 행은 값 문자열이 길어진다(`249m` → `연포초등학교 · 직선 249m`). 지하철 행이 이미 `못골역 부산2호선 · 직선 342m`로 더 길어 같은 행 스타일에서 검증된 길이다.

**권장**: 실제 기기에서 상세 진입 직후 Hero와 차트를 한 번 눈으로 확인.
