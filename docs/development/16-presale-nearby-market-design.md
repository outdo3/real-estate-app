## 2. 현재 실거래 API 구조 (코드 직접 확인, 추측 없음)

`src/lib/api-molit.ts`의 `fetchMolitData({ lawdCd, dealYmd, type })`를 직접 읽어 확인했다.

- **실시간 외부 API 호출형**(DB cache 아님). 엔드포인트: `RTMSDataSvcAptTradeDev`, 파라미터 `LAWD_CD`+`DEAL_YMD`(월 단위), `numOfRows=1000`.
- **`aptSeq`를 추출하지 않는다** — 응답 원본에는 `aptSeq` 필드가 존재하지만(§4에서 실측 확인), `fetchMolitData`의 반환 객체에는 이 필드가 아예 없다. 현재 프로덕션 코드 전체(`api/apt/[name]`, `api/transactions`, `api/school/apartments`, admin dashboard)가 **단지명 문자열 정규화 매칭**만으로 실거래를 연결하고 있음을 재확인했다(문서 10/11의 기존 발견과 동일, 이번 조사로 재확인).
- **캐시**: `src/lib/server-cache.ts`의 `getOrSetCache`(순수 in-memory `Map`, 서버 인스턴스 생존 기간 TTL) — `/api/apt/[name]`이 `molit:{type}:{lawdCd}:{dealYmd}` 키로 이미 사용 중이다. **이 키가 lawdCd+월 단위라는 점이 중요하다** — 같은 지역의 여러 단지를 조회해도 원본 월별 데이터는 한 번만 fetch된다(§13에서 이 구조를 그대로 재사용 제안).
- **조회 기간**: `/api/apt/[name]`은 기본 36개월(`period` 쿼리파라미터, 12개월 단위 chunk로 분할 요청).
- **거래유형**: `type=apt`만 사용하는 라우트들은 `RTMSDataSvcAptTradeDev`(아파트 매매)만 조회한다 — 분양권전매(`silv`)나 전월세(`rent`)와 혼합되지 않음을 코드로 확인했다(§19의 우려사항에 대한 답).

## 3. aptSeq 직접 연결 — 실 API 검증 (추측 아님, 실제 호출)

MOLIT는 `aptSeq` 단건조회 API를 제공하지 않는다(문서 11 §22에서 이미 확정, 이번에도 재확인). 따라서 유일하게 실현 가능한 구조는 **"lawdCd+월로 거래를 받아온 뒤 응답 내부 `aptSeq`로 필터링"**이다.

실제로 서구(26140)에서 이름이 완전히 같은 3개 서로 다른 단지("문화", `aptSeq` 각각 `26140-63`/`26140-15`/`26140-77`, 서로 다른 동/지번)를 대상으로 최근 4개월 원본 거래를 직접 호출해 검증했다.

| 검증 | 결과 |
|---|---|
| MOLIT 원본 응답에 `aptSeq` 필드 존재 여부 | **존재**(`fetchMolitData`가 추출하지 않을 뿐, 원본에는 항상 있음) |
| `aptSeq`로 필터링한 결과 | 실거래 2건이 각각 `26140-15`(동대신동3가)/`26140-63`(토성동2가)로 정확히 분리됨 |
| 단지명 문자열("문화")만으로 필터링했다면 | 이번 표본(2건)에서는 우연히 같은 결과였으나, 이는 두 거래의 `dong`이 서로 달라 기존 코드의 `dong` 보조검증이 우연히 걸러낸 것 — `dong` 없이 이름만 썼다면 두 단지가 뒤섞였을 것 |

**결론**: `ApartmentMaster.aptSeq`를 이미 확보한 상태(M4-B)이므로, 주변 후보 각각에 대해 "지역코드+월 조회 → 그 후보의 `aptSeq`로 필터링"하면 이름 매칭(문서 10 §5-2, 실측 약 79%)이나 `dong` 보조검증 없이 **100% 정확한 연결**이 가능하다. 이는 문서 10 P2-D4-A가 B판정을 내린 핵심 근거("Apartment Master 부재")가 M4-B로 해소됐음을 실측으로 보여주는 이번 조사의 가장 중요한 발견이다.

## 6. 반경 정책 설계 (§7)

**adaptive radius를 권장한다.**

1. 기본 1km로 검색
2. 후보(좌표 보유 ApartmentMaster) 5개 미만이면 2km로 확장
3. 그래도 5개 미만이면 3km까지 확장
4. 3km에서도 부족하면(§17 강서구 사례처럼 저밀도 지역) 후보 수 그대로 표시하고 "이 지역은 비교 가능한 단지가 적습니다"라고 명시 — **억지로 반경을 더 넓혀 "주변"의 의미를 훼손하지 않는다.**

고정 반경(예: 무조건 1.5km)은 §5의 실측 편차(3개~192개)를 고려하면 밀집지역/저밀도지역 어느 쪽에도 맞지 않는다. 다만 상한 반경은 반드시 필요하다 — 반경 자체를 무한정 넓히면 "주변"이라는 표현이 더 이상 성립하지 않으므로(문서 10 §3의 D안 논쟁과 동일 원칙), **3km를 최대 상한으로 고정**할 것을 권장한다.

## 7. 표시 개수·정렬 정책 (§8)

실측(§5)에서 밀집지역은 반경만으로 이미 후보가 넘치므로, **표시 개수를 별도 상한(최대 5개)으로 관리하고 정렬 기준으로 실제 비교 가치가 높은 순서를 우선**해야 한다.

권장 정렬: **(1순위) 최근 거래가 있는 단지만 우선 노출 → (2순위) 그중 거리순.** 이유:
- "가장 가까운 아파트"가 실거래 없는(§18) 단지라면 사용자에게 비교할 가격 정보를 주지 못한다 — 요청안 §8이 지적한 대로 "가장 가까움"과 "비교 가치"는 다르다.
- 유사면적 우선 정렬은 §9~10에서 확인한 대로 "houseTy 앞자리=전용면적" 가설이 아직 공식 확정 전이라, 1순위 정렬 기준으로 쓰기엔 근거가 약하다 — 카드 내부 필터/뱃지로는 쓰되 정렬 1순위로는 쓰지 않는다.
- 거래량순은 신축 분양 인접지에 구축 대단지가 많으면 거리와 무관하게 상위를 독점해 "주변"이라는 감각을 해칠 수 있어 채택하지 않는다.

## 8. 면적 의미 재검증 (§9)

테스트 Presale 8건의 `PresaleHouseTypeDetail` 55개 행 전부를 `houseTy` 앞자리와 `supplyArea`로 대조했다(문서 10 §14가 15개 행으로 확인한 것을 이번에 55개 행으로 확장 재검증).

**55개 행 전부에서 `houseTy` 앞자리가 `supplyArea`보다 항상 작았고**, 그 차이가 면적대별로 일관됐다: 59㎡대는 약 19.8~23.5㎡ 차이, 84㎡대는 약 24.5~32.6㎡, 104㎡대는 약 35.3~35.7㎡, 125㎡대는 약 44.7~45.0㎡, 154㎡는 53.0㎡, 244㎡는 88.6㎡ — 면적이 커질수록 차이(공용면적)도 커지는 통상적인 패턴과 정확히 일치한다.

**이 결과는 문서 10 §14의 가설("houseTy 앞자리=전용면적")을 강하게 재확인하지만, 이번에도 청약홈 공식 API 문서로 최종 확정하지는 못했다** — "확인 필요" 상태를 그대로 유지한다(추측을 확정값으로 승격하지 않는다는 원칙, 요청안 §9).

## 9. 면적 매칭 허용범위 실측 (§10)

실제 MOLIT 거래로 "같은 평형"이라 불리는 유닛들의 실제 `excluUseAr` 분포를 확인했다.

- **남구 12개월, 전용 58~62㎡ 구간**: 808건 거래에 **고유 면적값 75종**(58.08㎡ ~ 61.56㎡까지 폭넓게 분산).
- **부산진구 12개월, 전용 83~86㎡ 구간**: 1,577건 거래에 **고유 면적값 175종**(83.04㎡ ~ 86㎡대까지).

같은 "국민평형 59㎡/84㎡"로 통칭되는 유닛도 실제로는 소수점 이하는 물론 정수부까지 1~2㎡ 이상 갈라져 있다.

| 허용범위 후보 | 평가 |
|---|---|
| ±0.5㎡ | 59.90 기준 59.40~60.40 — 다소 타이트, 58㎡대 유사 타입 일부를 놓칠 수 있음 |
| **±1㎡(권장)** | 59.90 기준 58.90~60.90 — 실측 분포의 밀집 구간을 대부분 포괄하면서 61㎡대 이상은 배제 |
| ±2㎡ | 59.90 기준 57.90~61.90 — 실측상 58㎡대(소형)~61㎡대(준대형)까지 섞여 "같은 평형"이라 부르기엔 지나치게 넓음 |

**±1㎡를 권장**한다 — 실측 분포의 밀집 구간을 포괄하면서, 사용자가 명백히 다른 타입(58㎡대 vs 61㎡대)이라 느낄 만한 차이는 배제한다.

## 10. 사용자 면적 표현 (§11)

§8의 "확인 필요" 상태와 §9의 허용범위(±1㎡, 근사치)를 감안하면, **"같은 평형"이라는 단정적 표현은 사용하지 않는다.**

| 후보 | 채택 여부 |
|---|---|
| "같은 평형" | ❌ — 정확성 근거 부족(§8), 오해 소지 |
| "유사 평형" | △ — "평형"이라는 단어 자체가 공급면적 기반 관행(평 단위)이라 전용면적 비교 맥락에서는 부정확 |
| **"비슷한 전용면적(OO~OO㎡)"** | ✅ 권장 — 범위를 함께 명시해 정확한 근거를 그대로 노출 |
| "전용 59~60㎡ 거래" | ✅ 대안 — 짧은 카드 UI에는 이 표현이 더 적합 |

**권장**: 카드처럼 공간이 좁은 곳은 "전용 OO~OO㎡ 거래", 설명 텍스트가 들어가는 곳은 "비슷한 전용면적(OO~OO㎡ 대) 최근 거래"로 구분해 쓴다.

## 11. 실거래 조회 기간 (§12)

동래구(밀집)/강서구(저밀도)/서구(중간) 3개 대표 지역에서, §5의 반경 내 후보들이 실제로 몇 개월 내 거래를 보유하는지 실측했다.

| 지역(반경) | 후보 수 | 3개월 내 거래 | 6개월 내 | 12개월 내 | 24개월 내 |
|---|---|---|---|---|---|
| 동래구(1.5km) | 91 | 46(50.5%) | 67(73.6%) | 82(90.1%) | 91(100%) |
| 강서구(2km) | 3 | 2 | 3 | 3 | 3 |
| 서구(1.5km) | 28 | 16(57.1%) | 22(78.6%) | 24(85.7%) | 28(100%) |

**3개월 단독으로는 후보의 약 40~50%가 거래 자체가 없다** — 분양가 비교 대상으로 삼기엔 표본이 너무 적다. 6개월에서 73~79%, 12개월에서 86~90%까지 올라간다.

**권장 fallback 구조**: 기본 6개월 → 부족(비교 가능 단지 5개 미만)하면 12개월로 확장 → 그래도 부족하면 24개월까지. 요청안이 제시한 구조(§12)가 실측으로 뒷받침된다. 24개월을 항상 기본으로 쓰지 않는 이유는, 오래된 거래일수록 시세 변동(문서 10 §13)이 반영되지 않아 "최근 비교"라는 취지에서 멀어지기 때문이다.

## 12. 실거래 대표값 (§13)

| 후보 | 평가 |
|---|---|
| 최근 거래 1건 | 단순하지만 §9에서 확인한 면적 분산 때문에 그 1건의 면적이 분양 타입과 정확히 일치하지 않을 수 있음(허용범위 내 최근접 1건이라면 유효) |
| 최근 3건 | 로열층/저층 편차를 어느 정도 완화하지만 거래가 적은 단지(§11 강서구 사례)에는 3건 자체가 없을 수 있음 |
| 중앙값 | 극단치(급매/직거래)에 덜 민감 — 표본이 적을 때(3건 미만)는 중앙값의 의미가 약함 |
| 평균 | 표본이 적을 때 극단치에 취약(문서 10 §13이 이미 지적) |
| 최저/최고 범위 | 분양가(범위)와 형식이 맞아 직관적이지만 "대표값"이라 부르기엔 편차 정보만 주고 중심값을 안 줌 |

**권장**: **허용범위(§9, ±1㎡) 내 최근 거래 최대 3건의 목록을 그대로 보여주고, 그 중앙값(또는 3건 미만이면 최근 1건)을 대표값으로 병기**한다. 단일 숫자로 뭉개지 않고 "최근 3건: 5.8억(26.07)/5.9억(26.06)/5.7억(26.05)" 처럼 원본을 노출하는 편이, 평균/중앙값 하나만 보여주는 것보다 문서 10 §22가 요구하는 "면책 설명"과 자연스럽게 어울린다.

## 13. 분양가 비교 기준 (§14)

Presale에는 `minPrice`/`maxPrice`(공고 전체), `PresaleHouseTypeDetail.topAmount`(주택형별 최고가)가 있다. §5~10에서 확인한 대로 이제는 **분양 주택형별 `topAmount`(전용면적 추정치 보유) ↔ 그 면적과 ±1㎡ 이내인 주변 실거래**를 짝지을 수 있다.

`Presale.maxPrice`(공고 전체 최고가) ↔ 주변 모든 아파트를 통짜로 비교하는 방식은 **채택하지 않는다** — 문서 10 §13이 이미 지적한 대로 면적이 다르면 비교 자체가 무의미하기 때문이다. **주택형 단위 비교만 한다.**

## 14. 평당가/㎡당 가격 (§15)

`topAmount`(만원)와 `houseTy` 앞자리(추정 전용면적, §8 "확인 필요" 상태)로 ㎡당 가격을 계산하는 것은 기술적으로는 가능하지만, **이번 버전에서는 넣지 않는다.**

- `houseTy` 앞자리가 공식적으로 전용면적이라고 확정되지 않은 상태에서(§8) 이를 분모로 쓴 "평당가"를 화면에 노출하면, 잘못된 전제 위에 숫자를 하나 더 만드는 것이 된다 — 원칙 #4(임의 값 생성 금지)와 같은 맥락의 위험.
- 실거래 쪽도 `excluUseAr`(전용면적, 공식 확정)와 `dealAmount`로 정확한 ㎡당가 계산은 가능하지만, 분양 쪽 분모가 불확실한 상태에서 한쪽만 정밀한 평당가를 보여주면 비교 자체가 비대칭적으로 오해를 부를 수 있다.

§8의 "확인 필요"가 해소된 이후 재검토 대상으로 남긴다.

## 15. 카드에 표시 가능한 정보 (§16)

`ApartmentMaster`(M4-B, §AA-7 확보율) 필드 기준.

| 필드 | 확보율 | 카드 표시 |
|---|---|---|
| 단지명(name) | 100% | **핵심(항상 표시)** |
| 거리(계산값) | 좌표 보유분 90.2% | **핵심** |
| 주소(roadAddress/jibunAddress) | 40.8%(건축물대장 확보율과 동일) | optional |
| buildYear(준공연도, MOLIT 원본) | 100% | **핵심** — 건축물대장 아니라 MOLIT 자체 제공 필드라 확보율이 다름(문서 15 §AA-7) |
| totalHouseholds(세대수) | 38.5% | optional("정보 없음"이면 숨김) |
| mainBuildingCount(동수) | 40.1% | optional |

**건축물대장 계열 필드(주소/세대수/동수)는 40% 안팎으로 누락이 많아 핵심 UI로 쓰지 않는다** — 문서 15 §AC-5가 이미 "Master identity 실패가 아닌 optional enrichment 한계"로 정리한 판단을 그대로 UI 설계에 반영한다. `buildYear`는 예외적으로 MOLIT 원본 필드라 100% 확보돼 있어 핵심 정보로 안전하게 쓸 수 있다.

## 17. 거래 없는 주변 아파트 처리 (§18)

§11에서 확인한 대로 6개월 기준으로도 약 21~27%의 후보가 거래가 없다.

**권장**: **카드에서 제외**한다(주변 아파트 "목록"에는 남기되, "가격 비교" 카드에는 노출하지 않음 — 요청안 §18 네 번째 후보 채택). "최근 거래 없음"이라고 굳이 표시해 카드 슬롯을 채우기보다, 실제로 비교 가능한 단지 위주로 §7의 정렬 정책(거래 있는 단지 우선)을 그대로 적용하는 편이 사용자에게 더 유용하다. 기간을 자동 확장하는 로직은 §11의 fallback 정책(전체 목록 기준)과 통합해서 처리하고, 개별 카드 단위로 별도 확장하지 않는다(복잡도 최소화).

## 18. 신축/분양권 특수상황 (§19)

§2에서 확인한 대로 프로덕션 라우트들은 `type='apt'`(`RTMSDataSvcAptTradeDev`, 매매 실거래)만 조회하며 분양권전매(`RTMSDataSvcSilvTrade`)나 전월세는 혼합하지 않는다. 주변 아파트 비교 기능도 동일하게 **매매 실거래만** 사용하면 되고, 이는 기존 코드 패턴을 그대로 따르는 것이라 별도 설계가 필요 없다. 입주 직전 신축이라 아직 매매 실거래가 없는 단지는 자연히 §18의 "거래 없음" 케이스로 처리된다(분양권 거래를 대체로 끌어오지 않음 — 혼합 시 발생할 수 있는 "분양권 웃돈"과 "완공 후 실거래가"의 혼동을 원천 차단).

## 19. 사용자 화면 정보 구조 (§20)

실제 구현은 하지 않으며, 아래는 §5~18의 실측 근거로 검증된 구조 제안이다.

```
주변 아파트 시세
이 분양단지 반경 [adaptive, §6] 내
최근 [6/12/24개월, §11] 거래가 있는 아파트입니다.

[아파트 A]  거리 420m · 2009년 입주
전용 59㎡대 최근 거래 3건: 5.8억(26.07) · 5.9억(26.06) · 5.7억(26.05)

→ 주변 실거래 중앙값 대비 약 +5,000만원

주변 실거래는 참고용이며 단지 연식·층·입지·상품 구성 등에
```

요청안 예시(§20)와 달리 "최근 실거래 1건"이 아니라 §12에서 정한 "최대 3건+중앙값" 구조로 조정했다 — 단일 거래의 대표성 부족(문서 10 §13) 문제를 완화하기 위함이다.

## 20. "이집 분석" 문구 정책 (§21)

투자 판단형 문구("주변보다 싸다", "적정 분양가다", "투자가치가 높다")는 **만들지 않는다**(요청 원칙 그대로 재확인). 대신 §19 예시처럼 **"주변 실거래 중앙값 대비 약 +OOOO만원"** 형태의 사실 기반 차액만 표시하고, 비교 조건(반경/기간/면적 허용범위)을 함께 명시해 사용자가 직접 판단할 수 있게 한다.

## 21. 면책/설명 UX (§22)

§19 예시의 마지막 줄("주변 실거래는 참고용이며...")을 **모든 비교 카드 하단에 고정 노출**할 것을 권장한다. 거래시점/층/향/동/옵션/신축여부/브랜드/단지규모 차이를 전부 나열하면 UI가 무거워지므로, 대표적으로 "연식·층·입지·상품 구성"만 언급하고 나머지는 생략한다(문서 10 §13이 확인한 위험 목록 중 사용자가 가장 쉽게 이해할 수 있는 항목 위주로 압축).

## 22. API 호출량/성능 실측 (§23, §25)

3개 대표 지역(동래구=밀집, 강서구=저밀도, 서구=중간)에서 **DB 반경검색 + MOLIT 24개월 순차 조회 + aptSeq 필터링**의 전체 처리시간을 실측했다.

| 지역 | 반경 내 후보 | DB 반경검색 | MOLIT 24개월(순차 24회 호출) | 원본 거래건수 |
|---|---|---|---|---|
| 동래구(1.5km) | 91 | 412ms | 6,078ms | 6,590 |
| 강서구(2km) | 3 | 43ms | 3,056ms | 2,906 |
| 서구(1.5km) | 28 | 40ms | 2,224ms | 1,722 |

**핵심 구조적 발견**: MOLIT 호출 수는 **반경 내 후보 수와 무관하게 lawdCd당 월 수(=24회)로 고정**된다 — 후보가 91개든 3개든 동일하게 24회만 호출하면 그 지역의 모든 후보를 한 번에 커버할 수 있다(§3에서 검증한 aptSeq 필터링 구조 덕분). 만약 후보 단지 각각을 개별 호출했다면 동래구는 91×24=2,184회가 필요했을 것이다 — **기존 `getOrSetCache`(lawdCd+월 키)를 그대로 재사용하면 이 24회조차 다른 Presale/사용자 요청과 공유**할 수 있다(§2).

**병렬화 효과**: 동래구 12개월을 `Promise.all`(기존 `/api/apt/[name]`의 chunk 패턴)로 병렬 호출하면 2,609ms — 순차 24개월(6,078ms)의 절반 기간을 절반 이하 시간에 처리해, 병렬화가 실질적인 개선을 준다는 것을 확인했다.

**응답시간 평가**: 캐시 미스 상태에서 순차 24개월 기준 2.2~6.1초는 상세페이지 첫 진입 시 다소 느리다. 병렬 chunk + 기존 in-memory 캐시를 결합하면 캐시 히트 시 1초 미만, 캐시 미스라도 3~4초대로 개선될 것으로 예상된다(병렬 24개월 실측은 이번 STEP에서 수행하지 않음 — 12개월 병렬 실측치로부터의 추정).

## 23. Cache 필요성 판단 (§24)

| 선택 | 판단 |
|---|---|
| A. 현재 실시간 API 구조로 그대로 구현 가능 | 응답시간(§22, 캐시 미스 시 최대 6초)을 고려하면 그대로는 다소 느림 |
| **B. 간단한 서버 cache 정도 필요** | ✅ — 기존 `getOrSetCache`(신규 인프라 아님) + 기존 병렬 chunk 패턴(신규 코드 아님, 재사용) 정도의 최소 보강으로 충분 |
| C. 실거래 DB cache(M4-C)가 먼저 필요 | 근거 부족 — §22에서 확인한 대로 MOLIT 호출 수 자체가 후보 수와 무관하게 lawdCd당 상한(24회)이 있어 트래픽이 폭증하지 않음 |

**M4-C(실거래 DB cache)는 P2-D4-B의 blocker가 아니다.** 기존 in-memory 캐시 재사용과 병렬 fetch 패턴 재사용만으로 실용적인 응답시간을 확보할 수 있을 것으로 판단한다(caching 계층의 정확한 히트율은 Vercel 서버리스 환경 특성상 실측하지 못했다 — §22 문서 10 §19-B의 한계가 그대로 남아있음, "확인 필요"로 남긴다).

---

## 24. 기존 /presales/[id] 구조와의 연결 (§26)

문서 09(P2-D3)의 섹션 순서(A.핵심요약 → B.청약일정 → C.주택형·분양가 → D.사업정보 → **E.위치정보** → F.청약홈CTA)를 그대로 유지하고, **주변 아파트 시세 섹션을 E(위치정보) 바로 다음, F(청약홈 CTA) 이전**에 추가할 것을 권장한다 — 사용자가 "이 위치가 어디인지" 확인한 직후 "이 위치 주변엔 뭐가 있고 얼마인지"로 자연스럽게 이어지는 정보 흐름이며, 기존 6개 섹션의 순서·레이아웃을 재작성하지 않고 새 섹션 하나만 끼워 넣는 최소 변경이다.

## 25. 지도와의 관계 (§27)

문서 09 §13이 이미 "인터랙티브 지도는 P2-D4에서 재검토"로 유보해뒀다. 이번 조사 결과, **주변 아파트 비교(가격/거리 텍스트+카드)와 지도 시각화는 독립적으로 구현 가능**하다는 것을 확인했다 — §5~18의 모든 설계가 좌표·거리 계산(서버/DB 단)에만 의존하며 지도 렌더링(클라이언트 SDK) 여부와 무관하다. **분리를 권장한다**:
- P2-D4-B1: 주변 아파트/실거래 비교(텍스트+카드, 지도 없음)
- P2-D4-B2: 지도 시각화(분양 마커+주변 단지 마커, `MapViewer.tsx`/`/map` 인프라 재사용)

지도까지 한 번에 만들면 스코프가 커져 검수 주기가 길어진다 — 먼저 B1로 핵심 가치(가격 비교)를 검증한 뒤 B2를 붙이는 순서가 안전하다.

## 26. 모바일 UX (§28)

주변 아파트가 밀집지역에서는 §7 정렬 후에도 최대 5개까지 나올 수 있다. **세로 카드 스택 + "더보기"(상위 3개 기본 노출, 나머지는 접기)**를 권장한다.

- 데스크톱 표 형태(❌): 이 프로젝트는 모바일 우선 원칙(문서 09가 이미 확립)이 있고, 표는 좁은 화면에서 가로 스크롤을 유발한다.
- 가로 스와이프 카드(△): 정보 밀도가 높은 카드(단지명+거리+면적+실거래+분양가차이 5줄)를 가로로 배치하면 한 카드 안의 줄바꿈이 부자연스러워질 수 있다.
- **상위 3개 세로 카드 + 더보기(권장)**: 문서 09 §8이 이미 확립한 `<details>/<summary>` 네이티브 아코디언 패턴을 재사용할 수 있어(신규 컴포넌트 최소화), "더보기" 클릭 시 나머지 카드를 펼치는 구조와 자연스럽게 맞는다.

## 29. 구현 단계 분리안 (§31)

요청안이 제시한 4단계(B1~B4)를 실측 결과에 맞춰 그대로 채택한다 — 불필요하게 단계를 더 쪼개지 않는다.

- **P2-D4-B1**: 주변 `ApartmentMaster` 검색 API(§5~7의 adaptive radius + 정렬 정책을 구현하는 신규 route, 예: `GET /api/presales/[id]/nearby`)
- **P2-D4-B2**: 실거래 연결(§3의 aptSeq 필터링 구조, §11 기간 fallback) + 면적 비교(§9~10)
- **P2-D4-B3**: 상세 UI(§19 카드 구조, §24 섹션 위치, §26 모바일)
- **P2-D4-B4**: 지도/고도화(§25의 B2, 이번 문서의 §25와는 별개 항목 — 지도 시각화)

B1~B3까지 완료하면 "가격 비교"라는 핵심 가치는 이미 사용자에게 전달된다. B4(지도)는 검증 후 우선순위를 다시 판단하는 것을 권장한다.

## 30. 발견된 기존 코드 문제

1. `fetchMolitData`(`src/lib/api-molit.ts`)가 MOLIT 원본에 있는 `aptSeq` 필드를 추출하지 않는다(§2, §3) — 프로덕션 실거래 조회 전체가 여전히 이름 매칭에만 의존 중. P2-D4-B1/B2 구현 시 이 파일을 확장하거나 별도 fetch 로직을 둘지 결정이 필요하다(이번 STEP에서 수정하지 않음).
2. `getOrSetCache`가 순수 in-memory라 Vercel 서버리스 인스턴스 재시작/분산 시 히트율이 보장되지 않는다(문서 10 §19-B, 이번 조사에서도 재확인만 하고 개선하지 않음).

## 발견된 데이터 문제

이번 STEP에서 새로 발견한 데이터 이상은 없다 — M4-B가 이미 발견·수정한 이슈(교차 aptSeq, sigungu 오염) 외에 추가로 발견된 것은 없으며, §9의 면적 분포처럼 "이상"이 아니라 "실제 시장의 정상적인 분산"으로 확인된 사항만 있다.

## 31. 최종 판단

### 판단: **B. 기능 구현은 가능하지만, 간단한 추가 기반작업이 먼저 필요**

**근거(5개 이내)**:

1. 문서 10(P2-D4-A)이 B판정을 내린 핵심 이유였던 "좌표 기반 아파트 마스터 부재"가 MASTER M4-B(부산 16개 구·군, 3,402건, 좌표 90.2%)로 해소됐다 — 이번 조사에서 실제로 그 위에서 반경검색(§5)·aptSeq 직접 연결(§3)이 실제 API/DB로 작동함을 확인했다.
2. `aptSeq` 기반 연결이 실측으로 100% 정확함을 확인했지만(§3), 프로덕션 `fetchMolitData`는 아직 이 필드를 쓰지 않는다 — **새 API route(P2-D4-B1/B2)가 필요**하고, 기존 `fetchMolitData`를 그대로 재사용할 수 없다(최소한 aptSeq를 추출하는 확장이나 별도 fetch 로직이 필요).
3. 응답시간(§22, 캐시 미스 시 2.2~6.1초)이 상세페이지 첫 진입치고는 느려, **기존에 이미 존재하는 병렬 chunk 패턴과 in-memory 캐시를 재사용하는 최소 보강**이 필요하다 — 이것이 B(간단한 기반작업)의 핵심 근거이며, 신규 인프라나 M4-C DB cache까지는 불필요하다(§23).
4. 면적 매칭(§8~10)의 핵심 전제("houseTy 앞자리=전용면적")가 55개 표본에서 매우 일관되게 재확인됐지만 공식 문서로 확정되지 않은 상태라, 면적 비교 기능은 "확인 필요" 라벨을 유지한 채 보수적으로("비슷한 전용면적", §10) 구현해야 한다 — 이는 기능을 막을 정도는 아니지만 설계에 신중함이 필요하다는 근거다.
5. 강서구 사례(§5, §11)처럼 지역 밀도 편차가 커서 고정 정책(고정 반경/고정 기간)으로는 부적절하고, adaptive radius(§6)+기간 fallback(§11) 같은 조건부 로직이 필요하다 — "그대로 구현 가능"(A)이라 하기엔 설계 디테일이 더 필요하고, "M4-C가 먼저 필요"(C)나 "신뢰 불가"(D)라 하기엔 근거가 부족하다.

P2-D4-B 실제 구현으로 넘어가지 않는다. M4-C, 재개발, 커뮤니티, 전국 ApartmentMaster 확장을 시작하지 않는다. 검수를 기다린다.
