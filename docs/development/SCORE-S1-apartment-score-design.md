이 문서 전체에서 제시하는 모든 coverage/분포 숫자는 production DB에 대한

`scripts/_score_s1_pilot.ts`)는 문서 작성 후 삭제하고 저장소에 남기지
않는다(지시사항 43).

## 4. V1 실행 가능성 재평가(원래 6분류를 그대로 쓰지 않음)

이 STEP의 목적이 "점수 구현이 아니라 정직한 설계"이므로, 원래 지시가
예시로 든 6개 카테고리를 억지로 채우지 않고 **실제 가능한 접근 방식별로
재분류**한다.

### 즉시 가능(persisted 데이터만으로, 배치 작업 없이)

- **단지 기본 정보 뱃지**: 준공연도(buildYear, 부산 100%), 세대수(있으면
  표시, 없으면 "확인 중") — 이건 이미 상세페이지 AptSpecGrid가 하고
  있는 일과 사실상 같다. 새로 "점수화"할 실익이 크지 않다.
- **주차 percentile(부산 서구 한정, 데이터 있는 26건끼리만)**: 표본이
  작아(26건) 신뢰구간이 넓다 — 표시는 가능하나 "confidence: LOW" 급.

### 배치 작업이 선행되어야 가능(스키마 변경 없이도 가능하나 별도 STEP 필요)

- **가격/가치**: 이미 검증된 MOLIT API 연동을 **부산 서구 171건에 한해
  배치로 1회 호출**하면(신규 schema 불필요, 기존 `RedevelopmentSourceRecord`
  같은 별도 캐시 테이블을 새로 만들 필요는 있음 — 이건 스키마 변경이라
  S1 범위 밖) 지역 내 상대 가격 위치를 계산할 수 있다. **이번 S1에서는
  실행하지 않음**, S2 전제조건으로만 기록.
- **교통/생활편의**: 마찬가지로 부산 서구 171건에 대해 배치로 한 번씩만
  Kakao/TAGO를 호출해 캐싱하면 벌크 스코어링이 가능해진다. 이것도 캐시
  테이블이 필요하므로 스키마 변경 — S1 범위 밖.

### V1에서 사실상 불가능(구조적 한계)

- **학군 품질**: NEIS에 진학률/학업성취도 데이터가 없다는 것은 이미
  이전 STEP(1.5-A, 50)에서 확정된 사실이고 이번 조사로도 재확인됐다 —
  "인근 학교 3곳"이라는 존재 정보만으로 "학군이 좋다/나쁘다"를 점수화하는
  것은 이 프로젝트의 원칙(추정 금지)에 정면으로 위배된다. **V1/V2
  어느 쪽에도 넣지 않고 NOT AVAILABLE로 유지**하는 것을 권고한다(향후
  학원가 밀집도, 학업성취도 공개 데이터가 나오면 재검토).

## 5. V1 최종 분류(원 지시의 6개 틀에 실제 결과를 매핑)

```text
교통       PARTIAL  (라이브 API로 개별 조회는 이미 상세페이지에 있음, 벌크 배치 캐시 없이는 스코어링 불가)
생활편의   PARTIAL  (동일 이유)
주차       PARTIAL  (부산만, coverage 15.2%로 낮음, confidence LOW 전제로만 가능)
학군       NOT AVAILABLE (진학률/학업성취도 데이터 소스 자체 없음 — V2에도 넣지 않음)
단지규모   PARTIAL  (부산만, buildYear는 100%지만 세대수 38.5%)
가격/가치  PARTIAL  (개별 정확, 배치 캐시 없이는 스코어링 불가)
```

**V1 INCLUDED가 하나도 없다는 게 이 STEP의 핵심 결론이다.** 이는 실패가
아니라 정직한 감사 결과다 — 억지로 하나를 "INCLUDED"로 우기지 않는다
(원칙 0).

## 6. 이집 기본점수 구조 제안(설계만)

```text
LEVEL 1  전국 공통 Core Score      → 현재 데이터로는 "부산 pilot Core"로 시작해야 함
LEVEL 2  지역 보정 Score           → 부산 내에서도 sigungu 단위조차 표본이 얕음(서구 171건이 그나마 최선)
LEVEL 3  개인화 My Score(V2)       → 회원 가중치 개인화, 이번 S1은 architecture만 언급
```

### Core 비중 제안

원 지시가 제안한 "Core 70~80% / 지역보정 20~30%"는 **지금은 근거가
없다** — 지역 보정을 논하려면 최소 2개 이상 지역에서 비교 가능한 데이터가
있어야 하는데, 현재 `ApartmentMaster`가 부산 하나뿐이라 "지역 간 차이"를
계산할 방법이 아예 없다. **제안: 지역 보정 비중을 0%로 시작**하고,
2번째 지역(예: 서울 강남 또는 인천)의 `ApartmentMaster`급 데이터가
확보된 뒤에 실제 분포를 보고 재조정한다.

## 7. 지역 보정 방식(장기 설계만, 지금 적용 안 함)

섹션 18의 "임의 rule보다 지역 데이터 분포 상대평가"에 동의 — 실제로
2개 이상 지역 데이터가 갖춰지면 `findNearbyApartments()`가 이미 하는
adaptive-radius 방식을 그대로 확장해, "시군구" 같은 행정구역 대신
**지리적 반경 기반 peer group**으로 상대평가하는 것을 제안한다(사람이
수동으로 시군구별 weight table을 만드는 방식은 배제 — 섹션 17이 이미
경고한 유지보수 문제와 정확히 같은 이유).

## 8. Peer Group 설계

**새로 설계하지 않고 기존 `findNearbyApartments()`를 재사용**하는 것을
제안한다:

```text
반경 1km → 부족하면 1.5km → 2km → 3km(최소 5건 확보까지 확장)
```

이미 프로덕션에서 검증된 로직(분양 인근 시세 비교 기능에 쓰이고 있음)이라
새로 만들 필요가 없다. 단, 표본이 5건 미만이면(부산 외곽 등) percentile
계산 자체를 하지 않고 "비교 단지 부족"으로 정직하게 표시해야 한다.

## 9. 결측치 처리 정책(제안)

```text
카테고리 데이터가 아예 없음        → 그 카테고리는 총점 계산에서 제외,
                                    나머지 카테고리 가중치로 재분배
카테고리 데이터가 있지만 표본(peer group) < 5건 → percentile 계산 안 함,
                                    "비교 데이터 부족"으로 표시
```

**0점을 주는 경우는 없다.** "데이터 없음"과 "나쁜 점수"를 구조적으로
분리한다(섹션 21 그대로).

## 10. 최소 데이터 충족 조건(제안)

coverage 실측 결과(주차 15.2%, 세대수 38.5%)를 보면, 지금 기준을 세게
잡으면 대다수 단지가 "점수 산정 준비 중"이 된다. **제안**:

```text
MIN_CATEGORIES = 1개 이상 카테고리에 실제 계산 가능한 데이터가 있으면
                  "부분 점수"로 표시(전체 100점 만점 점수는 아님)
전체 점수(0~100)는 배치 캐시가 갖춰진 이후(S2+) 카테고리 커버리지가
                  실제로 늘었을 때 재검토
```

## 11. 정규화 방식(제안)

원자값(raw value)이 아니라 **peer group 내 percentile**을 기본으로
한다(섹션 19 동의) — 단 peer group 표본이 통계적으로 유의미할 때만
(위 섹션 9 결측 정책과 연결). Z-score는 정규분포를 가정하는데 세대수/
주차대수처럼 오른쪽으로 긴 꼬리를 가진 분포(대단지 소수 + 소규모
다수)에는 percentile이 더 안전하다 — 실측 분포(주차대수 min 0.20 ~
max 2.05, median 1.14)로 봐도 극단값이 존재해 Z-score보다 percentile이
왜곡에 덜 취약하다.

## 12. Explainability 예시(실측 데이터 기반)

```text
"세대당 주차 1.27대, 부산 서구 내 상위 23%(비교 26개 단지 기준)"
"준공 2024년, 부산 서구 내 신축 상위 10%"
```

블랙박스 숫자가 아니라 "무엇과 비교해서 몇 %인지"를 항상 함께 보여주는
구조 — 이건 이미 `apt-brief.ts`가 "N건 평균으로 단일 이상치에 덜
흔들리게" 하는 것과 같은 철학이라 일관성 있다.

## 13. 부산 서구 pilot 시뮬레이션(read-only, DB 미저장)

`ApartmentMaster` 서구 171건 중 세대당 주차대수 계산 가능한 26건에서
10개 표본 추출, percentile만 시뮬레이션(실제 score 공식 아님):

## 14. Bias 검사 결과

- **대단지만 상위권?** → 표본상 그렇지 않음. 협성르네상스(489세대,
  2001년)가 8%로 최상위권, e편한세상송도더퍼스트비치(1,302세대,
  2024년)는 23%로 중상위 — 세대수와 주차percentile 사이에 명확한
  선형관계는 보이지 않는다(정성적 확인, 표본 26건이라 통계적 상관계수는
  계산하지 않음 — 표본 부족).
- **신축만 상위권?** → 아니다. 협성르네상스(2001년)가 1위, 대신해모로
  센트럴아파트(2022년)가 62%(중하위)로 준공연도와 순위가 단순 비례하지
  않음.
- **가격 bias** → 이번 pilot은 가격 데이터를 다루지 않아 확인 불가
  (F 카테고리 자체가 PARTIAL/배치 인프라 없음).
- **결측 bias** → **실제로 확인됨(중요)**: coverage 자체가 신축(27.7%)
  대 구축(10.5%)으로 2.6배 차이 난다 — 결측을 0점 처리했다면 구축 단지가
  구조적으로 불리했을 것이다. 위 섹션 9 정책(결측=카테고리 제외, 0점
  아님)이 이 문제를 막는 유일한 방법임을 실측으로 재확인.
- **이상치 발견**: 삼경빌라맨션(0.29대/세대, 1989년, 181세대)이 극단적
  저점 — 데이터 자체가 틀렸을 가능성(예: parkingCount가 부속 시설
  일부만 반영)과 실제로 주차가 부족한 노후 단지일 가능성을 구분할 수
  없다. **표본이 26건뿐인 상태에서 이런 극단값 1개가 median/percentile
  전체를 흔들 수 있다** — S2에서 이런 이상치에 대한 별도 검수 절차가
  필요하다는 신호로 기록한다.

## 15. DB 저장 여부(제안, migration 없음)

이번 S1에서는 schema를 건드리지 않았다. S2로 넘어갈 때 판단 기준:

```text
실시간 계산 전용(캐시 없음) → 라이브 API(Kakao/MOLIT/NEIS) 데이터는
  요청마다 재계산 비용이 크고 레이트리밋 위험 — 배치 캐시 테이블이

  추가 스키마 불필요.
```

## 18. 법적/신뢰 표현(제안)


"투자 추천"/"가격 상승 보장"/"교육 성과 보장"으로 읽히는 표현은
