## 3. 지역 집계 계약 (REGION AGGREGATION CONTRACT)

```
CURRENT_SCOPE  = lawd_cd 가 26* 인 16개 코드만 (allowlist 권장, LIKE 26% 는 차선)
LEGACY_SCOPE   = 해당 없음 (부산 legacy 코드 부재 — 정규화 매핑 불필요)
OUT_OF_SCOPE   = 27110(대구 중구), 11680(서울 강남구)
                 → 부산 시/구/동 리포트의 분자·분모 어디에도 포함하지 않는다.
                 → 행은 보존한다. 삭제·재매핑하지 않는다.
```

세부 규칙:

1. **부산 전체 리포트 분모** = 16개 코드 합. 2건의 비부산 코드는 제외.
   (제외해도 부산 총계는 변하지 않는다 — 애초에 부산이 아니다.)
2. **historical rows 롤업 불필요** — 부산에는 legacy 코드가 없다.
3. **2년/장기 윈도우** — 코드 변경이 없으므로 기간과 무관하게 동일 allowlist를 쓴다.
4. **한 아파트가 여러 lawd_cd에 걸치는가** → **4개 aptSeq가 2개 이상 lawd_cd에 존재**한다.
   반면 **dong이 2개 이상인 aptSeq는 0개**다.
   → 집계 귀속은 **아파트가 아니라 거래 행의 `lawd_cd`** 기준으로 한다(행 단위 귀속).
   단지 리포트에서 지역을 표기할 때는 최빈 lawd_cd가 아니라 **해당 거래의 lawd_cd**를 쓴다.
   4건은 소수지만 원인 미확인이므로 **추정 매핑을 만들지 않는다**.
5. **master 미매칭** — 부산(26*) 거래 중 `apartment_masters`에 매칭되지 않는 행이 **40,292건(4.7%)**

   (INNER JOIN 하면 4.7%가 조용히 사라진다).

### 4.1 cron 실제 가동 상태 (문서 불일치 정정)

`src/app/api/cron/sale-sync/route.ts` 주석은 "vercel.json에 cron이 등록돼 있지 않다"고
적고 있으나 **현재는 등록되어 실제로 돌고 있다.** `vercel.json`:

```
/api/cron/sale-sync?mode=apply     0 19 * * *   (UTC)
/api/cron/rent-sync?mode=apply     0 21 * * *
/api/cron/sale-recheck?mode=apply  0 23 * * *
```

관측된 runId가 정확히 일치한다: `sale-2026-09-09T19-59-…`, `rent-…T21-57-…`,
`sale-recheck-…T23-29-…`. **주석이 낡았다**(코드 동작 문제 아님, 이번 STEP에서 수정하지 않음).

> 시간대 주의: `created_at`은 **naive UTC**로 저장된다. KST = +9h.
> sale-sync 19:00 UTC = **04:00 KST 익일**, recheck 23:00 UTC = 08:00 KST 익일.
> 따라서 "KST 하루"의 관측 묶음은 전날 저녁(UTC) 실행분을 포함한다 — 일일 리포트의
> 날짜 경계를 UTC 기준으로 잡을지 KST 기준으로 잡을지 반드시 명시해야 한다.

## 7. 안전한 일일 리포트 규칙 (WITHHOLD 우선)

```
BACKFILL_SUSPECTED(day) :=
     COUNT(DISTINCT deal_ymd of rows created that day) > SALE_RECHECK_MAX_MONTHS_BACK(=12)
  OR MIN(deal_date of rows created that day) < (day - 12 months)
```
근거: 정기 sale/recheck 창의 상한(3개월 ∪ 3~12개월)을 벗어난 월은 정기 실행이 만들 수 없다.

두 조건 모두 위 실측표에서 **백필 2일만 잡고 정상 6일은 전부 통과**한다(오탐 0, 미탐 0).

## 8. 동기화 미실행 vs 진짜 0건

`SyncCoverageCell`은 `@@unique([dataset, lawdCd, dealYmd])`로 **upsert**되므로
**과거 날짜에 대해 "그날 검증됐는가"를 사후 재구성할 수 없다.** 최신 상태만 남는다.

따라서 게이트는 **"그날 그 실행이 있었는가"가 아니라 "지금 이 스코프가 검증된 상태인가"**로
정의해야 한다.

현재 상태 실측: SALE 202604~202608 **각 16/16 구 COMPLETE**(최종 검증 2026-09-09).
단 **202609(당월) coverage cell = 0** — 당월은 아직 COMPLETE로 검증된 적이 없다.
"오늘 새로 확인된 거래"는 대부분 dealYmd=202609이므로 **이 사실을 반드시 표기**해야 한다.

```
0건 처리:
  - BACKFILL_SUSPECTED 이거나 셀이 COMPLETE/EMPTY_VALID가 아니면

      → "오늘 새로 확인된 거래가 없습니다" (검증된 0건)
표기:
  - 제목은 "오늘 새로 확인된 실거래" (❌ "오늘 거래"/"오늘 계약")
  - 각 행에 실제 계약일 병기 (9/9 사례: 관측 89건의 계약일이 2026-02-10까지 소급)
```
