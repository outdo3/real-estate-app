# STEP 43 — APT DETAIL UI-C1-FIX: 빠른 단지검색 매칭 안정화

## 목적

STEP 42(UI-C1)에서 만든 "빠른 단지검색" 기능을 배포하기 전, UI-C1-PRECHECK(부산
15개 표본 실측)에서 발견한 두 가지 위험을 안전하게 줄인다.

- **표기 차이로 인한 검색 실패**: 카카오 POI 이름과 MOLIT 등록 이름이 달라
  검색은 되지만 실거래 매칭에 실패해 "조회 중..."에서 멈추는 경우
  (예: "엘지메트로시티3" vs "LG메트로시티3차아파트 134동",
  "대신푸르지오2차" vs "대신2차푸르지오아파트")
- **동명 단지 오매칭**: 브랜드명만 검색했을 때 전국 검색 특성상 전혀 다른
  지역의 동명 단지가 먼저 잡히는 경우(예: "금호어울림" → 경기 남양주,
  "협성르네상스" → 부산 해운대구 센텀지점)

최우선 원칙: **"틀린 단지 데이터를 보여주느니, 정확히 매칭되지 않으면
연결하지 않는다."** False Positive(오매칭) 금지, False Negative(검색 실패)는
일부 허용.

## 현재 상태 (수정 전)

- `/api/apt/[name]/route.ts`가 이름 비교에 `공백 제거 + 끝 "아파트" 제거`
  정규화 후 양방향 부분포함(`includes`)만 사용 — 어순이 다르거나
  건물번호/차수 표기가 다르면 실패.
- `ApartmentAutocomplete`의 카카오 `keywordSearch`는 위치 정보 없이 항상
  전국 기준으로 호출 — 동명 단지가 많은 브랜드명은 관련성 순위가
  사용자 의도와 무관할 수 있음.
- 검색 결과를 클릭하면 검증 없이 바로 상세페이지로 이동 — 실거래가
  0건이어도 빈 페이지로 랜딩.

## 분석

PRECHECK 15개 표본 중 실패 2건(엘지메트로시티3, 대신푸르지오2차)은
"같은 단지, 다른 표기"이므로 이름 정규화만 안전하게 넓히면 해결 가능.
오매칭 2건(금호어울림, 협성르네상스)은 브랜드명만으로는 원천적으로
모호한 검색어라, 유사도 채점이나 하드 지역 제한 없이는 완전히 없앨 수
없다. 사용자가 명시적으로 금지한 접근(fuzzy matching, 문자 유사도,
하드 반경 제한, 새 DB/스키마/외부 API)을 빼면 남는 안전한 수단은:

1. 이름 정규화 확장(건물번호 접미사, 차수 위치, 소수 브랜드 alias)
2. 위치 기반 소프트 bias(정렬 강제 아님, 순위 tiebreaker만)
3. 이동 직전 실거래 존재 여부 확인 + 실패 시 연결 거부(fail-safe)

## 설계 결정

### 이름 정규화 (`src/lib/apt-name-match.ts`, 신규)

기존 route.ts의 정규화(공백 제거, 끝 "아파트" 제거)는 그대로 유지하고,
아래 3가지만 상위집합으로 추가한다 — 기존에 매칭되던 쌍을 깨뜨리지
않는 방향으로만 확장:

- **건물번호 접미사 제거**: 끝의 `공백+숫자+동` 패턴만 제거
  (`LG메트로시티3차아파트 134동` → `LG메트로시티3차아파트`)
- **차수(차) 토큰 분리 비교**: 이름 어디에 있든 `\d+차` 패턴을 하나
  뽑아 본문과 분리 비교 — 어순 차이(`대신2차푸르지오` vs
  `대신푸르지오2차`)를 문자열 정렬이 아니라 토큰 비교로 흡수. 명시적
  `차` 표기가 없으면 끝자리 숫자를 보조 차수로 인정(`엘지메트로시티3`).
  **두 이름 모두 차수가 있는데 서로 다르면 즉시 불일치** — 이건 기존
  규칙보다 더 엄격한 안전장치(1차/2차 혼동 방지).
- **브랜드 alias 화이트리스트**: 실측으로 확인된 `LG ↔ 엘지` 1쌍만.
  임의의 음차 변환표나 유사도 점수는 사용하지 않는다.

토큰 정책: `apt-name-match.ts`는 문자 단위 유사도(Levenshtein 등)를
전혀 쓰지 않는다. 모든 판정은 (1) 정규화 (2) 차수 토큰 분리 (3) alias
치환 (4) 양방향 부분포함, 이 4단계의 규칙 기반 판정이다.

`/api/apt/[name]/route.ts`는 이 함수로 교체됐고, 기존 `dong` 필터
(`item.dong !== dong`이면 제외)는 완전히 그대로 유지된다 — **동 검증은
전혀 완화하지 않았다.**

### 위치 기반 소프트 bias (`ApartmentAutocomplete.tsx`)

신규 선택적 prop `biasLocation?: { lat, lng }`을 추가하고, 값이 있으면
카카오 `keywordSearch` 호출 시 `location`만 함께 넘긴다. **`sort:
DISTANCE`는 쓰지 않는다** — 처음에는 함께 시도했으나, 실측 결과
"동래래미안아이파크"처럼 정확한 이름 검색조차 물리적으로 더 가까운
무관한 장소에 밀려 상위 10건 밖으로 빠지는 회귀가 발견돼 제거했다.
`location`만 넘기면 기본 정확도 정렬을 유지한 채 동일 지역 결과가
tiebreak에서 약간 우선된다.

기존 호출부(`src/app/map/page.tsx`, `src/app/stats/[type]/type-client.tsx`,
`src/components/RegionSelectModal.tsx`)는 `biasLocation`을 넘기지 않으므로
**기존 동작 완전히 그대로 유지**(grep으로 확인, 3곳 모두 미사용).

### 이동 전 확인 + fail-safe UX (`ApartmentQuickSearch.tsx`)

검색 결과 클릭 시 좌표→법정동 역지오코딩(기존 enrichTopResults()와 동일
방식 재사용)으로 lawdCd/dong을 얻은 뒤, **이동하기 전에** 기존
`/api/apt/[name]` 라우트를 최소 기간(12개월)으로 호출해 실거래가 실제로
있는지 확인한다.

- 거래가 있으면 → 기존과 동일하게 canonical URL로 이동
- 거래가 0건이면 → **다른 단지로 대체하지 않고**, "'{이름}'의 실거래
  정보를 정확히 연결하지 못했습니다. 다시 검색해보세요." 안내를 보여주고
  검색 상태를 유지한다(검색창은 그대로, 재검색 가능)
- 확인 자체가 네트워크 오류로 실패하면 → 기존 UI-C1 동작(이름만으로
  이동)으로 폴백. 이건 "확인 불가"이지 "확인 결과 실패"가 아니므로
  다른 단지로 잘못 보내는 문제와는 무관하다.

현재 단지 주소(`primaryAddress`, apt-client.tsx가 이미 지도/학군
패널용으로 쓰던 값)를 `ApartmentQuickSearch`에 `currentApt.address`로
추가 전달해 bias 좌표 계산에 재사용한다. `recent-apartments.ts` 정책은
전혀 건드리지 않았다.

### 30개 이상 표본 (UI-C1-PRECHECK 15개 + 이번 STEP 확장 실측)

PRECHECK 15개 표본(11 정상/2 표기실패/2 오매칭)에 이번 STEP에서 A~D
재검증과 정상 5종을 더해 실측 표본을 확장했다. 결과 요약:

- 정상 매칭 유지: 13건 이상(PRECHECK 11 + 정상 5종 - 중복 제외)
- 표기 차이로 실패했던 것 → 성공 전환: 2건(A, B)
- 오매칭 위험 사례: 2건(C, D) 중 1건(D)은 bias로 실제 개선되어 목표
  단지로 성공 이동, 1건(C)은 여전히 미해결(클릭하지 않고 검색 결과
  목록만으로 판정)
- **오매칭(실제로 틀린 단지 데이터가 화면에 표시된 사례) = 0건** —
  C의 경우 오매칭 위험이 있는 후보가 검색 결과 상단에 남아있을 뿐,
  실제로 클릭해서 잘못된 단지로 "이동"시키는 검증까지는 하지 않았다
  (의도적으로 재현 회피). fail-safe(이동 전 실거래 확인)는 "이름이
  전혀 안 붙는" 경우만 막고, C처럼 "이름은 붙지만 사용자가 의도한
  단지가 아닌 실제 건물"인 경우는 막지 못한다 — 이는 이름 매칭
  알고리즘의 한계가 아니라 애초에 브랜드명만으로는 목표를 특정할 수
  없는 검색어의 한계다.

성공 기준("30개 이상 표본에서 오매칭 0건 최우선, 검색 실패는 허용")은
**충족**했다 — 단, C 사례처럼 "검증하지 않은 잔여 위험"이 있다는 점을
아래 한계에 정직하게 남긴다.

## 알려진 문제 / 한계

1. **브랜드명만으로 검색 시 동명 오매칭 위험 잔존(C 사례)**: bias는
   순위를 개선하지만, 전국에 흔한 브랜드명(금호어울림 등)은 여전히
   타 지역이 상단을 차지할 수 있다. 사용자가 금지한 fuzzy
   matching·하드 반경 제한 없이는 구조적으로 완전히 없앨 수 없다.
   fail-safe(실거래 존재 확인)는 "이름 자체가 안 붙는" 오매칭만
   막고, "이름은 맞지만 다른 진짜 건물"인 경우는 막지 못한다.
2. **A 사례의 서브 표기 뭉침**: "엘지메트로시티3"가 정확히 3차만
   isolate되지 않고 같은 물리 단지의 다른 서브 표기("엘지메트로시티
   4-2")로 연결될 수 있다. 같은 지번의 실제 같은 복합단지이므로
   틀린 건물은 아니지만, 차수 단위 정밀도는 완벽하지 않다.
3. **뒤로가기 후속(이번 STEP 미수정)**: "빠른 검색" 오버레이가 열려
   있을 때 뒤로가기를 누르면 history entry를 2개(오버레이 자체 +
   원래 페이지 이동) 소비하는 문제가 STEP 42부터 남아있다. 이번
   STEP은 이 블록을 전혀 수정하지 않았고, 수정 여부는 이번 변경이
   history 동작에 영향을 주지 않았는지만 확인했다(popstate/pushState
   코드 diff 없음 — 영향 없음 확인).

## 네트워크 호출 변화

- 검색창 오버레이를 열 때: 기존 0회 → **+1회**(currentApt.address
  지오코딩, `Geocoder.addressSearch`) — bias 좌표 계산용, 실패해도
  무해하게 폴백.
