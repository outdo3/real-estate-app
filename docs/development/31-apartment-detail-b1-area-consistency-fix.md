## 1. FIX-1 — 면적 chip 표시 충돌 해결

### 1.1 문제

STEP 30에서 도입한 기본 2자리 반올림 정책은 84㎡대 다중 타입은 잘 구분했지만, 실측
사례(대신롯데캐슬) `59.8826㎡`/`59.8839㎡`처럼 2자리에서 반올림하면 둘 다 `59.88㎡`로
같아지는 경우가 있었다.

### 1.2 정책 — "충돌한 값만" 정밀도 확장

`src/lib/area-utils.ts`에 `getUniqueAreaLabels(rawAreasM2: number[]): Map<number, string>`
신설. 단일 값 포맷터(`formatExclusiveArea`, 기본 2자리)와 "같은 목록 안에서 라벨이
겹치는 값만 필요한 만큼만 정밀도를 올리는" 책임을 분리했다:

1. 2자리로 전체 라벨을 만든다.
2. 라벨이 겹치는 값들만 모아 3자리로 다시 시도.
3. 그래도 겹치면 4자리로 다시 시도.
4. 4자리(정밀도 상한)에서도 겹치면 — 사실상 동일한 면적으로 보고 더 늘리지 않는다.
5. 이미 어느 단계에서 유일해진 값은 그 즉시 확정하고, 목록의 나머지 값에 영향을
   주지 않는다(일부 충돌 때문에 전체 목록의 정밀도를 함께 올리지 않음).

정밀도 상한 4자리는 추측이 아니라 부산 5개 단지 1,800건+ 실측(대신푸르지오1차 443건,
대연힐스테이트푸르지오 1,422건 등)에서 관찰된 MOLIT 원본 최대 소수 자릿수를 근거로
정했다.

### 1.3 formatter와 selector 책임 분리 (요청사항 반영)

- `formatExclusiveArea(m2)` — 단일 값, 기본 2자리. 변경 없음(내부 구현은 정밀도
  파라미터화로 리팩터링했지만 동작은 동일).
- `getUniqueAreaLabels(areas)` — 목록 전체를 받아 충돌 해소 라벨 맵을 만든다.
- `resolveAreaLabel(m2, labels?)` — 맵에서 조회, 없으면 `formatExclusiveArea`로 안전
  fallback.
- `getAreaDetailLabel(m2, labels?)` — Hero/헤더용 "전용 OO㎡ · 약 OO평". `labels`를
  넘기면 충돌 해소된 라벨을 쓰고, 안 넘기면 기본 2자리.

internal area key(원본 area 문자열/숫자)는 어디서도 만들거나 바꾸지 않았다 — 세
함수 모두 표시 문자열만 반환한다.

### 1.4 영향 범위 — 어디에 적용했고, 어디는 안 했는가

**같은 페이지 안에서 "여러 면적이 나란히 보이는" 곳(AreaSelector 칩·전체 평형
드롭다운, TradeTimelineList 행, ai-search.ts의 비교 카드 평형 옵션)** 은 전부
`getUniqueAreaLabels()`로 계산한 하나의 라벨 맵을 공유하도록 만들었다. 그 근거:

> 사용자가 칩에서 "59.883㎡"를 선택했는데 거래목록 같은 행이 "59.88㎡"로 다르게
> 보이면, 애초에 이번 STEP이 해결하려던 "같은 면적처럼 보이는데 실제로는 다른
> 값"이라는 혼란을 페이지 안에서 새로 만드는 셈이다. 따라서 **동일 페이지에서 같은
> 원본 면적은 항상 같은 라벨**을 쓰는 쪽을 선택했다(스펙이 명시한 두 옵션 중 후자).

이를 위해 라벨 맵을 **부모(apt-client.tsx)가 이 단지의 전체 거래(`trades`, 필터
무관) 기준으로 한 번만 계산**하고, `AreaSelector`/`TradeTimelineList`/`FloorPlanPanel`
전부에 prop으로 내려준다(`areaLabels?: Map<number, string>`). 부모가 아니라 각
컴포넌트가 자기 `trades`/`filteredTrades` prop만 보고 각자 계산하면, 평형이 이미
선택된 상태의 `TradeTimelineList`는 그 시점에 오직 한 종류 면적만 받으므로 애초에
"충돌"을 판단할 근거 자체가 없어져 칩과 다른(더 짧은) 라벨을 낼 위험이 있었다 —
그래서 계산 지점을 부모 하나로 모았다.

**단일 값만 보여주는 곳**(예: FloorPlanPanel의 "OO㎡ 평면도 준비 중" 헤드라인)도
동일한 원칙(같은 면적 = 같은 라벨)을 위해 같은 맵을 받아 쓰도록 했다 — 이 패널은
"준비 중" placeholder라 리스크는 낮지만, prop 하나 추가하는 비용이 낮고 페이지
전체 일관성을 지키는 쪽이 더 안전하다고 판단했다.

**ai-search.ts의 비교 카드** — `areaOptions`도 "이 단지 안에서 비교할 평형을 고르는"
선택지 목록이라 AreaSelector와 동일한 성격의 UI다. 해당 단지의 `areaEntries` 전체
기준으로 독립적으로 `getUniqueAreaLabels()`를 호출한다(별도 API 응답이라 `/apt/[name]`
과 라벨 맵을 공유하지는 않지만, 같은 정책·같은 함수를 쓰므로 같은 입력에는 같은
결과가 나온다).

## 2. FIX-2 — Hero 거래 데이터 일관성 버그

### 2.1 원인

`apt-client.tsx`의 `latestPrice`는 원래도 `filteredTrades[0]`(선택 평형 + 매매/전월세
필터 반영)을 우선 쓰고 있었다. 그런데 Hero의 면적·층·거래일은 이 값과 무관하게
항상 `trades[0]`(필터 전 전체 거래 중 최신 1건)을 따로 참조했다 — 평형을 선택하면
가격은 그 평형 기준으로 바뀌는데 층/거래일은 다른 평형의 최신 거래가 그대로 남는
불일치였다.

### 2.2 수정 — 단일 source-of-truth

```
const heroTrade = filteredTrades.length > 0 ? filteredTrades[0] : (trades.length > 0 ? trades[0] : null);
```

`latestPrice`가 이미 쓰던 것과 동일한 우선순위(필터링된 결과 → 없으면 전체 최신)를
따르는 단일 거래 객체를 만들고, Hero의 가격·면적·층·거래일 전부 이 객체 하나에서만
가져오도록 했다. `latestPrice`/`latestPriceNum` 자체의 계산식은 건드리지 않았다
(대출한도 계산에 쓰이는 `latestPriceNum`은 원래도 필터 결과가 없으면 0으로 떨어지는
의도된 비대칭이 있어 그대로 유지 — 이번 FIX 범위 밖).

매매/전세 토글은 이미 `filteredTrades`의 필터 조건(`tradeTypeFilter`)에 포함돼
있었으므로 `heroTrade`가 자동으로 "선택 평형 + 선택 매매/전세의 최신 거래"가 된다 —
별도 로직을 새로 만들지 않고 기존 필터 체인을 그대로 재사용했다.

### 2.3 fallback 동작(데이터 없는 경우)

선택된 평형에 현재 매매/전월세 타입의 거래가 하나도 없으면(예: 그 평형이 매매만
있고 전월세 기록이 없는 경우) `filteredTrades`가 비어 `heroTrade`가 `trades[0]`
(그 타입의 전체 최신 거래)로 fallback한다 — 이 경우 Hero에 표시되는 면적이 칩에서
선택한 면적과 다를 수 있다. 이는 새로 만든 동작이 아니라 `latestPrice`가 이미 갖고
있던 기존 fallback을 층/거래일에도 동일하게 맞춘 것뿐이며, 최소한 Hero 안의
가격·면적·층·거래일 네 값은 항상 서로 같은 거래를 가리키도록(내부적으로는 일관되게)
보장한다. 실측(§5)에서 재현하고 의도된 동작임을 확인했다.
