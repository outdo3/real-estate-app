# STEP R1 — Redevelopment Data Source Audit

상태: **조사 완료 — DB/schema/migration/UI 변경 없음**

## 목적

전국 재개발·재건축 데이터의 실제 원천을 확인하고, 전국 커버리지·
API 가용성·필드·진행단계 체계를 실측 데이터 기준으로 비교해
이집 재개발 Master DB의 후보 데이터 구조를 판단한다. 이번 STEP은
조사만 하며 DB/schema/migration/UI는 건드리지 않는다.

## 현재 프로젝트 상태

`/redevelopment` 화면(`src/app/redevelopment/redevelopment-client.tsx`)은
"재개발·재건축 구역 정보 연동 준비 중입니다" 안내 카드만 보여주는
정직한 placeholder다(실제로 미연동 상태를 오류로 위장하지 않음).
데이터를 가져오는 API route나 mock 데이터는 없다.

Prisma에는 이미 스키마가 준비돼 있다(`prisma/schema.prisma`):

```prisma
enum RedevelopmentStage {
  ZONE_DESIGNATED               // 구역지정
  UNION_ESTABLISHED             // 조합설립
  PROJECT_APPROVED              // 사업시행인가
  MANAGEMENT_DISPOSAL_APPROVED  // 관리처분인가
  RELOCATION_DEMOLITION         // 이주철거
  CONSTRUCTION                  // 착공
}

model RedevelopmentProject {
  id, zoneName, lawdCd, stage, targetHouseholds,
  polygonGeojson (Json?, 좌표 확보 전까지 null), lat, lng
  @@map("redevelopment_projects")
}
```

`src/services/publicDataService.ts`의 `upsertRedevelopmentProject()`가
이 테이블에 쓰는 저장 함수만 제공하며, 코드 주석이 이미 "정비사업
진행단계는 전국 통합 공공데이터가 없고(구청/조합 공고, 정비사업
정보몽땅 등 지자체별 비정형 소스), 수동 입력 또는 지자체별 크롤러가
필요하다"고 명시해뒀다. 이번 STEP은 이 가정을 실제 데이터로
재검증하는 작업이다.

**결론(선반영)**: 이 가정은 부분적으로만 맞다 — 전국 단위 공공데이터
자체는 존재하지만(후보 A), 필드가 매우 얕고 좌표가 없다. 부산은
지자체 자체 API(후보 C)가 있어 훨씬 풍부하지만 이마저 실측에서
데이터 누락이 발견됐다(아래 참고).

  기존 Prisma `RedevelopmentStage` enum(6단계)보다 훨씬 세밀하고,
  "이주철거"는 실측 값에 없는 대신 "이전고시"·"조합해산"·"해제"가

  삼아야 한다(이번 STEP에서는 스키마 변경하지 않음).
- **사업유형**: 전용 필드가 없어 `areaName` 접미사로 추정(공식
  분류 아님, 참고용):

  ```text
  재개발: 171건 / 재건축: 67건 / 가로주택정비: 56건 / 소규모재건축: 49건
  (합계 343 — 전수 일치)
  ```

- **좌표/폴리곤**: 필드 자체가 없음(23개 키 중 lat/lng/geometry
  계열 전무). `location`은 자유 텍스트이며, 프로젝트 현장 주소
  ("동래구 명장동 623번지 일원")와 조합 사무실 주소("남구 수영로
  26(문현동, 문현대림시티프라자 상가 208호)")가 뒤섞여 있어 형식이
  일관되지 않는다.
- **부산 구·군별 대략 분포**(location 텍스트에 구/군명이 직접
  포함된 경우만 정규식으로 집계 — 268/343건 중 148건만 매칭,
  나머지 195건은 구/군명이 텍스트에 없어 미집계):

  ```text
  연제구 21 / 동래구 18 / 해운대구 18 / 부산진구 17 / 북구 14 /
  수영구 13 / 동구 11 / 사하구 11 / 남구 8 / 영도구 5 / 금정구 4 /
  사상구 4 / 중구 3 / 기장군 1 / 서구 0 / 강서구 0
  ```

- **부산 서구 검증 — 중요한 데이터 품질 문제 발견**: `location`
  필드는 물론 `areaName`, `businessEntities` 등 전체 응답 원문을
  대상으로 "서구" 문자열을 직접 grep했으나 **343건 전체에서 단
  한 건도 나오지 않았다**(정규식 매칭 실패가 아니라 원본 데이터
  자체에 없음, raw grep으로 재확인). 그런데 외부 검색(공공데이터
  포털 밖)으로 확인한 결과 **부산 서구에는 실제로 진행 중인
  재개발 구역이 존재한다**(아미동 재개발, 서대신4구역 재개발 등 —
  서구청 자체 게시판·부동산 정보 사이트에서 확인). 즉 **부산시
  자체 API가 서구 사업장을 누락하고 있을 가능성이 높다** — 이
  API를 그대로 Master로 쓰면 이집의 초기 타깃 지역인 서구가
  통째로 빠지는 심각한 데이터 갭이 생긴다. 원인은 이번 STEP에서
  확정하지 못함(서구청 자료 미연동 vs API 필터링 문제 등) — R2에서
  반드시 재확인 필요.

## 진행단계 distinct 정리

- **A**: 숫자 코드형("N)단계명"), 표본에서 1·3·4·5·6·7 확인, 전체
  범위 미확정(전체 파일 필요)
- **B**: `PRGRS_STP_CN` 필드는 명세됐으나 API 미승인으로 실값 미확인
- **C**: 12종 전수 확보(위 목록) — 이번 STEP에서 가장 신뢰할 수
  있는 실측 데이터

## 좌표/지도 가능성

세 후보 전부 **위도/경도/폴리곤 필드가 없다**. 정비구역 경계
(polygon)는 이번 STEP에서 구현하지 않으며, 향후 필요 시:

- 지오코딩(주소 → 좌표): 이 프로젝트가 이미 Kakao Geocoder를
  다른 기능(아파트 상세, 지도 검색)에 쓰고 있어 재사용 후보 —
  단, 후보 A/B는 주소가 아예 없어(시군구까지만) 지오코딩 자체가
  불가능하고, 후보 C만 부분적으로(78% location 필드) 시도 가능.
- 정비구역 경계(polygon): VWorld, 지자체 공간정보포털의 SHP/WFS/WMS
  레이어가 별도 후보로 필요할 수 있음(이번 STEP에서 실제 조사는
  하지 않음, 후보로만 기록).

## 데이터 최신성

- A: 연간 갱신, 최근 등록 2026-07-01 — 상대적으로 최신이나 다음
  갱신까지 1년 격차.
- B: 연간 갱신, 등록 2026-08-04(가장 최근) — 다만 참여 기관 자체가
  적어 "최신"의 의미가 제한적(늘어날 데이터가 애초에 적음).
- C: 포털에 "실시간"으로 명시돼 있으나, 서구 데이터 누락 사례처럼
  실제 완전성은 별도 검증이 필요함이 이번 조사로 드러남.

## 데이터 품질 문제

1. **후보 B는 이름과 실제 커버리지가 크게 다르다** — "전국"이라는
   이름에도 9개 기관만 참여, 사용자가 사전에 우려한 대로 확인됨.
2. **후보 C(부산 API)의 서구 데이터 누락** — 실제 존재하는 서구
   재개발 사업(아미동, 서대신4구역 등)이 API 응답에 전혀 없음.
   이집의 초기 타깃 지역이 통째로 빠지는 심각한 문제.
3. **좌표 필드가 세 후보 모두 없음** — Master로 삼을 어떤 후보를
   쓰더라도 지도 표시를 위해서는 반드시 별도 지오코딩 단계가
   필요하다.
4. **location 필드(후보 C) 형식 불일치** — 현장 주소와 조합
   사무실 주소가 섞여 있어 단순 텍스트 매칭으로는 구/군 귀속을
   43%(148/343)밖에 못 정한다.
5. **후보 A/B는 재개발과 재건축을 실제로 구분할 수 있지만(코드
   필드), 후보 C는 공식 필드가 없어 이름 텍스트로만 추정** —
   추정 정확도는 검증되지 않았다.

## Master 후보

**후보 A(국토부 전국 통합 데이터)를 전국 존재-확인/카운트용
Master 후보로 우선 검토한다** — 사용자가 제시한 "후보 A" 구조
(국토부 전국 통합 = Master, 부산 API = 상세 보강)가 실측 데이터로
가장 근접하게 뒷받침됨. 근거:

- 국토부가 직접 제공하는 유일한 진짜 전국 데이터(1,566건)이고,
  코드화된 진행단계/유형 필드가 있어 향후 표준화 기반으로 쓸 수
  있다.
- 후보 B는 9개 기관만 참여해 Master로 쓰기엔 커버리지가 지나치게
  좁고, API 자체도 현재 호출 불가 상태다.

단, 후보 A는 주소·좌표가 전혀 없어 "Master"라기보다는 "전국 존재
인덱스"에 가깝다 — 상세 정보(주소/시공사/세대수 실측치/이미지)는
지역별 API로 보강해야 실사용 가능한 수준이 된다.

## Regional enrichment 후보

**부산은 후보 C(부산광역시 정비사업 API)를 상세 보강 소스로
검토한다** — 필드가 가장 풍부하고(23개), 실제 API 호출도 성공했다.
다만:

- 서구 데이터가 통째로 빠져있는 문제를 R2에서 반드시 재확인해야
  한다(원인 규명 또는 대체 소스 확보 없이는 이집 초기 타깃 지역을
  이 소스만으로 커버할 수 없음).
- 좌표가 없어 location 텍스트(78% 채움) 기반 지오코딩이 필요하고,
  그마저 현장 주소/조합 사무실 주소가 섞여 있어 정확도 검증이
  선행돼야 한다.

부산 외 지역은 이번 STEP에서 지자체별 API를 조사하지 않았다
(범위 밖) — 다른 광역시/도 확장 시 각 지자체가 부산처럼 자체
data.go.kr API를 운영하는지 별도 조사가 필요하다.

## BLOCKER

**하드 BLOCKER 없음** — 조사 자체는 완료했다. 다만 R2 진행 전
반드시 짚어야 할 제약 3가지:

1. **후보 B API 미승인(403)** — data.go.kr에서 별도 활용신청 필요,
   승인 소요 시간 불확실(자동승인 여부 페이지에 명시 안 됨).
   Master 후보에서는 이미 제외했으므로 진행 자체를 막지는 않음.
2. **후보 A의 부산 포함 여부 미확정** — 전체 CSV(1,566행) 다운로드
   후 재확인 필요.
3. **부산 API 서구 데이터 누락** — 원인 미상, 대체 소스(서구청
   직접 크롤링 등) 검토가 필요할 수 있음.

## STEP R2 권장사항

1. 후보 A의 전체 CSV(1,566행)를 다운로드해 실제 부산 포함 건수와
   진행단계/유형 코드의 전체 범위(1~n)를 확정한다.
2. 후보 B는 data.go.kr에서 활용신청을 넣고 승인 후 실제 호출
   재시도(승인 자동/수동 여부 확인 포함) — Master 후보가 아니므로
   급하지 않음.
3. 부산 API의 서구 데이터 누락 원인을 부산시 정비사업 통합홈페이지
   (dynamice.busan.go.kr)와 대조해 재확인한다.
4. 지오코딩 전략(기존 Kakao Geocoder 재사용 가능성) 및 좌표 확보
   방법을 후보 C의 location 필드 기준으로 설계한다.
5. 위 결과를 바탕으로 그때 처음으로 `RedevelopmentProject` 스키마
   개편 여부(현재 6단계 enum → 실측 12단계 기준 재설계 등)를
   논의한다 — 이번 R1에서는 스키마를 건드리지 않았다.
