## A. 표본 조사 방법

- Detail: `page=1&perPage=50` **단 1회 호출**로 50건 확보(반복 호출 최소화를 위해 필요한 표본을 한 번에 큰 페이지로 가져옴).
- 확보된 50건의 실제 유형 분포: `HOUSE_SECD_NM` 기준 APT(민영/민간) 46건, 신혼희망타운(공공) 4건. `HOUSE_DTL_SECD_NM` 기준 민영 40건, 국민(공공) 10건. 지역(`SUBSCRPT_AREA_CODE_NM`) 기준 경기 20 / 경남 9 / 서울 6 / 부산 3 / 충남 3 / 강원 2 / 제주 2 / 대구·세종·울산·전북·경북 각 1 — 민간분양·공공분양(신혼희망타운 포함)·다양한 지역이 모두 포함된 표본임을 확인했다.
- Mdl(주택형별): 위 50건 중 유형이 서로 다른 4건(공공 신혼희망타운 1건 + 민영 APT 3건, 지역도 성남/서울×2/용인으로 분산)을 선택해 각각 조회(각 `perPage=10`).
- 가격 검증을 위해 이 중 3건을 실제 뉴스 보도와 교차검증했다(§G).
- 원본 응답은 이번 세션의 로컬 스크래치 파일에만 저장했고, 이 문서와 저장소에는 raw JSON 전체를 커밋하지 않았다(요청대로 구조 중심으로만 기록).

## B. 고유 식별자

- 50건 표본 전체에서 `HOUSE_MANAGE_NO`는 **null 0건, 빈 문자열 0건, 중복 0건**(50/50 유니크) — 안정적 식별자로서의 조건을 표본 내에서는 충족한다.
- `HOUSE_MANAGE_NO == PBLANC_NO`가 **50건 전부에서 성립**했다. P1에서는 "표본이 적어 일반화 불가"로 남겨뒀으나, 이번 50건 확장 표본에서도 예외 없이 동일했다 — 다만 50건도 전체 2,843건의 일부일 뿐이므로 "항상 같다"고 100% 단정하지는 않는다(과거 공고나 특수 케이스에서 달라질 가능성은 남겨둔다).
- 형식: 10자리 숫자 문자열, 앞 4자리가 연도로 보임(`"2026..."`, `"2027..."` 등 발생 가능성 있음 — 이번 표본은 전부 2026년 공고).
- **판단**: `Presale.houseManageNo`의 현재 `@unique` 제약은 Detail 레벨(공고 1건 = row 1개) 저장에는 **표본 범위 내에서 충분**하다고 판단한다. 다만 Mdl(주택형별) 데이터를 저장하려면 별도 식별자 전략이 필요하다(§O).

## C. 주택 유형

50건 표본에서 관측된 실제 값:

| `HOUSE_SECD` | `HOUSE_SECD_NM` | 건수 |
|---|---|---|
| `01` | `APT` | 46 |
| `10` | `신혼희망타운` | 4 |

| `HOUSE_DTL_SECD` | `HOUSE_DTL_SECD_NM` | 건수 |
|---|---|---|
| `01` | `민영` | 40 |
| `03` | `국민` | 10 |

**핵심 발견**: `HOUSE_SECD_NM`은 코드의 `mapHouseType()`이 기대하던 `"오피스텔"`/`"도시형생활주택"`/`"잔여"`/`"무순위"` 같은 한글 풀네임이 **50건 표본 전체에서 단 한 번도 나오지 않았다.** 대신 `"APT"`(영문 코드성 문자열)와 `"신혼희망타운"`(주택 유형이 아니라 공급 프로그램명)만 관측됐다.

이는 우연이 아니라 구조적인 이유로 보인다: 이번에 조사한 endpoint(`ApplyhomeInfoDetailSvc/v1/getAPTLttotPblancDetail`)는 이름 그대로 **"APT" 전용 조회 서비스**다. 공공데이터포털에는 이 API와 별개로 오피스텔/도시형생활주택/생활숙박시설 등을 위한 **별도의 엔드포인트 계열**이 존재하는 것으로 보인다(이번 P2-A에서 실제로 호출해 확인하지는 않았음 — 추측이 아니라 "확인하지 못했다"는 사실만 기록). 즉 `PresaleHouseType` enum의 `OFFICETEL`/`URBAN`은 **지금 연동 중인 API(APT 전용)만으로는 원천적으로 채워질 수 없는 값**일 가능성이 높다 — 이는 필드 매핑 버그 수준이 아니라 "어떤 API를 몇 개 더 연동해야 하는가"의 아키텍처 질문이다.

**저장 방식 제안**: 원칙(공식 API 원본 의미 보존, 불필요하게 자체 enum으로 축소하지 않음)에 따라, 현재처럼 `PresaleHouseType`(4종 enum)으로 강제 변환하기보다 **원본 `HOUSE_SECD`/`HOUSE_SECD_NM` 값을 그대로 저장할 별도 컬럼을 두고, `PresaleHouseType`은 "이 API가 실제로 커버하는 범위(APT)"를 반영하도록 재정의하거나, 오피스텔/도시형 등 다른 API 계열을 실제로 연동하기 전까지는 사용하지 않는 것**을 권고한다(확정은 P2-B에서).

## D. 분양/임대 구분

50건 표본에서 관측된 값:

| `RENT_SECD` | `RENT_SECD_NM` | 건수 |
|---|---|---|
| `0` | `분양주택` | 49 |
| `1` | `분양전환 가능임대` | 1 |

단순한 "분양 vs 임대" 이분법이 아니라 **"분양전환 가능임대"라는 중간 범주가 실제로 존재함**을 확인했다(순수 임대와도, 순수 분양과도 다른 성격). 이번 P2-A에서는 요청대로 어떤 유형도 삭제·제외하지 않았고, 단지 값의 존재만 확인했다.

**저장/필터 정책 제안**:
- 원본 `RENT_SECD`/`RENT_SECD_NM` 값을 그대로 보존하는 컬럼을 둔다(임의로 "분양"/"임대" 2분법으로 뭉개지 않는다).
- 향후 UI에서는 "분양주택"을 기본 노출로 하되, "분양전환 가능임대"는 별도 배지나 필터로 구분 표시하는 방향을 검토할 수 있다(최종 UI 정책은 이번 문서에서 확정하지 않음).
- 50건 표본에서 순수 "임대주택"(전환 불가능한 장기임대 등) 값은 관측되지 않았다 — 더 큰 표본에서 다른 값이 나올 가능성은 열어둔다.

## E. 청약 접수기간

P1에서 "9종의 세분화된 순위/지역별 접수기간 중 무엇을 대표값으로 쓸지" 정책 결정이 필요하다고 남겼던 부분을, 50건 표본 검증으로 **명확히 해결**했다.

**세부 필드별 non-null 비율(50건 중)**:

| 필드 | non-null | 의미 |
|---|---|---|
| `RCEPT_BGNDE` / `RCEPT_ENDDE` | **50/50** | (아래에서 확인) 전체 접수기간의 대표값 |
| `SPSPLY_RCEPT_BGNDE` / `ENDDE` | 39/50 | 특별공급 접수기간 |
| `GNRL_RNK1_CRSPAREA_*` | 50/50 | 1순위 해당지역 접수기간 |
| `GNRL_RNK1_ETC_AREA_*` | 50/50 | 1순위 기타지역(수도권 등) 접수기간 |
| `GNRL_RNK1_ETC_GG_*` | 7/50 | 1순위 기타경기 접수기간(경기 지역 공고에서만 사용되는 것으로 보임) |
| `GNRL_RNK2_CRSPAREA_*` / `ETC_AREA_*` | 50/50 | 2순위 접수기간 |
| `GNRL_RNK2_ETC_GG_*` | 7/50 | 2순위 기타경기 |

**핵심 발견**: `RCEPT_BGNDE`는 **50건 전부에서 정확히 "특별공급 시작일 포함 모든 세분화 시작일 필드 중 가장 이른 날짜"와 일치**했고, `RCEPT_ENDDE`는 **50건 전부에서 정확히 "모든 세분화 종료일 필드 중 가장 늦은 날짜"와 일치**했다(프로그램으로 직접 비교 계산해 확인, 예외 0건).

즉 **API가 이미 "가장 빠른 시작 ~ 가장 늦은 종료"라는 대표값을 `RCEPT_BGNDE`/`RCEPT_ENDDE`로 별도 제공하고 있었다** — 이 두 필드를 직접 사용하면 되고, 세분화 필드들을 순회하며 min/max를 계산하는 로직을 새로 만들 필요가 없다.

**정책 확정**:
- `Presale.receiptStartDate` ← `RCEPT_BGNDE`
- `Presale.receiptEndDate` ← `RCEPT_ENDDE`
- (P1에서 제안했던 "9종을 순회해 직접 min/max 계산" 방식은 불필요함이 확인됐다 — 더 간단하고 API가 보장하는 방식으로 대체)
- 상세페이지에서 순위/지역별 세부 일정을 보여줄 필요가 있다면, `SPSPLY_RCEPT_*`/`GNRL_RNK1_*`/`GNRL_RNK2_*` 원본 필드들을 별도로 보존할 가치가 있다(스키마 확장 후보, §N).

## G. 분양가격 단위 검증 — 매우 중요

`getAPTLttotPblancMdl`의 `LTTOT_TOP_AMOUNT`를 4개 공고 27개 주택형에서 확인했다. **숫자 크기만으로 단위를 추측하지 않고**, 아래 두 가지 독립적 방법으로 교차검증했다.

### G-1. 공공데이터포털 설명 조회
웹 검색 결과, 공공데이터포털이 제공하는 청약홈 분양정보 서비스 설명에서 "공급금액(분양최고금액) 단위는 만원"이라는 설명을 확인했다. 다만 이는 검색 결과 요약이며 API 필드 명세 원문(Swagger 등)을 직접 열람해 문구를 그대로 인용하지는 못했다 — data.go.kr 페이지를 직접 fetch했으나 필드 단위가 명시된 명세 표는 페이지에 렌더링되지 않아(별도 문서/Swagger 링크로 안내됨) 이 경로로는 확정하지 못했다.

### 결론

- **단위: 만원(10,000원) — 검증 완료.** "미확정"으로 남겨두지 않아도 될 만큼 근거가 명확하다(공공데이터포털 설명 + 3개 프로젝트의 독립적 언론 보도 교차검증, 그중 1건은 소수점까지 정확히 일치).
- **의미: 해당 주택형의 분양 최고가(상한액)** — "최고"라는 표현이 언론 보도와 필드명 양쪽에서 일관되게 확인됨. 평균가나 하한가가 아니라 **상한가**라는 점을 저장/표시 시 명확히 해야 한다(그렇지 않으면 사용자가 "최저가"로 오인할 위험).
- `LTTOT_TOP_AMOUNT`의 데이터 타입은 문자열(`"79831"`처럼 따옴표 포함 숫자 문자열), 쉼표 없음, null/0 사례는 이번 27건 표본에서 관측되지 않았다(더 큰 표본에서는 있을 수 있음 — 공고 초기 단계 등에서 가격 미정 케이스 가능성은 배제하지 않는다).

## H. 주택형 데이터

`getAPTLttotPblancMdl` 4개 공고, 총 27개 row를 확인했다.

- `MODEL_NO`: 공고별로 `"01"`부터 순차 부여되며 **4개 공고 전부에서 중복 없음**(공고당 4~10개 row, 전부 유니크).
- `HOUSE_TY`: `"055.9700A"`, `"059.9025A"` 같은 형식 — 앞부분(소수점 포함 6자리)이 전용면적(㎡)으로 보이고, 끝의 알파벳이 같은 면적대 안에서의 세부 구분(동/향/구조 차이 등으로 추정)이다. 4개 공고 전부에서 `MODEL_NO`와 1:1로 대응하며 중복 없음.
- `SUPLY_AR`(공급면적, ㎡): 소수점 4자리 문자열(예: `"83.6488"`) — null 관측 없음.

- 특별공급 세부 유형별 세대수(`NWBB_HSHLDCO` 신혼부부, `MNYCH_HSHLDCO` 다자녀, `OLD_PARNTS_SUPORT_HSHLDCO` 노부모부양, `LFE_FRST_HSHLDCO` 생애최초, `YGMN_HSHLDCO`, `INSTT_RECOMEND_HSHLDCO`, `TRANSR_INSTT_ENFSN_HSHLDCO`, `ETC_HSHLDCO`, `NWWDS_HSHLDCO`)도 전부 number 타입, 대부분 0(해당 유형 공급이 없는 경우) — 관측된 표본에서는 이 "0"도 실제 값으로 보이며, null은 아니었다.
- 가격 null 사례: 27건 표본에서 없음(§G 참고).
- `GNRL_HSHLDCO`(요청서에 예시로 있던 필드명)는 **실제 응답에 존재하지 않았다** — 실제로는 `SUPLY_HSHLDCO`(일반공급)가 그 역할을 하는 것으로 보인다.

## I. 주소 품질

`HSSPLY_ADRES` 50건 표본을 전수 확인했다(null 0건).

관측된 패턴:
- **정상 지번/도로명 혼합 주소**: `"경기도 성남시 수정구 신흥동 81-8"`처럼 지오코딩이 비교적 수월해 보이는 형태가 다수.
- **"일원" 표현 포함**: `"서울특별시 영등포구 신길동 413-8번지 일원"`처럼 정확한 필지가 아니라 대략적 위치("일원" = "부근/일대")를 나타내는 경우가 상당수 관측됨 — 지오코딩 결과가 정확한 필지가 아니라 근사 위치가 될 수 있음을 의미한다.
- **택지지구/산업단지/생활권 표현 포함**: `"세종특별자치시 다솜동 5204-1번지 일원(행정중심복합도시 5-2생활권 S1BL)"`, `"경기도 용인시 처인구 원삼면 용인 반도체 클러스터 일반산업단지 D1-1BL"`, `"경기도 시흥시 거모동, 군자동 일원 시흥거모 공공주택지구 내 A-5블록"`처럼 신규 택지지구/산업단지 내 블록 번호로 표기된 경우가 많다 — 이런 주소는 일반적인 지오코딩 API(도로명주소 기반)가 정확히 인식하지 못할 가능성이 있다.
- 결론: 주소 품질은 "완전 정형화된 도로명주소"와 "택지지구 블록 표기" 사이에 걸쳐 있어, 지오코딩 시 일부 케이스는 실패하거나 부정확한 좌표(예: 읍/면 중심점)로 떨어질 위험이 있다 — 대량 지오코딩 전에 실패율을 별도로 측정할 필요가 있다(이번 P2-A에서는 실제 지오코딩을 실행하지 않았다).

**기존 Kakao 지오코딩 재사용 가능성**: 이 프로젝트에는 이미 여러 곳에서 Kakao 지오코딩을 쓰고 있음을 확인했다(`src/lib/geocode-apt.ts`의 아파트명 기반 지오코딩, `src/app/api/transactions/route.ts`의 `geocodeApt()`, `src/app/school/*`의 학교 좌표 검색 등 — STEP 1 감사에서 이미 확인된 인프라). 이번 P2-A에서 새로 호출하지는 않았지만, **주소 텍스트를 좌표로 바꾸는 Kakao Local 주소 검색 API 자체는 이미 이 코드베이스의 여러 곳에서 검증되어 쓰이고 있으므로, 분양 주소 지오코딩에도 동일 인프라를 재사용하는 방향이 합리적**으로 보인다(신규 외부 지도 API 도입 불필요 — 요청 원칙과 일치). 다만 "일원"/블록 표기가 섞인 주소에 대한 성공률은 별도로 검증해야 한다.

## J. 입주예정월

`MVN_PREARNGE_YM` 50건 전수 확인.

- null: **0/50**.
- 형식: **`"YYYYMM"` 6자리 문자열**(`"YYYY-MM"`이 아님) — 50건 전부 정규식 `/^[0-9]{6}$/`에 일치.
- 관측값 예: `"203005"`(2030년 5월), `"202911"`(2029년 11월), `"202702"`(2027년 2월) — 분양 공고 시점부터 짧게는 약 1년, 길게는 5년 뒤까지 다양하게 분포.

**저장 방식 제안**: "일(day)" 정보가 원천적으로 없는 연/월 단위 값이므로, `DateTime`으로 저장하면서 임의로 1일을 채워 넣는 것은 "없는 정보를 만들어내는 것"에 해당해 원칙에 어긋난다. 다음 두 방식 중 하나를 권고한다(최종 선택은 P2-B에서):
1. **문자열 그대로 저장**(`String? // "YYYYMM"`) — 가장 원본을 보존하는 방식, 표시할 때 파싱.
2. **연/월을 분리한 두 개의 `Int?` 컬럼**(`moveInYear`, `moveInMonth`) — 정렬/필터링(예: "2030년 이후 입주 예정만 보기")이 쉬움.

`DateTime`으로 강제 변환(예: 해당 월 1일로 채움)하는 방식은 권고하지 않는다.

`CNTRCT_CNCLS_BGNDE` / `CNTRCT_CNCLS_ENDDE` 50건 전수 확인.

## O. PresaleType 설계안

실제 Mdl 응답(§H)을 기준으로 한 설계 후보 — **이번 P2-A에서 schema를 생성하지 않으며, 아래는 P2-B 논의를 위한 제안일 뿐이다.**

이 프로젝트의 기존 명명 규칙(`PascalCase` 모델명, `camelCase` 필드명 + `@map("snake_case")`, 예: `RedevelopmentProject`, `Property`)을 따르면 `PresaleHouseTypeDetail`(또는 `PresaleUnitType`) 정도의 이름이 자연스러워 보인다.

```prisma
// 설계 후보 — 확정 아님, P2-B에서 논의
model PresaleHouseTypeDetail {
  id             Int      @id @default(autoincrement())
  presaleId      Int?     @map("presale_id")       // Presale.id FK 후보(관계 방식은 P2-B에서 결정)
  houseManageNo  String   @map("house_manage_no")  // Presale.houseManageNo와 조인
  modelNo        String   @map("model_no")         // "01", "02" ... — 표본상 공고 내 유니크
  houseTy        String   @map("house_ty")         // "055.9700A" 원본 코드 그대로 보존
  supplyArea     Float?   @map("supply_area")       // SUPLY_AR(㎡)
  generalSupply  Int?     @map("general_supply")    // SUPLY_HSHLDCO(일반공급 세대수, 0 허용)
  specialSupply  Int?     @map("special_supply")    // SPSPLY_HSHLDCO(특별공급 세대수 합계, 0 허용)
  topAmount      Int?     @map("top_amount")        // LTTOT_TOP_AMOUNT(만원 단위로 확정, §G)
  createdAt      DateTime @default(now()) @map("created_at")
  updatedAt      DateTime @default(now()) @updatedAt @map("updated_at")

  @@unique([houseManageNo, modelNo])
  @@map("presale_house_type_details")
}
```

**설계 근거**:
- `(houseManageNo, modelNo)` 복합 unique는 §H에서 4개 공고 27개 row 전부 중복 없음을 확인해 실측으로 뒷받침됨.
- `generalSupply`/`specialSupply`는 0을 허용하는 `Int?`로 두되, "0"과 "null(미확인)"을 구분해서 저장해야 한다(§M).
- `topAmount`는 §G에서 확정한 대로 **만원 단위, 최고가(상한액) 의미**임을 컬럼 주석에 명시할 것을 권고.
- 특별공급 유형별 세부 세대수(신혼부부/다자녀/생애최초 등 9종)는 이번 설계안에는 포함하지 않았다 — 필요성이 확인되면 별도 컬럼 또는 JSON으로 확장 검토(우선순위 낮음, §N의 "E" 분류와 유사한 성격).
- `Presale.minPrice`/`maxPrice`는 이 하위 테이블의 `topAmount` 값들에서 min/max를 파생시켜 상위 테이블에 캐싱하는 방식을 제안한다(동기화 시점에 계산) — 다만 이는 설계 판단이며 P2-B에서 최종 확정한다.

**관계**: `Presale`(1) : `PresaleHouseTypeDetail`(N). Prisma `@relation` 사용 여부(FK 강제 vs `houseManageNo` 느슨한 조인)는 P2-B에서 결정 — 이번 문서에서는 후보만 제시한다.

## P. P2-B 구현 계획

**이번 P2-A에서는 아래 중 어느 것도 실행하지 않는다.** 다음 STEP(P2-B) 착수 시 참고할 구체적 작업 목록이다.

1. **Presale schema 보완** — §N에서 "B(필드명 수정)"로 분류된 3개 필드(`receiptStartDate`/`receiptEndDate`/`pblancUrl`)의 매핑 버그 수정 + "C(추가 권장)"로 분류된 신규 컬럼(사업주체, 입주예정월, 계약기간, 공급지역, 분양/임대 구분, 원본 주택유형) 추가.
2. **`PresaleHouseTypeDetail`(가칭) 추가** — §O 설계안 기준으로 실제 schema 작성.
3. **migration** — 위 두 항목을 반영한 Prisma migration 생성 및 적용.
4. **API parser 수정** — `syncApplyhomeListings()`의 확인된 필드명 버그 수정, `mapHouseType()` 재작성(원본 값 보존 방식으로 전환 여부 포함).
5. **Detail 저장** — 수정된 parser로 Detail 데이터를 `Presale`에 upsert.
6. **Mdl 저장** — 신규 `PresaleHouseTypeDetail`에 주택형별 데이터를 upsert(§O의 복합 unique 활용).
7. **upsert 전략** — 기존 "houseManageNo 없으면 skip" 원칙 유지, `PresaleHouseTypeDetail`은 `(houseManageNo, modelNo)` 기준 upsert.
8. **중복 방지 검증** — 동일 공고 재수집 시 row가 늘어나지 않는지 실제 재호출로 확인.
9. **날짜 normalization** — `RCEPT_BGNDE/ENDDE`(확정), `CNTRCT_CNCLS_BGNDE/ENDDE`(신규), `MVN_PREARNGE_YM`(§J의 문자열 또는 연/월 분리 정책 확정 후 적용).
10. **가격 normalization** — `LTTOT_TOP_AMOUNT`를 문자열→정수 변환, null 방어 처리(§M).
11. **좌표 enrichment** — `HSSPLY_ADRES` 기반 Kakao 지오코딩 파이프라인 설계(§I, 기존 인프라 재사용 검토) — "일원"/블록 표기 주소의 실패율을 소량 표본으로 먼저 측정할 것을 권고.
12. **소량 DB 적재 테스트** — 실제 저장 전, 이번 P2-A 표본(50건 Detail + 4건 Mdl) 규모로 스테이징 저장을 먼저 시도해 parser/schema 정합성 검증.
13. **검증** — 저장된 데이터를 실제 값(이번 문서의 표본, 특히 §G의 3개 검증된 가격 사례)과 재대조.
14. **이후 전체 동기화** — 검증 완료 후에만 전체 2,843건 대상 동기화 진행, 관리자 트리거/배치 설계는 그 다음 단계로 미룬다.

## P2-A 최종 검수 결정

검수일: 2026-08-12

### 고유 식별자

Detail 레벨의 외부 고유키는 `HOUSE_MANAGE_NO`를 기본으로 사용한다.

현재 표본 50건에서 null/중복은 확인되지 않았다.

다만 `HOUSE_MANAGE_NO`와 `PBLANC_NO`가 항상 동일하다고 시스템적으로 가정하지 않는다.

두 값을 모두 원본 그대로 보존한다.

### 청약 접수기간

`receiptStartDate` → `RCEPT_BGNDE`

`receiptEndDate` → `RCEPT_ENDDE`

로 매핑한다.

표본 50건에서 세부 접수일정의 min/max와 정확히 일치함을 확인했다.

### 공고 URL

`PBLANC_URL`을 사용한다.

기존 `LTTOT_PBLANC_URL` 참조는 P2-B에서 수정한다.

### 분양가격

`LTTOT_TOP_AMOUNT`는 만원 단위의 해당 주택형 최고 분양가로 사용한다.

P2-A에서 실제 공고 3건과 교차검증했다.

가격이 null 또는 비어 있는 경우 0으로 임의 변환하지 않는다.

### 입주예정월

`MVN_PREARNGE_YM`은 `YYYYMM` 문자열로 원본 보존한다.

임의로 `YYYY-MM-01` DateTime으로 변환하지 않는다.

### 주택유형

`HOUSE_SECD` / `HOUSE_SECD_NM`의 공식 API 원본값을 별도 저장한다.

현재 `PresaleHouseType` enum을 이번 단계에서 억지로 확장하거나 삭제하지 않는다.

오피스텔/도시형생활주택 등은 향후 해당 전용 API 연동 시 통합 정책을 결정한다.

### 분양/임대 구분

`RENT_SECD` / `RENT_SECD_NM` 원본값을 보존한다.

"분양주택", "분양전환 가능임대" 등의 실제 값을 임의의 2분류로 축소하지 않는다.

향후 UI에서는 별도의 표시/필터 정책을 설계한다.

### 주택형 하위 데이터

`Presale`과 `PresaleHouseTypeDetail`(가칭)은 1:N 관계로 설계한다.

`PresaleHouseTypeDetail`은 Prisma relation FK를 사용한다.

동시에 외부 데이터 중복방지를 위해

`@@unique([houseManageNo, modelNo])`

를 두는 방향을 P2-B 기본안으로 한다.

### 좌표

청약 API에는 좌표가 없으므로 기존 Kakao 지오코딩 인프라를 우선 재사용한다.

주소 지오코딩에 실패한 경우 임의 좌표를 생성하지 않는다.

`latitude` / `longitude`는 null을 허용한다.
