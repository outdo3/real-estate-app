## 17. "정보 준비중" UX 평가

현재 구조(§2)는 5칸 중 값이 없는 칸만 개별적으로 "정보 준비중"+[제보/수정]을
보여준다. §18(coverage 실측)에서 확인했듯 **캐시가 안 된 단지는 5칸 중 세대수/준공년월
(실거래 데이터 기반이라 비교적 잘 채워짐)을 제외한 나머지 3칸(용적률/건폐율/주차대수)이
동시에 "정보 준비중"으로 뜰 확률이 높다** — 사용자가 신고한 증상(문서 서두 "1. 용적률/
건폐율/주차대수가 '정보 준비중'으로 나옴")과 정확히 일치하는 구조적 원인이다.

이번 STEP에서 요청받은 3개 항목(용적률/건폐율/주차대수)은 **API 응답 구조상 항상
함께 오거나 함께 없는 값**(같은 `getBrRecapTitleInfo` 호출 결과)이므로, 3칸이 개별
"정보 준비중"으로 흩어져 보이는 현재 방식보다 **C안(별도 "상세정보 준비중" 묶음)**이
더 자연스럽다고 판단한다 — 세대수/준공년월은 독립된 소스(실거래 데이터 우선)라 별도
유지가 맞고, 용적률/건폐율/주차대수 3개는 "건축물대장 정보"라는 하나의 묶음으로
설명하면 "왜 하필 이 3개만 항상 같이 비는가"가 사용자에게 자연스럽게 전달된다.
(구현은 이번 STEP 범위 아님 — 제안만.)

2. §17의 C안(3개 항목을 "건축물대장 정보" 등 하나의 묶음으로 처리, 비어있을 때는

   다음 구현 STEP 후보로 제안.
3. Coverage 자체(캐시 극소량)를 넓히는 것은 이번 STEP(조사/설계)의 범위가 아니며,
   운영 관점의 별도 과제(예: 인기 단지 사전 배치 워밍업, `scripts/backfill_apt_details.ts`
   활용 확대)로 분리해 기록만 한다.

## 27. 매매/전세 색상 정책 — 문제 원인 및 최종 추천

**현재 문제 원인(코드 확정)**: `PriceTrendChart.tsx` line 151-152.

```
<Line dataKey="salePrice" stroke="var(--primary-color)" .../>   // #03c75a (네이버 그린)
<Line dataKey="rentPrice" stroke="#10b981" .../>                 // Tailwind emerald-500
```

`--primary-color`는 `globals.css` line 4에서 `#03c75a`로 정의돼 있다. `#10b981`은
하드코딩된 별도 초록(에메랄드) 값 — **두 색 모두 "초록 계열"이라 색상환에서 가까워
작은 모바일 화면·범례 없이 얼핏 보면 구분이 어렵다.** 이게 사용자가 신고한 "매매/전세
시세차트 색상이 유사해 구분이 어렵다"의 정확한 코드 원인이다.

**최종 추천**: 매매는 기존 `var(--primary-color)`(#03c75a) 유지, 전세는
`globals.css`에 이미 정의된 `--down-color`(#3152d6, "하락색"으로 line 19에 정의됨,
현재는 다른 곳에서 등락 표시에 쓰임)와 **같은 파란색 계열**로 교체할 것을 제안한다.
근거:

- 새 브랜드 색상 체계를 만들지 않는다는 지침 준수 — 이미 존재하는 팔레트 값 재사용.
- 초록(매매) vs 파랑(전세)은 색상환에서 충분히 떨어져 있어 즉시 구분됨(접근성 관점의
  색상 대비도 초록-초록보다 초록-파랑이 명확히 큼).
- 다만 **`--down-color`라는 변수 이름 자체는 "하락"이라는 별도 의미를 담고 있어**,
  전세 라인에 그대로 재사용하면 변수명과 실제 용도가 어긋난다(값은 재사용하되 이름은
  재사용하지 않는 편이 안전). 구현 시에는 `--down-color`와 **같은 hex 값**을 쓰는
  새 시맨틱 변수(예: `--chart-rent-color: #3152d6;`)를 추가하거나, PriceTrendChart
  안에서 `#3152d6`을 직접 쓰되 주석으로 "`--down-color`와 동일 팔레트"임을 남기는
  두 방식 중 하나를 다음 구현 STEP에서 결정하도록 남겨둔다(이번엔 설계만).
- 범례(`<Legend formatter>`)와 tooltip 텍스트 색상(line 144-145, 현재도 `var(--primary-color)`
  / `#10b981`로 각각 하드코딩)도 같은 페어로 함께 바꿔야 일관된다.

## 31. selectedArea 정책 최종 추천

**A안(선택 평형 반영)을 기본으로, 데이터가 부족한 경우에만 자동으로 전체 기준으로
폴백 + "해당 평형 거래가 적어 전체 평형 기준으로 표시합니다" 안내**를 추천한다.
순수 C안(수동 토글)보다 이 방식을 추천하는 이유:

- §30 실측에서 대부분(레이카운티 12/12평형, 동래래미안아이파크 11/12평형, 화명롯데
  캐슬카이저 15/15평형)이 12개월 3건 이상이라 A안이 문제없이 동작한다 — 즉 "항상
  토글이 필요할 만큼 데이터가 부족한 경우"는 드물다.
- 데이터가 부족한 소수 케이스(은하 아파트류 초소형 단지, 또는 대형 단지의 희귀
  평형인 레이카운티 114㎡대)에서만 자동 폴백 + 안내 문구를 넣으면, 사용자가 매번
  토글을 조작할 필요 없이 "왜 지금 전체 기준으로 보이는지"만 이해하면 된다.
- B안(항상 전체 유지)은 Hero와의 기준 불일치(§32)를 구조적으로 남겨두므로 후순위.
- 순수 C안(항상 수동 토글)은 A안의 자동 폴백과 병행 가능한 상위 옵션으로, "사용자가
  명시적으로 전체를 보고 싶을 때"를 위해 함께 두는 것도 고려할 수 있으나, 이번 조사
  결과(대부분 평형에 충분한 데이터)로는 자동 폴백만으로도 커버되는 비율이 높아 1차
  구현에서는 필수가 아니라고 판단한다.

## 32. 특정 평형 최근 1년 거래 희소성 — 실측 결과

§37(대표 검증 5단지)의 "최근 12개월 기준 평형별 거래건수(매매+전월세 합산)" 데이터를
평형 단위로 모아 재집계(5개 단지, 총 47개 평형 표본 — 매매/전월세 분리는 MOLIT
원본상 개별 조회는 가능하나 이번 표본은 합산 기준으로 집계, 한계로 명시):

| 최근 12개월 거래건수 구간 | 평형 수 | 비율 |
|---|---|---|
| 0건 | 0개(표본 자체가 "실제 거래가 있었던 평형"만으로 구성돼 0건 평형은 집계 밖 — 한계로 명시, 아래 참고) | — |
| 1~2건 | 3개 (은하 49.59㎡, 엘지메트로시티3 243.35㎡, 동래래미안아이파크 114.84㎡) | 6.4% |
| 3건 이상 | 44개 | 93.6% |

**한계**: "0건" 평형(그 단지 매물표에는 존재하지만 최근 1년간 단 한 건도 거래되지
않은 평형)은 MOLIT 실거래 API 특성상 애초에 응답에 나타나지 않아 이번 방식으로는
직접 셀 수 없다(그런 평형이 있다는 것 자체를 실거래 데이터만으로는 알 수 없음 —
분양 정보나 세대수 데이터와 교차해야 파악 가능, 이번 STEP 범위 밖). 위 표는 "실제
거래가 있었던 평형 중" 얼마나 희소한지에 대한 하한선 추정치로 해석해야 한다.

**결론**: 부산 대표 단지 표본에서는 "선택 평형에 최근 1년 거래가 3건 미만"인 경우가
소수(6.4%)이고, 대부분 3건 이상으로 A안(선택 평형 반영)이 실용적이다. 다만 이
6.4%가 존재한다는 사실 자체가 §31의 "자동 폴백" 로직을 정당화한다 — 무조건 A안만
쓰면 이 소수 케이스에서 텅 빈 차트를 보여주게 된다.

| C. 월별 평균 | 이상치에 약간 취약 | B와 동일 문제 | 흡수됨 | 중간(이상치 하나가 평균을 끌어당김) |

| E. 월별 min/max band + 대표값(중앙값) | 밴드가 그 달의 가격 분산을 보여줌(부가 정보) | 밴드 폭이 0에 가까움(거래가 적어 사실상 점) | 밴드로 시각화되어 오히려 정보가 됨 | 밴드 폭으로 이상치 존재를 드러냄(숨기지 않음) |

## 34. aggregation 최종 추천

**B안(월별 중앙값)**을 1차 추천한다. 근거:

- 거래량이 많은 단지(§30 레이카운티 84㎡대 월평균 20건 이상)에서 평균(C안)은 고가
  이상치 1건에도 쉽게 흔들리지만 중앙값은 안정적.
- 거래량이 적은 달(월 1건)에는 중앙값이 곧 그 값이 되어 A안(개별 거래)과 사실상
  동일하게 동작 — 별도 분기 없이 자연스럽게 저희소성 상황에 적응한다.
- D안(최근 거래값)보다 그 달 전체를 대표하는 값으로서 통계적으로 더 안정적.
- E안(min/max 밴드)은 정보량은 가장 많지만 구현 복잡도가 높고, "이집" 사용자가
  일반 소비자층(전문 투자자가 아님)이라는 점을 고려하면 밴드 차트보다 단일 추세선이
  더 이해하기 쉽다 — 다만 "이 값이 대표값일 뿐 실제로는 폭이 있다"는 정보 손실은
  감수해야 한다. 향후 고도화 후보로 기록.

**selectedArea(§31의 자동 폴백 포함)와 조합 시**: 평형이 좁혀지면 월별 거래 건수가
자연히 줄어드는데(§32), 중앙값은 표본이 1건이어도 안전하게 동작하므로 두 정책의
조합이 특히 잘 맞는다.
