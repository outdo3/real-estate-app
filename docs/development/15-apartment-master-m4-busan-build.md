## F. Pilot

**부산진구(lawdCd=26230, distinct aptSeq 404개)**를 첫 신규 pilot으로 선정했다(M4-A에서 건축물대장 성공률을 별도 조사한 지역이라는 요청안 근거 그대로 채택).

### F-1. 1차 시도 — STOP 조건 발생

`--concurrency=4`로 404건을 실제 처리한 결과 **`ledger.apiError=310/404`(76.7%)**가 발생했다. 이는 §23 STOP 조건("반복 API 오류", "예상과 크게 다른 데이터 패턴")에 해당해 즉시 중단하고 원인을 분석했다.

**원인**: 건축물대장(`BldRgstHubService`) API 자체의 **초당 서비스 요청제한**(`LIMITED_NUMBER_OF_SERVICE_REQUESTS_PER_SECOND_EXCEEDS_ERROR`, HTTP 429)이었다. 실측 진단 결과 800ms 간격도 429를 유발했고, 30초 냉각 후에야 안정적으로 성공했다. **같은 조건에서 Kakao API는 전혀 영향받지 않아**(별도 실측 확인, 5건 전부 200 OK) 이 API에만 특이한 제약임을 확인했다.

### F-2. 최소 수정

건축물대장 호출만 전역적으로 직렬화하고 최소 1.5초 간격을 강제하는 큐(`throttledLedgerCall`)를 추가했다(유닛 단위 concurrency와 분리 — Kakao/DB 작업까지 직렬화하지 않음). 429/503(재시도 가능, §28)만 최대 2회 추가 재시도(지수 백오프)하도록 했다 — not_found/parse_error 등 재시도 무의미한 실패는 즉시 반환.

20건 소표본으로 수정을 검증한 뒤(0 api_error, 실제 not_found만 관측), 404건 전체를 재실행했다.

### F-4. 추가 발견 — 좌표 중복

전체 검증(§G) 중 **서로 다른 aptSeq 9쌍이 완전히 동일한 좌표**를 공유하는 것을 발견했다(예: "서면2차봄여름가을겨울"과 "서면봄여름가을겨울"). 원인은 Kakao 키워드검색이 유사한 이름의 단지를 하나의 POI로만 색인해 발생하는 것으로 확인했다(M3의 "행정구역 대표좌표" 결함과는 다른 종류). "성공률보다 정확도" 원칙에 따라 **좌표 중복 정정 로직**(`deduplicateCoordinates`)을 추가했다: 그룹 내 `exact` 품질이 정확히 1개면 그것만 신뢰하고 나머지는 null 처리, `exact`가 0개나 2개 이상이면(어느 쪽이 맞는지 판단 불가) 그룹 전체를 null 처리. 적용 결과 6개 그룹, 9건이 안전하게 null 처리됐다(임의 보정 없이 데이터를 지우기만 함).

이 로직을 seed 스크립트에 정식 반영해(§J) 이후 모든 batch에서 자동 실행되도록 했다.

### AA-5. 새로 발견한 문제 2건

**(발견·조사 완료, STOP 아님) 교차-LAWD_CD aptSeq 1건**: 동래구(26260) 배치 중 `aptSeq=26470-1566`("아시아드코오롱하늘채")가 이미 연제구(26470) 배치에서 생성된 기존 row와 겹쳤다. aptSeq의 접두사(26470)와 건축물대장 주소(부산광역시 연제구 거제동)는 모두 연제구를 가리키지만, 이 단지의 실거래 1건이 동래구 LAWD_CD로 조회한 MOLIT 응답에도 잡힌 것으로 보인다(경계 지역 MOLIT 데이터 특성으로 추정, 원인을 코드로 단정하지 않음). `aptSeq` upsert 덕분에 **중복 row는 생성되지 않았지만**, "MOLIT 소스 필드는 항상 최신 배치로 갱신한다"는 기존 병합 규칙 때문에 sigungu/sggCd가 일시적으로 "동래구"로 덮어써졌다. 이후 연제구를 idempotency 재검증(§AA-6)하면서 자연스럽게 "연제구"/26470으로 다시 정정됨을 확인했다(현재 상태 정상). 전체 3,402건 중 1건(0.03%)에 국한된 edge case로 STOP 조건에 해당하지 않지만, 검수 시 참고할 사항으로 기록한다.

**(발견·수정 완료, 이번 세션 자체 실수)** idempotency 재검증(§AA-6)에 사용한 CLI 라벨을 "부산 서구 idempotency재검증"처럼 설명적으로 붙였는데, `apartment_master_seed.ts`의 `sigungu = label.split(' ').slice(1).join(' ')` 파싱 로직이 라벨 전체를 그대로 흡수해 서구/해운대구/부산진구/연제구(총 1,127건)의 `sigungu` 필드가 일시적으로 "서구 idempotency재검증" 등으로 오염됐다. **원인은 스크립트 결함이 아니라 검증용 라벨을 잘못 고른 이번 세션의 실수**다. 발견 즉시 영향 범위를 정확히 특정(4개 구·군, 1,127건, 전부 `sigungu LIKE '%idempotency%'`로 식별 가능)한 뒤, 각 row를 라벨에서 접미사만 제거한 원래 값("서구"/"해운대구"/"부산진구"/"연제구")으로 직접 정정했다 — 임의의 값을 새로 만든 것이 아니라 실수로 덧붙인 문자열만 제거해 원상복구한 것이므로 원칙 #4(임의값 생성 금지)를 위반하지 않는다. 정정 후 재검증 결과 잔여 오염 0건, 총 Master 행 수는 정정 전후 3,402건으로 불변임을 확인했다. **향후 재발 방지**: 이 스크립트를 실행할 때 label 인자는 항상 `"{시/도} {구/군}"` 형식만 사용해야 한다(테스트/검증 목적이라도 부가 텍스트를 붙이면 안 됨) — 스크립트 자체 수정(라벨 파싱 로직 방어) 여부는 검수 시 판단 필요 사항으로 남긴다.

현재 부산 `ApartmentMaster`(16/16 구·군, 3,402건, identity 100% 확보)는 **P2-D4-B 사용자 기능 개발을 시작할 수 있는 수준**으로 판단한다. M4-C는 실제 사용자 기능 개발과 병행하거나, 그 과정에서 필요성이 명확히 확인되는 시점에 진행 여부를 별도로 결정한다 — 이번 STEP에서 자동으로 착수하지 않는다.
