# 이집(ejip) 프로젝트 개발 로드맵

## 프로젝트 비전

이집은 단순히 부동산 정보를 많이 보여주는
플랫폼을 목표로 하지 않는다.

사용자의 조건과 취향을 바탕으로

"나에게 맞는 집을 골라주는 부동산 플랫폼"

을 목표로 한다.


## 제품 포지셔닝

제품 방향을 다음과 같이 정의한다.

호갱노노:
집과 단지를 탐색하고 정보를 확인하는 경험

아실:
부동산 데이터를 분석하고 비교하는 경험

이집:
사용자에게 맞는 집을 선택하고 추천하는 경험

※ 위 문구는 경쟁사를 평가절하하는 의미가 아니라
이집의 제품 방향을 구분하기 위한 내부 정의이다.


## 핵심 제품 철학

사용자가 이집을 사용한 뒤 최종적으로

"그래서 나는 어떤 집을 보면 되는가?"

라는 질문에 답을 얻을 수 있어야 한다.


## 핵심 차별화 후보

향후 검증을 전제로 다음 기능을 핵심 차별화 후보로 둔다.

1. 이집 단지점수
2. 나와의 궁합
3. 개인 맞춤 아파트 추천
4. 추천 TOP 5
5. 추천 이유
6. 아쉬운 점
7. 사용자 조건 기준 단지 비교
8. 추천 결과 지도 연동


주의:

위 기능과 점수체계는 아직 확정된 구현 사양이 아니다.

향후 데이터 검증과 설계를 거쳐 확정한다.


## AI 사용 원칙

Gemini/OpenAI 등의 생성형 AI를
추천 시스템의 필수 기반으로 만들지 않는 방향을 우선 검토한다.

가능한 기능은

데이터
+

+
자체 추천 알고리즘

으로 구현한다.

## 지역 확장 전략

데이터 품질과 추천 정확도를 검증하면서
지역별로 단계적으로 제공하는 방식을 검토한다.

이후:
부산광역시 전체

장기:
전국

### SCHOOL SCORE IMPACT SIMULATION V1

**상태: 시뮬레이션 완료(2026-09-11) — 교정은 여전히 보류. 권고: 부산 출시 후 진행**

시뮬레이션 결과: `docs/development/SCHOOL_SCORE_IMPACT_SIMULATION_V1.md`

핵심 수치(실제 운영 함수로 3,401건 전수 시뮬레이션, DB 쓰기 0건):

- 41건 재현 확인(25m 초과 21건 + 1km 밖 null 20건)
- 학교 점수가 움직이는 단지 **584건** = 직접 362 + **간접 222**(자기 데이터 불변)
- 반올림 후 표시 점수가 바뀌는 단지 **48건** — 그중 **27건이 하락**
- 최대 +5.65점 / 최대 −3.19점
- **부작용 사례: 466m → 467m(1미터)인데 총점 −3.19점** — 사상구에서 21건이 한꺼번에
  올라오며 그 구의 percentile 곡선을 눌렀기 때문이다
- 임계값 판정: **RE-ANCHOR RECOMMENDED** — 200/400/650은 분포가 그대로라 유효하지만
  933은 "1km 검색의 인공적 상한"이라 무효. NEIS에서는 36건이 그 위에 실재한다
- null 의미 결함 확인: "검색 실패"를 "확인된 부재"로 다루고 있다(sentinel 최하위)

**권고: OPTION D → 출시 직후 OPTION C**(임계 재앵커 + 출처 교체를 함께).
출처만 바꾸면(OPTION B) 933 임계가 무효인 채로 나가고, 잘못된 적 없는 27개 단지의
점수가 설명 없이 떨어진다.

착수 시 필요: 수집기 수정안(SC4 페이지네이션 vs NEIS 직접 사용) + `ApartmentLocationFeature`
3,401행 재수집(프로덕션 bulk write → **승인 필수**) + 임계 재산출 + 회귀 계획.

발견 경위: `SCHOOL_DISTANCE_SOURCE_RECONCILIATION_V1` (2026-09-11, 커밋 `5ca7cfd`). 전수 대조 3,401건.

무엇이 문제인가:

- `collectors/location.ts`가 `categorySearch('SC4', lat, lng, 1000)`를 **단일 페이지(size=15)** 로만 호출한다. SC4는 초·중·고·대를 전부 포함하는 카테고리라, 1km 안에 학교가 많으면 **진짜 최근접 초등학교가 상위 15건 밖으로 밀린다.** 이후 `filterElementary`가 이름으로 걸러도 이미 잘려 나간 학교는 복구되지 않는다.
- **21건**: 저장된 Kakao 거리가 NEIS 최근접 결과보다 뚜렷하게 멀다. 21건 전부 같은 방향(Kakao가 더 멀다) — 무작위 오차가 아니라 구조적 누락이다. 최악 사례 `26200-22`는 **376m로 저장돼 있으나 실제 최근접은 59m**(신선초등학교).
- **20건**: 가장 가까운 초등학교가 1km 검색 반경 밖이라 `nearestElementaryDistanceM = null`이다. NEIS로는 전부 찾힌다(1,052~1,422m). `null`은 "학교가 없다"가 아니라 "1km 안에서 못 찾았다"인데, Score는 `treatCompleteNullAsWorst: true`로 **최악값 취급**한다.
- **직접 영향 41건**(전체 3,401건의 1.2%).

왜 아직 고치지 않았나:

`nearestElementaryDistanceM`은 점수에 **두 경로**로 들어간다.

1. `categories/school-access.ts` — peer pool 내 **percentile 하위지표**(상대 순위). 한 단지 값이 바뀌면 **같은 pool의 다른 단지 percentile도 함께 움직인다.** 즉 영향 범위가 41건으로 끝나지 않는다.
2. `school-distance-band.ts` — 절대 band(200/400/650/933). 교정하면 실제로 구간이 바뀐다(`26200-22`: `CLOSE` → `VERY_CLOSE`, `26530-104`: `NORMAL` → `VERY_CLOSE`).

게다가 band 임계값 자체가 **Kakao 분포에 앵커링**돼 있다(코드 주석: "반경 1000m 검색이라 933m를 넘는 값은 실측 표본에 없었다"). NEIS는 1,052~1,422m를 만들어내므로 **임계 근거까지 다시 세워야 한다.**

E-JIP Score는 신뢰 임계 시스템이라 승인 없이 공식·출처·임계값을 바꾸지 않는다(AGENTS.md).

진행 조건 — 착수 전에 아래를 문서로 제시하고 승인받는다:

1. 수집기 수정안 (SC4 페이지네이션 vs NEIS School 테이블 전환)
2. **점수 변동 분포 시뮬레이션** — 41건 직접 영향 + peer pool 간접 영향까지, 단지별 점수/순위 변화
3. band 임계값 재앵커링 근거 (새 분포 기준 percentile 재산출)
4. 순위 역전 사례 목록
5. 회귀 계획 및 롤백 방법

상세 근거: `docs/development/SCHOOL_DISTANCE_SOURCE_RECONCILIATION_V1.md`

## 출시 후

부산 출시에 필수는 아니지만 잃어버리면 안 되는 과제. 착수 시 이 목록에서 지우고 CHANGELOG에 결과를 남긴다.

관련 문서: `docs/development/REAL_ESTATE_TOOLS_FINANCE_ACTION_LOOP_V1.md` §13

- ~~취득세 1차 출처 대조~~ → **완료**(2026-09-11). 지방세법 제11조·제151조, 농어촌특별세법 제5조와 대조했고 세 산식 모두 일치해 고칠 부분이 없었다. `verifiedAgainstPrimarySource = true`.
- **취득세 확장** — 2주택 이상 중과, 생애최초 감면. 조정대상지역 지정 데이터 확보가 선행돼야 한다(지정이 수시로 바뀌므로 값을 박아둘 수 없다).
- **등기 비용 채권 할인차손 자동 계산** — 국민주택채권 시세 연동이 선행. 그 전에는 금액을 만들지 않는다.
- **임장 노트 저장** — 저장소가 생긴 뒤에만 입력칸을 연다(지금은 준비중).
- **경매·공매 데이터 연동** — 실제 데이터 전까지 예시 매물을 만들지 않는다.
- **상세 LTV 모달 통일** — 상세의 80/70/40% 가정 모달을 `lib/finance-tools/ratios.ts` 기반으로 옮긴다. 현재는 그 모달만 기준일 없는 가정을 쓰고 있다.
- **갭 계산기 단지 컨텍스트 prefill** — 동일 단지·동일 전용면적 확인 로직이 선행돼야 한다. 확인 없이 채우면 존재하지 않는 갭이 나온다.
- **출퇴근 분석 / 재개발 고급 분석 / 청약 경쟁률 / AI 추천 / 브로커 PRO** — 미착수. 완성 전까지 도구 화면에 노출하지 않는다.

## 출시 직후 / P1

`BUSAN_LAUNCH_READINESS_AUDIT_V1`(2026-09-11)에서 확인·정리한 목록. 출시를 막지는 않지만 출시 직후 다뤄야 한다. **완료 전까지 지우지 않는다.**

- **MASTER COVERAGE SYNC AUTOMATION** — 출시 전 `--apply` 1회는 **완료**(2026-09-11, 승인 받은 INSERT 20건, 커버리지 99.39% → 99.97%). 남은 것은 **자동화**다. `scripts/master-coverage-sync.ts`는 CLI 스크립트일 뿐 cron이 없고, `vercel.json`의 cron은 sale-sync/rent-sync/sale-recheck 셋뿐이다. 방치하면 하루 약 2곳씩 다시 밀린다. 자동화 감사 판정은 **B. NEEDS FOLLOW-UP** — 스크립트 자체는 안전(외부 API 호출 0건, DB 전용, 2.4초, INSERT 전용 단일 쓰기, 재실행 시 0건 삽입)하지만 무인 실행 전에 네 가지가 선행돼야 한다: (1) `scripts/`는 Next 번들에 포함되지 않으므로 로직을 서버 모듈로 옮기고 기존 세 cron과 같은 `CRON_SECRET` fail-closed 게이트를 쓰는 `/api/cron/master-coverage-sync` 신설, (2) 좌표 없는 master가 조용히 쌓이므로 지오코딩 백필과 짝지어야 함, (3) REVIEW_REQUIRED 누적 알림, (4) 아래 "동명 단지 AMBIGUOUS" 부작용이 무인 실행으로 재발하지 않게 하는 장치. **이 STEP에서는 프로덕션에 쓰는 cron을 추가하지 않았다.**
- **동명 단지 AMBIGUOUS — score identity를 aptSeq로** — **해결됨**(2026-09-11, `SCORE_CANONICAL_APTSEQ_RESOLUTION_FIX_V1`). 상세페이지가 검증된 canonical aptSeq로 점수를 묻고, 라우트가 aptSeq를 최우선으로 해소한다. 부산 전역 감사 결과 이름 경로에서 법정동 없이 116건·법정동이 있어도 8건이 AMBIGUOUS였고(다른 단지로 잘못 확정된 사례는 0건), 124건 전부 aptSeq로 되살아난다. **남은 것**: 비교(CompareV2)는 거래/점수를 의도적으로 병렬 호출해 aptSeq를 쓰지 않으므로 같은 동 동명 8건이 비교 화면에서 여전히 AMBIGUOUS다. `/api/apt/[name]/education`도 같은 이름 기반 해소를 쓴다. 둘 다 점수 산식과 무관한 별도 경로라 백로그로 둔다.
- **[REVIEW_REQUIRED] `26440-329 에코델타더베르힐`(강동동)** — `MASTER_COVERAGE_SYNC_V1`이 `F_SOURCE_ALIAS_MISMATCH`로 보류한 유일한 미매칭 단지. 같은 주소(dong+jibun)에 다른 `aptSeq`의 기존 Master가 있어 rename/alias 여부가 확정되지 않았다. **확인 전까지 자동 생성 금지** — sync를 자동화해도 이 건은 계속 사람이 판단해야 한다. 해소되기 전까지 이 항목을 지우지 않는다.
