## 6. MOLIT 거래면적 검증(§6)

`src/lib/api-molit.ts:117-122`:
```ts
const areaVal = item.전용면적 || item.excluUseAr || '';
...
const excluUseArea = areaVal !== '' ? parseFloat(String(areaVal)) : null;
```
API 원본 필드명 자체가 `전용면적`이다 — **표시 문자열(`area`)과 별개로
raw 숫자(`excluUseArea`)를 그대로 보존**하며, 어떤 반올림도 거치지 않고
`parseFloat`만 적용한다. 즉 84.99 vs 84.996 같은 차이는 파싱 과정에서
생긴 게 아니라 **원본 API 응답 자체의 정밀도 차이를 그대로 반영한
것**임을 코드 레벨에서 확인했다(추가로 §10 실측 데이터가 이를
정량적으로 뒷받침).

## 9. 타입 identity 조사(§9)

`PresaleHouseTypeDetail.houseTy` 실제 값 샘플(20건 직접 조회):
```
"055.9700A" supplyArea=83.6488   "055.9700B" supplyArea=83.6488
"055.9800C" supplyArea=83.6638   "084.9993A" supplyArea=118.98
```
**패턴 확인**: `houseTy`의 선행 숫자(`084.9993`)가 **전용면적과 동일
정밀도의 값**이고, 말미 알파벳(`A/B/C/D...`)이 **동일 전용면적대
안에서의 서브타입 구분자**다 — 이는 청약홈의 실제 관행이며, **원칙적
으로 타입 identity key 후보가 될 수 있는 유일한 실존 데이터**다.

단, §8에서 확인했듯 이 데이터는 기존 준공 단지(MOLIT 거래 대상)에
연결되지 않는다 — 즉 **오늘 시점에서는 이 key를 기존 상세페이지
거래에 실제로 적용할 방법이 없다.** 향후(§31) 이름/좌표/준공연도
기반의 검증된 매핑이 별도로 구축된다면 재검토 가치가 있다는 점만
기록한다.

## 10. Near-duplicate audit(§10)

살아있는 `/api/apt/[name]` 실거래 API로 서구 3곳(e편한세상송도더퍼스트
비치, 대신푸르지오2차, 골든캐슬), 해운대 3곳(경동, 더샵센텀파크1차,
해운대힐스테이트위브), 부산진구 2곳(서면롯데캐슬스카이, 양정자이더샵
SKVIEW), 동래구 2곳(동래3차SKVIEW, 삼정그린코아) — 총 10개 단지,
전체 5,240건 거래를 조회해 0.5㎡ 미만 근접값 쌍을 전수 추출했다.

**핵심 발견**: 근접값 diff가 **뚜렷하게 두 그룹으로 나뉜다**:
- **diff < 0.05㎡**(대부분 0.001~0.03㎡): 예) 양정자이더샵SKVIEW
  84.9268 vs 84.9296(diff 0.0028), 삼정그린코아 84.9251 vs 84.9282
  (diff 0.0031), 더샵센텀파크1차 84.6389 vs 84.6528(diff 0.0139).
  **경동 단지에서는 서로 무관한 3개 면적대(220㎡대/221㎡대/222㎡대)
  쌍이 전부 정확히 동일한 0.0045㎡ 차이를 보였다** — 우연이라기엔
  너무 정확히 일치해, 특정 시기/소스의 시스템적 정밀도 변환(예: 등록
  단위 환산 시 반올림 방식 차이)일 가능성을 시사한다.
- **diff 0.15~0.47㎡**: 예) e편한세상송도더퍼스트비치 84.3850 vs
  84.8040(diff 0.419), 해운대힐스테이트위브 84.5871 vs 84.9628(diff
  0.376), 경동 82.0093 vs 82.4320(diff 0.423). 이 폭은 실제 서로 다른
  평면/구조 타입일 가능성이 diff<0.05㎡ 그룹보다 유의미하게 높다(단,
  §11에서 설명하듯 100% 확정은 불가).
- 서면롯데캐슬스카이(683건 거래)는 근접값 쌍이 **0건** — 근접 중복이
  모든 단지에 보편적인 현상은 아님을 함께 확인.

## 11. Near-duplicate 원인 분류(§11)

| 분류 | 정의 | 실측 근거 |
|---|---|---|
| **A. 원본 source precision 차이** | 없음(MOLIT는 단일 source) | 이번 감사에서 두 개 이상의 원본 API를 비교 대조한 사례가 없어 A는 관측되지 않음 |
| **B. 실제 다른 타입** | diff가 상대적으로 큼(0.15㎡ 이상) | 강한 정황(§10), 그러나 타입코드 부재로 100% 확정 불가 |
| **C. 동일 타입, source별 decimal 차이(등록 시점/방식 차이)** | diff가 매우 작음(<0.05㎡), 특히 여러 쌍이 동일한 offset을 보이는 경우 | 경동의 0.0045㎡ 반복 패턴이 가장 강한 증거 |
| **D. 매핑 오류** | — | 이번 감사 범위(단일 source 파싱)에서는 매핑 자체가 없어 해당 없음 |
| **E. 판단 불가** | **개별 사례 대부분** | 타입 코드/공급면적 연결이 없는 한, diff 크기로 "강한 정황"은 말할 수 있어도 개별 쌍을 B 또는 C로 최종 확정할 근거는 없음 |

**결론**: 확률적으로 "diff<0.05㎡는 십중팔구 C(동일 타입), diff≥0.15㎡는
B(다른 타입) 쪽에 더 가깝다"는 **경향**은 실측으로 뒷받침되지만, 이를
근거로 자동 병합하는 것은 사용자 지시("임의 병합 금지", "근사값만으로
병합 금지")에 반한다 — §12/§13에서 이 결론을 어떻게 안전하게 반영할지
다룬다.

## 13. Grouping key 우선순위 — 실제 데이터 기준 결론(§13)

| 우선순위 | Key | 오늘 사용 가능? |
|---|---|---|
| 1. type code | `PresaleHouseTypeDetail.houseTy` | ❌ 기존 준공 단지에 연결 안 됨(§8) |
| 2. supply area + exclusive area | `supplyArea` | ❌ 동일 이유 |
| 3. verified source mapping | — | ❌ 검증된 매핑 자체가 없음(§8의 1건도 미확정) |
| 4. exact exclusive area | MOLIT `excluUseArea` | ✅ 유일하게 지금 쓸 수 있는 key |

**핵심 결론**: 1~3번이 전부 오늘 사용 불가능하므로, **현재는 4번(정확한
전용면적 값, 병합 없음)이 유일하게 안전한 선택이다.** `round
(exclusiveArea)`류의 단순 반올림 그룹핑은 명시적으로 채택하지 않는다
— §11에서 확인했듯 diff<0.05㎡ 쌍이 "십중팔구 동일 타입"이라는
통계적 경향이 있더라도, 이를 근거로 **디스플레이 레벨에서조차
자동 병합하는 기능을 이번 STEP에서 새로 제안하지 않는다**: 이미
직전 STEP(APT DETAIL QA/IA)에서 칩 개수 문제(최대 39종)를 "상한 제거
+ 전체 가로스크롤"로 해결했으므로, 근접 중복이 많아도 UI가 깨지지
않는다 — 즉 "칩이 너무 많아서" 병합이 필요한 상황 자체가 이미
해소돼 있다. 병합의 이득(칩 개수 감소)보다 위험(검증 안 된 병합)이
더 크다고 판단한다.

| C. 거래 상세 | `전용 84.9986㎡`(필요시 원본 정밀도까지) | 좌동(공급면적은 타입 단위라 거래 상세엔 보통 불필요) |

## 15. "평형" 사용 조건(§15) — 원칙 확정

**"OO평형"이라는 표현은 검증된 공급면적이 있을 때만 사용한다.** 전용
면적만 있는 경우(오늘의 사실상 전체 케이스) "약 25.7평"처럼 **근사
평 환산**으로만 표시하고, "평형"이라는 단어 자체를 대표 라벨에
붙이지 않는다 — 사용자 관행("34평형"은 공급면적 기준이라는 암묵적
합의)과의 충돌을 피하기 위함이다.

**실무 점검 결과**: 기존 `formatPyeong()`(Hero 표시용)은 이미 "약
{N}평"(평형이 아닌 "평") 형태로 올바르게 구현돼 있다. 다만
`AreaSelector`/`TradeTimelineList`의 평 토글이 쓰는
`getUniquePyeongLabels()`의 칩 라벨은 `"{N}평"`만 반환하고 `formatPyeong()`
처럼 "약" 접두어를 붙이지 않는다 — **경미하지만 실제로 존재하는
일관성 차이**(칩은 "25.7평", Hero는 "약 25.7평")로, "평형" 오용은
아니지만 정확도 표현의 일관성 측면에서 향후 정리 후보로 기록한다
(이번 STEP은 코드 변경 금지 원칙상 수정하지 않음, §35 unresolved).

## 16. 공급면적 없을 때 fallback(§16)

**정책 확정**: 대표 칩 = `전용 {N}㎡`(또는 평 토글 시 `약 {N}평`),
상세 = 필요한 정밀도까지의 정확한 전용면적. **"34평형" 추정 절대
금지** — 오늘 이 정책이 사실상 100%의 케이스에 적용된다(§8 coverage
0%).

## 17. Supply → 평형 rounding 규칙(향후 대비 설계, §17)

공급면적이 실제로 확보되는 미래를 대비해 규칙만 미리 정의한다(오늘
적용 대상 없음):

- `평형 = Math.round(공급면적M2 / 3.305785)`(nearest integer, 반올림).
- 검증: 33.5 → 34(반올림), 34.4 → 34(내림), 34.5 → 35(반올림) —
  JS `Math.round`의 표준 동작(0.5는 올림)과 일치, 특별한 예외 임계값
  처리 불필요.
- **국내 관행과의 정합성 확인**: 흔히 "34평형"으로 불리는 전용
  84~85㎡대 아파트의 실제 공급면적은 통상 112~113㎡대(청약홈 실측
  샘플에서도 `084.9993A` supplyArea=118.98처럼 84공급면적대가 110~
  119㎡ 범위로 관측됨) — 112~113㎡ 구간이 위 공식으로 34평형을
  만들어내는지 확인: 112.4/3.305785=34.01→34, 113.9/3.305785=34.46
  →34, 118.98/3.305785=36.0→36(더 큰 평면 타입) — **관행과 대체로
  합치**하나, 84타입이라고 전부 34평형은 아니라는 것도 함께 확인됨
  (타입마다 공급면적 자체가 다르므로 전용면적만으로 평형을 추정하면
  안 된다는 §15/§16 원칙의 실증).

## 18. 동일 평형 여러 타입(§18)

공급면적 확보 후에도 `34A`/`34B`처럼 서브타입이 있을 수 있음을
`houseTy`의 말미 알파벳에서 이미 확인했다(§9). **정책**: 실제 타입
코드(`houseTy`의 알파벳)가 존재할 때만 `34A`/`34B`로 구분 표시하고,
타입 코드가 없는 소스에서는 **임의로 A/B/C를 생성하지 않는다** —
사용자 지시 그대로. 오늘은 어차피 타입 코드가 기존 단지에 연결되지
않으므로 이 케이스 자체가 발생하지 않는다(§16).

## 19. AreaChip contract 제안(§19)

사용자가 예시로 든 구조를 **오늘 실제로 채울 수 있는 필드만** 반영해
최소화했다. `exclusiveAreaVariants` 같은 "병합된 값들의 배열"은
포함하지 않는다 — §13 결론상 병합 자체를 하지 않기 때문에, 정확한
전용면적 값 하나당 칩 하나가 그대로 유지된다(변형 배열이 필요 없음).

```ts
interface AreaChip {
  id: string;              // 오늘: exclusiveAreaM2를 문자열화한 안정적 key(병합 없음, raw 값 그대로)
  exclusiveAreaM2: number; // 원본 그대로, 절대 반올림 저장 안 함
  displayLabel: string;    // "84.99㎡"(충돌 해소된 라벨, 기존 getUniqueAreaLabels 로직 그대로) 또는 평 토글 시 "25.7평"
  supplyAreaM2: number | null;  // 오늘은 사실상 항상 null(SUPPLY_AREA_NOT_AVAILABLE)
  pyeongLabel: string | null;   // supplyAreaM2가 검증됐을 때만 "N평형", 그 외 null(칩 라벨의 평 환산은 displayLabel이 이미 담당)
  tradeCount: number;      // 이 정확한 raw 값에 속한 거래 수(참고 정보, 신뢰도 표시용)
}
```

`sourceConfidence` 같은 enum은 사용자에게 그대로 노출하지 않는다는
기존 원칙(S2C Score Engine과 동일)을 유지 — `supplyAreaM2 === null`
자체가 이미 "전용만 있음"이라는 충분한 신호이므로 별도 confidence
enum 없이도 UI가 안전하게 분기할 수 있다(§27).

## 20. 거래 grouping(§20)

오늘은 타입 검증이 불가능하므로, "34평형을 선택하면 검증된 타입
거래만 보인다"는 목표는 **공급면적 연결이 확보된 이후에만** 실현
가능하다. 지금은 이미 올바르게 동작 중인 방식 — **정확한 전용면적
값이 곧 필터 key**(`t.area === selectedArea`, 이전 STEP들에서 확인된
그대로) — 을 유지한다. 이 방식은 "다른 타입 거래 혼합" 위험이
구조적으로 없다(애초에 정확히 같은 raw 값만 필터링되므로).

## 21. Chart grouping(§21)

`PriceTrendChart`/`InvestmentMetrics`는 이미 `selectedArea`(정확한
raw 문자열 key)를 그대로 받아 필터링한다(이전 STEP 감사에서 확인) —
AreaSelector/TradeTimelineList/Hero/차트/투자지표가 **전부 동일한
raw 값 identity**를 공유하고 있어, 사용자가 요청한 "모두 같은 group
contract 공유" 요건을 오늘 기준으로 이미 만족한다(그룹 자체가
"raw 값 = group"이기 때문에 별도 매핑이 필요 없다).

## 22. selectedArea 구조 조사(§22, 구현 안 함)

`selectedArea`는 MOLIT 원본 문자열에 단위가 붙은 형태(`"84.99m²"`류,
`api-molit.ts`의 `area` 문자열 생성 로직 그대로) — 반올림되지 않은
raw 값이다. 근본적으로 "표시 문자열을 데이터 identity로 재사용"하는
형태라 이상적이지 않지만(표시 정밀도가 바뀌면 key도 영향받을 이론적
위험), 실제로는 이 문자열이 애초에 원본 API 응답을 그대로 옮긴
것이라 표시 로직과 무관하게 안정적이다. **이번 STEP에서 구조를
바꾸지 않는다** — 사용자 지시대로 조사만.

## 23. Precision 정책 확정(§23)

| 목적 | precision |
|---|---|
| 대표 칩 | 충돌 시에만 자동 확장되는 2~4자리(기존 `getUniqueAreaLabels`, 그대로 유지) |
| 타입 상세 | 2자리 기본(`전용 84.99㎡`) |

기존에 이미 구현된 정밀도 정책(직전 STEP)이 그대로 이 기준에
부합한다 — 추가 변경 불필요.

## 24. ㎡ ↔ 평 토글 재평가(§24)

**추천: C. 상세 숫자 변환용으로만 유지.**

- A(유지)는 사실상 C와 같은 결론이지만, "대표 평형 중심 UI로 오해될
  가능성"에 대한 명시적 점검이 필요해 C로 명확히 한다.
- B(대표칩에서 제거)는 과함 — 토글 자체는 정확한 전용→평 환산이라
  "오해"를 일으키지 않는다(§15에서 확인했듯 "평형" 단어를 쓰지 않고
  "평"만 쓰는 현재 구현이 이미 안전).
- D(공급면적 확보 후 평형 중심 UI로 교체)는 **오늘 데이터로는
  불가능**(§8 coverage 0%) — 미래 방향으로는 맞지만 이번 STEP의
  실행 대상이 아니다.

**조건부 권고**: §15에서 발견한 "약" 접두어 불일치(Hero는 "약
25.7평", 칩은 "25.7평")를 향후 작은 정리 STEP에서 통일할 것 —
사용자에게 "이게 정확한 값"이라는 오해를 줄 여지를 낮춘다(이번
STEP은 코드 변경 안 함).

## 25. 호갱노노식 UX 비교(§25, 원칙만 분석)

호갱노노류 UI의 "대표 34평 + 보조 공급/전용" 구조는 **공급면적이
확보돼 있다는 전제** 위에서만 성립한다. 이집의 현재 데이터는 그
전제를 충족하지 못한다(§8) — 그대로 복제하면 "34평형"을 추정해
표시하게 되어 사용자 지시("임의 평형 생성 금지")를 정면으로
위반한다. **적용 가능성 평가**: 구조 자체(대표/보조 2단 표기)는
차용할 가치가 있으나, "대표"의 기준을 오늘은 전용면적으로, 향후
공급면적이 확보되면 자동으로 전환되는 방식으로 설계해야 한다 — §26.

## 27. Data Confidence(§27)

내부적으로 `HIGH`(공급면적이 검증된 매핑에서 직접 확보)/`MEDIUM`
(이름/좌표 기반 추정 매핑, 오늘은 미채택)/`LOW`(불확실) 단계를
정의할 수 있으나, **오늘은 공급면적 데이터 자체가 없어 이 enum이
실질적으로 쓰일 곳이 없다.** `AreaChip.supplyAreaM2 === null`이
곧 "정보 없음"을 뜻하므로 별도 enum 없이 충분하다(§19) — 향후 §8의
매핑이 실제로 구축되면 그때 `HIGH`/`MEDIUM` 구분이 의미를 가진다.
사용자에게는 어떤 경우든 enum을 그대로 노출하지 않는다(기존 Score
Engine 원칙과 동일).

## 30. DB 필요 여부(§30)

**결론: A. 기존 데이터만으로 충분(단, 실제로는 "포기"에 가까움) —**
공급면적을 안전하게 제공하려면 사실상 **D(외부 supply data 수집
필요)** 가 유일한 실질적 해법이지만, 이는 새 외부 API 연결이 필요한
작업이라 이번 STEP 범위 밖이다(신규 유료/외부 API 금지 원칙과도
연결). **B(별도 AreaType cache)/C(ApartmentMaster 확장)**는 원본
공급면적 데이터가 없는 상태에서 스키마만 준비하는 것이라 실익이
없다 — 데이터 소스가 확보된 이후에 진행하는 것이 순서상 맞다.

**이번 STEP에서 schema 변경 없음**(원칙대로).

## 31. 전국 확장 가능성(§31)

이번 감사에서 채택한 정책(전용면적 우선, 공급면적은 검증된 매핑이
있을 때만 사용, 병합 금지)은 **부산 전용 가정이 전혀 없다** — MOLIT
API/`ApartmentMaster` 스키마가 전국 공통이고, 공급면적 부재 문제도
지역 특성이 아니라 **데이터 아키텍처 자체의 구조적 한계**이기 때문에
서울/경기 등 다른 지역에서도 동일하게 적용 가능하다. 향후 공급면적
source(§30-D)가 확보된다면 지역 무관하게 동일한 `AreaChip.supplyAreaM2`
분기 로직이 그대로 작동한다.
