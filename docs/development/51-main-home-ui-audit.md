- "최근 본 단지" 섹션이 **없다**(상세페이지 UI-C1에서만 존재).
- "재개발·분양" 진입점이 본문에 **없다**(상단/하단 nav에만 있음).
- 브랜드 태그라인/슬로건이 **없다**(h1이 캐주얼한 질문형 문구뿐).

## 2. 현재 사용자 동선 (production 기준)

**A. 특정 아파트를 아는 사용자**("대신롯데캐슬 보고 싶다")
```
홈 → 검색창에 "대신롯데캐슬" 입력 → "✨ AI 검색" 클릭
→ /ai-search로 이동 → Gemini가 자연어를 해석 → intent 판정
→ (운 좋으면) condition_search로 해석돼 결과 카드에 뜸
→ 카드 클릭 → 상세 이동
```
**문제**: 정확한 단지명을 알고 있어도 AI 해석 단계를 강제로 거친다.
LLM 호출 1회, 응답 대기, 오분류 가능성이 전부 불필요한 마찰이다.
클릭 수 최소 3~4단계, 게다가 "정확히 그 아파트"가 아니라 "조건에 맞는
후보들"로 보여줄 가능성이 있다(AI 검색은애초에 조건검색 엔진).

**B. 조건으로 찾는 사용자**("5억 이하 학교 가까운 집")
```
홈 → 검색창 입력 → AI 검색 → /ai-search(condition_search) → 결과 카드 → 상세
```
**문제 없음** — 이 동선이 바로 AI 검색이 설계된 목적이라 자연스럽다.

**C. 지도를 탐색하고 싶은 사용자**
```
홈 → "지도 검색" 카드 클릭 → /map
```
**문제 없음** — 클릭 1회, 명확.

**D. 최근 봤던 아파트로 돌아가는 사용자**
```
홈에는 진입점이 없음 → 브라우저 뒤로가기 또는 재검색만 가능
```
**문제**: 기능(localStorage 저장)은 이미 있는데 홈에서 접근할 방법이
없다 — 상세페이지의 "빠른 검색" 모달을 열어야만 보인다.

**E. 재개발/분양을 보려는 사용자**
```
홈 본문에는 진입점 없음 → 상단/하단 nav의 "재개발·분양" 클릭해야 함
```
**문제**: 홈 스크롤만으로는 이 기능의 존재를 알기 어렵다.

## 3. 현재 홈의 최대 문제 (요약)

**"일반 아파트 이름 검색"이라는, 사용자가 가장 많이 쓸 가능성이 높은
기능이 홈에 아예 없다.** 대신 모든 검색이 AI 자연어 해석을 거치도록
강제된다 — ROLE 1과 ROLE 2가 하나의 입력창에 뒤섞여 있다.

## 5. 일반검색 재사용 가능성 조사 (핵심 결론)

**결론: 100% 재사용 가능, 신규 코드 거의 불필요.**

`ApartmentQuickSearch.tsx`가 이미 정확히 이 기능을 구현해 두었다
(상세페이지 UI-C1 "빠른 검색" 모달에서 사용 중):

- 내부적으로 `ApartmentAutocomplete`(카카오 키워드 검색, 세대수/준공
  보강)를 그대로 사용
- 검색어가 비어 있으면 `getRecentApartments()`로 **"최근 본 단지"를
  자동으로 보여줌** — ROLE 1과 ROLE 4(최근 본 단지)를 이미 한
  컴포넌트로 통합 제공
- 선택 시 좌표→법정동 역지오코딩 + 실거래 1년 조회로 "이 이름+동에
  실제 데이터가 연결되는지" 검증한 뒤에만 상세로 이동(오매칭 방지,
  STEP47/48 이전부터 이미 검증된 정책)
- 실패해도 다른 단지로 대체하지 않고 정직하게 실패를 알림

현재는 `activeModal === '빠른 검색'`일 때 **모달로만** 뜬다
(`apt-client.tsx` 660번대 참고). 홈에서는 두 가지 배치 방식이 가능:

- **A안(권장)**: 홈에서도 동일하게 모달/오버레이로 열기 — 코드
  변경이 사실상 0에 가깝다(이미 `onClose` prop을 받는 독립
  컴포넌트).
- **B안**: 홈 첫 화면에 인라인으로 바로 배치 — `ApartmentQuickSearch`를
  감싸는 wrapper만 살짝 조정(모달 전용 스타일 일부 제거) 필요.

**새 검색 API, 새 매칭 로직, 새 DB 테이블 전부 불필요.**

## 6. AI 검색 역할 재확인

`ai-search-client.tsx`를 읽어 확인 — Gemini 3-intent 구조
(`condition_search`/`regional_stats`/`compare`)로 이미 설계된
**조건/통계/비교 전용 도구**다. 이름을 안다고 바로 찾는 도구가
아니라 애초에 "생각하고 찾아주는" 역할로 설계돼 있다 — ROLE 2로
재배치하는 것이 도구의 원래 설계 의도와도 일치한다. **AI 검색 로직은
전혀 건드리지 않는다.**

## 7. 최근 본 단지 — 홈 배치 판단

- **localStorage 재사용**: 가능(`recent-apartments.ts`, 이미
  DB 미저장 원칙으로 구현됨)
- **표시 가능 필드**: `name`/`address`/`lawdCd`/`dong`/`visitedAt`뿐 —
  **가격 필드가 없다.** 가격을 보여주려면 단지마다
  `/api/apt/[name]` 실거래 API를 추가로 호출해야 한다(최대 8건 →
  최악의 경우 홈 진입마다 8회 API 호출, N+1 패턴).
- **V1 권장**: 이름 + 지역만 표시(가격 없이). `ApartmentQuickSearch`가
  검색어 없을 때 이미 이 형태(이름+주소)로 렌더링하므로 그대로
  재사용하면 추가 API 호출이 발생하지 않는다.
- **DB 신규 저장 금지** 원칙 그대로 유지(이미 클라이언트 전용).

## 9. 하단 Navigation 전수검토

**현재 컴포넌트**: `Header.tsx`의 `<ul className={styles.menuList}>`,
데스크톱 상단바와 모바일 하단탭바를 **같은 마크업 하나**로 처리하고
CSS `@media (max-width: 900px)`에서 `position: fixed; bottom: 0`으로
전환한다(`/map` 페이지만 `hideMobileNav`로 이 기본 탭바를 끄고
`MapBottomNav`라는 자체 구현을 별도로 씀 — 코드 중복이지만 이번
STEP에서 통합하지 않음, 범위 밖).

**아이콘 방식**: 이모지 직접 사용(🏠🗺️📊🏗️👤), SVG 아이콘 라이브러리
**전혀 설치돼 있지 않다**(`package.json`에 lucide-react/heroicons/
react-icons/phosphor 등 전무, grep으로 확인).

**Active state**: `pathname` 기준 클래스 토글, 정상 작동
(`color: var(--text-primary) !important; font-weight: 800`).

**높이**: 고정 60px.

**Safe-area**: **`.menuList` 자체에는 `env(safe-area-inset-bottom)`
처리가 없다.** 다만 각 페이지의 본문 하단 패딩(`home-client.module.css`
등)이 `calc(5.5rem + env(safe-area-inset-bottom))`처럼 콘텐츠가 nav에
가리지 않도록 여백을 확보하고는 있다 — **nav 바 자체의 탭 영역이
홈 인디케이터 제스처 존과 겹칠 수 있는 것**은 이번 조사에서 발견한
실제 개선 여지(경미, BLOCKER 아님).

**메뉴명 길이 실측**(iframe 격리 테스트, 360/375/390px 3개 폭):

| 폭 | overflow | 줄바꿈 | "재개발·분양" 실제 폭 | 다른 라벨 대비 |
|---|---|---|---|---|
| 360px | 없음 | 없음 | 59px | 홈(12px)·지도/통계(25px)·MY(18px) 대비 **2.4~5배** |
| 375px | 없음 | 없음 | 62px | 동일 경향 |
| 390px | 없음 | 없음 | (동일 경향, 측정 완료) | 동일 경향 |

**결론**: overflow나 줄바꿈 같은 하드 버그는 없다(사용자가 우려한
"모바일 폭 문제"가 깨짐으로 이어지지는 않음). 다만 **5개 중 압도적으로
가장 긴 라벨이라 시각적 균형이 깨진다** — 실제 개선 여지로 인정,
§14에서 처리 방안 제시.

**각 메뉴 가치**:
- 홈: 항상 필요
- 지도: ROLE 3 핵심, 항상 필요
- 통계: AI 검색(regional_stats)과 목적이 겹치는 면이 있으나, AI 검색은
  자연어 질의고 통계는 구조화된 랭킹/차트 화면이라 도구 성격이 달라
  병존 가치 있음
- 재개발·분양: 독립적인 콘텐츠 영역(분양 정보/재개발 프로젝트), 다른
  메뉴로 흡수 불가
- MY: 로그인/마이페이지, 향후 즐겨찾기 등의 그릇으로 필요

## 10. 아이콘 시스템 추천

이모지 그대로 두거나(무료, 이미 일관되게 쓰고 있음, 플랫폼별 렌더링
차이는 있으나 큰 문제 보고 없음), SVG 아이콘 라이브러리로 교체 중
하나를 선택해야 한다.

**신규 package 필요**: 예. 현재 아무 아이콘 라이브러리도 없다.
**추천**: `lucide-react` — MIT 라이선스(무료, CLAUDE.md 8번 원칙의
"유료 API"에 해당하지 않음), tree-shakeable(쓴 아이콘만 번들에
포함), Next.js/React 생태계에서 가장 널리 쓰이는 선택지 중 하나,
stroke 기반이라 "동일 stroke/동일 크기/active=그린/inactive=회색"
요구사항을 CSS 한 줄(`color`, `stroke-width`)로 통일하기 쉽다.

**단, 이번 STEP에서 설치/적용하지 않았다** — 새 의존성 추가는 구현
STEP에서 사용자 확인 후 진행 권장(선택지만 제시).

## 12. 모바일 우선 전략 (360/375/390px)

- 검색창: 현재도 `width: 100%` 기반이라 폭 자체는 문제없음 — 다만
  버튼 텍스트("✨ AI 검색")가 고정 노출이라 인풋 폭을 잠식한다.
  일반검색 추가 시 입력창과 버튼의 비율 재조정 필요(구현 STEP에서
  실측).
- 한 손 터치: 검색창 상단 배치는 이미 엄지 도달 범위 안 — 유지.
- 카드 폭: `iconGrid`가 이미 `repeat(auto-fit, minmax(...))` 계열로
  반응형 — 실제 값은 CSS에서 재확인 필요(이번 STEP은 코드 존재
  확인까지, 픽셀 미세조정은 구현 STEP).
- section 간격: 현재 2개 섹션(검색/Quick메뉴) 뿐이라 간격 문제
  적음 — 최근 본 단지/일반검색 추가 시 카드 밀도 재검토 필요.
- 하단 nav: §9~11 참고.
- **첫 화면(스크롤 없이 보이는 영역)에 무엇이 보이는가**: 현재는
  검색 Hero 전체 + 추천 프롬프트 일부만 보임(핵심 Quick 메뉴는
  스크롤해야 보임). 지도/일반검색 CTA를 첫 화면 안으로 끌어올리는
  것이 §11 IA안의 핵심 목표.

## 13. PC 전략

- 현재 `max-width` 컨테이너 패턴은 앱 전체에서 이미 일관 사용 중
  (`globals.css` `.container { max-width: 1200px }`) — 홈도 동일
  패턴 재사용.
- PC에서는 하단탭바가 사라지고 상단 메뉴로 전환되므로(이미 구현됨),
  홈 좌우 여백/카드 열 수만 데스크톱 폭에 맞게 조정하면 된다 — 모바일
  구조를 억지로 늘리지 않는다는 원칙과 이미 부합.

## 14. 경쟁 서비스 원칙 참고 (외부 조사 없이, 코드/사용자 관점만)

호갱노노/아실 계열이 공통적으로 지키는 원칙(이미 알려진 일반 지식
기준, 신규 웹조사 안 함):
- 지도가 항상 최우선 진입점 중 하나
- 검색은 즉시성(이름 → 상세)이 최우선, 부가 기능이 검색을 가리지 않음
- 상세 화면 몰입도가 높음(이집은 이미 STEP39~50에서 V1 LOCK까지
  완료해 이 축은 강점)
- 비교/필터는 있지만 첫 화면의 주인공은 아님

## 15. 이집 V1 홈 차별화

이미 확보된 자산 중 홈에서 전면에 내세울 만한 것:
- **실거래 기반 상세페이지**(방금 V1 LOCK) — "검색하면 바로 실제
  데이터가 나온다"는 것 자체가 차별점
- **AI 조건검색**(Gemini 3-intent) — "5억 이하 학교 가까운 집" 같은
  자연어 질의는 호갱노노/아실에 없는 이집만의 기능
- **대중교통(버스 실노선)/생활편의/교통** — 상세페이지에 이미 있음,
  홈에서는 약속만 하지 않고 상세로 자연스럽게 유도

**하지 않을 것**: 출퇴근 접근성/점수체계는 미구현이므로 홈에서
암시하거나 문구로 약속하지 않는다(§18 지시 그대로 준수).

## 16. 현재 홈에서 발견된 제거/축소/유지 후보

| 항목 | 발견 사실 | 판단 |
|---|---|---|
| AI 검색 Hero | 유일한 검색 진입점으로 과부하 | **역할 분리**(Secondary로 재배치, 삭제 아님) |
| 추천 프롬프트 칩 4개 | 실제로 유용(AI 검색 사용법 예시), 중복 아님 | 유지 |
| 광고 영역 2곳 | `NEXT_PUBLIC_ADS_ENABLED=false`라 현재 **아무것도 렌더링 안 함**(빈 placeholder조차 없음, 코드로 확인) | 유지(이미 문제 없음) |
| 큰 카드 2개(지도/시장통계) | 실제 기능, 문제 없음 | 유지 |
| 아이콘 그리드 6개(stats 하위) | 전부 실제 페이지로 연결, 빈 카드 없음 | 유지(다만 위치는 IA안에서 재배치 검토) |
| 브랜드 메시지 | **없음** — 발견된 결핍 | §17 IA안에서 추가 검토(과하지 않게) |
| 일반 아파트 검색 | **없음** — 가장 큰 결핍 | §5 대로 추가 |
| 최근 본 단지 | **없음** — 결핍 | §7 대로 추가 |
| 개발중 placeholder | 홈 안에는 없음(모두 실제 라우트로 연결됨) | 해당 없음 |

**"의미 없는 hero"/"AI search 강제 동선"/"중복 CTA"**: 정확히
해당하는 것은 "AI 검색 강제 동선" 하나다(hero 자체는 의미가 있으나
유일한 검색 경로라는 게 문제). 빈 카드나 개발중 placeholder는 홈에
없었다(상세페이지와 달리 홈은 애초에 실제로 존재하는 기능만 배치돼
있었음).

## 17. 추천 V1 홈 구조안

사용자가 제시한 "후보 A"를 조사 결과에 맞춰 다음과 같이 구체화한다
(구조는 후보 A와 동일하되, 각 요소가 무엇을 재사용하는지 명시):

```
[Header] — 기존 그대로

[Search Hero]
  "복잡한 부동산, 이집으로 쉽게" (또는 유사 톤, 과하지 않게 1줄)
  [🔍 아파트 이름을 검색하세요]  ← 신규 배치, ApartmentQuickSearch 재사용(§5)
  → 검색어 없을 때 자동으로 "최근 본 단지" 노출(같은 컴포넌트, §7)

[빠른 액션] (2버튼, 동일 시각 무게)
  🗺️ 지도에서 찾기        → /map (기존)
  ✨ 조건으로 집 찾기      → 기존 AI 검색 Hero를 이 자리로 이동
                            (placeholder에 기존 추천 프롬프트 예시 유지)

[탐색] (기존 "핵심 Quick 메뉴" 재구성)
  📊 지역/아파트 통계 큰 카드 1개 (기존 6개 아이콘 그리드는 /stats
     페이지 자체에서 이미 보여주므로 홈에서는 통계 큰 카드 1개로
     축약하고 나머지는 /stats 진입 후 노출 — 홈 스크롤 길이 감소)
  🏗️ 재개발·분양 큰 카드 1개 (신규 배치 — 기존에 홈 본문에 없었음)

[하단 nav] — 기존 컴포넌트 그대로, 라벨만 §11 반영
```

**핵심 변경 논리**: AI 검색을 없애지 않고 "먼저 보여줄 도구"에서
"두 번째 CTA"로 역할만 재배치한다. 일반검색을 최상단에 두는 이유는
"이름을 아는 사용자"가 조건 없이 즉시 목적지에 도달할 수 있어야
한다는 §4 원칙 때문이다.

## 18. 전체 Home IA (섹션 순서 최종)

1. Search Hero(일반검색 Primary + 최근 본 단지 자동 표시)
2. 빠른 액션(지도 / AI 조건검색)
3. 탐색(통계 / 재개발·분양)
4. (광고 — 활성화되면 자연스럽게 노출, 현재는 비노출 유지)
5. 하단 nav

기존 대비 섹션 수는 거의 그대로(2→3~4개)이고, 정보량이 아니라
**역할 순서**만 재배치했다 — "길게 늘어놓지 않는다"는 §10 원칙을
지켰다.

## 19. 목표 동선 (V1 설계 기준)

- 특정 단지 검색: **홈 → 검색 → 상세 = 2단계**(현재 AI 경유 3~4단계
  대비 개선)
- 지도: 홈 → 지도 → marker → 상세(기존과 동일, 이미 최소)
- 조건검색(AI): 홈 → AI Search → 결과 → 상세(기존과 동일, 위치만
  이동)
- 최근 본 단지: 홈 → (검색창의 빈 상태에서 바로 노출) → 상세 =
  **1.5단계**(검색창을 누르기만 하면 바로 보임)

두 동작을 구분할지는 MAP UX 후속 STEP에서 별도 판단.

## 22. 구현 STEP 분리안

**2개 STEP으로 압축**(요청된 "2~3개, 10개로 쪼개지 말 것" 원칙 반영):

### MAIN UI-B1 — 검색 Hero 재구성 (핵심)
- `ApartmentQuickSearch`를 홈 Search Hero에 재사용 배치(§5 A안 또는
  B안 중 구현 시점에 확정)
- 기존 AI 검색을 "빠른 액션"의 Secondary 카드로 이동(로직 무수정,
  위치만 이동)
- "지도에서 찾기" 카드를 같은 빠른 액션 행에 나란히 배치
- 브랜드 태그라인 1줄 추가(과하지 않게)
- 예상 파일: `home-client.tsx`, `home-client.module.css` (2개)

### MAIN UI-B2 — 탐색 섹션 + 하단 nav 정리
- "핵심 Quick 메뉴"를 통계/재개발·분양 큰 카드 2개로 재구성(기존 6개
  아이콘 그리드는 /stats 페이지로 위임)
- 하단 nav "재개발·분양" 라벨 축약 적용
- (선택) `lucide-react` 도입 여부 사용자 확인 후 아이콘 교체 —
  별도 하위 STEP(MAIN UI-B3)으로 더 쪼갤 수도 있음, 이모지 유지도
  유효한 선택지
- 예상 파일: `home-client.tsx`, `home-client.module.css`,
  `Header.tsx`, `Header.module.css` (4개)

두 STEP 모두 새 API/DB/schema가 필요 없다 — 전부 기존 컴포넌트
재배치 수준.

## 23. DB/API 필요 여부

**불필요.** `ApartmentAutocomplete`(카카오 키워드 검색),
`recent-apartments.ts`(localStorage), 기존 `/api/apt/[name]` 검증
호출까지 전부 이미 존재하는 자산이다. 신규 API/DB/schema/migration
없이 구현 가능하다.

## 24. 발견된 BLOCKER

**없음.** STOP 조건(§27) 어느 것도 해당하지 않았다:
- 홈 검색에 신규 DB/API 필수 아님
- `ApartmentAutocomplete` 재사용 가능(이미 여러 화면에서 재사용 중인
  범용 컴포넌트)
- Quick Search 매칭 로직(`ApartmentQuickSearch`) 재사용 가능(모달
  전용 스타일만 약간 조정하면 인라인 배치도 가능)
- 하단 nav 구조 변경이 전체 routing 변경을 요구하지 않음(라벨/배치만
  조정)
- 홈 개편이 상세 V1 LOCK 해제를 요구하지 않음(상세페이지 코드를
  전혀 건드리지 않는 설계)
