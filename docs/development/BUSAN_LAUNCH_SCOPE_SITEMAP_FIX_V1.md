# BUSAN LAUNCH SCOPE + SITEMAP FIX V1

브랜치: `main` / 기준 커밋: `02c4f31`
대상 도메인: `https://e-jip.com` (커토버 완료, 200 응답 확인)

검색엔진 등록 **직전** STEP. 색인 범위를 실제 출시 범위(부산)로 맞추고, 부산 밖
사용자에게 그 사실을 정직하게 알린다. DB/schema/migration 변경 없음.

## 1. 문제 — 실측

배포된 사이트맵을 직접 받아 확인했다.

```
curl https://e-jip.com/sitemap.xml | grep -c "<loc>"      → 462
그중 부산 관련                                              →  32
<loc>https://e-jip.com/stats?sido=%EC%84%9C%EC%9A%B8...&amp;sigungu=%EA%B0%95%EB%82%A8%EA%B5%AC</loc>
                                    ↑ 서울특별시                        ↑ 강남구
```

462개 중 **약 460개가 지역 URL**이고, 그 대부분이 부산이 아니었다.

### 근본 원인

`src/app/sitemap.ts`의 `buildRegionRoutes()`가 `src/lib/regions.ts`의 `REGION_DATA`
(전국 17개 시도 · 약 230개 시군구)를 **통째로** 순회하며 시군구마다 `/stats`와
`/school` URL을 하나씩 만들고 있었다.

`REGION_DATA`는 지역 **선택 UI**를 위한 전국 목록이다. 그걸 색인 범위로 그대로 쓰면
"이집은 전국 서비스"라고 검색엔진에 말하는 셈이 된다. 실제로는 부산 데이터를 제공하므로
서울 강남구 통계 페이지를 연 사용자는 빈 화면을 받는다.

## 2. 부산 우선 사이트맵 정책

### 포함

| 경로 | 개수 |
|---|---|
| `/`, `/stats`, `/school`, `/community` | 4 |
| `/stats?sido=부산광역시&sigungu=<16개 구·군>` | 16 |
| `/school?sido=부산광역시&sigungu=<16개 구·군>` | 16 |
| `/community/<id>` (최근 500개) | ≤ 500 |

### 제외

서울 / 경기 / 인천 / 대구 / 대전 / 광주 / 울산 / 세종 / 강원 / 충북 / 충남 / 전북 /
전남 / 경북 / 경남 / 제주 — 즉 **부산 외 전 지역**.

`/api/`, `/admin`, `/my`, `/community/write`는 기존대로 robots에서 막혀 있다.

### 지역 목록의 출처

새로 적지 않았다. `src/lib/report/region-scope.ts`의 `BUSAN_DISTRICTS`
(부산 현행 16개 자치구·군, Production 실측값으로 검증된 단일 출처)를 그대로 쓴다.
리포트 스코프 검증(`isBusanCurrentLawdCd`)과 **같은 목록**이므로 둘이 갈라질 수 없다.

전국 확장 시에는 그 목록만 늘리면 사이트맵이 따라온다.

### 접근 ≠ 색인

사이트맵에서 뺐다고 접근을 막지 않는다. `/stats?sido=서울특별시&sigungu=강남구`는
지금도 그대로 열린다. **사이트맵은 색인을 정하고, robots는 접근을 정한다** — 부산 외
지역을 robots로 막는 방식은 쓰지 않았다(§8).

## 3. `&amp;`는 오타가 아니다 (회귀 방지)

쿼리 구분자는 `&`가 아니라 `&amp;`다. 처음 보면 버그처럼 보이지만 아니다.

Next.js의 사이트맵 직렬화는 `<loc>`에 넣는 문자열을 **XML 이스케이프하지 않는다.**
실측 근거: 배포된 XML에 `&amp;`가 **한 겹으로만** 나온다 — 만약 Next가 이스케이프했다면
소스의 `&amp;`가 `&amp;amp;`가 됐어야 한다.

따라서 well-formed XML이 되려면 여기서 직접 이스케이프해야 하고, XML 파서가 이를 다시
`&`로 디코드하므로 크롤러가 받는 최종 URL은 `?sido=...&sigungu=...`로 정확하다.

이걸 `&`로 "고치면" 사이트맵이 well-formed XML이 아니게 된다. 테스트로 고정해뒀다.

## 4. 부산 밖 사용자 UX

### 원칙

지도는 **사용자의 실제 위치로 열린다.** 이 동작은 의도된 것이며 되돌리지 않았다.
진주·남해에서 열면 마커가 거의 없는데, 그게 "고장"처럼 보인다. 사실은 이집이 아직
부산 데이터를 우선 제공하는 것이다 — 그 사실만 말한다.

### 문구

```
현재 위치는 부산 외 지역입니다.
이집은 현재 부산 지역 데이터를 우선 제공하고 있습니다.
```

### 동작 규칙

| 규칙 | 구현 |
|---|---|
| 지도 사용을 막지 않는다 | 하단 상태 스택(`pointer-events: none`) 안에 넣고 카드만 `auto` |
| 오류처럼 보이지 않는다 | 경고색/에러 아이콘 없음 — 기존 '준비중' 배너와 같은 중립 톤 |
| pan/zoom마다 뜨지 않는다 | 세션당 1회, `sessionStorage`로 닫음 기억 |
| 닫을 수 있다 | 44px 터치 타깃 닫기 버튼 |
| 로그인 불필요 | 세션/네트워크 의존 없음 |
| 가짜 마커를 만들지 않는다 | 안내만 표시, 데이터는 건드리지 않음 |

### 판정 방식 — 네트워크 호출 0

역지오코딩을 부르지 않는다. 좌표 bounding box 하나로 판정한다.

```
BUSAN_BBOX = { minLat: 34.9, maxLat: 35.45, minLng: 128.6, maxLng: 129.35 }
```

이 박스도 새로 만든 값이 아니다. `BUSAN_DATA_UX_AUTOMATED_QA_V1`에서 실측/합의해
`scripts/busan-qa-logic.ts`와 `src/lib/education/schoolinfo-stat-validate.ts`가 이미
쓰던 값이며, 세 번째 사본이 생기지 않도록 `src/lib/busan-bounds.ts` 하나로 모으고
학교 좌표 검증이 그걸 import하게 했다(**값은 그대로 — 판정 결과 변화 없음**).

여유를 둔 박스라 김해·양산 접경에서는 부산으로 판정될 수 있다. 이 용도에는 그 편이
맞다 — 부산 사용자에게 "부산 밖입니다"라고 잘못 말하는 쪽이 더 나쁘다.

## 5. 통계 기본 지역

### 감사 결과 (변경 전)

| 질문 | 답 |
|---|---|
| 정확한 현재 기본값 | `부산광역시 서구` (`lawdCd: '26140'`) |
| 어디서 오는가 | `src/contexts/RegionContext.tsx`의 `FALLBACK_REGION` |
| 언제 쓰이는가 | **GPS 실패/거부/비브라우저일 때만** |
| 마지막 선택 지역이 저장되는가 | **아니다** — 영속화 없음. 매 세션 새로 판정 |
| 현재 위치가 통계에 영향을 주는가 | **그렇다** — 첫 진입 시 GPS → 카카오 역지오코딩 → 그 지역으로 설정 |

GPS가 통계 지역을 정하는 동작은 **원래 의도된 아키텍처**다(코드 주석에 근거가 남아
있음: 홈/통계/학군이 하나의 지역 상태를 공유하기 위한 설계). §6에 따라 **바꾸지 않았다.**

### 변경한 것

`FALLBACK_REGION`만 `부산광역시 서구` → `부산광역시 전체`로 바꿨다.

```
lawdCd: '26140' → null
sigungu: '서구'  → ''
sidoCode: '26'  (그대로)
```

**안전하다고 판단한 근거:**

- `lawdCd: null` + `sigungu: ''`는 `RegionSelectModal`의 "시도 전체" 선택이 **이미
  만들어내는 상태**다. 새 상태를 발명한 게 아니다.
- 통계 뷰들의 prop 타입이 전부 `lawdCd: string | null`이고, null이면 `sidoCode`로
  시도 단위 집계를 요청하도록 이미 구현돼 있다(`VolumeChartCard`, `TransactionFeedView`,
  `PriceRankingView`, `ConcentrationView`, `GapInvestView` 등에서 확인).
- 서버 API가 `sidoAll` 플래그로 그 스코프를 되돌려준다 — 클라이언트가 추측하지 않는다.

**왜 바꿨나:** 부산 출시 범위는 16개 구·군 전체인데, 위치를 모르는 사용자를 특정 한
구에서 시작시키면 (1) 왜 하필 서구인지 설명할 수 없고 (2) 서비스 범위가 그 구뿐인
것처럼 보인다.

지도의 기본 중심(`DEFAULT_MAP_CENTER`, 부산 서구)은 **바꾸지 않았다** — 지도와 통계는
서로 다른 규칙을 따른다(§6).

## 6. MAP vs STATS 정책

| | MAP | STATS / SCHOOL / REPORT |
|---|---|---|
| 현재 위치 | 따른다(의도) | GPS로 초기 지역을 잡되, 사용자가 고르면 그 선택이 이긴다 |
| 부산 밖 | 열린다 + 안내 | 사용자가 명시적으로 선택 |
| 기본값 | 부산 서구 좌표 | 부산광역시 전체 |
| 데이터 범위 | 부산 우선 | 부산 16개 |

`userSelectedRef` 가드(사용자가 직접 고른 지역을 뒤늦은 GPS 응답이 덮어쓰지 않게 하는
장치)는 그대로 유지했다.

## 7. noindex

**추가하지 않았다.** §3에 따라 이 STEP은 사이트맵 범위로 한정했다.

부산 외 지역 페이지는 여전히 직접 열 수 있고 색인도 원천 차단되지 않는다(사이트맵에서
빠졌을 뿐). 이들에 `noindex`를 붙이려면 `/stats`·`/school`이 쿼리스트링으로 지역을
받는 구조상 **동적 메타데이터 분기**가 필요하고, 잘못 만들면 정상 페이지까지 색인에서
빠질 위험이 있다. 광범위한 noindex 도입은 하지 않는다 — 후속 과제로 기록한다.

### [선택] 부산 리포트 경로 색인

경로이지만, 현재 사이트맵에 **원래 포함돼 있지 않았고** 이번 STEP은 사이트맵 구조를
