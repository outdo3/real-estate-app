## 1. 라우트

| 경로 | 예시 | 렌더 |
|---|---|---|
| `/report/city/busan` | — | 부산 전체 |
| `/report/district/[lawdCd]` | `/report/district/26350` | 구·군 |
| `/report/dong/[lawdCd]/[dong]` | `/report/dong/26350/우동` | 동 |

- 전부 **서버 컴포넌트**이고 `dynamic = 'force-dynamic'`이다. 리포트는 수집 상태에 따라
  달라지고 `dataAsOf`/완전성을 화면에 그대로 노출하는 계약이라, 정적 캐시된 리포트는
  곧 거짓말이 된다.
- 스코프 검증은 **REPORT-1의 `isBusanCurrentLawdCd()`만** 쓴다. 화면에서 규칙을 다시
  만들지 않는다.
- `?period=30|90|365`만 허용한다(그 외 값은 조용히 30일로). 임의 기간을 URL로 받으면
  캐시 키가 파편화되고 스캔 범위가 무제한이 된다.

## 2. 데이터 흐름

```
page.tsx (server)
  → readRegionReport()      ← 유일한 DB 접근 지점 (REPORT-1)
  → ReportEnvelope
  → <RegionReportSheet envelope={...} />   ← envelope만 읽는 순수 표현 컴포넌트
```

**템플릿은 Prisma를 import하지 않고, 집계도 trust 재해석도 하지 않는다.**
화면의 모든 숫자·문구·신뢰 표시는 envelope 안에서 이미 결정되어 있다.
`grep -rn "prisma" src/components/report/` → 0건.

## 3. 템플릿 구조

`src/components/report/RegionReportSheet.tsx` 하나가 세 레벨을 모두 그리고,
**차이는 데이터(envelope)와 KPI 키 선택뿐**이다.

```
HEADER (브랜드 / 제목 / 기간·취소제외)
KPI 4개
DISTRIBUTION (city=구·군별, district=동별, dong=없음)
거래가 많은 단지
최근 실거래
최근 2년 최고 거래가 (기간 문구 필수)
이집 데이터 해석 (결정론적 문장만, 없으면 섹션 자체가 없음)
FOOTER (완전성 배지 / dataAsOf / 기간 / 주의사항 / 출처)
ACTION BAR (공유 / 저장 준비 중 / 지도)
```

레벨별 KPI:

| 레벨 | KPI |
|---|---|
| CITY / DISTRICT | 거래건수 · 중앙 거래가 · 직전 대비 거래량 · 최근 계약일 |
| DONG | 거래건수 · 중앙 거래가 · **㎡당 중앙가** · 최근 계약일 |

동에서 증감률 대신 ㎡당 중앙가를 쓰는 이유: 동은 표본이 작아 증감률이 한두 건에
좌우되는 경우가 많다(§5).

## 5. 신뢰 UX

| envelope | 화면 |
|---|---|
| `trust=SAFE` | 배지 없음 |
| `trust=LIMITED` | 노란 `참고` 칩 + 푸터에 사유 |

## 6. 표본 게이트 UX

건수는 사실이므로 그대로 보여주고, 비교성 지표만 `참고`로 낮추며, 해석 문장은
아예 만들지 않는다. 실제 렌더(부산 중구 보수동1가):

```
거래건수 1건
중앙 거래가 [참고] 1,550만원
㎡당 중앙가 [참고] 42.6만원/㎡
…
최근 1년 거래 7건으로 표본이 10건 미만입니다.
```

리포트가 깨져 보이지 않으면서 한계가 분명하다.

### 6.1 이번 STEP에서 강화한 규칙 — 직전 기간 표본

QA에서 거래 0건인 동이 **"1건 → 0건, 100% 감소"**라는 해석을 냈다. 수치는 참이지만
한 건에 좌우되는 문장이라 표본 게이트를 둔 취지에 어긋난다. 그래서 증감률은
**최근 1년 표본과 직전 기간 표본이 둘 다 10건 이상일 때만** `SAFE`가 되고, 그렇지
않으면 `LIMITED` + 해석 미생성으로 바꿨다(`region-report.ts`).

## 7. 딥링크

대표 거래/단지 카드는 **canonical `aptSeq`가 있을 때만** 링크한다:
`/apt/{name}?aptSeq={aptSeq}`. aptSeq가 없으면 링크 없이 카드만 렌더한다 —
이름만으로 링크를 만들면 다른 단지로 보낼 수 있다(AGENTS.md canonical identity).
QA에서 렌더된 모든 `/apt/` 링크가 `aptSeq=`를 포함함을 확인했다.

## 9. 성능 (§17)

`readRegionReport()` 실측(개발 PC → Supabase, 네트워크 왕복 포함, 워밍업 후):

| 스코프 | 기간 | 행수 | BEFORE | AFTER |
|---|---|---|---|---|
| 부산 city | 30일 | 1,861 | 2,060ms / 71.7MB | **273ms / 0.8MB** |
| 부산 city | 90일 | 6,680 | 2,604ms / 104.0MB | **318ms / 10.5MB** |
| 부산 city | 365일 | 35,194 | 3,136ms / 166.5MB | **964ms / 49.7MB** |
| 해운대구 | 365일 | 4,582 | 417ms / 35.8MB | **191ms / 12.5MB** |
| 우동 | 365일 | 1,078 | 123ms / 8.0MB | **83ms / 2.9MB** |

원인은 SQL이 아니라 **필요 없는 행을 읽던 것**이었다:

1. `previousRows`를 전부 읽어놓고 `.length`만 썼다 → `count()`로 교체.
2. 하이라이트 1건을 뽑으려고 **2년치 전체**를 읽었다(도시 단위 7만 행) →
   `orderBy(금액 desc, 계약일 desc, aptSeq asc) take 5`로 교체.
   정렬 우선순위를 순수 레이어 `topPricedTrades`와 **동일하게** 맞춰 결과가 같다.

라우트 실측(로컬 프로덕션 빌드): city 331ms / district 132ms / dong 111ms,
스코프 밖은 6~8ms(DB 조회 없이 즉시 거부).

**결론: 지금 SQL 집계로 옮길 필요 없다.** 기본 30일 city가 273ms다.
365일 city 964ms는 사용 가능하지만 가장 무거우므로, 장기 기간을 기본값으로 올리거나
동시 사용자가 늘면 그때 SQL 집계를 재검토한다.
