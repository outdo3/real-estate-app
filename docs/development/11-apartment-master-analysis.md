## D. aptSeq 안정성/유일성 — 구조 후보 평가

§C의 실측을 근거로 요청안의 4개 후보를 평가한다.

| 후보 | 평가 |
|---|---|
| A. `aptSeq` 단독 unique | **가능성 높음** — 형식 자체에 lawdCd가 접두어로 포함돼 있어 문자열 그대로 이미 전역 유일성을 만족한다(4개 지역 16,579건 실측 중복 0건). 다만 관측 기간이 18개월로 제한적이라 장기 안정성(재건축/대장 통폐합 등)은 미검증(§25). |
| B. `lawdCd + aptSeq` 복합키 | 형식상 `lawdCd`가 이미 `aptSeq` 문자열 안에 포함돼 있어 **중복 정보**가 된다 — A안 대비 추가 이점이 크지 않다. |
| C. `법정동 + 지번 + aptSeq` | 검증(§X)용 보조 정보로는 유용하나(같은 aptSeq에 다른 주소가 붙는지 감시하는 무결성 체크에 활용 가능), unique key 자체로 쓰기엔 과도하게 복잡하다. |
| D. **자체 Master id(내부 PK) + `aptSeq`(external unique, nullable)** | **권장** — §R에서 상세 근거를 제시한다. |

**결론**: `aptSeq`를 문자열 그대로 **external unique 후보 키**로 사용하는 것은 실측 근거상 타당하나, 이를 Prisma의 내부 Primary Key로 직접 쓰지는 않는 것을 권장한다(§R).

### E-2. 이번 STEP의 새 발견 — REGCODE_PROXY 의존을 피할 수 있는 경로

§C의 원본 XML에는 `umdNm`(법정동명)뿐 아니라 **`umdCd`(법정동 5자리 코드)가 이미 포함돼 있다**(예: 암남동 → `umdCd=12400`). 이를 직접 실측으로 검증했다 — `sigunguCd(=lawdCd)` + `bjdongCd(=umdCd)` + `bun/ji(=jibun)`를 그대로 건축물대장 API(`getBrRecapTitleInfo`)에 넣었을 때 **REGCODE_PROXY를 전혀 거치지 않고도 정상 응답을 받았다**(§G에서 실제 응답 전문 확인).

**즉, MOLIT 실거래가 있는 단지에 한해서는 법정동코드 확보에 REGCODE_PROXY가 필요하지 않다** — 이는 Master 구축 시 단일 장애점(01 문서 R-6) 리스크를 상당 부분 줄일 수 있는 실질적 발견이다. 다만 MOLIT 거래 이력이 전혀 없는 신축/미거래 단지는 여전히 Kakao `coord2regioncode` 또는 REGCODE_PROXY 둘 중 하나에 의존해야 한다(§W).

### E-3. 행정구역 개편 재확인 — 인천 서구(28260) 실측 이상 현상

§C의 5번째 지역으로 인천 서구(`lawdCd=28260`)를 18개월 조회했으나 **`resultCode=000`(정상) 응답에 거래 0건이 전 기간에 걸쳐 반복**됐다(API 오류 아님, 정상 응답의 빈 결과). `REGCODE_PROXY`에 `28260`을 질의하면 여전히 "인천광역시 서구"로만 응답하고 "검단구"/"서해구" 관련 코드는 **전혀 존재하지 않았다**(전수 검색 결과 0건). 즉:

- Kakao 지오코더는 이미 새 행정구역명("검단구"/"서해구")을 반환하기 시작했는데(06/10 문서에서 이미 관측),
- `REGCODE_PROXY`는 여전히 옛 코드/이름만 갖고 있고,
- MOLIT 자체는 옛 `lawdCd`(28260)로 거래를 전혀 매칭시키지 못하는 상태다.

**이 앱이 쓰는 세 개의 지역 데이터 소스(Kakao/REGCODE_PROXY/MOLIT)가 서로 다른 시점의 행정구역 기준을 갖고 있다는 것을 실측으로 확인했다** — 이는 Master의 `lawdCd` 필드가 "현재 시점 기준 단일 진실 공급원"이 될 수 없다는 뜻이며, §T(갱신 정책)에서 반드시 재검토가 필요한 사안으로 기록한다. 이번 STEP에서 원인을 완전히 규명하거나 해결하지 않는다.

건축물대장 API(§G) 응답에도 **좌표(lat/lng) 필드는 없다**(실측 확인 — `platPlc`/`newPlatPlc` 등 텍스트 주소만 제공). 따라서 Apartment Master에 좌표가 필요하다면 원천은 **Kakao geocoding뿐**이다(이 프로젝트에 다른 좌표 소스 없음, 신규 API 도입은 금지 항목).

| 확인 항목 | 결과 |
|---|---|
| 주소→좌표 성공률 | 이번 STEP에서 대량 지오코딩은 하지 않았다(금지 항목). §14(부산 서구 표본)의 소규모 실측에서 9/10건이 Kakao 키워드검색("동+이름")으로 좌표를 얻었다(90%) — 단, 이는 표본이 작아 전국 대표성을 주장하지 않는다. |
| 단지 중심 좌표 vs 건물 좌표 | Kakao 키워드검색 결과는 보통 단지 대표 지점(정문/관리사무소 등) 좌표로 보이며, 동별 정밀 좌표는 제공하지 않는다. |
| 동일 단지 여러 동 처리 | Kakao 키워드검색은 단지명으로 검색 시 대표 좌표 1개만 반환 — 개별 동 좌표는 별도 검색이 필요하며, 대단지의 "동수만큼의 정밀 좌표"까지는 이번 조사에서 확인하지 못했다. |
| 대단지 대표점 문제 | 확인됨(위와 동일) — Master가 "단지 중심점 1개"만 저장하는 정책이면 충분한지, 동별 좌표까지 필요한지는 향후 Master 활용처(지도 마커 등)에 따라 결정할 사항으로 남긴다. |
| 행정구역 개편 영향 | §E-3과 동일한 문제가 좌표 확보에도 이어질 수 있음(Kakao 자체는 좌표 확보엔 문제없으나, 좌표→행정구역 역산 시 §E-3 불일치가 재현될 수 있음) |

### G-4. 기존 코드의 숨은 결함 발견(이번 STEP에서 발견, 수정하지 않음)

`src/app/api/school/apartments/route.ts`의 `fetchBuildYearFromRegistry()`는 **폐기된 구 엔드포인트(`BldRgstService_v2/getBrTitleInfo`)를 여전히 호출**하고 있다 — 실제로 호출해보니 `NO_OPENAPI_SERVICE_ERROR`(해당 오픈API 서비스가 없거나 폐기됨)를 반환한다. `src/lib/apt-building-info.ts`는 이미 신 엔드포인트(`BldRgstHubService/getBrRecapTitleInfo`)로 교체된 반면(코드 주석에 교체 이력 명시), `school/apartments/route.ts`는 별도 구현이라 이 교체가 반영되지 않았다. 현재는 `try/catch`로 조용히 실패해 `buildYear`가 MOLIT 매칭값 또는 `null`로 대체되고 있어 사용자에게 에러가 노출되지는 않지만, **의도한 "건축물대장 기준 정확한 준공연도"라는 목표는 항상 달성되지 못하고 있다.** 이번 STEP은 조사 전용이라 수정하지 않으며, 별도 STEP에서 처리할 후보로 기록한다(§41).

## I. 단지명 정규화

### I-1. 현재 정규화 수준

§B에서 확인한 대로 `공백 제거 + "아파트" 접미사 제거`가 전부이며, 괄호 제거·브랜드 표기 통일·차수(1차/2차) 처리 로직은 없다.

### I-2. 실제 표본 비교(MOLIT vs Kakao, P2-D4-A에서 이미 검증한 것을 이번 STEP에서 재확인)

P2-D4-A(§5-2)에서 부산 서구 14개 Kakao 결과 대 MOLIT 23개 고유 단지를 대조해 "아파트" 접미사 제거만으로 약 79% 매칭됨을 확인한 바 있다. 이번 STEP에서는 §G-2의 `bldNm`(건축물대장 공식 명칭)까지 추가로 대조했다 — e편한세상 송도 더퍼스트비치의 경우 MOLIT `aptNm`="e편한세상송도더퍼스트비치"(공백 없음), 건축물대장 `bldNm`="e편한세상 송도 더퍼스트비치"(공백 있음), Kakao `place_name`="e편한세상송도더퍼스트비치아파트" — **세 소스가 모두 공백 유무나 접미사가 다르다**는 것을 실측으로 재확인했다.

### I-3. 안전 범위 평가

"공백 제거 + 아파트 접미사 제거" 규칙은 이번 조사(P2-D4-A 79%, 이번 STEP 강남구 사례들)에서 **일관되게 상당히 높은 매칭률**을 보였지만 100%는 아니다. **정규화된 이름을 primary key처럼 쓰지 않는다**는 요청 원칙을 그대로 확정한다 — 정규화 이름은 어디까지나 "후보를 좁히는 보조 신호"로만 쓰고, 최종 식별은 `aptSeq`(있으면) 또는 좌표+주소 조합으로 검증해야 한다.

## J. 실거래 연결 구조 설계

이 앱은 실거래를 DB에 저장하지 않고 매 요청 MOLIT를 실시간 호출하는 구조를 유지 중이다(P2-D4-A에서 이미 확인, 이번 STEP에서 변경하지 않음 — 스키마/저장 방식 변경은 금지 항목). 이 전제 위에서 두 설계 후보를 비교한다.

| 후보 | 구조 | 평가 |
|---|---|---|
| A. `ApartmentMaster → aptSeq(그대로 저장) → 매 요청 MOLIT를 aptSeq로 재조회` | 단순 | MOLIT API 자체가 조회 파라미터로 `aptSeq`를 받지 않는다(`LAWD_CD`+`DEAL_YMD`만 지원, 실측 확인) — **aptSeq로 직접 재조회하는 API가 없어 이 구조는 성립하지 않는다.** 여전히 `lawdCd`+월 단위로 가져온 뒤 `aptSeq`로 필터링하는 방식이 필요하다. |
| B. `ApartmentMaster → own id → external aptSeq mapping(비교/검증용) → lawdCd+월 단위로 MOLIT 조회 후 aptSeq로 매칭` | Master는 "이 단지의 aptSeq가 무엇인지"만 알고 있고, 실제 조회는 여전히 지역+월 단위로 수행한 뒤 결과에서 `aptSeq` 일치 항목만 골라낸다 | **권장** — MOLIT API 제약과 맞고, 이름 매칭 대신 `aptSeq` 매칭을 쓸 수 있어 §B의 충돌 위험을 구조적으로 제거한다. |

## K. 외부 식별자 매핑 — 두 개의 강력한 후보 발견

이번 STEP에서 두 개의 독립적인 정부/공공 식별자 후보를 실측으로 확인했다.

| 식별자 | 출처 | 형식(실측) | 안정성 근거 |
|---|---|---|---|
| `aptSeq` | MOLIT 실거래 API | `{lawdCd}-{일련번호}` | §C~D(18개월, 4개 지역, 16,579건 무결) |
| `mgmBldrgstPk`(건축물대장 관리번호) | 건축물대장 총괄표제부 API | 매우 큰 정수(예: `1.0000000000000042e+21`, 부동소수점 정밀도 문제로 JS Number로는 정확히 표현 안 될 위험 있음 — **문자열로 취급해야 함**, 확인 필요 사항으로 기록) | 정부 공식 건축물 관리 PK — 원칙적으로 `aptSeq`보다도 더 권위 있는 식별자일 가능성이 높으나, 이번 STEP에서 시간축/유일성 검증은 하지 못했다(추가 검증 필요) |

이 두 값은 서로 다른 기관(MOLIT vs 국토부 건축물대장 시스템) 소관이라 **직접적인 상호 변환 규칙이 없다** — 둘 다 저장하되 서로 다른 목적(거래 매칭용=`aptSeq`, 건물 정체성용=`mgmBldrgstPk`)으로 취급해야 한다.

### 매핑 테이블 필요성 평가

향후 소스(MOLIT/Kakao/건축물대장/분양/재개발/학교)가 늘어날수록, 각 식별자를 `ApartmentMaster`에 컬럼으로 직접 두는 방식은 소스가 늘 때마다 schema를 계속 넓혀야 하는 문제가 생긴다.

**후보 `ApartmentExternalId`**(`apartmentId`/`source`/`externalId`/`rawName`/`rawAddress`) 구조의 장단점:

| 장점 | 단점 |
|---|---|
| 신규 소스 추가 시 schema 변경 없이 row만 추가 | JOIN이 항상 필요해 조회가 한 단계 늘어남 |
| 소스별 원본 이름/주소(`rawName`/`rawAddress`)를 그대로 보존해 향후 재매칭/감사(audit) 가능 | 소스가 2개(`aptSeq`, `mgmBldrgstPk`) 뿐인 현재는 컬럼 방식 대비 이점이 크지 않음 |
| 한 단지가 여러 소스에서 서로 다른 이름으로 불리는 현실(§I)을 자연스럽게 표현 | 초기 구현 복잡도가 컬럼 방식보다 높음 |

**이번 STEP에서는 만들지 않는다.** 다만 향후 분양/재개발/학군 연결까지 고려하면(§L~N) 소스 수가 늘어날 것이 확실해, 초기 Master 스키마 설계 시점(M2)부터 이 구조를 염두에 두는 것을 권장한다.

| A. 입주 전 Presale 별도 유지 → 준공/입주 후 Master와 연결 | 분양 단계에서는 Master row를 만들지 않고, `Presale.moveInExpectedYm` 경과 후(또는 MOLIT에 첫 거래가 잡히는 시점) Master에 신규 등록 | **권장** — P2-D4-A §9-10에서 실제로 확인한 사례(부산 서구 id=479, e편한세상 송도 더퍼스트비치)가 정확히 이 패턴이다: 분양 당시엔 존재하지 않다가, 준공 후 MOLIT에 `aptSeq=26140-1361`로 나타났다. "분양=아직 실체가 없는 예정" → "준공=Master 진입"이 데이터로 이미 검증된 흐름이다. |
| B. 분양 시점부터 provisional(가등록) Apartment 생성 | 분양 시점에 미리 Master row를 만들고 준공 후 실제 값으로 채움 | 분양 계획이 변경/취소되는 경우(P2-D3에서 실측된 "조합원 취소분" 같은 사례가 이미 존재) provisional row가 유령 데이터로 남을 위험이 있다. 준공 전에는 `aptSeq`/건축물대장 정보가 아예 존재하지 않아(§C, §G) 채울 수 있는 필드가 거의 없다. |

**"분양 = Apartment 1:1"이라고 무조건 보지 않는다**는 원칙을 그대로 확정한다 — A안(입주/준공 이후 연결)을 권장하며, 연결 키는 좌표 근접성(P2-D4-A §4의 Kakao 반경검색 재사용) + 이름 정규화(§I) 조합으로 후보를 찾고, `aptSeq`가 확보되면 그것으로 확정하는 2단계 검증을 제안한다.

## M. 재개발(RedevelopmentProject)과 Master 연결 가능성

재개발은 "정비구역(옛 저층/노후 단지) → 철거 → 신축 → 분양(`Presale`) → 준공(`Apartment` Master)"이라는 **lifecycle**을 갖는다. `RedevelopmentProject`에 `Apartment`를 직접 FK로 붙이는 것보다, **`RedevelopmentProject`를 lifecycle의 축으로 두고 그 결과물로 `Presale`/`Apartment`가 순차적으로 생성·연결되는 구조**를 후보로 제시한다.

```
RedevelopmentProject(정비구역)
  → (철거 전) 기존 Apartment Master row(있다면, 옛 단지)
  → (사업 진행) Presale(신규 분양)
  → (준공 후) 신규 Apartment Master row
```

세 단계 모두 좌표/lawdCd 근접성으로 느슨하게 연결하고, FK 강제는 하지 않는 것을 권장한다(정비사업은 계획 변경·지연이 매우 흔해 강한 FK가 오히려 데이터 정합성을 해칠 위험이 있다). 이번 STEP에서 실제 schema는 만들지 않는다(§38).

## N. 학군 연결 가능성

`api/school/apartments/route.ts`(§G-4에서 이미 다룸)가 현재 "학교 좌표 → Kakao 반경검색(1.5km) → `@turf/turf`의 `distance()`로 정밀 거리 계산 → 이름 정규화로 MOLIT 매칭"이라는, **이번 조사가 필요로 하는 패턴을 이미 실제로 구현해 운영 중**이라는 것을 확인했다. 이는 P2-D4-A 문서가 "Haversine 등 기존 거리 계산 함수가 없다"고 기록한 것에 대한 **정정 사항**이다 — 정확히는 "자체 구현 함수는 없지만, 이미 설치된 `@turf/turf` 패키지의 `distance()`로 동일한 기능을 이미 쓰고 있다"가 맞는 서술이다(§41에 정정 기록).

Master가 좌표를 갖게 되면, 현재 학교마다 개별 반경검색을 하는 구조를 "Master 좌표 ↔ 학교 좌표" 직접 거리 계산으로 통일할 수 있어, 학군 연결 정확도와 성능(중복 Kakao 호출 감소) 모두 개선될 잠재력이 있다 — 다만 이번 STEP에서 구현하지 않는다.

## O. 커뮤니티 연결 가능성(개념 평가만)

## R. 내부 PK 정책

**권장: `ApartmentMaster.id`(자체 autoincrement 내부 PK) + `aptSeq`(nullable, unique 후보 external key)** — 요청안이 제시한 후보 그대로 채택한다.

근거:
1. `aptSeq`는 MOLIT(국토부) 소관 외부 시스템의 값이다 — 이 프로젝트가 통제할 수 없는 값을 내부 관계(FK)의 기준으로 삼으면, 외부 API가 이 값의 형식/발급 방식을 바꿀 경우(예: 재건축으로 새 번호 발급, 대장 통폐합) 이 앱의 전체 관계가 연쇄적으로 깨질 위험이 있다.
2. 거래 이력이 없는 신축/미거래 단지, 재개발 진행 중인 옛 단지 등은 `aptSeq`가 아예 없을 수 있다(§C에서 실측한 "거래가 있는 단지"만 `aptSeq` 100% 확보였지 "모든 단지"가 아니다) — nullable external key 구조여야 이런 케이스를 자연스럽게 수용한다.
3. `mgmBldrgstPk`(§K)처럼 향후 추가될 수 있는 다른 외부 식별자도 같은 패턴(내부 PK + nullable external unique)으로 확장 가능해, 구조 일관성이 생긴다.
4. 이 프로젝트의 기존 관례(`Presale.houseManageNo`도 정확히 이 패턴 — 자체 `id` PK + 외부 `houseManageNo` nullable unique)와 일치한다 — 이미 검증된 패턴을 재사용하는 것이라 리스크가 낮다.

`aptSeq` 직접 PK 방식의 단점: 위 1~3과 동일 + Prisma에서 PK 값 자체가 nullable일 수 없어(위 2번 케이스를 원천적으로 배제) 거래 없는 신축 단지를 아예 등록할 수 없게 되는 구조적 문제가 생긴다(§W와 직결).

## S. Data Provenance 필요성

각 필드의 출처를 추적할 필요가 있는지 평가한다.

| 방식 | 평가 |
|---|---|
| 컬럼별로 저장(예: `totalHouseholdsSource`, `totalHouseholdsUpdatedAt`) | 정확하지만 필드 수만큼 컬럼이 2배로 늘어나 schema가 비대해짐 |
| 별도 metadata(JSON 컬럼 또는 별도 테이블) | 유연하지만 쿼리/색인이 어려워짐 |
| 코드/문서로만 관리 | 이 프로젝트의 기존 관례(`Apartment` 모델 자체가 코드 주석으로 출처를 설명하는 방식, §A)와 일치, 구현 비용 최소 |

**권장**: 핵심 식별 필드(`aptSeq`, `mgmBldrgstPk`)는 그 자체가 출처를 함의하므로 별도 provenance 컬럼이 불필요하다. 나머지 enrichment 필드(세대수/주차/좌표 등)는 **`updatedAt`(필드 단위가 아닌 레코드 단위, 이미 Q에 포함)만으로 최소한의 신선도 추적**을 하고, 상세 출처는 코드/문서로 관리하는 방식을 권장한다 — 이 프로젝트 전체가 이미 이 방식을 일관되게 쓰고 있다(`Apartment` 모델 주석 등).

## W. "최근 12개월 무거래 단지" 문제 해결 가능성

01 문서가 지적한 구조적 문제("지도가 최근 12개월 무거래 단지를 표시할 수 없다")는, **거래 유무와 무관하게 독립적으로 존재하는 단지 레지스트리(Master)가 생기면 원천 해결된다.** 현재 구조는 "지도 마커 = MOLIT 최근 거래"라는 등식이 강제돼 있어 무거래 단지가 곧 "존재하지 않는 단지"로 취급되지만, Master가 생기면 "단지는 항상 존재 + 거래 정보는 있으면 붙이고 없으면 '거래 정보 없음'으로 표시"로 관계가 분리된다. 다만 §V에서 확인한 대로 무거래 단지까지 포함하려면 A(MOLIT 전용) seed만으로는 부족하고 C(Kakao)/B(건축물대장) 보완이 필요하다는 전제가 붙는다.

### X-2. 이번 조사에서 실제로 겪은 데이터 함정 — fast-xml-parser 숫자 자동변환

이번 조사용 스크립트에서 `parseTagValue: true` 옵션의 `fast-xml-parser`가 `jibun`(예: `"771"`)처럼 숫자로만 이뤄진 태그 값을 **자동으로 JS 숫자형으로 변환**해, 이후 `.split('-')` 같은 문자열 연산이 조용히 실패하는 사례를 실제로 겪었다(§G-3). 이 프로젝트의 기존 `src/lib/api-molit.ts`는 이미 `.toString()`을 방어적으로 호출해 이 문제를 피하고 있음을 확인했다 — **향후 Master 구축 코드가 MOLIT 원본 XML을 직접 다룰 때 반드시 같은 방어(모든 태그 값에 `.toString()`)를 적용해야 한다**는 것을 실제 함정으로 기록한다.

### X-3. 표본 수동검증

§Y(부산 서구)와 §14(전체 10표본)를 이번 STEP의 표본 수동검증으로 갈음한다.

## Z. 이집 전체 구조 — Master 이후 개념도

Master(`id` 중심)가 생기면 다음과 같이 연결될 수 있다(개념 설명, 구현 아님).

- **지도**: 마커 데이터 소스가 "MOLIT 최근 거래"에서 "Master 전체 + 거래정보는 있으면 병합"으로 전환 → §W 해결.
- **단지 상세**: URL을 이름 대신 `Master.id` 기반으로 바꿀 여지가 생김(단, 기존 `/apt/[name]` URL과의 호환성은 별도 마이그레이션 설계 필요, 이번 STEP 범위 밖).
- **실거래**: 여전히 실시간 MOLIT 호출이지만, 조회 키가 이름 매칭에서 `aptSeq` 매칭으로 바뀌어 §B의 충돌 위험이 사라짐.
- **학군**: §N에서 설명한 대로 좌표 통일로 개선 여지.
- **분양**: §L의 lifecycle로 연결.
- **재개발**: §M의 lifecycle로 연결.
- **추천**: Master가 곧 추천 대상 엔티티의 안정적 단위가 됨(01 문서의 "추천 플랫폼 전환 준비도 — 아파트 MASTER DB 10%"를 끌어올리는 핵심 전제).
- **커뮤니티**: §O에서 설명한 대로 점진적 FK 도입 여지.
- **중개사 SaaS**: 이번 STEP에서 조사하지 않은 신규 영역이라 개념 설명을 보류한다(확인 필요 사항으로만 기록).

## 단계별 구현안 제안

요청안의 M2~M6 5단계 후보를 이번 조사 결과에 맞춰 재검토했다 — **불필요하게 단계를 늘리지 않기 위해 그대로 5단계를 유지하되, 각 단계의 실제 범위를 조정 제안한다.**

- **MASTER M2**: schema 설계 확정(내부 PK + `aptSeq`/`mgmBldrgstPk` nullable unique, §Q 필드 후보 확정) — 이번 STEP에서 확정하지 않은 세부사항(Region 계층 포함 여부, ApartmentExternalId 도입 여부)을 여기서 결정.
- **MASTER M3**: 부산 서구 seed(§V의 E 복합전략: MOLIT 우선 → Kakao 보완 → 건축물대장 enrichment), 156개 규모로 전수 수동검증(§X) 포함.
- **MASTER M4**: 좌표/건축물대장 enrichment 자동화(§F~G) + 품질검증 자동화(§X-1) — M3와 병행 가능성도 있어 M3 진행 중 재평가.
- **MASTER M5**: 부산 전체 확장.
- **MASTER M6**: 전국 확장(§E-3 행정구역 개편 대응이 이 시점까지는 반드시 정리돼야 함).

## 최종 판단

### **B. 새 `ApartmentMaster` 모델을 만들고, 기존 `Apartment`를 점진적으로 이관하는 것이 적절**

**핵심 근거(5개 이내)**:

1. 기존 `Apartment`는 좌표 필드 자체가 스키마에 없다 — "안전하게 확장"(A안)하려면 결국 좌표/전체주소/`aptSeq`/동수 등 마스터 필수 필드(§Q)를 대거 추가해야 하는데, 이는 사실상 새 모델을 만드는 것과 다르지 않다.
2. `Apartment`의 현재 unique key(`[name, dong]`)는 §B에서 실측 확인한 "같은 이름 다른 단지" 충돌(강남구 10건)을 구조적으로 방지하지 못한다 — `aptSeq` 기반의 새 unique 정책(§R)이 필요하며, 기존 키 정책 자체를 바꿔야 하는 변경은 대규모 개편에 해당한다.
3. 그럼에도 기존 `Apartment`를 쓰는 실사용 코드(`api/apt/[name]/route.ts`, `api/apt/[name]/info/route.ts`)가 실제로 존재하고 20건이나마 정상 동작 중이므로(C. "기존 구조 유지만으로 해결 가능"은 아님), **전면 교체보다는 새 모델을 별도로 만들고 기존 코드/데이터는 그대로 둔 채 점진적으로 이관하는 것**이 "기존 정상 기능을 임의로 삭제하지 않는다"는 이 프로젝트의 원칙(CLAUDE.md)에 부합한다.
4. 이번 STEP에서 확보한 실측 근거(aptSeq 안정성 §C~D, 건축물대장 연결 §G, REGCODE_PROXY 우회 경로 §E-2)가 모두 "새 스키마를 설계할 근거"로는 충분히 강하지만, "기존 20건 데이터를 그대로 새 구조로 자동 변환해도 안전하다"는 것까지 검증하지는 못했다 — 즉시 migration(B의 더 급진적인 하위옵션)까지는 근거가 부족하다.

## aptSeq 최종 판단

### **B. `aptSeq`는 유용하지만 복합키/추가 검증 필요**

**근거**:

- 이번 STEP의 실측(4개 지역, 18개월, 16,579건)은 null 0%, 지역간 중복 0건, 월별 불안정 0건, 이름충돌 정확 구분(10/10)이라는 **매우 강한 긍정적 근거**를 보였다 — 이것만 보면 A(단독 unique key로 즉시 채택)로 판단해도 될 정도다.
- 그러나 (1) 관측 기간이 18개월로 제한적이라 재건축/대장통폐합처럼 수년 단위로만 발생하는 이벤트에 대한 안정성은 검증하지 못했고, (2) MOLIT API가 `aptSeq`로 직접 조회하는 기능을 제공하지 않아(§J) 실거래 연결 시 여전히 `lawdCd`+월 단위 조회 후 사후 필터링이 필요하다는 구조적 제약이 있으며, (3) 거래 이력이 전혀 없는 단지에는 애초에 `aptSeq` 자체가 존재하지 않아(seed 전략 §V와 직결) 이 값에만 전적으로 의존하는 설계는 성립하지 않는다.
- 따라서 "외부 unique key 후보로 즉시 신뢰"(A)라고 단정하기보다, **"내부 PK(자체 id) 중심 설계에서 `aptSeq`를 nullable unique 검증키로 두고, 정기적인 무결성 재검증(§X)을 병행"**하는 B가 더 안전한 결론이다.
