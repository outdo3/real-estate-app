## 3~4. 호출 API 및 실제 연결 키

`/api/ledger/route.ts`(GET)가 이 기능의 유일한 서버 진입점이다.

```
apt-client.tsx (fetch)
  → GET /api/ledger?type=title|expos&lawdCd=...&dongName=...&jibun=...&aptName=...&dong=...&ho=...
    → (dongName으로 법정동코드 프록시 조회 → bjdongCd 획득)
    → 외부 data.go.kr BldRgstHubService (getBrTitleInfo 또는 getBrExposInfo) 직접 호출
    → 응답 items를 aptName/dong/ho로 후처리 필터링
    → NextResponse.json({ data: matchedItem })
```

**실제 연결 키(코드 기준 확정)**:
1. `sigunguCd` = `lawdCd`(법정동코드 앞 5자리, URL/DB/지오코딩으로 이미 확보된 값)
2. `bjdongCd` = `dongName`(법정동 이름, 실거래 데이터의 `trades[0].dong`)을 별도 프록시 API로 역조회해서 얻은 코드
3. `bun`/`ji` = `jibun`(지번, `trades[0].jibun`)을 파싱한 값 — **이게 있어야 외부 API 호출 자체가 특정 지번으로 스코프된다**
4. **`aptName`(단지명 문자열) — 위 1~3으로 좁혀진 결과 안에서 `bldNm`/`platPlc`에 이 문자열이 포함되는지로 2차 필터링.** 즉 "단지명 문자열만으로 연결하는 구조"가 **부분적으로 존재**한다: 1~3이 정상 작동하면 aptName 필터는 보조적 역할이지만, jibun이 비어있으면(아래 §12) aptName 문자열 매칭이 사실상 유일한 안전장치가 된다.
5. `dong`/`ho`(사용자가 폼에 직접 입력한 값) = 위 결과 안에서 `dongNm`/`hoNm`에 포함되는지로 최종 선택. **일치하는 게 없으면 에러 없이 `itemArray[0]`(후보 목록의 첫 건)으로 조용히 대체**(§12에서 실측 재현).

## 5. "단지명 문자열만으로 연결하는 구조" 위험도 평가

정상 경로(`jibun` 존재)에서는 aptName 문자열 매칭이 최종 결정자가 아니라 `sigunguCd`+
`bjdongCd`+`bun`+`ji`로 이미 좁혀진 후보 안에서의 보조 필터일 뿐이라 위험도가 낮다.
그러나 **`jibun`이 빈 문자열이면 코드상 `bun`/`ji` 파라미터 자체가 API 요청에서
누락되어(`if (bun) apiUrl += ...`, bun이 `''`면 이 블록 자체가 스킵) 그 법정동
전체(최대 1000건)가 후보가 되고, 이 경우 aptName 문자열 매칭이 사실상 유일한
방어선이 된다.** §12에서 이 상황을 의도적으로 재현해 실제로 무관한 건물이 반환됨을
확인했다 — 정확도 위험은 "낮음"이 아니라 **"jibun 가용성에 전적으로 의존"**으로
평가한다.

## 7. `mgmBldrgstPk` 정밀도 처리 — **BLOCKER 확인**

코드를 먼저 정직하게 확인한다(과거에 고쳤다고 가정하지 않음): `/api/ledger/route.ts`
어디에도 `mgmBldrgstPk`에 대한 타입 변환·문자열 캐스팅 코드가 없다. `res.json()`이
파싱한 값을 그대로 `matchedItem`에 담아 그대로 `NextResponse.json({ data: matchedItem })`
으로 내려보내고, `apt-client.tsx`는 `${d.mgmBldrgstPk || '-'}`로 그대로 HTML에 꽂는다.

**외부 API(BldRgstHubService)의 원본 응답 자체가 `mgmBldrgstPk`를 따옴표 없는 JSON
숫자로 내려준다**(raw text 직접 확인, `"mgmBldrgstPk":1000000000000002740246` — 22자리,
따옴표 없음). Node의 `res.json()`(V8 `JSON.parse`)이 이 숫자를 IEEE754 double로 파싱하는
순간 이미 정밀도가 깨진다(double은 2^53≈9×10^15까지만 정수를 정확히 표현, 22자리
≈10^21은 훨씬 초과) — **우리 코드가 손상시키는 게 아니라, 원본 응답을 표준
`JSON.parse`로 받는 순간 이미 되돌릴 수 없이 손상된다.**

**실제 프로덕션 재현(§11에서 상세)**: 대신해모로센트럴(2022년 준공) 113동 표제부
조회 시 사용자가 실제로 받는 값은 `1.0000000000000028e+21` — 그 단지의 16개 동 전부가
서로 다른 실제 고유번호를 갖고 있음에도 JSON.parse 이후에는 **16개 동 전부 동일한
`1.0000000000000028e+21`로 뭉개진다**(원본 22자리 값들이 서로 마지막 몇 자리만 달라
double 정밀도 범위 안에서 모두 같은 값으로 반올림되기 때문).

- string 유지 여부: **아니오, number로 파싱됨**
- number 변환 여부: **예, 그것도 이미 손실된 상태로**
- scientific notation 가능성: **예, 실제로 발생(`1.0000000000000028e+21`)**
- DB 저장값 사용 여부: 해당 없음(DB를 거치지 않는 라이브 조회, §6)
- precision-safe 여부: **아니오. 이 기능은 22자리 `mgmBldrgstPk`에 대해 precision-safe하지 않다.**

## 8. 외부 건축물대장 API

- Endpoint: `http://apis.data.go.kr/1613000/BldRgstHubService/{getBrTitleInfo|getBrExposInfo}`
- 요청 파라미터: `serviceKey`, `sigunguCd`, `bjdongCd`, `numOfRows=1000`, `pageNo=1`,
  `_type=json`, (있으면) `bun`, `ji`
- 인증키 환경변수명: `DATA_GO_KR_API_KEY`(`.env.local`에 존재함을 확인, **값 자체는
  출력하지 않음**)
- 페이지 크기: `numOfRows=1000`(사실상 페이지네이션 없이 한 번에 다 받음)
- **timeout: 없음.** `apt-building-info.ts`(별개 파일, §2)는 `AbortSignal.timeout(2500/4000)`을
  명시적으로 걸어두는데, `/api/ledger/route.ts`의 `fetch(apiUrl)` 2곳(표제부/전유부 각각)
  모두 timeout 설정이 없다 — 외부 API가 응답을 지연시키면 이 요청이 무한정 대기할 수
  있는 구조적 위험(이번 실측 5건은 모두 0.8~2.3초에 응답해 문제가 드러나지 않았을
  뿐, 코드 구조상의 결함으로 기록).
- retry: 없음.
- 429 처리: 별도 처리 없음(위 §7 에러 체크 로직이 `resultCode !== '00'`이면 일괄
  `API_ERROR`로 처리 — 429도 이 경로로 흡수되긴 하지만 재시도·backoff는 없음).
- 응답 포맷: JSON(`_type=json`).
- 파싱: `res.json()`(§7의 정밀도 손실 원인).

## 9. 총괄표제부 / 표제부 / 전유부 처리

**건축물대장 버튼은 표제부(`getBrTitleInfo`, "아파트 동 전체") 또는 전유부
(`getBrExposInfo`, "개별 호실")만 조회한다 — 총괄표제부(`getBrRecapTitleInfo`, 단지
전체 집계)는 이 기능에서 전혀 쓰이지 않는다.** 총괄표제부는 `apt-building-info.ts`
(§2, AptSpecGrid 전용)에서만 쓰인다.

모달의 라디오 버튼 라벨("개별 호실(전유부)" / "아파트 동 전체(표제부)")은 실제로
조회하는 단위와 **정확히 일치**한다 — 이 부분은 사용자에게 정직하게 설명돼 있다.
다만 UI 진입점인 퀵버튼 라벨 자체는 그냥 "건축물대장"이라 클릭 전에는 "단지 전체"가
아니라 "동 단위"라는 사실을 알기 어렵다 — 모달을 열어야 비로소 명확해진다.

**혼동 가능성**: AptSpecGrid(1구역)가 보여주는 세대수/용적률/건폐율/사용승인일은
**총괄표제부**(단지 전체) 값인 반면, 이 모달의 표제부 결과는 **특정 동 1개**의 값이다
— 같은 페이지 안에 "단지 전체 값"과 "동 단위 값"이 동시에 존재하지만 사용자에게 그
차이가 설명되지 않는다(§15에서 추가 평가).

5개 표본 전부 단지명·주소·법정동·준공(사용승인)일이 아파트 상세 기본정보와 논리적으로
일치했다 — **정상 조건(jibun 확보됨)에서는 오매칭 0건.**

**단, 아래 2가지 실패 모드를 의도적으로 재현해 코드상 위험이 실재함을 확인했다
(정상 5표본과는 별개의 통제된 테스트):**

1. **단지 간 오매칭(jibun 없을 때)** — `/api/ledger`를 jibun 없이(빈 문자열) 호출하도록
   재현한 결과, `sigunguCd`+`bjdongCd`만으로 좁혀진 후보 중 `itemArray[0]`이 대신해모로
   센트럴이 아닌 **"제세하이빌"**(전혀 무관한 별도 건물)로 반환됐다. 정상 사용 흐름에서는
   `aptName` 2차 필터가 이를 막아주지만, aptName 필터가 우연히도 0건을 반환하는
   케이스(별칭·표기 차이 등, 문서26 §2가 이미 지적한 aptName/displayName 불일치와 동일한
   근본 원인)에서는 이 방어선도 사라진다.
2. **동 간 오매칭(단지 내, 동 번호 오류/부재 시)** — 협성르네상스를 존재하지 않는
   "999동"으로 조회하면 에러 없이 **"114동"** 데이터가 조용히 반환됐다. 다운로드되는
   문서 자체는 `dongNm`이 정직하게 "114동"으로 라벨링돼 문서가 999동이라고 거짓
   주장하지는 않지만(§21 STOP 조건의 "단지와 불일치"까지는 아님), 사용자는 자신이
   요청한 동과 다른 동의 대장을 받고도 아무 안내를 받지 못한다.

**결론**: 실측 5표본에서 "다른 단지" 수준의 오매칭은 0건이었으나, §21이 명시한
"다른 단지로 오매칭" 위험이 존재하지 않는다고 말할 수는 없다 — jibun 가용성이라는
단일 조건에 전적으로 의존하는 구조적 취약점이다(BLOCKER까지는 아니되, 별도의 High
심각도 항목으로 기록).

## 13. 데이터 없음 / 오래된·소규모 단지 실패 처리

`/api/ledger/route.ts`는 응답에 `items`가 없으면 `{ error: 'NO_DATA', message:
'데이터가 없습니다.' }`(HTTP 404)를, 외부 API 자체가 실패하면 `{ error: 'API_ERROR',
message: ... }`(HTTP 500)를 반환한다 — **코드 레벨에서는 두 상황이 구분된다.**

그러나 `apt-client.tsx`의 처리는 `if (result.error) { alert('데이터를 불러오지
못했습니다: ${result.message || result.error}') }` 한 줄뿐이다 — 두 경우 모두 **동일한
형태의 브라우저 네이티브 얼럿**으로 뭉뚱그려 표시되며, "데이터 없음"과 "API 오류"의
구분은 얼럿 안의 텍스트(`message`)로만 미세하게 드러날 뿐 UI적으로는 구분되지 않는다.
버튼 자체는 데이터 존재 여부와 무관하게 **항상 노출**된다(숨김 처리 없음) — 클릭해서
동/호수를 입력하고 제출해봐야 비로소 실패 여부를 알 수 있다.

표본 B(대가하이츠, 소규모)·D(협성르네상스, `approvalDate:null`이던 단지)도 실제로는
표제부 조회에 성공했다(§12) — 이번 5표본에서는 NO_DATA를 실제로 재현하지 못했다
(코드 로직 확인은 위 문단대로 완료, 실사례 재현은 못함 — 한계로 기록).

## 15. 중복 정보 평가

AptSpecGrid(1구역, 총괄표제부 기준)와 이 모달(표제부/전유부, 동·호 단위) 사이에
**사용승인일·건폐율·용적률**이 개념적으로 겹친다. 단위가 다르다는 점(단지 전체 vs
특정 동)이 있어 값이 실제로 다를 수 있고, 그 차이 자체가 유의미한 정보일 수도 있지만
**현재 UI 어디에도 "이건 단지 전체 값, 저건 특정 동 값"이라는 설명이 없어** 사용자는
그냥 "같은 숫자가 또 나온다"고 느낄 가능성이 높다. B1/B4 이후 이 모달을 유지하더라도
필드 구조 재설계(중복 필드는 "AptSpecGrid와 다를 수 있는 이유" 안내 추가, 또는 겹치는
필드는 모달에서 생략) 후보로 기록한다. **이번 STEP에서는 수정하지 않는다.**

## 16. 사용자 가치 평가

- 이해 용이성: 필드명이 관공서 서식 그대로(예: "허가일/착공일", "고유번호")라 일반
  사용자에게 다소 전문적 — 다만 문서 형태 자체가 "실제 서류처럼 보이는 것"이 신뢰도
  측면에서는 의도된 장점일 수 있음.
- 단지 판단 도움: 사용승인일/면적 등은 도움이 되나, 대부분 AptSpecGrid에서 이미 확인
  가능(§15).
- 기존 단지정보와 차별성: **낮음** — 차별화되는 정보는 "동 단위로 쪼개서 볼 수 있다"는
  점 정도.
- 신뢰 가능한 공공 원본 정보 여부: 원본 데이터 자체(data.go.kr)는 신뢰할 수 있으나,
  **고유번호 필드는 우리 쪽 처리 과정에서 손상돼 원본과 다른(거짓) 값을 보여주고
  있다** — 이 필드만 놓고 보면 신뢰할 수 없는 정보를 신뢰할 수 있는 것처럼(실제
  공문서 서식으로) 보여주는 셈이다.
- 클릭할 이유: "다운로드해서 실제 서류처럼 인쇄/보관하고 싶다"는 수요에는 부합하나,
  고유번호 손상은 그 문서의 공신력 자체를 훼손한다.

**최종 평가: D. 오매칭/기능오류 때문에 현재 노출 부적절.**
근거: (1) §7/§11에서 실제로 재현된 `mgmBldrgstPk` 정밀도 손상이 "실제 서류처럼
보이는" 다운로드 문서에 명백히 틀린 값을 인쇄하는 것은 단순 버그를 넘어 **신뢰
훼손** 문제이고, (2) §12에서 확인한 "동 오매칭 시 조용한 대체" 역시 사용자가 요청하지
않은 데이터를 그런 줄 모르고 받게 하는 구조이며, (3) §8 timeout 부재·§13 오류/빈
데이터 미분리·§15 기존 정보와의 중복까지 겹쳐 있어, 현재 상태로 B1 이후에도 그대로
노출을 유지하는 것은 권장하지 않는다.

## 17. ErrorLog / 오류 로깅

`/api/ledger/route.ts`의 유일한 에러 처리는 `console.error('Ledger API Error:', error)`
뿐이다. `logServerError`를 import하지도, 호출하지도 않는다 — **ErrorLog 미연결**
(문서25 R1이 이미 지적한 "분양 도메인 외 ErrorLog 공백"과 같은 패턴이 이 기능에도
그대로 있음). 향후 ErrorLog 확장 후보로 기록만 하며 이번엔 연결하지 않는다.

## 19. 모바일 UX

브라우저 자동화 창이 1536×864에 고정돼 실제 모바일 뷰포트 스크린샷은 얻지 못함
(문서26/27과 동일한 환경 제약, 명확히 재보고). 데스크톱 뷰포트에서 실측한 모달 구조로
근사 평가:

- 모달 자체는 `detail.module.css`의 `.modalContent`(width 90%, max-width 500px)를
  그대로 사용 — 건축물대장 모달만 별도 폭 지정 없음(지도/로드뷰만 800px로 예외 처리돼
  있고 건축물대장은 기본 500px 규칙을 따름, apt-client.tsx line 621 확인).
- 닫기 버튼: 다른 모달과 동일한 `.closeButton`(×) 공용 컴포넌트 — 별도 이슈 없음.
- 폼(라디오 2개 + 입력 2개 + 버튼)이 세로로 충분히 여유 있게 배치돼 있어 좁은 화면에서
  깨질 가능성은 낮아 보이나 실측은 못함.
- 긴 주소(`platPlc`)·긴 필드명은 다운로드된 HTML 문서 자체(별도 탭/파일로 열림) 안의
  내용이라 이 앱의 반응형 CSS 영향권 밖 — 문서 자체는 `max-width:800px` 고정 레이아웃이라
  모바일에서 좌우 스크롤이 발생할 가능성이 있음(다운로드된 문서 자체를 모바일에서
  열어보는 실측은 하지 않음, 코드 검토 수준).
- 하단 nav와 충돌: 모달은 `position:fixed`+전체 오버레이라 B0(문서27)에서 다룬
  `StickyPriceBar`/`Header` 하단탭바 충돌과는 무관(모달이 열리면 그 위를 전부 덮음).

## 발견된 문제 요약 (심각도순)

1. **[BLOCKER]** `mgmBldrgstPk` 22자리 값이 `JSON.parse` 단계에서 정밀도 손상 →
   다운로드 문서의 "고유번호"가 실제 값과 다른 값(과학적 표기법 문자열)으로 표시됨.
   신축 단지(2022·2024년 준공 표본에서 재현)일수록 새 PK 포맷을 쓸 가능성이 높아
   시간이 지날수록 영향 범위가 넓어질 것으로 예상.
2. **[High]** `jibun`이 비어있으면 `aptName` 문자열 매칭만으로 단지를 특정하게 되고,
   그 필터마저 실패하면 완전히 무관한 건물이 반환될 수 있음(재현 완료).
3. **[Medium]** 사용자가 입력한 동/호가 등록부와 일치하지 않으면 에러 없이 다른
   동/호로 조용히 대체(재현 완료, 단 라벨은 정직하게 실제 동을 표기).
4. **[Medium]** 외부 API 호출에 timeout이 없음(다른 유사 코드 `apt-building-info.ts`는
   있음 — 이 라우트만 누락).
5. **[Low]** NO_DATA/API_ERROR가 모두 동일한 `alert()`로 뭉뚱그려짐, ErrorLog 미연결,
   캐시 없음, AptSpecGrid와 필드 중복(사용승인일/건폐율/용적률).
