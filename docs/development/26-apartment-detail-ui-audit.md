### 1-A. `page.tsx` (서버 래퍼)

```
generateMetadata({ params }) {
  const aptName = decodeURIComponent(name);
  title: `${aptName} 실거래가·시세 - ${siteConfig.name}`
  description: 고정 템플릿 문자열(aptName만 삽입)
  openGraph: buildOpenGraph(...)  // DB 조회 없음
}
```

- **SEO 관찰**: title/description이 URL 파라미터(검색 진입 시 사용자가 타이핑한 표기 그대로)로만 만들어진다. 캐노니컬 명칭(`displayName`, 클라이언트에서 실거래 데이터로 확정)은 메타데이터에 반영되지 않는다 — 예를 들어 "금호어울림"으로 들어오면 실제 페이지 본문은 "서대신금호어울림"으로 표시되지만 `<title>`은 "금호어울림 실거래가·시세"로 남는다. 검색엔진에는 이 페이지가 실제 표시 내용과 살짝 다른 제목으로 색인되는 셈이다. **버그로 단정하지 않음** — 서버 컴포넌트가 DB/MOLIT를 왕복하지 않고 즉시 메타데이터를 낼 수 있다는 성능상 트레이드오프이므로, 이번 STEP에서는 "구조적 특성으로 기록"만 하고 수정 범위에 넣지 않는다(§16 참고).

## 2. URL / 식별자(identity) 구조

- 라우트: `/apt/[name]` — **name은 아파트명 문자열이며 aptSeq/PK 같은 안정 식별자가 아니다**(R1 STEP1이 이미 지적한 구조적 리스크가 상세페이지 자체에는 아직 해소되지 않음. `ApartmentMaster`는 현재 분양 주변비교에만 쓰이고 이 페이지는 연결돼 있지 않다).
- 동일 이름이 여러 지역에 존재할 수 있어(예: "롯데캐슬", "푸르지오") `lawdCd`/`dong` 쿼리파라미터로 소구역까지 좁힌다. 두 파라미터가 없는 진입(지도 마커 클릭 등)은 (1) DB `Apartment` 캐시 → (2) 단지명 지오코딩 → (3) 기본값(서울 강남구 `11680`) 순으로 자동 보정한다.
- 화면 상단 제목(`displayName`)은 검색 진입 시 사용자가 입력한 표기(`aptName`)가 아니라 **MOLIT 실거래 데이터의 대표 표기**로 치환된다(`trades[0].name`). 이번 실측(§4, 대신해모로센트럴 사례)에서 실제로 "대신해모로센트럴"로 검색해도 헤더는 "대신해모로센트럴아파트"로 표시됨을 확인 — 설계대로 동작.
- **표기 불일치 발견(경미)**: 같은 화면 안에서 헤더 타이틀(`displayName`, MOLIT 대표 표기)과 커뮤니티 CTA 카드·공유 텍스트(`aptName`, 검색 진입 원문)가 서로 다른 문자열을 쓴다. 위 실측 사례에서 헤더는 "대신해모로센트럴**아파트**"인데 바로 아래 커뮤니티 카드는 "대신해모로센트럴 실거주민 이야기가 궁금하다면?"(접미사 없음)으로 표시됐다 — 사용자에게 노출되는 화면 안에서 같은 단지 이름 표기가 두 가지로 보인다.
- 독립된 검색/목록 페이지는 없다(R1과 동일 결론 재확인) — 진입 경로는 검색창(다른 화면의 아파트 자동완성)·지도 마커·커뮤니티 글의 단지 링크·분양 상세의 주변 아파트 링크 뿐이다.

- `InvestmentMetrics`의 "데이터 부족" 폴백(단지 B, 전세 비교 매물 없음) 실측 확인 — 추정치를 만들지 않는 원칙 그대로 동작.

### 4-B. 발견된 문제 (실측 근거 있음)

1. **평형 칩 중복 라벨(AreaSelector)** — 단지 A에서 상단 평형 칩이 `전체 · 84(26평) · 59(18평) · 59(18평) · 84(26평) · ▼전체평형` 순으로, **서로 다른 원본 전용면적(예: 84.84㎡ vs 84.9x㎡)이 `getCompactAreaLabel()`의 절사 표기 때문에 동일한 라벨("84(26평)")로 겹쳐 두 개의 칩으로 노출**된다. 코드상 `AreaSelector`의 `topAreas`는 원본 면적 문자열(`trade.area`, 예: `"84.84"`/`"84.92"`) 단위로 구분하지만 화면 라벨은 절사 표기라 사용자 입장에서는 "똑같이 생긴 칩이 왜 두 개 있는지" 구분할 수 없다.
2. **KTX 키워드 검색 오탐(NeighborhoodInfoPanel/KakaoPlaces)** — 단지 A "교통" 탭에서 "KTX" 키워드 검색 1순위 결과가 실제 KTX역이 아니라 **"KTX특송퀵서비스"(택배 회사)**로 노출됨. `EXCLUDED_NAME_SUBSTRINGS`(아파트/빌라/화장실/맨션/타워)에 이런 업체명 패턴이 포함돼 있지 않아 걸러지지 않는다.
3. **소규모 단지에서 "거래 활발" 오판(buildAptBrief)** — 단지 B(88세대)에서 최근 3개월 거래가 **단 1건**뿐인데 브리핑 문구가 "최근 3개월간 1건 거래되어 **거래가 활발한 편입니다**"로 표시됨. 로직은 `(최근거래수/세대수)*100 >= 1.0`이면 "활발"로 판정하는데(`1/88 = 1.14%`), 이 임계값은 대단지 기준으로는 합리적이나 세대수가 작을수록 거래 1건의 비중이 기형적으로 커져 왜곡된다.
4. **커뮤니티 시설 정보가 사실상 항상 비어 있음** — Prisma `Apartment` 캐시 테이블을 직접 조회한 결과 전체 20행 중 `communityFacilities`가 채워진 행은 **0건**이다(전부 `null`). `/apt/[name]/facilities` 라우트는 이 테이블만 조회하므로, 크롤러(`scripts/crawl_facilities.py`, 이전 세션에서 파이프라인 자체는 검증됨)가 채운 데이터와 현재 페이지 방문으로 캐싱된 20행이 아직 겹치지 않는 것으로 보인다 — 결과적으로 퀵버튼 "⛳ 커뮤니티 시설"은 실사용자에게 거의 항상 "등록된 정보가 없습니다 + 제보하기" 빈 상태만 보여준다. (원인 추정이며 크롤러/캐시 테이블 자체를 이번 STEP에서 변경하지 않음 — §13 project 원칙에 따라 "미연동"으로 분류, 오류로 단정하지 않음.)
5. **표기 불일치** — §2에서 서술한 헤더 타이틀 vs 커뮤니티 카드/공유 텍스트의 단지명 표기 차이(displayName vs aptName 혼용).
6. **죽은 CSS 클래스** — `detail.module.css`의 `.contentGrid`(2단 그리드 레이아웃 정의)가 JSX 어디서도 사용되지 않음. 실제 페이지는 항상 단일 컬럼.
7. **모바일 하단 고정바 이중 렌더(가장 영향도 높음)** — `Header`의 전역 하단 탭바(`hideMobileNav` 미전달로 항상 노출, z-index 1000)와 페이지 자체 `StickyPriceBar`(z-index 500)가 모바일에서 동시에 `position:fixed; bottom:0`으로 렌더된다. 상세 근거는 §9.

7번은 코드 두 파일(`Header.tsx`/`Header.module.css`)을 대조해 확정적으로 판단한 것이고, 나머지 1~6번은 실제 프로덕션 클릭/조회로 실측 확인한 것이다. 7건 모두 이번 STEP에서는 **기록만 하며 수정하지 않는다**(§16에서 우선순위·후속 STEP 분류).

## 5. 첫 진입(첫 화면) 분석

데스크톱 뷰포트(1536×864, 실제 브라우저 창 높이 639px 가시영역) 기준 스크롤 없이 보이는 범위를 실측한 결과, **헤더 바 + 주소 한 줄 + 5칸 스펙 그리드 + 매매/전월세 토글 + 가격 + 최고/최저가 + 시세 차트 상단 절반** 정도까지만 보이고, 퀵버튼/투자지표/실거래 타임라인은 전부 스크롤해야 나온다.

모바일(코드 기준, 390~430px 폭 추정)은 데스크톱보다 가로가 훨씬 좁아 5칸 스펙 그리드가 자동으로 줄바꿈되고(`.grid`가 `AptSpecGrid.module.css`의 반응형 grid, 이번 STEP에서 해당 CSS 파일도 열람함 — `repeat(auto-fit, minmax(...))` 계열 패턴 확인) 세로 길이가 데스크톱보다 오히려 더 길어질 가능성이 높다. 즉 **"빠른 첫인상 이해"라는 재설계 목표에 비춰볼 때, 현재 첫 화면은 뚜렷한 단일 히어로 요소 없이 표+토글+숫자+차트가 동시에 밀도 높게 나열되는 구조**다 — R1이 이미 "B등급, 세로밀도 재검토 여지"로 평가한 것과 일치한다.

## 6. 정보 우선순위 분류 (P1~P4)

| 우선순위 | 정의 | 해당 요소 |
|---|---|---|
| P1 (즉시 필요) | 사용자가 이 페이지를 연 이유 그 자체 | 단지명, 최근 실거래가(매매/전세), 위치(지역명) |
| P2 (빠르게 확인) | 매수/전세 판단에 바로 쓰이는 핵심 지표 | 최고/최저가, 세대수, 준공년월, 평형, 시세 추이(상승/하락 방향) |
| P3 (탐색 시 필요) | 결정을 굳히는 단계에서 찾는 정보 | 실거래 타임라인 상세, 투자지표(전세가율/갭), 환경/교통/학군 |

**현재 화면과의 괴리**: P1(가격)과 P2(스펙) 순서 자체는 맞지만, P2 안에서도 "세대수/준공년월/용적률/건폐율/주차대수"라는 5개 항목이 동일한 시각적 무게로 나열되어 있어 그중 실제 의사결정에 자주 쓰이는 세대수·준공년월과, 상대적으로 전문가용 지표인 용적률·건폐율이 구분되지 않는다. 또한 P3에 해당하는 시세 차트·투자지표가 P1 바로 아래(퀵버튼보다도 위)에 있어 "빠른 확인"과 "탐색"의 경계가 화면 순서상 흐릿하다.

## 7. 딥다이브

### 7-1. 실거래 타임라인
- 강점: 4컬럼(계약월/일/가격/타입)으로 모바일 가로 스크롤 없이 고정(코드 주석상 의도적 설계, 등기정보·거래동 컬럼 제거 이력 있음), 직전 동일 평형 대비 등락 배지(▲/▼) 제공.
- 약점: `saleFilter`(select)와 `tradeTypeFilter`(상단 토글)가 별개 상태로 공존 — "매매/전월세" 토글(상단, API 재조회 유발)과 "전체 보기/매매만/전월세만"(select, 클라이언트 필터만) 두 UI가 유사한 의미를 가진 채 같은 화면에 공존해 혼동 가능성이 있다(코드 주석은 "별개"라고 명시하지만 사용자에게는 설명되지 않음).

### 7-2. 평형 선택 (AreaSelector)
- 상위 4개 평형만 칩, 나머지는 모달. 현재 선택된 평형이 상위 4개 밖이면 강제 포함 — 설계 의도는 합리적이나 §4-B-1의 중복 라벨 문제가 이 로직과 맞물려 발생.

### 7-3. 가격 표시
- 억/만원 한글 조합 표기(`formatKoreanPrice`, `priceStr`)로 일관됨. 매매·전세·월세가 섞인 데이터에서 "월세 없는 순수 전세만" 갭/전세가율 계산에 사용하는 필터링이 `PriceTrendChart`/`InvestmentMetrics` 양쪽에 동일하게 적용돼 있어 두 컴포넌트 간 정의는 일관적이다.

### 7-4. 차트 (PriceTrendChart)
- 매매+전세 동시 라인, 1/3/5년 토글. §1-B에서 지적한 대로 상단 매매/전월세 토글과 무관하게 항상 둘 다 보여주는 것은 "갭 비교"라는 목적에는 맞지만, 화면에 토글이 2군데(상단 매매/전월세, 차트 내부 1/3/5년) 있어 첫 사용자에게는 상단 토글이 차트에도 영향을 줄 것이라는 기대를 만들 수 있다.

### 7-5. 단지 기본정보 (AptSpecGrid)
- 값 없을 때 "정보 준비중"+제보 링크 — 추정치 미생성 원칙을 UI 레벨에서 가장 잘 지키는 컴포넌트. 다만 5칸이 시각적으로 동일 크기라 "핵심(세대수/준공)"과 "전문가용(용적률/건폐율)"의 위계가 없다(§6과 동일 지적).

### 7-6. 지도
- `KakaoMapEmbed`는 주소 지오코딩 실패 시 지번 지오코딩→키워드 검색까지 3단 폴백을 자체적으로 구현하고 있고, SDK 스크립트를 다른 컴포넌트가 미리 로드해뒀다고 가정하지 않고 직접 보장한다(코드 주석에 과거 무한 대기 버그 이력 명시) — 방어적으로 잘 짜여 있음.

### 7-7. 학교·생활 정보
- `KakaoPlaces`가 카테고리+키워드 검색을 병행하는 유일한 소비처(교통/학군 탭). §4-B-2의 KTX 오탐은 이 범용 컴포넌트의 필터 로직 한계.

### 7-8. CTA (공유/커뮤니티/제보)
- `KakaoShareButton`은 `navigator.share()`(모바일 OS 네이티브 공유 시트) 우선, 실패 시 카카오 SDK, 그마저 실패 시 클립보드 복사까지 3단 폴백 — 과거 세션에서 실측된 팝업 차단 문제(코드 주석에 상세 기술)를 반영한 견고한 구현.

### 7-9. loading / error / empty state 전반
- **loading**: 통합 스켈레톤(1구역) + 컴포넌트별 개별 로딩 문구(차트/투자지표/커뮤니티/시설) 혼재 — 일관된 스켈레톤 디자인 시스템은 없음(전부 텍스트 또는 펄스 바).
- **error**: 명시적 에러 배너 없이 "데이터 부족"/"불러오지 못했습니다" 같은 완곡한 문구로 흡수. 건축물대장 모달만 예외적으로 브라우저 네이티브 `alert()`를 사용(이 페이지의 다른 모든 에러 표현 방식과 이질적).
- **empty**: 대부분 "준비 중"/"정보 없음" + 제보 CTA 패턴을 일관되게 따름(FloorPlanPanel, 관리비, 학생수 추이, 커뮤니티 시설, 커뮤니티 글 등) — 이 부분은 화면 전체에서 가장 일관성 있게 지켜지는 패턴.

## 9. 하단 네비게이션 겹침 확인

**초기 grep 조사(파일명 패턴 `*Nav*`/`bottom-nav` 검색)로는 놓쳤던 부분을, `Header.tsx`/`Header.module.css` 원본을 직접 읽어 재확인한 결과 아래와 같이 정정한다.**

- `Header.tsx`는 R1 문서(§2)가 서술한 대로 **상단바 + 모바일 하단 탭바(홈/지도/통계/재개발분양/MY)를 실제로 겸한다.** `Header.module.css`의 `.menuList`가 `@media (max-width:900px)`에서 `position:fixed; bottom:0; height:60px; z-index:1000; background:white`로 전환되는 것이 그 하단 탭바다. `hideMobileNav` prop을 `true`로 넘긴 화면만 `.menuListHideMobile{display:none}`로 이를 숨길 수 있다(코드 주석: "페이지가 자체적인 모바일 하단 탭바를 이미 그리는 경우… 중복 표시되는 것을 막기 위해").
- `apt-client.tsx`의 실제 Header 호출부(§3-A)는 `<Header hideLogo pageTitle={...} pageTitleLarge pageTitleAlign="left" />`로 **`hideMobileNav`를 전달하지 않는다.**
- 즉 `/apt/[name]` 페이지는 모바일에서 **서로 다른 두 개의 `position:fixed; bottom:0` 요소가 동시에 렌더된다**: (1) `Header`의 전역 5탭 하단바(60px, z-index 1000, `@media max-width:900px`) and (2) 페이지 자체의 `StickyPriceBar`(`.stickyBar`, z-index 500, `@media max-width:768px`). 두 요소 모두 `bottom:0`을 기준으로 배치되므로 **같은 화면 좌표를 두고 경합**하며, z-index가 더 높은 Header 하단바(1000)가 항상 위에 그려져 `StickyPriceBar`(가격 요약 + "글쓰기" 버튼)를 완전히 또는 부분적으로 가릴 것으로 코드상 확정적으로 판단된다(실제 모바일 뷰포트 스크린샷으로 최종 확인하지는 못함 — §0 환경 제약).
- **이것은 §4-B에 새 항목으로 추가해야 할, 이번 조사에서 발견된 가장 영향도 높은 문제다.** 코드 전체에서 `hideMobileNav`를 실제로 전달하는 호출부는 `Header.tsx` 자신의 선언부 외에는 **단 한 곳도 없다**(grep 재확인). 비교 삼아 `/presales/[id]`(`presale-detail-client.tsx`)도 확인했는데, 이 화면은 `<Header pageTitle="분양정보" />`만 호출하고 **페이지 자체 sticky 하단바가 없어** 애초에 충돌 조건 자체가 성립하지 않는다. 즉 `hideMobileNav`는 설계는 돼 있으나 실제로 필요했던 유일한 페이지(`/apt/[name]`, 자체 `StickyPriceBar` 보유)에서 정작 호출되지 않은 것으로 판단된다.

## 10. 화면 길이 측정 (정보주도 vs 여백주도)

실측 3단지 모두 1구역(요약)만으로 데스크톱 뷰포트 기준 약 1.7~2 화면 분량, 전체 페이지는 4구역+모달을 합쳐 6~9 화면 분량으로 나타났다(단지 A처럼 거래가 많을수록 실거래 타임라인이 길어져 전체 길이가 늘어남 — 이는 정보량에 비례하는 정당한 길이다). 반면 1구역의 `.panel { padding: 2rem }`처럼 **정보량과 무관하게 고정된 여백 값**이 §8에서 확인한 대로 분양 상세보다 훨씬 크다 — 즉 이 페이지의 길이는 "정보가 많아서 길다"와 "여백이 커서 길다"가 섞여 있으며, 후자(`.panel`/`.quickBtn` 등 미개선 spacing)는 B3-FIX와 동일한 방식의 압축으로 정보 손실 없이 줄일 수 있는 여지가 있다.

## 12. 재설계 원칙

1. **첫 화면은 "빠른 이해"가 목적이다** — 전문 데이터 테이블처럼 모든 지표를 동일 무게로 나열하지 않는다. P1(가격)과 P2 중에서도 가장 일반적인 판단 지표(세대수·연식·평형)만 첫 화면에 남기고, 전문가용 지표(용적률·건폐율)는 한 단계 뒤로 미룬다.
2. **정보량이 곧 화면 길이가 되어야 한다** — 거래가 많은 단지는 자연히 길어지는 것이 맞다(§10). 다만 정보량과 무관한 고정 여백(`.panel` 2rem 등)은 B3-FIX 수준으로 압축해 "정보주도" 비중을 높인다.
3. **분양 상세(B3/B4)와 시각 언어를 공유한다** — 같은 앱 안에서 "상세페이지"라는 동일한 개념을 두 가지 다른 밀도로 보여주지 않는다(§8).
4. **기존에 잘 작동하는 정직한 빈 상태/폴백 패턴은 건드리지 않는다** — §11 Keep 목록은 재설계에서도 그대로 재사용한다.
5. **버그는 디자인 재설계와 분리해 먼저 고친다** — §4-B의 3건(중복 라벨/KTX 오탐/브리핑 임계값)은 UI 구조와 무관하게 별도로 수정 가능하고 사용자 신뢰에 직접 영향을 준다.

## 14. 상단 섹션(1구역) 재설계안 A/B/C

### 안 A — 히어로 압축형
단지명·주소를 한 줄로, 가격을 매매/전세 토글이 붙은 큰 숫자 하나로, 스펙은 세대수·연식·평형 3개만 인라인 배지로, 차트·투자지표·나머지 스펙(용적률/건폐율/주차)은 모두 한 단계 아래로 내림. 퀵버튼은 CTA 2~3개(공유/제보/지도)만 노출하고 나머지는 "더보기"로 묶음.
- 장점: 재작업 범위가 가장 작다(기존 컴포넌트 재배치+일부 축소만으로 가능, 새 컴포넌트 불필요). 재설계 원칙 1·2와 가장 직접적으로 부합.
- 단점: 용적률/건폐율처럼 이미 존재하는 정보가 한 단계 더 숨어 접근성이 살짝 떨어질 수 있음.

### 안 B — 탭 전환형
1구역 자체를 "시세 / 투자지표 / 단지정보" 3개 탭으로 나눠 3구역(환경/교통/학군)과 동일한 탭 UI 패턴을 재사용.
- 장점: 이미 3구역에 있는 탭 패턴을 그대로 재사용해 화면 안에서 인터랙션 일관성이 생김.
- 단점: 사용자가 진입 즉시 보고 싶어할 가능성이 높은 차트/투자지표가 탭 뒤로 숨어, 오히려 "빠른 이해"라는 목표와 상충할 수 있음(가격 다음으로 가장 자주 보는 정보가 시세 추이일 가능성이 높음).

### 안 C — 가로 캐러셀형
스펙 5칸을 가로 스크롤 캐러셀 카드로 바꾸고 차트는 축소 높이(약 160~180px)로 기본 노출, 탭하면 확대.
- 장점: 모든 정보를 한 화면 안에 유지하면서 세로 길이만 줄임.
- 단점: 가로 스크롤 UI는 존재를 인지하지 못하고 넘기는 사용자가 생길 수 있음(AreaSelector가 이미 유사 패턴을 쓰고 있어 학습효과는 있으나, 이 앱 다른 화면에서 스펙 정보를 가로 스크롤로 감춘 선례는 없음).

### 최종 pick(권고)
**안 A(히어로 압축형)를 권고한다.** 근거: (1) 재작업 범위가 가장 작아 "임의로 확장하여 수정하지 않는다"는 프로젝트 원칙과 가장 잘 맞고, (2) 재설계 원칙 1·2·3과 직접 부합하며, (3) 안 B의 단점(핵심 정보가 탭 뒤로 숨음)과 안 C의 단점(가로 스크롤 학습 비용)을 모두 피할 수 있다. 다만 이는 이번 STEP의 권고일 뿐이며, 사용자 확인 후 다음 STEP에서 확정한다.

## 16. 결론

아파트 상세페이지(`apt-client.tsx`, 820줄)는 기능적으로는 R1의 평가("실데이터 기반, 완성도 높음")대로 견고하다 — 추정치 미생성, 정직한 빈 상태, 다단 폴백(지도/공유) 등 프로젝트 원칙을 잘 지키고 있음을 이번 실측으로 재확인했다. 다만 (1) `Header`의 전역 모바일 하단 탭바를 숨기는 `hideMobileNav`를 전달하지 않아 페이지 자체 `StickyPriceBar`와 동시에 `position:fixed; bottom:0`으로 겹쳐 렌더되는, 코드 대조로 확정된 구조적 버그가 있고(§4-B-7/§9 — 이번 조사에서 가장 영향도가 높다고 판단), (2) B3/B4 세대의 압축 spacing이 전혀 적용되지 않아 정보량과 무관하게 화면이 여유롭게 길며, (3) 첫 화면이 전문 데이터 테이블처럼 모든 지표를 동일 무게로 나열하고, (4) 실측 과정에서 그 외에도 실제 로직 버그 3건(평형 라벨 중복, KTX 오탐, 브리핑 임계값 왜곡)을 발견했다. 재설계는 "안 A(히어로 압축형)"를 권고하며, 하단바 중복(B0)과 버그 수정(B1)과 spacing 압축(B2)은 재설계보다 먼저(또는 독립적으로) 진행할 수 있는 낮은 리스크 작업으로 분리했다(§15).
