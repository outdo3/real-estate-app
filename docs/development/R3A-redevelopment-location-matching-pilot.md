실제 확보 가능한 값만 조합(추측 주소 생성 안 함), 우선순위:


**SUCCESS 11건 중 9건(82%)에 층/호수/건물명 등 사무실 특유의

케이스들이 오히려 실제 현장 부지를 가리키는 진짜 주소일 가능성이
높다(예: 가야1의 원문 "가야동 410번지 일원(가야초교 남측 일원)"은

**결론(중요)**: **`location` 필드를 그대로 지오코딩해서 얻는
좌표는, 성공률이 높아 보여도 대부분 정비구역 "현장"이 아니라
조합·추진위 "사무실" 위치를 가리킬 가능성이 크다.** 지오코딩
성공 = 좌표 정확도 보장이 아니다. R2에서 "location이 조합
사무실일 수 있다"고 정성적으로만 지적했던 것을, 이번 파일럿에서
**9/11(82%)이라는 구체적 비율로 실증**했다.

## geocoding 성공률

```text
전체 22건 기준: SUCCESS_EXACT 11 / AMBIGUOUS 1 / FAILED 10
  → 좁은 의미 성공률(EXACT만) 50.0%
  → location 존재 12건 기준 성공률 91.7%(11/12)

서구 8건 기준: SUCCESS_EXACT 4(서대신4·부민2·부민3·서대신5) / FAILED 4
  → 50.0%(location 존재 4건 전부 성공, location 없는 4건 전부 실패)
```

서구만 놓고 봐도 전체 경향과 동일 — location 유무가 성공/실패를
그대로 가른다.

## 이름 normalization

R2·R3A에서 실제 사용한 규칙(코드 그대로):

```python
def normalize(name):
    n = name.strip()
    n = re.sub(r'\s+', '', n)      # 공백 제거
    n = n.replace('제', '')          # "제" 제거
    for suf in ['재개발정비사업','재건축정비사업','주택재개발정비사업',
                '주택재건축정비사업','가로주택정비사업','소규모재건축사업',
                '소규모재건축','재개발사업','재건축사업','정비사업',
                '정비구역','재개발','재건축','구역','지구','사업']:
        if n.endswith(suf):
            n = n[:-len(suf)]
    return n
```

## 위험한 normalize 규칙(실증)

**"재개발"/"재건축" 접미사 완전 제거가 실제로 오매칭을 만든다는
것을 이번 STEP에서 실증으로 확인했다.** 아래 "충돌 분석"의 부산
API 내부 충돌 20건은 **전부 예외 없이** 이 패턴이다: `"거제2
재개발"`과 `"거제2 재건축"`처럼 같은 번호를 쓰는 서로 다른(재개발
트랙과 재건축 트랙) 두 사업이, 유형 접미사를 지워버리는 순간 같은
키로 뭉쳐버린다. `"숫자 제거"`, `"동명 제거"`, `"구역번호 제거"`
규칙은 이번 정규화 함수에 애초에 포함하지 않았다(정규화 규칙에
없는 위험은 검증하지 않았다).

## 충돌 분석

**국토부 부산 내부(227건) 충돌 — 정규화 이름이 2개 이상인
그룹: 16건.**

이 중 13/16이 뚜렷한 반복 패턴: 같은 정규화 이름으로 "5)주거환경
개선 + 2)정비구역지정(최초 단계) + 세대수 0" 레코드와 "재개발/
재건축 + 진행된 단계 + 실제 세대수" 레코드가 **같은 시군구 안에
동시에 존재**한다(대연3, 문현1, 범일2, 범일3, 초량2, 수정2,
수정3, 초량3, 안락1, 가야4, 가야1, 양정3, 괴정2, 당리2 등). R2의
"국토부 데이터가 뒤처져 있을 가능성"이 국토부 CSV **내부에서도**
확인된다 — 최초 지정 시점 스냅샷 행이 갱신되지 않고 새 행과 함께
남아있는 구조로 추정된다(확정 아님). `촉진5`는 아예 **금정구와
영도구라는 서로 다른 구**에 같은 이름으로 존재 — 시군구 없이
이름만으로 매칭하면 완전히 다른 두 사업을 하나로 합칠 뻔한
실제 사례다.

**부산 API 내부(343건) 충돌 — 20건, 전부 "재개발/재건축 접미사
제거"가 원인**(위 "위험한 normalize 규칙" 참고).

**Cross-source(공유 키 129개) 카디널리티**:

```text
1:1  = 107 (83%, 안전하게 자동 후보 가능)
1:N  = 7   (국토부 1건에 부산API가 여러 건 걸림)
N:1  = 12  (국토부 여러 건이 부산API 1건에 걸림 — 위 "국토부 내부 충돌" 패턴과 겹침)
N:N  = 3
```

129개 공유 키 중 22개(17%)가 단순 1:1이 아니다 — 자동 병합은
위험하고 사람 검수가 필요하다.

## match confidence 설계(문서 설계만)

```text
EXACT
  시도 + 시군구 + normalized(name) + businessType 4개 전부 일치
  (예: 서대신4/서구/재개발/재개발 — 정규화 시 유형 접미사를
  지우지 않고 별도 필드로 비교)

HIGH
  시도 + 시군구 + normalized(name) 일치, businessType은
  한쪽에만 있거나(국토부에만 유형코드 있음) 유형 분류 체계가
  달라 직접 비교 불가한 경우

MEDIUM
  시도 + 시군구 일치 + name 유사(편집거리 등) + 세대수가 임계치
  이내로 근접(예: ±10%) — 세대수는 보조 신호일 뿐 identity로
  쓰지 않는다

LOW
  name만 유사, 시군구 불일치 또는 세대수 근거 없음 — 자동 merge
  절대 금지

UNMATCHED
  대응 후보를 찾지 못함 — 별도 사업으로 유지
```

## 자동 merge 기준

```text
EXACT / HIGH  → 자동 병합 후보(그래도 최초 1회는 사람이 훑어보는
                것을 권장 — 이번 파일럿에서 EXACT조차 세대수가
                꽤 차이나는 사례(명서1: 1521 vs 785)를 발견했다)
MEDIUM        → review queue(사람 검수 필수)
LOW           → merge 금지, 두 소스 값을 별도로 표시
UNMATCHED     → 별도 사업(source 필드로만 구분)
```

이번 STEP에서 이 로직을 코드로 구현하지 않았다 — 설계안이다.

### 아미1 / 아미3

국토부에만 존재(5)주거환경개선 / 2)정비구역지정 / 0세대), 부산

있지만 서구는 없음 — 지자체별로 등록 여부가 다름). 외부 포털/
블로그의 "아미동 재개발" 언급은 존재 확인의 보조 참고일 뿐 공식
좌표 소스가 아니다.

## polygon 조사

- **VWorld**: "도시계획정보" 카테고리 아래 개발행위허가제한지역·
  도시계획시설_결정조서·건축한계선·취락지구 등 레이어가 있음을
  확인했으나, **"정비구역 경계"라는 이름의 명시적 레이어는 이번
  검색에서도 확인하지 못함**(R2와 동일 결론 — 재확인만 하고
  새로 알아낸 것 없음).
- **data.go.kr 지자체별 fileData**: 부산 16개 구·군 중 일부만
  (예: 동구) 개별 "도시정비 사업 현황" 파일을 올려뒀고, 서구는
  없음 — 있다 해도 표 형태 fileData이지 polygon(SHP/GeoJSON)이
  아닐 가능성이 높다(이번 STEP에서 실제 파일 형식까지 열어
  확인하지 않음).
- **부산 도시재생종합정보**: "도시재생"(주거환경 개선·마을만들기
  중심)은 "도시정비"(재개발/재건축)와 법적으로 다른 사업 범주라
  직접적인 polygon 대체 소스로 보기 어려움.

**전국 통합 polygon Master는 이번 STEP에서도 발견하지 못했다.**

## point-first 판단

**POINT_FIRST_OK — 조건부.** 좌표(point)만으로 지도 marker·목록·
상세·단계·세대수·사업유형을 보여주는 UX 자체는 가능하다. 다만:

1. location 기반 지오코딩 좌표의 82%가 사무실 위치일 위험이
   있으므로, marker를 "정비구역 정확한 경계 위치"가 아니라
   **"사업 정보 조회 지점(참고용)"** 수준으로 명확히 표시해야
   한다(정확한 부지 경계처럼 오인시키지 않기).
2. location이 아예 없는 사업(이번 파일럿에서 45%)은 point조차
   없다 — 이런 사업은 지도에는 안 나타나고 목록/상세에서만
   노출하는 방식으로 분리해야 한다.
3. Polygon은 이번 STEP에서 확보하지 못했지만, 위 두 가지를
   지키면 point-first로 V1을 시작하는 것 자체는 막히지 않는다.
