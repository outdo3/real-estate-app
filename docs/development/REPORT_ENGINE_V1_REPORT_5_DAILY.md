## 1. 이 리포트가 말하는 것 — 관찰일 ≠ 계약일

`/report/daily/{YYYY-MM-DD}`의 날짜는 **이집이 그 거래를 처음 확인한 날**(관찰일,
`created_at`)이다. **계약일이 아니다.**

이건 표현상의 뉘앙스가 아니라 데이터의 실제 모양이다. 실측(2026-09-10 관측분):

| 관찰일 | 새로 확인 | 계약일 범위 |
|---|---|---|
| 2026-09-10 | 89건 | 2026-02-10 ~ 2026-09-09 |
| 2026-09-09 | 129건 | 2026-05-05 ~ 2026-09-08 |

MOLIT는 계약 후 최대 30일의 신고 기한이 있고, 이집의 sale sync는 최근 3개월을
overlap으로, recheck는 3~12개월 전을 다시 본다. 그래서 "오늘 새로 확인된 거래"에는
반년 전 계약이 섞인다.

따라서 이 리포트는 **절대** "오늘 부산에서 N건 계약됐다"고 말하지 않는다. 대신:

- 제목이 `9월 10일 새로 확인된 부산 실거래` — "새로 확인된"이 제목에 박혀 있다.
- 모든 거래 행에 `계약일 2026.09.09` 배지가 붙는다.
- `계약일 범위` KPI가 관찰일과 계약일이 다르다는 걸 숫자로 보여준다.
- 관찰일/계약일 구분 문장이 툴팁이 아니라 **본문**과 envelope `trust.notes`에 있다.

§19(공유 안전)의 이유가 이것이다. 이 시트는 스크린샷으로 문맥 없이 돌아다닌다.
캡처 한 장만 봐도 오해가 없어야 한다.

## 2. 타임존 계약 (§2)

KST 하루 ↔ UTC 경계 변환은 `daily-observation.ts`의 `observationWindowKst()`
**한 곳에서만** 한다. 쿼리·컴포넌트 어디에서도 타임존 산술을 다시 하지 않는다.

```
KST D 00:00 ~ D+1 00:00  =  UTC [D-1 15:00, D 15:00)
```

한국은 현재 서머타임이 없다(1988년 이후). 그래서 고정 +09:00으로 안전하게 계산할 수
있고, `KST_OFFSET_MINUTES = 9 * 60` 상수 하나로 충분하다. 테스트에서 이 가정을
명시적으로 고정해 뒀다 — 만약 DST가 도입되면 그 테스트가 먼저 깨진다.

```

  → ReportEnvelope<DailyTradeReportData>
```

`daily-observation.ts`는 Prisma를 import하지 않는 **순수 규칙**이다:
타임존 경계(§2), 백필 판정(§6), 발행 상태 판정(§9)의 단일 출처.
`daily-report.ts`도 순수 — envelope 조립만 한다.

## 4. 집계 기준은 `created_at`이지 커버리지 셀이 아니다

`sync_coverage_cells`는 `(dataset, lawdCd, dealYmd)` upsert라서 **마지막 실행값만**
남는다. 일별 실행 로그가 아니다(PRECHECK §8). 그래서 `insertedCount`로 일별 수치를
재구성하지 않는다. 커버리지 셀은 오직 "지금 이 스코프가 검증된 상태인가"를 볼 때만 쓴다.

일별 수치는 append-only인 `apartment_trade_histories.created_at`으로만 만든다.

## 5. 백필 의심 가드 (§6/§7)

### 왜 필요한가

초기 적재/백필이 돌면 하루에 수십만 행이 들어온다. 그걸 "그날의 신규 거래"로 발행하면
완전한 거짓말이 된다. 실측:

| 관찰일(KST) | 관측 행 | 서로 다른 계약월 | 가장 오래된 계약일 |
|---|---|---|---|
| 2026-08-29 | 189,951 | 248 | 2006-01-02 |
| 2026-08-30 | 665,096 | 248 | 2006-01-01 |
| 2026-09-03 | 8,823 | 21 | 2006-11-01 |
| 2026-09-09 | 129 | 3 | 2026-05-05 |
| 2026-09-10 | 89 | 7 | 2026-02-10 |

### 판정 규칙 — 임의의 상수를 만들지 않는다 (§6)

두 임계값 모두 **이미 배포된 sync 상수에서 유도**한다. 매직 넘버가 아니다:

```ts
MAX_LEGITIMATE_DISTINCT_MONTHS = SALE_RECHECK_MAX_MONTHS_BACK + 1   // 13
MAX_LEGITIMATE_MONTHS_BACK     = SALE_RECHECK_MAX_MONTHS_BACK       // 12
```

근거: 정기 실행이 건드릴 수 있는 계약월의 합집합은 sale overlap(최근 3개월)과
recheck(3~12개월 전)의 합, 즉 "0개월 전 ~ 12개월 전" = 최대 13개의 서로 다른
`deal_ymd`다. 이 범위를 넘는 모양은 정기 수집으로 설명되지 않는다.

- `TOO_MANY_MONTHS` — 하루 관측된 계약월 수 > 13
- `CONTRACT_TOO_OLD` — 가장 오래된 계약일이 관찰일 기준 12개월 전보다 이전

**행 수는 판별자로 쓰지 않는다.** 실측에서 정상일(206건)이 비정상일(132건)보다 많았다.
건수는 백필의 신호가 아니다.

### 부분 차감 금지 (§7)

백필이 의심되면 **그날 전체를 보류**한다. "의심되는 행만 빼고 나머지로 집계"하지 않는다.
백필 실행 중에 들어온 정상 거래와 백필 거래를 사후에 구분할 방법이 현재 스키마에 없기
때문이다(§9 참고). 반쯤 맞는 숫자는 틀린 숫자다.

보류된 날은 `rows = []`, `newlyObserved` 값이 `null`/`확인 중`/trust `MISSING`이 된다.
**0건으로 채우지 않는다.**

## 6. 커버리지 게이트와 "진짜 0건" (§10/§12)

수집 실패를 0건으로 발행하는 것이 이 리포트에서 가장 위험한 실패 모드다.
그래서 검증되지 않은 날은 **0조차 말하지 않는다**.

확인 대상 = (그날 관측된 부산·취소제외 행들의 계약월) ∪ (관찰일이 속한 달).
그 모든 월에 대해 부산 16개 코드의 `SyncCoverageCell`이 전부 존재하고
상태가 `COMPLETE` 또는 `EMPTY_VALID`일 때만 `VERIFIED`다.

발행 상태 판정 순서 (`resolvePublicationState`):

```
1. 백필 의심            → WITHHELD_BACKFILL
2. 지원 범위 밖/미래     → OUTSIDE_SUPPORTED_RANGE
3. 커버리지 미검증       → PREPARING          (0건이라고 말하지 않음)
4. 검증됨 + 0건         → READY_ZERO         (진짜 0건)
5. 검증됨 + N건         → READY
```

**순서가 중요하다.** 백필을 지원 범위보다 먼저 본다. 2026-08-29는 지원 시작일 이전이면서
동시에 백필인데, 이걸 "그냥 범위 밖"이라고만 말하면 그날 무슨 일이 있었는지에 대한
정보를 잃는다. 실제 탐지된 이유가 가장 정확한 이유다.

`READY_ZERO`와 `PREPARING`은 화면에서 명확히 다른 문구를 쓴다. 전자만 "없습니다"라고
단정한다.

## 7. 지원 범위 (§11)

```ts
DAILY_SUPPORTED_FROM_KST = '2026-08-30'
```

그 이전은 초기 백필 구간이라 "그날 새로 확인했다"는 말 자체가 성립하지 않는다
(PRECHECK §3.3-4). 미래 날짜도 `OUTSIDE_SUPPORTED_RANGE`다.

## 8. 부산 스코프와 취소 (§4/§5)

부산 현행 16개 `lawdCd`만 분자·분모 양쪽에 들어간다(`region-scope.ts` 재사용, 목록
중복 정의 없음). 파일럿으로 들어온 서울 `11680`·대구 `27110` 행은 부산 수치에 절대
포함되지 않는다.

실증: 2026-08-31 관측 132행은 **전부 스코프 밖**이라 부산 0건이 됐고, 커버리지가
검증된 상태였으므로 `READY_ZERO`(진짜 0건)로 발행됐다. 132가 부산 건수로 새지 않았다.

스코프 밖 행 수는 숨기지 않고 `trust.notes`에 "부산 외 지역 N건은 부산 집계에 포함하지
않았습니다"로 남긴다.

취소 거래(`dealCanceled`)는 제외한다.

## 9. 성능 (§20) — 그리고 남은 한계

### 근본 원인: `created_at`에 인덱스가 없다

`apartment_trade_histories`는 855,179행 / 472MB인데 인덱스는
`(apt_seq, exclusive_area, deal_date)`, `(lawd_cd, deal_date)`,
`(identity_key, deal_date)`, `(deal_date)`, `(lawd_cd, exclusive_area, deal_date)`뿐이다.
**`created_at` 단독/선두 인덱스가 없다.**

관측창 질의는 전부 `created_at` 범위 필터이므로 매번 풀스캔이다. EXPLAIN ANALYZE 실측
(KST 2026-09-10, 89행을 고르는 질의):

```
Parallel Seq Scan on apartment_trade_histories
  Filter: created_at >= '2026-09-09 15:00+00' AND created_at < '2026-09-10 15:00+00'
  Rows Removed by Filter: 864,539
Execution Time: 15,701 ms   (cold)
```

같은 질의 반복 시 warm 1,266~1,865ms. **즉 관측창 스캔 1회의 바닥값이 ~1.3~1.9초다.**

### 이번 STEP에서 한 것: 스캔 횟수를 최소화

원래 구현은 그날 관측된 행을 전부 materialize한 뒤 요약했다. 2026-08-29(18만 행)에서
route 15,371ms(cold) / 7,063~7,842ms(warm)가 나왔고, **그 18만 행은 백필 보류로 전량
버려졌다.**

`detectBackfill`이 실제로 보는 건 숫자 3개(`totalRows`, `distinctDealYmd`,
`minDealDate`)뿐이다. 그래서 순서를 뒤집었다:

1. **관측창 풀스캔 1회**로 필요한 집계를 전부 얻는다 — 단일 `$queryRaw`에
   `COUNT(*) FILTER (...)` / `MIN(deal_date) FILTER (...)` / `array_agg(DISTINCT deal_ymd)`.
   (집계를 Prisma API로 4개 나눠 부르면 풀스캔이 4번 되어 **더 느려진다** — 실측으로 확인했다.)
2. 백필·커버리지·발행 상태를 판정한다.
3. **발행 가능한 날에만** 행을 읽는다. 보류된 날은 행을 아예 읽지 않는다.
4. 그 행 질의에는 1번에서 얻은 대상 집합의 실제 `MIN/MAX(deal_date)`를 경계로 얹는다.
   결과를 바꾸지 않는 항등 조건이지만 `(lawd_cd, deal_date)` 인덱스를 타게 해준다.
   실측(9/10): 풀스캔 대신 **191ms**.

### 남은 한계 — 목표 미달, 그리고 그 이유

§20 목표는 warm ≤500ms / route ≤1s다. **이 목표는 현재 스키마에서 달성 불가능하다.**
1번의 관측창 풀스캔만으로 warm 바닥이 1.3~1.9초이기 때문이다.

해결책은 하나뿐이다:

```prisma
@@index([createdAt])   // 또는 @@index([createdAt, lawdCd])
```

이건 **schema 변경이라 사용자 승인이 필요하다**(AGENTS.md / STEP §0). §20도 "No
premature SQL/schema redesign"이라고 못박았으므로, 이번 STEP에서는 인덱스를 추가하지
않고 **측정 결과와 함께 권고로만 남긴다.**

예상 효과: 관측일 하루는 전체의 0.01% 수준(89 / 855,179)이라 인덱스가 붙으면 이 질의는
풀스캔에서 인덱스 레인지 스캔이 되고, warm 응답은 §20 목표 안으로 들어올 가능성이 높다.
다만 이건 **예측이며 실측이 아니다** — 인덱스 승인 후 재측정해야 한다.

## 10. 향후 스키마 권고 (구현하지 않음)

현재 스키마로는 "이 행이 정기 수집으로 들어왔는가, 백필로 들어왔는가"를 **직접** 알 수
없다. 그래서 §5의 백필 가드는 계약월 분포로 **추정**한다. 추정이 맞았다는 건 실측으로
확인했지만(8/29·8/30·9/3 탐지, 9/9·9/10 통과), 추정은 추정이다.

권고 (승인 필요, 이번 STEP 범위 아님):

| 필드 | 목적 |
|---|---|
| `ingestRunId` | 같은 실행으로 들어온 행을 묶는다. 백필 실행 전체를 정확히 식별·제외 가능. |
| `ingestMode` | `INCREMENTAL` / `BACKFILL` / `RECHECK`를 **선언적으로** 기록. 추정이 불필요해진다. |
| `@@index([createdAt])` | §9의 성능 한계 해소. |

`ingestRunId`가 있으면 §7의 "전체 보류"를 "백필 실행분만 정확히 제외"로 좁힐 수 있어
8/29 같은 날도 그날의 진짜 신규 거래를 발행할 수 있게 된다.
