2,000세대 단지의 3건은 한산한 수준", "21건 중 최저가 단일 거래를 과거로,
최고가 근처 단일 거래를 현재로 잡아 57% 상승으로 계산됐지만 실제로는
변동성 큰 데이터"). 현재 로직:

- 시세 추이: 최신/최과거 각각 최대 3건 평균(면적당 가격으로 정규화)으로

- 거래빈도: `최근 3개월 거래건수 / 세대수` 비율로 활발/보통/한산 판단

표현 완화(예: 최소 표본 수 미만이면 "표본이 적어 판단이 제한적입니다"류

## 5. "이집 브리핑" 발전 가치 평가

단순 숫자 재서술을 넘어 "좋은 점/확인할 점/교통/생활편의/주차/준공년차/
최근 거래 흐름"을 종합하는 브리핑으로 발전시킬 가치는 **있다** — 다만
**선행조건이 있다**(§24). 현재 buildAptBrief가 다루는 데이터(시세/세대수/
연식)만으로는 "좋은 점/확인할 점"처럼 다면적 판단을 할 근거가 부족하다.
교통(§6-7)·생활편의(§8-9) 데이터가 먼저 확보돼야 브리핑이 실질적으로
풍부해진다 — 지금 무리하게 확장하면 근거 없는 판단(원칙 위반)이 되기
쉽다.

## 19. 상세페이지 내 다른 아파트 검색 진입점 — 부재 확정 + 낮은 리스크 해법 발견

`apt-client.tsx`가 렌더하는 `<Header />`(644행)는 `searchSlot` prop을
전달하지 않는 기본 호출 — 검색 진입점이 전혀 없음을 재확인.

**중요 발견**: `Header.tsx`는 이미 `searchSlot?: React.ReactNode` prop을
지원하도록 설계돼 있고 전용 CSS 클래스(`.searchSlot`)까지 있으나,
**현재 어느 페이지도 이 prop을 사용하지 않는다**(grep 전체 재확인 —
`Header.module.css`에만 클래스 정의가 존재, 실제 호출부 0건). 즉 검색
슬롯을 위한 배관은 이미 있고 비어있을 뿐이다.

추가로 `ApartmentAutocomplete.tsx`(카카오 키워드 검색 기반 자동완성,
`onSelect(result)` 콜백 패턴, 상위 결과 실데이터 enrichment 포함)가
`/map`, `/stats/[type]`, `RegionSelectModal`에서 **이미 재사용되고
있음**을 확인 — 상세페이지 전용의 새 검색 컴포넌트를 처음부터 만들
필요 없이, 기존 컴포넌트를 `Header`의 `searchSlot`에 연결하고
`onSelect`에서 `router.push('/apt/...')`만 추가하면 되는 구조다.

**추천**: **A. Header 검색 아이콘/슬롯**. 이유:
- 이미 존재하는 `searchSlot` prop을 그대로 활용 — 새 UI 컴포넌트
  레이아웃을 설계할 필요가 최소화됨(리스크 가장 낮음).
- B(Hero 검색 버튼)는 Hero 영역이 이미 정보 밀도가 높아(가격/평형/공유
  버튼) 추가 요소가 부담. C(Sticky 상단 검색)는 스크롤 중 항상 노출돼
  화면을 더 많이 차지. D(전체화면 오버레이)는 가장 유연하지만 구현
  범위가 가장 크다 — 1차 구현으로는 과함.
- Header는 모든 페이지에 공통이라, 상세페이지뿐 아니라 향후 다른
  페이지에도 자연스럽게 확장 가능.

## 20. 일반 단지검색 vs AI 검색 — 분리 필요성 평가

**분리가 맞다.** 홈(`src/app/page.tsx`)의 메타데이터가 이미 "AI 부동산
검색"으로 명시돼 있어(참고만, 미수정), 홈의 주력 검색은 자연어 조건
검색(Gemini 기반)이다. 반면 상세페이지에서 "다른 단지를 보고 싶다"는
요구는 대부분 **정확한 단지명이 이미 머릿속에 있는 경우**(예: "명륜
아이파크1단지")라 자연어 해석이 오히려 느리고 부정확할 수 있다 —
`ApartmentAutocomplete`처럼 즉시 이동하는 exact-match 자동완성이 이
맥락에 더 적합하다.

## 21. ApartmentSearch 공통 component 추천 여부

**추천하지 않음(신규 컴포넌트 불필요) — 기존 `ApartmentAutocomplete`
재사용을 추천.** 이미 3곳(`/map`, `/stats/[type]`, `RegionSelectModal`)
에서 검증된 채로 쓰이고 있어, 새 `ApartmentSearch` 컴포넌트를 만들면
오히려 코드 중복이 생긴다. 상세페이지에서 필요한 것은 새 컴포넌트가
아니라 "기존 컴포넌트 + Header의 searchSlot 배선 + onSelect 시
`/apt/[name]` 이동" 정도의 통합 작업이다(구현은 이번 STEP 범위 아님).

## 22. 지도 바텀시트 — 후속 판단(지도 미수정, 참고만)

`src/app/map/page.tsx` 확인 결과, 마커 선택 시 하단 카드(`selectedMarker`)
가 뜨고 "상세보기" 버튼(898-902행)을 눌러야 `/apt/[name]`으로
`router.push`한다 — 사용자가 불편하다고 한 2단계 흐름이 코드로도
확인된다. **이번 STEP에서 지도는 수정하지 않는다.** 후속 아이디어로만
기록: "정확한 단지명 검색 결과를 선택했을 때"와 "지도 마커를 직접
탭했을 때"는 사용자 의도가 다르다(전자는 이미 특정 단지를 찾고 있었고,
후자는 지도를 탐색하다 발견) — 전자는 바텀시트 없이 바로 상세 이동,
후자는 현재처럼 바텀시트 유지가 합리적이라는 동선 분리 아이디어를
후속 UX 항목으로 남긴다.

  컴포넌트 재사용), 리스크 낮음(Header 공통 컴포넌트라 전 페이지 영향
  범위를 신중히 봐야 함 — 선행조건: Header 변경이 다른 페이지 레이아웃을
  깨지 않는지 회귀 확인).
- **UI-C2. 생활편의 카테고리 확장(대형마트/편의점/약국/어린이집)**:
  사용자 가치 높음, 난이도 낮음(전용 카테고리 코드 존재, 기존 컴포넌트
  patterns 재사용), 리스크 낮음(신규 API 없음). 선행조건 없음 — 가장
  빠르게 구현 가능.
- **UI-C3. 버스 정보(정류장 개수 + 최근접 거리)**: 사용자 가치 높음,
  난이도 중(카카오 키워드 검색, KTX/공원과 같은 패턴이라 완전히 새로운
  기술은 아님), 리스크 낮음(신규 유료 API 없음). 선행조건 없음.
- (참고, 이번 요청 범위 밖 후보) UI-C4 단지 브리핑 소표본 표현 개선,
  UI-C5 커뮤니티/퀵버튼 정리(단지정보 중복 축소, 커뮤니티시설 숨김),
  UI-C6 학군 빈 placeholder 숨김.

**추천 순서**: UI-C2(생활편의) → UI-C1(검색 진입점) → UI-C3(버스) 순.
근거: C2가 리스크·난이도 최저면서 체감 가치가 즉시 큼(모든 단지에
바로 적용), C1은 Header 공통 컴포넌트 변경이라 회귀 범위 확인이 한 단계
더 필요, C3는 새로운 검색 패턴(정류장) 도입이라 상대적으로 검증 시간이
더 필요. 단, 실제 순서는 사용자 승인에 따라 변경 가능.

## 27. 점수체계 선행 데이터(계산식 설계 아님, 목록만)

교통(지하철/버스 거리 및 개수) · 주차(세대당 대수, B2-1에서 이미 확보) ·
세대수/준공년차(이미 확보) · 생활편의(카테고리별 개수, §11 확장 후) ·
학군(인근 학교 수/거리, 이미 확보) · 가격(실거래 추이, 이미 확보) ·
거래량(세대수 대비 비율, 단지브리핑에서 이미 계산 중) — 이 중 **교통
(버스)과 생활편의(확장 카테고리)가 아직 없어** 점수체계 설계 전에
먼저 채워야 할 항목으로 확정.

## 28. "이집 브리핑" 선행조건

부족한 데이터: **버스(§8, 현재 없음)**, **생활편의 확장 카테고리(§11,
현재 병원/공원뿐)**. 이 둘이 없으면 "확인할 점/교통/생활편의" 문장을
근거 있게 만들 수 없다 — 지어낼 수 없으므로(원칙4) 이 두 데이터가
먼저 확보돼야 브리핑 재설계(§5)를 시작하는 것이 안전하다. 반대로
"좋은 점"(시세 상승/거래 활발) 문장은 현재 데이터만으로도 이미 가능
(§2-3의 buildAptBrief가 사실상 이 부분을 담당 중).

## 최종 판단

APT DETAIL UI-C는 상세페이지 잔여 12개 영역을 코드 재조사 + DB 재확인 +
production 실측(단지 브리핑 10개 단지, read-only)으로 점검했다. 이전
audit이 지적한 브리핑 통계 버그는 이미 수정돼 있었고(코드·데이터로
재확인), 생활편의가 "공원/병원 위주"인 이유는 하드코딩된 카테고리 2개
뿐이기 때문임을 코드로 확정했다(대형마트는 이미 준비된 미사용 코드
발견). 상세페이지 내 검색 부재는 이미 존재하는 `Header.searchSlot`과
`ApartmentAutocomplete`를 연결하기만 하면 되는 낮은 리스크 구조임을
확인했다. 유지/개선/삭제 매트릭스와 3개 다음 STEP 후보(생활편의 확장 →
검색 진입점 → 버스)를 정리했다.

production code/API/DB/schema는 변경하지 않았고 commit/push 하지 않았다.

교통/버스, 생활편의, 이집 브리핑, 상세 내 아파트 검색의 실제 구현은
사용자 승인 후 별도 STEP으로 진행합니다.
