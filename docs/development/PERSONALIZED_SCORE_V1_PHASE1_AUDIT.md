## 1. 원칙

- **공통 점수**(이집 점수 V2)는 그대로. 개인화 점수는 공통 점수를 덮어쓰지 않는 **별도 값**이다.
- 개인화는 공통 점수 엔진이 이미 계산한 **축 점수의 가중 평균만 바꾼다**. 새 curve·새 임계값·새 데이터 추정 없음.
- 선호 미설정 → 개인화 점수 없음(기본 가중치로 임의 점수를 만들지 않는다). 비로그인 → 계산하지 않음.

### 4-1. 가격
- 공통 점수에 가격/시장 도메인이 없다(V1 market은 가중치 0 정보용).
- 사용자 예산은 어디에도 저장되지 않는다. 자금계획(finance-fit)은 입력을 저장하지 않는 계산기이며, 가용현금·대출은 민감 금융정보라 저장하지 않는 기존 결정이 있다.
- "싸면 고점수"는 개인 적합도가 아니다. 가격 적합도는 **내 예산 대비**여야 하며, 이는 예산 입력(민감)과 최신 가격(market feature 만료·원장 계산 필요)을 요구한다 → **V1 제외**, V2에서 "예산 적합도"로 별도 설계(저장 여부부터 결정).

### 4-2. 교통
- 공통 교통 접근성(지하철·버스) 가중치 조절은 V1 가능. 지하철 "반경 내 없음 확인"은 5점(결측 아님)으로 이미 구분된다.
- 한계: 직선거리·역 중심점 기준(출구 없음). 출퇴근 목적지 시간은 V2.

### 4-3. 학교(주의)
- 현재 교육 점수 = **초등학교 직선거리 하나**. 학업성취·진학률·중고교 데이터 없음 → "학군"이라고 부르면 과장이다. 축 이름은 **"초등학교 접근성"**.
- 알려진 오차(`SCHOOL_DISTANCE_SOURCE_RECONCILIATION_V1.md`): Kakao 거리와 공식 좌표 거리 차이가 25m를 넘는 21단지, Kakao 1km 내 결과 없음 20단지. NEIS 학교 테이블 기반 거리 재산정과 임계값 재보정이 후속 예정 → 공통 점수가 바뀌면 개인화 축도 같이 바뀐다(개인화는 재가중만 하므로 별도 수정 불필요).
- 개인화 UI에 "초등학교까지 거리 기준" 설명 필수. 사용자 선택지에서 과신 유도 금지.

### 4-4. 주차
- 건축물대장 주차대수/세대수(총괄표제부 우선). 점수 산출 단지 중 71.5%만 실측.
- **공통 점수의 연식대 중립값은 개인화에 쓰지 않는다**(사용자가 주차를 중요하게 골랐는데 추정값으로 점수를 주면 안 됨). 결측이면 이 축을 제외하고 재정규화 + "주차 정보 없음" 표시 → LIMITED.
- 이상치 31건(세대당 0.05 이하/5 초과)은 기존 curve가 clamp하지만 데이터 품질 확인 대상.

### 4-5. 신축
- 100%. 신축 선호가 높은 사용자는 `ageScore`(0년 95 → 40년 20) 가중을 높인다.
- 공통 curve는 재건축 기대를 반영하지 않는다(`curves.ts` 명시). 재개발 데이터는 aptSeq 연결이 없어 V1에서 "재건축 선호"를 반영할 수 없다. 신축 선호가 낮다고 구축에 가점을 주는 역방향 계산은 하지 않는다(중요도는 0이 아닌 1이 최소 — 반대 선호 표현 불가, V1 한계로 명시).

### 4-6. 향후가치
- 존재하는 결정적 데이터: 24개월 신고가/하락 랭킹(지역 단위), 지역 가격변동 중앙값, 갭·전세가율, 분양 공급(aptSeq 연결 없음), 재개발 단계(aptSeq 연결 없음).
- 단지 단위로 연결된 추세 지표 없음(`price_change_12m` 전부 null, 36개월 값 없음, feature 만료). 개발호재·교통 계획 데이터 없음. LLM이 점수에 관여하는 경로 없음(유지).
- → **NOT_READY**. 이름도 "향후가치"는 미래가격 예측으로 오해된다. 나중에 도입한다면 "거래 활발도"(최근 12개월 거래 건수, 원장 기반)처럼 **관측값을 그대로 말하는 이름**을 권장.

## 6. 로그인/비로그인 흐름(확정안, UI 미구현)

| 상태 | 공통 점수 | 개인화 영역 |
|---|---|---|
| 비로그인 | 그대로 | 계산하지 않음. "로그인하면 나에게 맞는 점수를 볼 수 있어요" CTA |
| 로그인 + 중요도 미설정 | 그대로 | 계산하지 않음. "나에게 맞는 점수 설정하기" |

## 7. 입력 방식

**각 축 1~5 중요도 → 내부 정규화**(권장). 합계 100 직접 배분은 사용자가 숫자를 맞춰야 해 이탈이 크다.
`w_i = importance_i / Σ importance`. 최소값 1(0 없음 — 축을 완전히 끄는 기능은 V1에서 제외, 결측 처리와 혼동 방지).
기본값을 미리 채워 저장하지 않는다(설정 전에는 점수 없음).

## 8. 계산·정규화

`personalScore = Σ_{i∈present} axisScore_i × importance_i / Σ_{i∈present} importance_i`

- 축 점수는 모두 공통 엔진의 0~100 absolute curve 결과(도메인 점수 또는 요소 점수) — 같은 척도. percentile 아님.
- 반올림은 표시에서만(공통 점수와 동일).
- 모든 단지·사용자에 결정적. 사용자 간 공유 상태 없음.

## 9. 결측 규칙

- 결측 축은 **분모에서 제외하고 재정규화**(0점 처리 금지). 주차는 실측(KNOWN)만 사용.
- `fitCoverage = Σ present importance / Σ importance`. **0.6 미만이면 LIMITED**(점수는 보이되 "정보가 부족한 항목이 있어요" + 제외 축 명시). 공통 점수가 NOT_ENOUGH_DATA면 계산 안 함.
- 사용자 설명 예: "주차 정보가 없어 주차를 뺀 나머지 항목으로 계산했어요."
- 예(합성값): 교통80·생활70·초등=없음·신축60·주차50, 중요도 가족형(2/4/5/3/3) → 64.2, coverage 0.71 → 표시 가능.

- 결정적(2회 계산 동일), 2,833단지 전체 계산 3.6~7.8ms(단지당 약 0.001~0.003ms).
- 해석: 공통 점수가 이미 교통·생활·교육 균형이라, 비슷한 선호에서는 차이가 작고(순위 상관 0.91), 신축·주차처럼 공통 점수 비중이 작은 축을 중시할 때 크게 달라진다. "모두 3"도 공통과 다른 이유는 단지 도메인을 신축·주차로 쪼개고 세대수를 빼며 주차 중립값을 쓰지 않기 때문 — **UI에서 두 점수가 같은 계산이 아님을 밝혀야 한다**.
- 대중교통 우선의 LIMITED 51은 교통 도메인 결측 단지(51)와 정확히 일치 → 결측 규칙이 의도대로 동작.

## 11. 설명 가능성

- 숫자 + 축별 표: 축 이름 · 내가 고른 중요도 · 이 단지 축 점수 · 반영 여부(제외 사유).
- "잘 맞는 점/아쉬운 점"은 **중요도 4~5로 고른 축** 중 축 점수 상·하위를 고르고, 문장은 공통 브리핑(`ApartmentBriefingV2`)의 원자료 기준 문구(예: 주차 세대당 1.2대 이상, 지하철 1km 이상/없음, 준공 30년 이상)를 재사용한다. 경계값 결정은 P2-B에서 승인. LLM 문장 생성 금지.
- 공통 점수와 나란히: "이집 점수 78 · 나에게 맞는 점수 86 (내 중요도 반영)".

## 12. 상세·비교 연동

- **상세**: `ApartmentScoreCard`(`apt-client.tsx`) 바로 아래 별도 카드. 이미 받은 `scoreResult._shadowV2`에서 축 점수를 뽑아 클라이언트 순수 함수로 계산. 선호는 로그인 시 `GET /api/my/preferences` 1회(세션 동안 메모리 캐시, URL·analytics에 넣지 않음).
- **비교**: `CompareV2` `ScoreSection`에 A/B "나에게 맞는 점수" 행 추가. `buildScore`가 이미 도메인 점수를 가지므로 요소 점수(`ageScore`, `parkingScore`)만 추가 매핑. 최대 2단지.
- **검색/정렬 반영 없음**(V2 이후).

## 13. 성능

- 추가 서버 계산·외부 API 0. 계산은 단지당 ~0.001ms.
- 추가 네트워크: 로그인 사용자당 선호 GET 1회(캐시). 상세 첫 로딩을 막지 않도록 공통 점수 렌더 후 비동기.
- 참고(범위 밖): 공통 점수 API는 요청마다 district cohort 조회·peer universe 캐시(인스턴스별 1시간) 비용이 있다 — 개인화는 이를 늘리지 않는다.

## 14. 법적·신뢰 문구

- 사용: "나에게 맞는 점수", "내 중요도를 반영한 적합도".
- 피함: "추천 점수", "투자가치 점수", "향후가치", 수익·가격 상승 암시.
- 고지: "이집 점수를 내가 고른 중요도로 다시 계산한 값이에요. 투자 판단이나 가격 전망이 아닙니다."

## 15. V1 권장 / V2 이후

- **V1 축(5)**: 교통(READY) · 생활편의(READY) · 신축(READY) · 주차(LIMITED, 실측만) · 초등학교 접근성(LIMITED, 거리 기준 명시)
- **V2 이후**: 예산 적합도(가격, 입력·저장 정책 결정 필요) · 출퇴근 시간(목적지 저장·경로 API 비용 검토) · 거래 활발도(원장 기반 feature 재산정 필요) · 재건축 선호(재개발-aptSeq 연결 필요) · 단지 규모 · 검색 정렬 반영
- **제외**: "향후가치"라는 이름과 예측성 지표

V2 출퇴근 확장성: 저장 JSON에 `version`을 두고 축을 추가하는 방식이면 V1 구조를 깨지 않는다. 통근지는 위치정보라 별도 동의·저장 정책 필요.

## 16. 구현 단계 제안(PHASE 2, 각각 승인)

| 단계 | 내용 | 승인 필요 |
|---|---|---|
| P2-A | 선호 저장(§5 안 A 권장) + `GET/PUT` 검증 + 테스트 | **schema(additive) 승인** |
| P2-B | 순수 계산 모듈(`_shadowV2` → 축 점수 → 개인화 점수·coverage·설명 항목) + 경계값 결정 | 설명 경계값·문구 |
| P2-C | 상세 카드(점수 카드 아래) + 로그인/미설정 상태 | UI |
| P2-D | 비교 행 | — |
| P2-E | MY 중요도 설정 UI(1~5) + 로그인 CTA | — |
| P2-F | analytics(설정 완료·카드 노출 — 값·중요도는 보내지 않음) + QA | analytics 이벤트 추가 |

## 17. 필요한 테스트(PHASE 2)

같은 단지·다른 중요도 → 다른 점수 / 같은 입력 → 같은 점수 / 미설정 → 점수 없음 / 비로그인 → 계산·요청 없음 /
결측 축 재정규화·0점 처리 없음 / 주차 중립값 미사용 / coverage<0.6 → LIMITED / 공통 NOT_ENOUGH_DATA → 개인화 없음 /
공통 점수 값·응답 불변(스냅샷) / 사용자 간 캐시 누수 없음(로그아웃 시 초기화) / 선호 API 본인만·검증 / aptSeq 식별 /
상세·비교 같은 단지 같은 값 / 계산 시간 / "투자·예측" 금지 문구.

## 18. 위험

- 두 점수 혼동 → 나란히 표시 + "내 중요도 반영" 라벨 필수.
- 초등학교 거리를 "학군"으로 오해 → 축 이름·설명 고정.
- 주차 결측 28.5% → 주차 중시 사용자에게 LIMITED가 자주 보임.
- 공통 점수 산출 불가 단지 17.6%(좌표 exact 아님)는 개인화도 불가.
- 교육 점수 NEIS 재산정 시 개인화 값도 함께 바뀜(의도된 동작, 변경 기록 필요).
- 선호 데이터 2행 — 사용 데이터로 가중치 효용을 검증할 표본 없음.

## 19. 부수 발견(수정하지 않음, 보고만)

- 공통 점수 단지 도메인은 주차 결측 시 중립값을 쓰면서 coverage 1.0으로 계산된다(주석은 coverage 손실을 말함). Score 보호 원칙상 변경하지 않았다.
- `score-v2/education.ts:10` 주석의 "School 좌표 0%"는 현재 사실(95.3%)과 다르다.
- `apartment_market_features` 2,937행 전부 `valid_until` 경과, `price_change_12m`·36개월 값 미수집.
- 상세 클라이언트 캐시는 V1 `score`가 null이면 V2가 있어도 캐시하지 않는다.
