## 6. 이집점수 V2 peer context 아키텍처 및 버전 표기 기준

날짜:
2026-09-01

결정:

이집점수 V2의 절대 평가(25/25/25/25 공식)는 변경하지 않고,
비슷한 단지와의 비교(peer context)는 엔진 밖에서 별도로 계산해
추가하는 구조를 채택한다.

Peer 비교군은 L1(구+연식대+세대수 규모)→L2(구+연식대)→
L3(연식대, 부산 전체)→L4(부산 전체) 순으로 최소 표본(8건) 이상을
만족할 때까지 넓혀가며, 세대수 정보가 없는 단지는 규모 기반 L1에
강제로 배정하지 않는다. 비교 신뢰도(confidence)가 낮을수록 정확한
순위(percentile) 숫자를 사용자에게 보여주지 않고, 방향성 문구
또는 "넓은 비교군 기준 참고 수준"이라는 안내만 제공한다. 이는
Phase 1.5/1.6에서 실측 검증한 구조를 그대로 프로덕션에 반영한
것이다.

점수 버전 문자열(`SCORE_V2_VERSION`)은 점수 산출 엔진(곡선/가중치/
도메인 공식) 자체가 바뀔 때만 올린다. peer context는 이미 계산된
절대 점수를 외부에서 비교만 할 뿐 엔진 계산에 관여하지 않으므로,
이번 추가만으로는 버전을 올리지 않는다.

이유:

절대 점수와 상대 비교(peer context)를 하나의 숫자/버전으로
뭉뚱그리면 "무엇이 바뀌어서 점수가 달라졌는지"를 사용자와
개발자 모두 추적하기 어려워진다. 또한 낮은 신뢰도의 비교군으로
계산한 정확한 순위를 그대로 노출하면 표본이 얇은 단지(구축/소규모
단지에 많음)에 실제보다 과도하게 확신에 찬 숫자를 보여주는 위험이
있다.

## 7. 성능 문제의 원인이 DB가 아닐 때는 index를 추가하지 않는다

날짜:
2026-09-01

결정:

84㎡ 부산 전체 조회 성능 문제(PERFORMANCE_V1)를 해결하기 위해
production index 1개(`lawd_cd, exclusive_area, deal_date`)를
사용자 승인 하에 추가했다. EXPLAIN ANALYZE로 실측한 결과 DB
레벨(buffer 사용량 -44%, 불필요하게 걸러지는 행 -96%)에서는
확실한 개선이 있었다.

하지만 실제 API 체감속도는 거의 개선되지 않았다(raw SQL은
75~150ms인데 Prisma `findMany()`는 여전히 3초 이상 — 병목이
SQL이 아니라 Prisma가 22,910개 row를 Node 객체로 만드는
비용이었기 때문). 이 사실을 확인한 뒤, 추가 index를 더 넣어
문제를 "때우려" 하지 않고, 대신 원인에 맞는 해결책(raw SQL로
직접 집계해 최종 결과만 Node로 가져오는 query rewrite)을
다음 STEP 권장사항으로 남겼다.

이유:

증상(느림)만 보고 손에 잡히는 조치(index 추가)를 반복하면,
실제 원인과 무관한 index가 계속 쌓여 쓰기 비용과 저장 공간만
늘리고 문제는 그대로 남는다. EXPLAIN으로 DB 비용과 애플리케이션
비용을 분리해서 실측한 뒤에만 다음 조치를 결정한다 — 이 원칙은
이번 STEP에서 국한된 것이 아니라 앞으로 유사한 "느리다" 문제에도
동일하게 적용한다.
