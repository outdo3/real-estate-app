## 6. 이집점수 V2 peer context 아키텍처 및 버전 표기 기준

날짜:
2026-09-01

결정:

이집점수 V2의 절대 평가(25/25/25/25 공식)는 변경하지 않고,
비슷한 단지와의 비교(peer context)는 엔진 밖에서 별도로 계산해
추가하는 구조를 채택한다.

Peer 비교군은 L1(구+연식대+세대수 규모)→L2(구+연식대)→
L3(연식대, 부산 전체)→L4(부산 전체) 순으로 최소 표본(8건) 이상을
만족할 때까지 넓혀가며, 세대수 정보가 없는 단지는 규모 기반 L1에
강제로 배정하지 않는다. 비교 신뢰도(confidence)가 낮을수록 정확한
순위(percentile) 숫자를 사용자에게 보여주지 않고, 방향성 문구
또는 "넓은 비교군 기준 참고 수준"이라는 안내만 제공한다. 이는
Phase 1.5/1.6에서 실측 검증한 구조를 그대로 프로덕션에 반영한
것이다.

점수 버전 문자열(`SCORE_V2_VERSION`)은 점수 산출 엔진(곡선/가중치/
도메인 공식) 자체가 바뀔 때만 올린다. peer context는 이미 계산된
절대 점수를 외부에서 비교만 할 뿐 엔진 계산에 관여하지 않으므로,
이번 추가만으로는 버전을 올리지 않는다.

이유:

절대 점수와 상대 비교(peer context)를 하나의 숫자/버전으로
뭉뚱그리면 "무엇이 바뀌어서 점수가 달라졌는지"를 사용자와
개발자 모두 추적하기 어려워진다. 또한 낮은 신뢰도의 비교군으로
계산한 정확한 순위를 그대로 노출하면 표본이 얇은 단지(구축/소규모
단지에 많음)에 실제보다 과도하게 확신에 찬 숫자를 보여주는 위험이
있다.

## 7. 성능 문제의 원인이 DB가 아닐 때는 index를 추가하지 않는다

날짜:
2026-09-01

결정:

84㎡ 부산 전체 조회 성능 문제(PERFORMANCE_V1)를 해결하기 위해
production index 1개(`lawd_cd, exclusive_area, deal_date`)를
사용자 승인 하에 추가했다. EXPLAIN ANALYZE로 실측한 결과 DB
레벨(buffer 사용량 -44%, 불필요하게 걸러지는 행 -96%)에서는
확실한 개선이 있었다.

하지만 실제 API 체감속도는 거의 개선되지 않았다(raw SQL은
75~150ms인데 Prisma `findMany()`는 여전히 3초 이상 — 병목이
SQL이 아니라 Prisma가 22,910개 row를 Node 객체로 만드는
비용이었기 때문). 이 사실을 확인한 뒤, 추가 index를 더 넣어
문제를 "때우려" 하지 않고, 대신 원인에 맞는 해결책(raw SQL로
직접 집계해 최종 결과만 Node로 가져오는 query rewrite)을
다음 STEP 권장사항으로 남겼다.

이유:

증상(느림)만 보고 손에 잡히는 조치(index 추가)를 반복하면,
실제 원인과 무관한 index가 계속 쌓여 쓰기 비용과 저장 공간만
늘리고 문제는 그대로 남는다. EXPLAIN으로 DB 비용과 애플리케이션
비용을 분리해서 실측한 뒤에만 다음 조치를 결정한다 — 이 원칙은
이번 STEP에서 국한된 것이 아니라 앞으로 유사한 "느리다" 문제에도
동일하게 적용한다.

## 8. 전월세 데이터는 매매와 별도 테이블로, 근거 없는 취소 컬럼은 만들지 않는다

날짜:
2026-09-01

결정:

전월세(RENT TRADE HISTORY V1) DB 설계에서 두 가지를 확정한다.

1. 매매(`ApartmentTradeHistory`)와 별도의 새 테이블
   (`apartment_rent_histories`)로 만든다. 기존 매매 테이블을
   확장하지 않는다.

2. 새 rent 테이블에는 `dealCanceled` 같은 취소 여부 컬럼을
   만들지 않는다.

이유:

실제 MOLIT 전월세 API(RTMSDataSvcAptRent) 응답을 직접 호출해
확인한 결과, 매매 API에 있는 등기일자/해제여부/해제사유발생일류
필드가 전월세 API에는 하나도 없다. 즉 전월세는 애초에 "취소
여부"를 소스에서 판단할 방법이 없다. 이런 상태에서 취소 컬럼을
만들면 기본값(false)이 "취소 아님이 확인됨"처럼 보이지만 실제로는
"확인 자체가 불가능"이라는 뜻이라 사용자와 개발자 모두를 속이게
된다(§13 데이터 정직성 원칙 위반).

money semantics도 근본적으로 다르다 — 매매는 금액 하나(dealAmount),
전월세는 보증금+월세 두 값이 항상 같이 필요하고, 갱신계약 전용
필드(종전 보증금/월세, 갱신요구권 사용여부)까지 있어 매매 테이블에
억지로 끼워 넣으면 기존 85만+ row 매매 데이터의 모든 컬럼이
nullable해지고 위험한 마이그레이션이 필요해진다.

## 9. RENT TRADE HISTORY V1 PHASE B — identity/자연키 세부 정책

날짜:
2026-09-01

결정:

1. rent row에 aptSeq가 없으면(PHASE A 실측상 0건이지만 방어적으로) sale의
   identityKey() "nd:{name}|{dong}" 이름 기반 폴백을 쓰지 않고 MISSING_APTSEQ로
   분류해 저장 자체를 막는다(blocked). 이 STEP의 작업 지시가 전월세에 한해 명시적으로
   요구한 정책이며, sale과 다른 정책이라는 점을 의도적으로 남긴다.

2. floor는 매매와 동일하게 자연키 구성요소이면서 DB 컬럼은 nullable(Int?)로
   유지하되, 정규화 단계(rent-history-logic.ts)에서 floor를 파싱할 수 없는 row는
   MISSING_FLOOR로 분류해 절대 저장하지 않는다. Postgres unique 제약은 NULL을
   서로 다른 값으로 취급(NULL != NULL)하므로, floor가 NULL인 채로 저장되는 row가
   하나라도 있으면 동일 거래가 재동기화 때마다 새 row로 쌓여 idempotency가
   깨진다 — 이 문제는 scripts/trade-history-logic.ts가 매매에서 이미 확인하고
   해결한 것과 동일 클래스이므로, 스키마를 바꾸는 대신 정규화 레이어에서 동일하게
   막는다.

3. occurrenceIndex는 MOLIT 응답 배열의 등장 순서가 아니라, row 전체 필드의
   결정적 직렬화 정렬 순서로 부여한다(rent-history-logic.ts의 § OCCURRENCE
   DETERMINISM). 같은 데이터를 다른 순서로 다시 받아도(재동기화, 페이지 재정렬 등)
   동일한 자연키 집합이 나와야 idempotent upsert가 안정적이기 때문이다.

4. 대량 sync 시 API 호출 속도는 라이브 트래픽용 GLOBAL_MOLIT_CONCURRENCY(동시 6,
   src/lib/molit-stats-helpers.ts)를 재사용하지 않고, scripts/backfill-trade-history.ts가
   이미 실측으로 검증한 보수적 순차 fetcher(동시 1, 최소 간격 350ms, 지수 백오프)를
   그대로 따른다. PHASE A §16은 원래 라이브 세마포어 재사용을 권고했지만, 그 권고보다
   먼저 존재하는 sale backfill의 실측 결과(라이브 세마포어로는 대량 호출 시 실제
   data.go.kr 스로틀이 걸림)가 더 구체적이고 검증된 근거이므로 이를 따른다.

이유:

전부 "idempotency와 identity 안전을 형식적 권고보다 우선한다"는 동일한 원칙에서
나온 결정이다. 특히 2번과 3번은 새 테이블이라 지금 당장은 문제가 드러나지 않아도
재동기화가 반복되는 순간 데이터가 조용히 부풀어 오르는 종류의 버그라 사전에
차단한다.

## 10. RENT TRADE HISTORY V1 PHASE D — 검증범위는 고정 스냅샷, rolling으로 재정의하지 않는다

날짜:
2026-09-02

결정:

1. PHASE C가 검증한 부산 전월세 범위(202408~202607)는 코드 상수(`RENT_VERIFIED_FROM`/
   `RENT_VERIFIED_TO`, `src/lib/rent-verified-range.ts`)로 고정한다. dashboard의
   `last12Months`(항상 `now` 기준 rolling window)와 매 요청마다 교집합을 계산하되,
   상수 자체를 "오늘 기준 최근 24개월"로 재계산하지 않는다. 시간이 흐르면 rolling
   window 뒤쪽(현재월+직전월)이 이 고정범위 밖으로 밀려나 verified 비중이 점점
   줄어드는 것을 의도적으로 허용한다 — 검증 안 된 기간을 DB complete로 가장하는
   것보다, "커버리지가 서서히 줄어들다가 결국 0이 된다"는 쪽이 훨씬 안전하고
   정직한 실패 방식이기 때문이다. 이 축소는 이번 STEP이 만든 버그가 아니라
   incremental sync가 아직 없다는 구조적 사실의 정직한 반영이며, ADMIN OPS 같은
   미래 소비처가 이 상수를 "24개월"로 재해석하면 안 된다는 경고를 코드 주석에
   남긴다(PHASE C §34가 이미 요구한 원칙의 실제 구현).

2. gapInvest/jeonseRate/volumeSummaryByPeriod(7d/30d/3m)가 row-level·day-level
   데이터를 요구하므로, PHASE C가 미리 만들어둔 "region+dealType GROUP BY" SQL
   aggregate 구조를 이번 PHASE의 실제 소비처로 배선하지 않는다. 사용되지 않는
   aggregate 함수를 "나중에 필요할 수도 있으니" 남겨두지 않고 제거했다 — 이
   프로젝트의 "가상의 미래 요구사항을 위해 설계하지 않는다" 원칙을 SQL 계층에도
   동일하게 적용한 것이다. 대신 raw row 조회 자체의 속도를 최적화한다
   (`findMany`→`select`→`$queryRaw`, PERFORMANCE_V1.1-A/B와 동일 접근).

3. 부산 전체(sido-wide) cold 목표(≤1~1.5초)를 이번 PHASE에서 달성하지 못했다는
   사실을 그대로 보고한다(실측 8.7초). 목표를 낮추거나, 측정 조건을 유리하게
   바꾸거나, 부분 결과를 전체 성공처럼 포장하지 않는다 — 미달성의 근본 원인
   (row-level 필요성 때문에 raw materialization을 완전히 없앨 수 없음)과 후속
   옵션(incremental sync, 또는 volume 비교 로직의 SQL 재구조화)을 문서에 명시하고
   PHASE E 후보로 남긴다.

이유:

세 결정 모두 "정확한 실패/제한을 감추지 않는다"는 이 프로젝트의 데이터 신뢰
원칙(AGENTS.md 데이터 진실성 정책, CLAUDE.md #13)을 PHASE D의 구체적 상황
(rolling window vs 고정 스냅샷, aggregate 불가능한 로직, 미달성 성능 목표)에
적용한 것이다.

영향:

MISSING_APTSEQ/MISSING_FLOOR로 분류된 row는 이번 PHASE 실측(3개 구 x 1개월,
1,238건)에서 0건이었다 — 정책은 존재하되 현재 비용은 0에 가깝다.

사용자는 차이를 설명할 방법이 없다. 제외 건수를 명시하면 "없어서"가 아니라 "위치를
모르기 때문"임이 드러난다.

영향:

동구1·부산진구1·동래구1·남구3·강서구1·사상구1, 총 8건이 메인 지도에 뜨지 않는다.
좌표가 확보되면 별도 코드 변경 없이 자동으로 지도에 나타난다.

## 2026-09-07 — 지도에서 아파트와 오피스텔은 동시에 보여주지 않는다(포커스 모드)

OFFICETEL MAP LAYER V1은 두 레이어를 독립 토글로 뒀다. 실제 모바일에서 둘 다 켜면
부산진구 서면 360px 레벨 3 기준 마커 67개가 화면 면적의 80.0%를 덮어, 도로도 지하철도
동 이름도 보이지 않았다.

아파트와 오피스텔은 배타적으로 전환된다. 항상 정확히 하나가 켜져 있으며(활성인 쪽을
다시 눌러도 꺼지지 않는다) 기본은 아파트다. 학교/재개발/경공매/생숙은 기존 독립 토글을
유지한다. "전체"(둘 다) 모드는 이 STEP에서 만들지 않는다.

근거:

지도는 가진 정보를 전부 얹는 면이 아니라 위치를 찾는 면이다. 두 종류를 겹쳐 놓으면
정보량이 두 배가 되는 게 아니라 지도 자체가 사라진다. 활성인 쪽을 다시 눌러 끄는 것을
허용하지 않은 이유도 같다 — 아무 매물도 없는 빈 지도는 사용자가 의도한 상태가 아니다.

"전체"를 지금 만들지 않은 이유: 두 종류를 함께 보여주려면 합성 묶음 마커와 종류별로
나뉜 목록이 필요하고, 그건 이 STEP의 밀도 문제를 푼 다음에야 설계할 수 있다.

영향:

지도 마커만 해당. 데이터/식별자/상세 경로는 그대로다. 검색으로 오피스텔을 고르면
포커스가 자동으로 오피스텔로 바뀌므로, 고른 결과가 안 보이는 상태로 끝나지 않는다.

## 2026-09-07 — "낱개로 그린다"와 "이름을 쓴다"는 다른 결정이다

맥락:

마커 밀도를 낮추려고 확대 단계별 규칙을 넣으면서, 처음에는 "레벨 3 이하는 낱개 + 이름,
그 이상은 묶음"으로 한 덩어리로 묶었다. 실측해보니 레벨 3 서면 360px에서 오피스텔
낱개 63개 자체는 화면의 25.4%였지만, 같은 63개에 이름표(칩 폭 ~112px)를 붙이자 71.3%가
됐다. 밀도를 만든 것은 마커 개수가 아니라 **라벨 폭**이었다.

결정:

두 규칙을 분리한다.
- 낱개 vs 묶음: 레벨 3 이하 = 낱개 (아파트·오피스텔 공통)
- 이름 표시 여부: 레벨 2 이하 = 이름 (오피스텔)

레벨 3에서는 모든 오피스텔의 **위치**가 아이콘 칩으로 그대로 보이고, 이름은 한 단계 더
확대하면 나온다.

근거:

"마커를 줄인다"와 "라벨을 줄인다"는 사용자에게 전혀 다른 손실이다. 마커를 지우면 그
건물이 거기 있다는 사실 자체가 사라지지만, 라벨을 미루면 위치는 남고 이름만 한 번 더
확대하면 된다. 값싼 쪽을 먼저 줄이는 것이 정보 손실을 최소화한다.

아파트에는 이 분리를 적용하지 않았다 — 아파트 칩의 가격은 그 확대 단계에서도 사용자가
찾는 핵심 정보이고, 단지는 오피스텔만큼 촘촘하지 않아(같은 화면 9개) 문제가 되지 않았다.

영향:

오피스텔 레이어만 해당. 아파트 렌더 경로의 라벨 규칙은 바뀌지 않았다.

## 2026-09-07 — 같은 좌표의 오피스텔은 펼치지 않고 목록으로 고른다

맥락:

V1은 좌표가 완전히 같은 master들(부산 32그룹/79건/최대 5개)을 격자로 부채꼴 전개해
각각 선택 가능하게 했다. 문제는 그 겹침이 **확대해도 절대 갈라지지 않는다**는 것이다 —
펼친 칩들은 서로를 가리고, 좁은 화면에서는 그 자체가 밀도가 된다.

결정:

픽셀 클러스터링 **이전에** 좌표가 완전히 같은 master를 하나의 표시 그룹으로 접고, 개수
배지 하나로 그린다. 누르면 선택 목록 카드가 열리고 각 항목이 표시명/동/규모와 함께
자기 officetelId로 이동한다. 좌표 키는 원본 숫자 그대로 쓰며 반올림하지 않는다.

근거:

확대로 풀리는 겹침(여러 좌표가 화면에서 가까움)과 확대로 안 풀리는 겹침(같은 좌표)은
성질이 다르므로 해법도 달라야 한다. 앞은 확대로, 뒤는 목록으로 푼다. 반올림해서 묶지
않는 이유는 명확하다 — 소수점 아래가 다른 두 건물은 서로 다른 위치이고, 그걸 한 위치로
접으면 없던 "같은 자리"를 만들어낸다.

데이터는 어느 단계에서도 합쳐지지 않는다. 그룹은 표시 단위이며, 어떤 항목도 다른 항목을
대표하지 않는다(DATA: separate / PRESENTATION: may group).

영향:

오피스텔 표시만 해당. 79개 master가 여전히 각자 선택 가능하며 상세 이동은 정확한 master
id로만 일어난다. 향후 "전체" 모드의 합성 마커도 이 표시 그룹 모델을 그대로 확장한다.

## 2026-09-07 — 매물 레이어는 독립 토글이며 전용 "전체" 버튼은 두지 않는다

맥락:

MAP_UX_V2는 아파트/오피스텔을 배타적 포커스 모드로 묶었다. 당시 목적은 밀도였다 —
둘 다 켜면 부산진구 서면 360px에서 마커가 화면의 80%를 덮었다. 그런데 그 STEP에서
확대 단계별 규칙과 묶음 마커를 함께 넣었고, 밀도는 사실 그쪽이 해결했다.

결정:

아파트/오피스텔을 학교·재개발과 같은 독립 ON/OFF 토글로 되돌린다. 네 조합이 모두
유효하며, 둘 다 끈 상태(기본 지도만)도 정상이다 — 빈 지도 방지 로직을 두지 않는다.
별도의 "전체" 버튼도 만들지 않는다.

혼합 모드에서만 오피스텔 밀도 예산을 한 단계 조인다(낱개 한계 3→2, 이름 한계 2→1).
아파트 가격 칩은 그대로 둔다.

근거:

배타성은 밀도 문제의 해법이 아니라 그 위에 얹힌 부수 제약이었다. 진짜 해법(확대 단계
규칙 + 묶음 마커)을 유지한 채 제약만 걷으면 "둘 다 보고 싶다"는 정당한 요구를 막지
않으면서 읽히는 지도를 유지할 수 있다 — 실측 28.8%로 확인했다.

"전체" 버튼을 두지 않는 이유: 두 칩을 모두 켜는 것이 곧 전체다. 별도 버튼은 같은
상태로 가는 두 번째 경로를 만들 뿐이고, 생활형숙박시설이 추가되면 "전체"의 의미가
또 달라져야 한다. 레이어마다 독립 토글 하나면 조합 수가 늘어도 규칙이 변하지 않는다.

혼합에서 오피스텔만 조이는 이유: 그 확대 단계의 오피스텔 칩은 아이콘만 있고 아파트 칩은
가격을 담고 있다. 화면을 나눠 써야 하면 정보가 적은 쪽을 먼저 묶는다 — MAP_UX_V2에서
"마커를 지우기보다 라벨을 미룬다"고 정한 것과 같은 판단 기준이다.

영향:

지도 표시와 컨트롤 접근성 의미(radio → aria-pressed)만 해당. 데이터·식별자·가격 의미·
상세 경로는 그대로다. 향후 합성 마커가 생기더라도 표시 최적화일 뿐 identity 병합이 아니다.

## 2026-09-08 — 불완전한 원본에서 나온 파생 지표를 어떻게 다룰 것인가

배경:

`/api/apt/[name]`은 이미 월별 성공/실패를 정직하게 내려주고 있었지만, 그 응답으로 값을
계산하는 소비자(투자지표, 비교 화면, 브리핑)들은 `trades`만 읽고 완전성 필드를 버렸다.
결과적으로 한 달만 실패해도 전세가율/갭이 확정 수치처럼 보였고, 조회 실패가
"데이터 부족"/"최근 거래 없음"이라는 무거래 표현으로 둔갑했다.

결정:

파생 지표를 **관측 사실**과 **결합 계산값** 두 종류로 나눠 다르게 취급한다.

- 관측 사실(매매가, 전세가, 최근 실거래가): 원본이 불완전해도 값은 유지하고 단서를 붙인다.
- 결합 계산값(전세가율 = 전세/매매, 갭 = 매매−전세): 원본이 하나라도 불완전하면
  숫자를 만들지 않고 "일부 기간의 데이터가 없어 현재 계산할 수 없습니다."로 대체한다.

단일 계열 지표는 자기 계열의 완전성만 본다 — 전월세 조회가 실패했다고 매매가까지 가리지
않는다.

비교 화면에서는 한쪽만 불완전해도 비교를 통째로 숨기지 않고, **어느 쪽이 불완전한지
반드시 밝힌 채로** 보여준다.

근거:

"불완전하면 전부 숨긴다"는 단일 규칙은 두 방향으로 틀린다. 실제로 일어난 거래까지
지워버리면(과잉 억제) 사용자는 존재하는 사실을 못 보고, 반대로 다 보여주면(과소 억제)
틀릴 수 있는 계산값이 확정치로 읽힌다. 구분 기준은 "빠진 달이 이 값을 바꿀 수 있는가"다.
관측된 거래 하나는 빠진 달이 있어도 여전히 일어난 사실이지만, 두 최신값의 비율/차이는
빠진 달이 최신값을 바꾸면 통째로 달라진다.

비교를 통째로 숨기지 않는 이유도 같다. 숨김은 안전해 보이지만 사용자가 얻을 수 있는
정보까지 없앤다. "무엇이 불완전한지 말해주는 것"이 "아무것도 안 보여주는 것"보다
정직하고 유용하다.

완전성 판정을 각 화면이 아니라 `lib/trade-read-state.ts` 한 곳에만 두는 이유:
화면마다 판정을 다시 구현하면 "완전함"의 뜻이 화면마다 갈라지고, 그 순간 어느 화면을
믿어야 하는지 알 수 없게 된다.

새 시각 문법(점선 등)을 만들지 않은 이유: 점선이 "불완전"을 뜻한다는 약속이 이 제품에
아직 없다. 없는 약속을 새로 만드는 것보다 이미 쓰이는 텍스트 배너/라벨을 확장하는 쪽이
학습 비용 없이 정확하다.

영향:

완전한 데이터 경로의 값과 표시는 한 글자도 바뀌지 않는다. 불완전할 때만 억제/단서/배너가
나타난다. 검증된 0건(성공 응답 + 그 달 거래 0건)은 여전히 완전한 데이터이며 기존
"거래 없음" 표현을 그대로 유지한다 — 실패와 진짜 0건의 구분이 이 결정의 전제다.

## 2026-09-08 — 인증키가 든 URL의 실패 메시지를 밖으로 내보내지 않는다

배경:

이 저장소에서 공공데이터 인증키가 샐 뻔한 경로는 항상 같은 모양이었다. 요청 URL에

결정:

인증키가 들어간 URL을 만드는 코드는 원본 실패 메시지를 **응답에도 로그에도 그대로

`apt-building-info.ts`처럼 순수 파서 단위 테스트를 그대로 돌리기 위해 의존성이 없어야
하는 모듈이 있어, 그런 곳에는 2번(원본을 안 쓰기)을 허용한다 — 마스킹할 원본이 없으면
마스킹도 필요 없다.

흘리는 코드가 들어오면 실패한다"는 방어는 결정적으로 남는다.

영향:

정상 경로의 응답/동작은 변화 없다. 실패 시 클라이언트가 받는 메시지가 원본에서 고정
문구로 바뀐다 — 진단에 필요한 정보는 서버 로그(마스킹된 형태)에 남는다.


## 2026-09-11 — 리포트의 웹과 문서는 템플릿이 아니라 밀도로 가른다

리포트를 PDF로 저장하면 단지 리포트가 2페이지로 나뉘고 1페이지 아래 절반이 비었다.
카카오톡으로 공유하면 374×2429px짜리 세로로 긴 웹 캡처가 나갔다. 화면 하나가
"읽는 화면"과 "저장·공유되는 문서" 두 가지 일을 동시에 하려던 결과다.

웹은 스크롤이 공짜지만 문서는 한 장이 예산이다. 이 둘은 같은 레이아웃일 수 없다.

결정:

**문서용 템플릿을 따로 만들지 않는다.** 같은 envelope · 같은 컴포넌트 · 같은 DOM을
쓰고, 레이아웃의 "변하는 값"만 CSS 변수로 갈라 낸다.

레이아웃의 변하는 값 — 열 수, flex 방향, 라벨 폭, 줄 높이, 여백, 글자 배율 — 을 전부
`.sheet`의 토큰으로 올렸다. 반응형/인쇄/내보내기는 구조 규칙을 다시 쓰지 않고 이
토큰만 덮어쓴다. 공유 이미지는 화면 밖에 A4 폭(794px) 클론을 세우고
`data-export-mode="a4"`를 켜서 굽는다.

근거:

문서용 템플릿을 복제하면 **곧 두 벌이 서로 다른 사실을 말하기 시작한다.** 리포트는
숫자와 신뢰 표시가 제품의 전부라서, 화면과 공유 이미지가 다른 값을 보여주는 순간
제품 신뢰가 먼저 깨진다. REPORT TEMPLATE REDESIGN V1에서 6종을 한 디자인 시스템으로
모은 것과 같은 이유다.

토큰으로 가르면 부수 효과도 하나 해결된다. 공유 이미지 클론은 화면 밖에 있어도
뷰포트 기준 media query(`max-width: 860px`)의 지배를 받는다. 구조 규칙을 덮어쓰려면
셀렉터 특이도 경쟁이 필요하지만, 토큰은 `.sheet` 한 곳에서 결정되므로 경쟁이 없다.

같이 정한 것:

- **압축은 여백으로 한다.** `transform: scale()`로 페이지를 통째로 줄이지 않고,
  글자도 작게 만들지 않는다. 여백·줄 높이·중복 배치를 줄인다. 글자 배율(`--r-fs`)은
  큰/중간 글자에만 곱하고 캡션은 그대로 둔다 — 균일하게 줄이면 칩과 각주를 못 읽는다.
- **큰 섹션을 통째로 보호하지 않는다.** `break-inside: avoid`는 쪼개지면 곤란한 작은
  단위(KPI 카드 한 장, 거래 한 줄, 인사이트 상자)에만 건다. 큰 섹션을 묶으면 한 장에
  못 들어갈 때 통째로 다음 장으로 뛰고 앞 장이 비는데, 그게 정확히 이번 결함이었다.
- **비율을 위해 내용을 자르지 않는다.** 내용이 A4를 넘치면 이미지가 그만큼 길어진다.
- **A4를 억지로 채우지 않는다.** 채움률이 65% 미만인 리포트(준비 중 상태 등)는 A4로
  늘리지 않는다. 늘리면 화면의 60%가 흰 여백인 문서가 나온다.
- **줄인 것은 문서 안에서 밝힌다.** 거래를 5건에서 4건으로 줄일 때 문구를 함께 싣는다.
  envelope은 손대지 않는다 — 줄이는 것은 표현이고, 전부인 척하지 않는다.

영향:

웹 화면은 그대로다(단지·비교·일별 시트 높이가 이전 커밋과 동일). PDF는 리포트 6종이
전부 1페이지가 됐고, 공유 이미지는 1080×1528(A4 세로비)로 고정된다.

한계: CSS는 클래스를 `@media print` 안으로 합성해 줄 수 없어, 밀도 값 자체는
`.sheet[data-export-mode='a4']`와 `@media print` 두 블록에 나뉘어 있다. 구조 규칙은
공유되고 값만 나뉘며, 두 블록은 서로를 가리키는 주석으로 묶여 있다.

## 2026-09-11 — GA4는 1st-party 분석을 대체하지 않고 그 옆에 선다

이집에는 이미 자체 분석이 있다(`trackEvent` → `/api/log/event` → `PageView`). GA4를
붙이면서 둘을 하나로 합치거나, 기존 이벤트를 GA4 스키마에 맞춰 다시 쓰는 선택도
가능했지만 그렇게 하지 않았다.

두 시스템이 답하는 질문이 다르기 때문이다. 1st-party는 "단지 A를 몇 명이 봤나",
"지금 몇 명이 접속해 있나" 같은 **제품** 질문을 답하고, 그 데이터는 관리자 대시보드와
직접 묶여 있다. GA4는 "카카오 공유로 몇 명이 들어왔나" 같은 **유입** 질문을 답한다.
합치면 한쪽의 제약(GA4의 이벤트 이름 상한, 자유 텍스트 금지)이 다른 쪽의 표현력을
깎는다.

그래서 어느 쪽도 다른 쪽의 선행 조건이 아니다. GA4가 꺼져 있거나 광고 차단기에
막혀도 제품과 1st-party 로깅은 그대로 동작하고, `sessionId`가 없어 1st-party가
기록하지 못하는 상황에서도 GA4는 독립적으로 동작한다. 연결 지점은 `trackEvent()`
**한 곳뿐**이라 호출부는 한 줄도 바뀌지 않았다.

영향: GA4로 내보낼 이벤트를 바꾸려면 `src/lib/analytics/ga-events.ts` 매핑표 하나만
고치면 된다. 기본값은 "보내지 않음"이며, taxonomy에 새 이벤트가 생겨도 매핑표에
적지 않는 한 자동으로 GA4에 실리지 않는다.

## 2026-09-11 — GA4 파라미터는 denylist가 아니라 allowlist로 막는다

GA4로 나가는 데이터에서 PII를 막는 방법은 두 가지였다. 금지 키 목록을 두고 걸러내거나,
허용 키 목록을 두고 그 밖을 전부 버리거나.

denylist를 고르지 않았다. denylist는 **새 호출부가 생길 때마다 빠뜨릴 수 있다** —
누군가 `ga: { owner_phone: ... }`를 넘기는 순간, 그 키를 미리 금지 목록에 적어 두지
않았다면 그대로 구글로 나간다. allowlist는 반대로 "적지 않은 것은 나가지 않는다"가
기본값이라, 실수의 방향이 안전한 쪽으로 기운다.

같은 이유로 값 수준 검사(이메일/전화 패턴)와 길이 절단을 한 겹 더 뒀다. 허용된 키에
잘못된 값이 실리는 경우까지 막기 위해서다.

`aptSeq`는 보내지 않기로 했다. 국토부 공개 단지 식별자라 그 자체로 PII는 아니지만,
GA4의 역할이 유입 분석으로 한정돼 있어 필요가 없고(단지 단위 제품 분석은 1st-party가
이미 커버한다), 고카디널리티 값은 GA4 커스텀 디멘션 할당량을 빠르게 소모하며,
사용자의 열람 단지 이력을 제3자에게 넘길 이유가 지금은 없다. 지역 분석에는 공개
행정구역 코드 `lawd_cd`로 충분하다.

영향: 새 파라미터를 GA4로 보내려면 `ga.ts`의 `GA_PARAM_ALLOWLIST`에 키를 명시적으로
추가해야 한다. 이 마찰은 의도된 것이다.

## 2026-09-13 — 부산 소프트런칭을 CONDITIONAL GO로 freeze하고, 남은 조건을 코드 밖에 둔다

날짜:
2026-09-13

결정:
`e867a40`을 BUSAN RELEASE CANDIDATE로 고정한다. 이 시점 이후 신규 기능 개발을
중단하고, 출시 전에는 P0/P1 bug fix만 허용한다. 판정은 GO가 아니라 **CONDITIONAL GO**
이며, 남은 조건 3건은 전부 코드가 아닌 영역(실기기 QA, 운영 결정, 외부 프로바이더)에
둔다. git tag는 만들지 않는다.

배경:
출시 직전 감사에서 P0 0건, P1 code blocker 0건이 나왔다. production route 40개가
5xx 없이 응답하고, 인증 경계는 전부 fail-closed이며, 직전 감사의 유일한 성능 P1
(12개월 부산 전체 22~25초)은 production에서 cold 4.73s / warm 0.65s로 재측정되어
해소를 확인했다. 테스트 1670/1670, build exit 0.

그럼에도 GO를 쓰지 않은 이유는 이 환경에 실제 device가 없기 때문이다. 지도/로드뷰는
Kakao JS 키 허용 도메인에 의존하고, 카카오 공유 말풍선과 report의 PNG/PDF export는
브라우저에서만 확인된다. 서버에서 대체 검증할 방법이 없다.

이유:
"코드가 준비됐다"와 "출시해도 된다"를 같은 말로 쓰지 않기 위해서다. 세 조건을 코드
blocker로 분류했다면 잘못된 수정을 유발했을 것이다.

- **Naver 로그인**: PC는 PASS이고 모바일에서만 state cookie 오류가 난다. 서버는 세
  프로바이더에 동일한 쿠키를 발급하므로 공용 인프라 문제가 아니다. 여기서 auth 전체를
  건드리면 정상 동작하는 Google·Kakao까지 위험해진다. LIMITED provider로 출시한다.
- **커뮤니티 게시글 0건**: API도 화면도 정상이고 loading/error/true-empty를 분리해
  보여준다. 빈 것은 운영 상태지 결함이 아니므로 코드에서 seed를 만들지 않는다.
- **실기기 QA**: 못 한 것을 PASS로 적지 않는다. 체크리스트로 남긴다.

감사 중 발견한 테스트 실패 1건도 같은 기준으로 갈랐다. `/api/transactions`의 완전성
가드가 실패했지만 원인은 낡은 정규식이었고 계약 자체는 살아 있었다. 제품 코드를
테스트에 맞추는 대신 가드를 현재 코드 형태에 맞췄다 — 단, `...completeness`가 빠지면
여전히 실패하도록 강도는 유지했다.

영향:
- 출시 판단의 잔여 리스크가 코드가 아니라 QA 1회 + 운영 결정 2건으로 명확해졌다.
  §15 Android Chrome 체크리스트를 통과시키면 GO로 승격한다.
- freeze 기간 동안 P0/P1 외의 변경은 들어가지 않는다. Score formula, DB schema,
  auth 정책은 승인 없이 변경하지 않는다.
- P2로 미룬 항목(`rel="canonical"` 부재, PWA maskable 아이콘, `www` DNS 미등록)은
  post-launch 목록에 올렸다. 어느 것도 첫 방문 경로를 막지 않는다.
