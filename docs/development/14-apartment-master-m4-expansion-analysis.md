## C. 거래 기반 seed coverage — 12/24/36개월 비교(실측)

대표 5개 지역(서구/해운대/부산진구/수영구/기장군, §33 요청 목록에서 M3 검증 완료 2곳 + 대형/특수 성격 3곳 추가)에서 36개월치를 실제로 수집해 12/24/36개월 시점별 distinct `aptSeq`를 비교했다.

| 지역 | 12개월 | 24개월 | 24개월 증가율 | 36개월 | 36개월 증가율(24→36) |
|---|---|---|---|---|---|
| 서구 | 137 | 171 | +24.8% | 196 | +14.6% |
| 부산진구 | 353 | 404 | +14.4% | 429 | +6.2% |
| 해운대구 | 277 | 308 | +11.2% | 337 | +9.4% |
| 수영구 | 214 | 251 | +17.3% | 269 | +7.2% |
| 기장군 | 120 | 152 | +26.7% | 161 | +5.9% |

**패턴**: 5개 지역 전부 12→24개월 구간에서 두 자릿수(%) 증가가 있었고, 24→36개월 구간은 증가폭이 절반 이하로 줄었다. 즉 **"몇 개월을 봐야 대부분의 거래단지가 발견되는가?"에 대한 답은 "24개월이면 상당수(약 85~90%)를 포착하지만, 36개월까지 봐야 증가세가 확실히 둔화된다"**는 것이 실측 결론이다. 12개월만으로는 지역에 따라 최대 27%(기장군)의 단지를 놓칠 수 있어, **M4-B의 기본 조회 기간은 24개월 이상을 권장**한다(36개월까지는 비용 대비 이득이 줄어드는 지점으로 판단).

이 비율을 나머지 11개 구·군에 그대로 적용해 부산 전체 24개월 규모를 추정하면(5개 지역 12→24 평균 증가율 +18.9%를 12개월 실측치 2,906건에 적용): **부산 전체 24개월 예상 distinct `aptSeq` ≈ 약 3,300~3,450개**(추정치, 직접 측정 아님 — 정확한 값은 M4-B에서 16개 구·군 전부 24개월로 재조사해야 확정된다).

## D. 무거래 단지 문제

§B~C의 수치는 전부 "최근 12~36개월 내 실거래가 있었던 단지"만 포함한다. M1이 이미 지적한 대로 **이 방식으로는 장기간(또는 한 번도) 거래되지 않은 단지가 원천적으로 발견되지 않는다.** 이번 STEP에서 무거래 단지의 정확한 규모를 정량화할 수 있는 독립적인 "부산 전체 단지 총목록" 소스가 없어(§E), 이 한계 자체의 크기(예: "부산 전체 실제 단지 수 대비 몇 %가 무거래로 누락되는가")는 이번 M4-A에서 측정하지 못했다 — **이것이 M4-B 이후 정량화가 필요한 명확한 한계로 남는다.**

## G. 신규 aptSeq 자동 발견 정책(질문 6)

M3가 초안으로 제시한 흐름(신규 `aptSeq` 발견 → Master 조회 → 없으면 생성 → enrichment)을 운영 관점에서 상세 검토했다.

| 확인 항목 | 판단 |
|---|---|
| 어느 실거래 동기화 경로에서 신규 발견 가능한가 | 이 프로젝트는 실거래를 DB에 저장하지 않고 매 요청 실시간 호출하는 구조(M1 §1-4 재확인)이므로, "동기화 배치" 자체가 현재 존재하지 않는다 — **신규 발견을 위한 별도 배치를 새로 만들어야 한다**(기존 실거래 조회 경로에 얹을 수 없음). |
| 실시간 사용자 조회 시 Master 생성해도 되는가 | **권장하지 않는다.** 사용자 요청 경로에서 건축물대장/Kakao enrichment(각 초 단위 지연 가능)까지 동기로 수행하면 응답 지연이 커지고, 동시 요청 시 같은 `aptSeq`에 대한 경쟁 조건(§동시성)이 발생하기 쉽다. |
| 관리자 batch가 더 적절한가 | **적절하다** — 이미 이 프로젝트에 `api/admin/presales/sync`처럼 관리자 수동 트리거 + 서버사이드 배치 처리 선례가 있다(P2-C에서 확정된 패턴, `requireAdmin()` 보호 + `MAX_SYNC_LIMIT` 클램프). Master 신규 발견도 같은 패턴(관리자 수동 트리거, 상한 클램프, `dryRun` 지원)을 재사용하는 것을 권장한다. |
| 중복/동시성 문제 | `aptSeq`에 이미 unique 제약이 걸려 있어(M3에서 실증) Prisma `upsert`가 DB 레벨에서 경쟁 조건을 안전하게 처리한다 — 별도 락 로직이 필요하지 않을 가능성이 높다(단, 배치가 병렬로 여러 개 동시 실행되는 경우까지는 이번 STEP에서 검증하지 않음). |
| 실패한 enrichment 재시도 방식 | `aptSeq` 확보(Master 행 생성) 자체와 enrichment(건축물대장/Kakao)를 분리하는 M4 정책(§4, 사용자 승인 사항)에 따라, enrichment 실패는 행 자체를 막지 않고 **`totalHouseholds`/`latitude` 등 개별 필드가 null로 남는 것으로 표시**하면 된다. 재시도는 "null인 필드만 다시 채우는" 별도 배치로 분리 설계 가능(이번 STEP에서 구현하지 않음). |

**결론**: M3의 초안 흐름은 타당하며, 운영 형태는 **관리자 수동 트리거 배치**(기존 청약홈 sync와 동일한 패턴)로 구현하는 것을 권장한다. 이번 STEP에서 구현하지 않는다.

## H. 실거래 ↔ ApartmentMaster 연결(질문 7)

MOLIT API가 `aptSeq`를 직접 조회 파라미터로 지원하는지 이번 STEP에서 재확인했다 — **API 파라미터는 여전히 `LAWD_CD`+`DEAL_YMD`뿐이며, `aptSeq` 직접 조회는 지원하지 않는다**(M1~M3와 동일 결론 재확인, 이번 STEP에서 공식 문서/실제 응답 구조로 재검증). 따라서:

```
ApartmentMaster.sggCd + 조회 대상 월(DEAL_YMD)
  ↓ MOLIT 월별 조회(기존 fetchMolitData 재사용)
  ↓ 응답에서 aptSeq == ApartmentMaster.aptSeq인 항목만 필터
```

이 구조가 유일한 실현 가능한 연결 방식이라는 M1~M3의 결론을 그대로 재확인한다. 단지 상세페이지에서 이 방식을 쓰면 **한 단지의 최근 거래를 얻기 위해 최소 1개월치(넓게는 12~36개월치) 그 구·군 "전체" 거래를 받아온 뒤 필터링**해야 한다는 비용 구조(§I)가 그대로 유지된다.

## I. 실거래 캐시 정책

| 방식 | 최신성 | 비용 | API 트래픽 | 응답속도 | 전국 확장성 | 운영 난이도 |
|---|---|---|---|---|---|---|
| A. 매 페이지 진입마다 실시간 호출 | 최고 | 낮음(캐시 인프라 불필요) | **높음**(같은 구·군을 여러 사용자가 조회하면 중복) | 느림(수 초) | 낮음(트래픽 선형 증가) | 낮음 |
| B. 서버 인메모리 캐시(현재 `getOrSetCache`, M1~M3에서 이미 확인) | 중간(TTL 동안 정체) | 낮음 | 중간 | 캐시 히트 시 빠름 | **서버리스(Vercel) 환경에서 인스턴스 간 미공유**(M1이 이미 지적한 한계, 재확인) | 낮음(이미 구현됨) |
| C. DB 거래 캐시(구·군+월 단위로 실거래를 DB에 저장) | 배치 주기에 의존 | 최초 저장 비용 | 낮음(저장 후 API 호출 감소) | 빠름(DB 조회) | 좋음 | 중간(스키마/배치 필요, 이번 STEP 금지 항목) |
| D. 월별/일별 batch 저장 | C와 유사, 주기가 더 명확 | C와 유사 | 낮음 | 빠름 | 좋음 | 중간~높음(스케줄러 필요) |
| E. Hybrid(B+C) | 최근 데이터는 인메모리, 과거 데이터는 DB 캐시 | 중간 | 낮음 | 빠름 | 좋음 | 높음 |

**평가**: 현재(B, 인메모리)는 Vercel 서버리스 환경 특성상 효과가 제한적이라는 것이 M1부터 일관된 결론이다. `ApartmentMaster`가 구축되면 "특정 `aptSeq`의 최근 거래"라는 조회 패턴이 명확해지므로, **C(DB 거래 캐시, `aptSeq` 단위)가 가장 합리적인 다음 단계**로 판단된다. 단, 이는 schema 변경(신규 거래 캐시 테이블)이 필요해 **이번 M4-A/M4-B 범위에 포함하지 않는다** — M4 이후 별도 과제로 명시한다.

## J. 건축물대장 실패분석(질문 9~10)

### J-1. M3 실패 유형 재확인 + 신규 실측

M3(서구 5건 실패 사례)에서 확인한 대로 **실패 사례 전부가 "API 오류"가 아니라 "총괄표제부 자체가 미등록"**(표제부에는 존재)이었다. 이번 M4-A에서 이 가설을 다른 지역(부산진구, 대형/다양한 상권 밀집 구)에서 건축년도 버킷별로 추가 검증했다.

| 건축년도 버킷 | 부산진구 표본(6건씩) 총괄표제부 성공률 |
|---|---|
| 1990년 이전 | **100%(6/6)** |
| 1990~2009년 | 83%(5/6) |
| 2010년 이후 | 83%(5/6) |

**중요한 정정**: M3가 시사했던 "오래된 건물일수록 실패율이 높다"는 가설은 **부산진구에서는 재현되지 않았다** — 오히려 pre-1990 건물이 100% 성공했다. 이는 **성공률을 결정하는 진짜 요인이 "건축년도"가 아니라 "건물의 형태(대형 다동 단지인가, 소규모 개별 건물인가)"**라는 것을 시사한다 — 부산진구는 도심 밀집지라 오래된 건물도 대개 정식 다동 아파트 단지인 반면, 서구의 실패 사례(구덕금호/일광/문화 등)는 이름에서도 유추되듯 소규모·개별 건물 성격이 강했다. **즉 건축물대장 성공률은 "건축년도"보다 "지역의 주택 유형 구성(대단지 비율)"에 더 크게 좌우된다**는 것이 이번 STEP의 새로운 발견이다.

### J-2. 실패 유형 분류(요청 예시 대조)

| 유형 | 실측 확인 여부 |
|---|---|
| 총괄표제부 없음(표제부는 존재) | **확인됨**(M3 5건 전수, §J-1 재확인) — 가장 흔한 유형으로 판단 |
| 오래된 소규모 공동주택 | **부분 확인**(§J-1에서 "오래됨"보다 "소규모"가 더 결정적 요인으로 재해석됨) |
| 지번 mismatch | 이번 STEP에서 별도로 확인되지 않음(MOLIT `jibun`을 그대로 썼고, 파싱 실패로 인한 mismatch는 §K-2(숫자 자동변환 문제)와 무관하게 발생 안 함 — M3에서 이미 `.toString()` 방어 적용) |
| 법정동코드 mismatch | 확인되지 않음(MOLIT `umdCd` 직접 사용, REGCODE_PROXY 미사용이라 이 문제 자체가 구조적으로 회피됨, M1 §E-2/M3 재확인) |
| API 원천 데이터 미등록 | 총괄표제부 없음과 사실상 동의어로 판단 |
| 건물/단지 구조 차이(소규모/개별 건물) | **확인됨**(§J-1, 이번 STEP 신규 발견) |

**지역별 성공률 재평가**: M3의 서구 40%/해운대 56%는 "부산 전체의 대표값"이 아니라 **각 지역의 소규모·비정형 건물 비율에 따라 달라지는 값**으로 재해석해야 한다. 부산진구처럼 대단지 위주 지역은 더 높은 성공률(약 89%, §J-1 전체 평균)을 보일 가능성이 있다.

## K. Ledger(건축물대장) 개선 후보(질문 10)

| 후보 | 정확도 위험 평가 |
|---|---|
| 표제부(개별 동) fallback | M3에서 총괄표제부 실패 시 표제부에는 실제로 값이 있음을 확인(§J-1)했다 — 다만 표제부는 **"단지 전체"가 아니라 "그 동 하나"의 값**이므로, 이 값을 `totalHouseholds`/`parkingCount`(단지 총괄 필드)에 그대로 넣으면 M2/M3가 이미 금지한 "동 단위 값을 단지 전체처럼 저장"하는 위험을 재현한다. **도입하려면 별도 필드(`buildingLevelHouseholds` 등, 단지 총괄과 명확히 구분)가 필요하다** — 단순 fallback은 위험하다고 평가한다. |
| 지번 본번/부번 정규화 | 이미 M3에서 안전하게 구현됨(`bun`/`ji` zero-pad), 추가 위험 없음. |
| 도로명주소 fallback | 이미 M3에서 Kakao geocoding 우선순위로 구현됨(§I-16, M3), 건축물대장 조회 자체에는 이 fallback이 없음 — 건축물대장 API는 지번 기반 조회만 지원해(`sigunguCd`+`bjdongCd`+`bun`+`ji`), 도로명주소로 직접 조회하는 별도 엔드포인트가 있는지는 이번 STEP에서 확인하지 못했다(확인 필요). |
| `mgmBldrgstPk` 기반 후속 조회 | 총괄표제부 조회로 `mgmBldrgstPk`를 먼저 얻은 뒤, 이 값으로 표제부(개별 동)를 정확히 열거하는 API가 있는지는 M3 §G-2에서 "확인 필요"로 남긴 사항 — 이번 M4-A에서도 추가 검증하지 않았다(위험 낮은 개선 후보로만 기록). |
| 복수 동 aggregation(표제부 여러 건을 합산해 단지 총괄 추정) | **위험이 크다고 평가** — 부속 건축물(관리동, 상가 등)을 세대수 없는 건물로 잘못 합산하거나 중복 합산할 위험이 있어, M2/M3가 이미 확정한 "총괄표제부의 확정값만 신뢰" 원칙과 충돌한다. 권장하지 않는다. |
| 기타 공식 endpoint | 이번 STEP에서 신규 조사하지 않음(범위 밖). |

**결론**: 표제부 fallback은 "총괄표제부가 없을 때 아예 null로 남기는 것보다는 낫다"는 논리로 매력적이지만, **단지 총괄 필드와 혼동되지 않도록 별도 필드로 분리해야 안전하다** — 이번 STEP에서 schema 변경은 하지 않으므로 이 방향을 M4-B의 스키마 결정 사항으로 넘긴다(§AB).

## N. 동수 확보 전략(질문 13)

`mainBldCnt`(주동 수)/`atchBldCnt`(부속동 수)가 총괄표제부 응답에 이미 존재함을 M1~M3에서 확인했다. 요청안이 언급한 "더 안정적인 다른 필드"는 이번 STEP에서 추가로 발견되지 않았다 — `mainBldCnt`가 사실상 유일한 신뢰 가능 출처다.

`ApartmentMaster.mainBuildingCount`의 정의를 명확히 한다: **총괄표제부의 `mainBldCnt`(주동 수)** — 부속건축물(관리사무소 등, `atchBldCnt`)은 포함하지 않는다. 총괄표제부가 없는 단지는 `null`(§J-2)이며, 표제부가 여러 건인 경우(§K, 도입 시)에도 이 필드는 총괄표제부 값만 신뢰하고 표제부 건수로 대체하지 않는다.

## P. 행정구역 개편 대응(질문 16)

부산 자체에서 M1(전북 45→52 이관)·M2(같은 발견 재확인)에 준하는 지역코드 이관 사례가 있는지 이번 STEP에서 재조사했다 — §B의 16개 구·군 조사에서 **전부 예상된 `lawdCd`로 정상 응답을 받았고(0건 이상 거래 확인), 인천 서구·전북처럼 "0건 지속"되는 이상 징후는 발견되지 않았다.** 부산은 최근 자치구 신설/통폐합 이력이 없어(강서구 이후 안정적) 이번 조사 범위 내에서는 §M1/M2가 발견한 종류의 문제가 재현되지 않았다.

다만 이는 "부산은 안전하다"는 뜻이지 "전국이 안전하다"는 뜻이 아니다 — M1/M2가 이미 인천·전북에서 실제 사례를 발견한 만큼, **Region Master(코드 신선도 관리)의 필요성 자체는 여전히 유효**하다(M2 §H-2 정책 재확인). **Region Master는 M4-B 이전에는 필요하지 않다고 판단한다** — 부산 범위에서는 문제가 재현되지 않았으므로, 전국 확장(M6+) 직전에 다시 점검하는 것으로 충분하다. 이번 STEP에서 Region schema는 만들지 않는다.

## Q. REGCODE_PROXY 의존성 범위(질문 17)

프로젝트 전체에서 `REGCODE_PROXY`/`grpc-proxy-server` 사용처를 재검색해 8개 파일을 확인했다.

## R. Kakao 지오코딩 부산 전체 확장 위험(질문 18)

M3의 실제 사고(빌라/맨션류의 짧고 흔한 이름 "에이스빌라"/"스카이맨션"/"대림맨션"이 경기도 부천시 동명 장소로 오매칭)를 근거로, 부산 전체 확장 시 위험 유형을 정리한다.

|---|---|
| 빌라/맨션(비-대단지) | M3에서 실제 발생(§I, M3 문서) — 짧고 흔한 이름일수록 위험 크다 |

**최종 validation 기준(M4-B 적용 정책)**:

1. **성공률보다 정확도를 우선한다**(요청 원칙 그대로 확정) — Kakao geocoding 결과의 지역(시/도, 가능하면 시/군/구까지)이 기대 지역과 일치하지 않으면 **좌표를 저장하지 않고 `null` 유지**.
2. M3에서 발견한 버그(키워드검색 응답에 중첩 지역 필드가 없어 검증이 우회되던 문제)를 그대로 재사용하지 않는다 — **평문 주소 문자열(`address_name`/`road_address_name`)의 토큰 파싱으로 지역을 검증**하는 M3의 수정된 로직을 M4-B에도 그대로 적용한다.
3. **의심 결과는 자동 보정하지 않고 null로 유지**한다(요청 원칙 재확인) — M3에서 실제로 겪은 "재검증 자체의 일시적 오류(rate limit 추정)로 정상 데이터까지 잘못 null 처리했던 사고"를 반복하지 않도록, 재검증 로직에 **호출 간 지연(delay)을 두는 것을 M4-B 필수 사항으로 제안**한다(M3 §S-2에서 이미 권고한 사항, 재확인).

## V. Batch/Retry 정책(질문 22~23)

### V-1. Batch 단위

요청안의 A~D 후보 중 **A(구·군별 batch)를 권장**한다 — 근거: §B에서 이미 구·군 단위로 데이터를 수집했고, 지역별 규모 편차가 커서(중구 52개 vs 부산진구 429개, §B) 고정 개수(50/100단지) 기준보다 **구·군 단위가 자연스러운 검증 경계**가 된다. 규모가 큰 구(부산진구 353~429개, §C)는 필요시 그 안에서 다시 소분할(예: 100단지씩)하는 **혼합(D) 방식**을 제안한다.

### V-2. Batch 후 검증

M3가 실제로 수행한 검증 항목(§29의 "duplicate/geocode/ledger/errors")을 그대로 batch 단위로 반복한다 — M3 문서 §F/§Q의 검증 패턴(aptSeq 중복 확인, 지역별 성공률 집계, 이름 충돌 확인)을 그대로 재사용 가능하다.

### V-3. 재시도 정책

| 실패 유형 | 재시도 가능 여부 |
|---|---|
| MOLIT 실패(네트워크/타임아웃) | 재시도 가능(1~2회 한도) |
| 건축물대장 실패(총괄표제부 없음) | **재시도 무의미** — §J에서 확인한 대로 "없는 데이터"이지 일시 오류가 아니다. 재시도 대신 null 유지가 맞다. |
| Kakao 실패(네트워크/rate limit) | 재시도 가능(M3에서 실제로 필요성 확인, §R-3) — 단 지연을 두고 제한적으로 |
| DB upsert 실패 | 재시도 가능(일시적 커넥션 문제일 가능성), 단 `aptSeq` unique 위반이면 **재시도가 아니라 즉시 중단·보고**(요청안 M3 원칙, 재확인) |
| validation 실패(지역 불일치 등) | **재시도 무의미** — 다른 검색어로 바꿔서 시도하는 것은 이미 `geocode()`의 fallback 체인(도로명→지번→키워드)에 포함돼 있고, 이 체인을 전부 실패하면 그 자체가 최종 결과(null)다. |

**무한 retry는 하지 않는다**(요청 원칙 재확인, M1의 `syncApplyhomeListings`가 이미 "각 fetch 1회만 시도"하는 것과 동일한 원칙).

## W. idempotency 부산 확장 정책(질문 24)

M3의 seed 코드 구조(`prisma.apartmentMaster.upsert({ where: { aptSeq } })`)를 재검토했다 — 이 구조는 **구·군이 몇 개든, 배치가 몇 번 재실행되든 동일하게 idempotent**하다(각 배치가 자기 지역의 `aptSeq` 후보만 다루고, `upsert`의 `where` 조건이 전역적으로 유일한 `aptSeq`이기 때문에 다른 구·군 batch와 충돌할 여지가 구조적으로 없다). **코드 수정 없이 그대로 부산 전체 batch에 재사용 가능하다고 판단한다.**

## X. 기존 33건과 부산 전체 통합(질문 25)

**이 기준들은 이번 STEP에서 처음 제안하는 것이며, M4-B 실행 결과로 재조정될 수 있다.**

## AA. 사용자 테스트와의 관계(질문 28)

**M4-B가 P2-D4-B(분양 연동)의 선행 조건인 것은 맞지만, 사용자 대면 Alpha 테스트 전체를 무기한 막을 필요는 없다**고 판단한다 — 근거:

- "서구 Alpha" 테스트가 검증하려는 대상(분양-주변아파트-실거래 UX, 사용자 반응)과 "부산 전체 Master 구축"(데이터 인프라 완성도)은 **서로 다른 축**이다.
- M3가 이미 부산 서구 15건으로 P2-D4-A가 설계한 "분양↔주변아파트↔실거래" 흐름을 **read-only로 실제 검증**했다(M3 §33, `@turf/turf` distance 테스트) — 서구 Alpha 수준의 사용자 테스트라면 이미 구축된 서구 33건(정확히는 서구 15건)만으로도 **병행 가능**하다고 판단한다.
- "해운대 Challenge"부터는 부산 전체 Master(또는 최소한 해운대 전체)가 필요할 가능성이 높다 — 해운대는 M3에서도 좌표 성공률(77.8%)이 서구보다 낮아, 사용자 대면 품질 기준을 만족하려면 M4-B의 enrichment 개선이 선행되는 것이 안전하다.

**권장**: 서구 Alpha는 M4-B 완료를 기다리지 않고 병행 가능, 해운대 Challenge부터는 M4-B(적어도 해운대 전체 enrichment 개선) 완료를 선행 조건으로 삼는다.

## AB. 부산→전국 확장 전 필요한 것(질문 29)

부산에서만 통하는 가정을 식별한다.

| 가정 | 부산에서 통하는 이유 | 전국 확장 시 위험 |
|---|---|---|
| `lawdCd` 접두어가 안정적(§P) | 부산은 최근 자치구 개편 이력이 없음 | M1/M2가 이미 확인한 인천(구 단위)·전북(도 단위) 사례가 재현될 수 있음 — **전국 확장 전 필수 재점검 대상** |
| 건축물대장 성공률이 지역 유형에 좌우(§J) | 부산은 도시 지역이라 대단지 비중이 상대적으로 높음 | 농어촌/소도시(요청 예시: 지방 저거래 지역)는 소규모 건물 비중이 높아 성공률이 부산보다 낮을 수 있음 — M1/M2에서 이미 전주/창원 등 일부 표본을 봤으나 건축물대장 성공률까지 지역별로 비교하지는 않았음(추가 표본 필요) |
| Kakao geocoding 위험(동명이역, §R) | 부산 내에서도 이미 실제 발생(§R) — 전국으로 갈수록 "같은 이름, 다른 도시" 충돌 빈도가 늘어날 것으로 예상(정량화 안 됨) | 이름 정규화만으로는 부족, `aptSeq`(지역 내장) 우선 원칙을 절대 포기하지 않아야 함 |
| 서울 고밀도 지역 | 부산에서 아직 확인 안 됨 | 서울 강남구 등에서는 M1/M2가 이미 "현대"/"삼성" 등 반복 충돌을 다수 확인(10건) — 부산보다 밀도 높은 지역에서 이름 충돌 빈도가 더 클 가능성 |
| 세종/제주(특별자치시/도) | 부산과 무관 | 이번 STEP에서 조사하지 않음 — 세종은 기초자치단체가 없는 특수 구조라 `lawdCd` 체계 자체가 다를 가능성(확인 필요) |

**전국 확장 전 추가 표본 지역 제안**: 서울(고밀도, 이미 M1/M2에서 일부 조사됨) + 세종(특수 행정구조) + 강원/제주(과거 특별자치도 전환 이력, 전북과 유사한 코드 이관 가능성) + 지방 소도시(저거래·소규모 건물 비중 확인용, 전주/창원 외 추가 표본).

**"부산 성공 ≠ 전국 자동 성공"임을 명확히 확정한다.**

참고: M4-B 구현범위(질문 30)에 대한 답은 문서 하단 "M4-B 권장 Scope"에서 별도 항목으로 정리한다(중복 방지).

## AB. 후속 단계(M4-C 필요 여부, 질문 31)

이번 M4-A 조사 결과, M4-B(부산 전체 거래기반 Master 구축) 이후 최소 **1개의 후속 단계가 필요하다고 판단**한다 — 근거: §D(무거래 단지)와 §I(DB 거래 캐시)라는 두 개의 명확히 분리된 과제가 이미 식별됐고, 둘 다 M4-B의 핵심 목표(24개월 거래기반 커버리지 확보)와는 성격이 다르다(전자는 커버리지 확장, 후자는 성능/비용 최적화). 다만 **불필요하게 단계를 쪼개지 않는다는 원칙에 따라, 이 둘을 하나의 M4-C로 묶는 것을 제안**한다(별도의 M4-D 등으로 세분화하지 않음):

- **M4-C(제안)**: 무거래 단지 보강(Kakao 반경검색 기반, §E) + 실거래 DB 캐시 설계(§I) — 둘 다 M4-B 완료 후 실사용 데이터로 우선순위를 재평가한 뒤 착수하는 것을 권장한다.

### **A. 현재 구조와 정책으로 MASTER M4-B 부산 전체 구축 진행 가능**

**근거(5개 이내)**:

1. 부산 전체 규모(distinct `aptSeq` 약 2,906~3,450개, §B~C)가 실측으로 확정됐고, M3가 이미 검증한 `aptSeq` unique 정책·seed 파이프라인 구조(upsert, idempotency)가 **코드 수정 없이 그대로 확장 가능**함을 이번 STEP에서 재확인했다(§W).
2. M3가 우려했던 "지역별 건축물대장 성공률 편차"의 원인을 이번 STEP에서 **건축년도가 아니라 건물 형태**로 재규명했다(§J) — 이는 schema나 파이프라인을 바꿔야 하는 문제가 아니라 이미 M2/M3가 채택한 "확정값만 신뢰, null 허용" 정책으로 충분히 안전하게 처리되는 문제다.
3. REGCODE_PROXY는 M4-B 범위에 전혀 영향을 주지 않는다는 것을 재확인했다(§Q) — 이미 우회 경로가 실증됐고, 이번 STEP의 재조사도 이를 재확인했을 뿐이다.
4. Kakao 지오코딩 위험(동명이역)에 대한 최종 validation 기준(정확도 우선, 의심 시 null, 재검증 시 지연 필수)이 M3의 실제 사고 경험을 근거로 명확히 확정됐다(§R).
5. 유일하게 확실히 정량화하지 못한 것은 API 일일 호출 한도(§T)와 무거래 단지 규모(§D) 두 가지인데, 전자는 M4-B 착수 직전 개발자 콘솔 확인으로 즉시 해소 가능한 확인 사항이고, 후자는 애초에 M4-B의 범위가 아니라 M4-C로 명시적으로 분리했다(§AB) — 둘 다 M4-B 진행을 막는 blocker가 아니다.

## M4-B 권장 Scope

### 반드시 할 것

- 부산 16개 구·군 MOLIT 거래단지(24개월 기준, §C) `aptSeq` 확보 및 `ApartmentMaster` upsert(기존 33건 포함, §X).
- 건축물대장 enrichment(총괄표제부만 신뢰, 실패 시 null 유지, §J~L~M~N).
- Kakao 좌표 enrichment(정확도 우선, 지역 검증 필수, 실패 시 null, §R).
- 구·군별(대형 구는 추가 소분할) batch 처리 + batch별 검증(duplicate/geocode/ledger 성공률, §V).
- 재시도 정책 적용(일시 오류만 제한적 재시도, 무한 retry 금지, §V-3).
- idempotency 유지 확인(M3와 동일 방식 재검증, §W).

### 해도 되는 것

- 표제부 fallback을 위한 별도 필드 설계 검토(단, 실제 schema 반영은 M4-B 내에서 신중히 판단 — §K).
- API 호출 간 지연(rate limit 대비) 등 seed 스크립트 안정성 개선(§R-3, M3 §S-2 권고 반영).
- 지역별(구·군별) 건축물대장 성공률·좌표 성공률 통계를 최종 보고서에 기록(§J-1 방식 확장).

### 하지 말아야 할 것

- 무거래 단지 전체 보강(§D~E) — **M4-C로 명시적으로 분리**.
- 실거래 DB 캐시 구축(§I) — **M4-C로 분리**, schema 변경 수반.
- 기존 `Apartment`(20건) 이관/FK 연결(§Y) — 이번 범위 아님.
- Region Master 구축(§P) — 부산 범위에서 불필요, 전국 확장 시 재검토.
- REGCODE_PROXY 제거(§Q) — Master 구축과 무관, 범위 밖.
- P2-D4-B/재개발/커뮤니티 구현 — 전부 범위 밖(요청 원칙 그대로).

## 최종 검수 결정 (2026-08-13)

MASTER M4-A(부산 전체 ApartmentMaster 확장 전 조사)를 **최종 승인**한다. 최종 판단 **A(현재 구조와 정책으로 MASTER M4-B 부산 전체 구축 진행 가능)**를 그대로 확정한다. 다만 **M4-B는 이번 승인만으로 착수하지 않으며, 별도 STEP으로 시작한다.**

### 1. 부산 전체 규모 최종 기록

- 부산 16개 구·군 조사 완료(§B).
- 최근 12개월 distinct `aptSeq` 합계: **2,906개**, `aptSeq` null 비율 **0%**(§B).
- 대표 5개 지역(서구/부산진구/해운대구/수영구/기장군) 기준: 12개월→24개월 평균 **+18.9%**, 24개월→36개월 평균 **+8.6%**(§C).
- **M4-B의 기본 discovery 기간을 최근 24개월로 확정**한다.
- 단, 24개월이 부산 전체 공동주택의 100% coverage를 의미하지 않는다는 것을 명시한다 — 거래가 없거나 장기간 무거래인 단지는 이번 24개월 discovery로 발견되지 않으며, **M4-C 이후 별도 보강 대상으로 유지**한다(§D~E, §AB).

### 2. 건축물대장 실패 원인 정정 — 최종 확정

M3가 제기한 "오래된/소규모 건물일수록 실패가 많다"는 가설을 **일반화하지 않는다.** 부산진구 pre-1990 표본이 오히려 100% 성공했고(§J-1), 지역별 성공률 편차도 크게 나타났다(서구 40%/해운대 56%/부산진구 약 89%).

**최종 정책**: 건축물대장 enrichment 성공 여부는 단순 건축연도가 아니라 **건물/단지 형태, 총괄표제부 존재 여부, 원천 데이터 구조, 지역별 데이터 품질**의 영향을 받는 것으로 본다. **확정되지 않은 원인을 코드 로직에 하드코딩하지 않는다** — M4-B 구현 시 "오래된 건물은 실패할 것"이라는 가정으로 조건 분기를 만들지 않고, 총괄표제부 조회 결과 자체(성공/실패)만으로 판단한다.

### 3. REGCODE_PROXY 정책 — 최종 확정

프로젝트 전체 REGCODE_PROXY 사용처 8곳 재확인 결과(§Q)를 그대로 기록한다. `ApartmentMaster` 구축 경로는 이미 MOLIT 원본 `sggCd`/`umdCd`로 proxy 의존성을 우회하고 있으므로, **M4-B에서 REGCODE_PROXY 제거 작업을 하지 않는다.** 기존 UI/API(`RegionSelectModal.tsx`/`SearchFilterBar.tsx`/`region-utils.ts` 등)의 REGCODE_PROXY 사용처는 별도 기술부채로 유지한다. `region-utils.ts`/`molit-stats-helpers.ts`의 중복 로직 발견도 향후 정리 후보로만 기록한다 — **이번 단계에서 코드를 수정하지 않는다.**

### 4. M4-B 기본 Scope 최종 확정

**반드시 할 것**: 부산 16개 구·군 / 최근 24개월 MOLIT 거래단지 discovery / `aptSeq` 기반 `ApartmentMaster` upsert(기존 33건은 삭제하지 않고 `aptSeq` 기준 upsert) / 건축물대장 enrichment / Kakao 좌표 enrichment / 구·군별 batch / batch별 검증 / idempotency / 데이터 품질 리포트.

**하지 않을 것**: 무거래 단지 보강 / 실거래 DB cache 구축(둘 다 필요 시 **M4-C 이후로 분리**) / legacy `Apartment` 이관 / Region Master 구축 / REGCODE_PROXY 제거 / P2-D4-B / 재개발 / 커뮤니티 / 전국 확장.

### 5. API 호출량 — 추정치로만 기록

MOLIT 약 384회 / 건축물대장 약 3,400회 / Kakao 약 7,100회 / 총 약 10,900회(§T)는 **추정치이며 실제 실행 결과와 다를 수 있음**을 명시한다. 정확한 API별 일일 한도/제한은 추측해서 기록하지 않는다(§T에서 이미 "미확인"으로 명시한 그대로 유지). M4-B에서는 호출 제한을 고려한 batch 실행을 사용한다(§V).

### 6. M4-B 실행 안전원칙 — 확정

M4-B에서 16개 구·군을 처음부터 무검증 연속 실행하지 않는다. **1개 구·군 실행 → 데이터 검증 → 이상 없으면 다음 batch**의 구조를 사용한다(§V-1~2와 일치). 한 batch에서 다음 문제가 발생하면 **즉시 다음 batch를 중단**한다: `aptSeq` unique 충돌, 잘못된 지역 좌표, DB 오류 반복, API 오류 반복, 비정상적으로 높은 enrichment 실패율, 데이터 무결성 문제. **성공률을 높이기 위해 의심 데이터를 억지로 저장하지 않는다**(§R의 "성공률보다 정확도" 원칙을 M4-B 실행 원칙으로 재확인).

MASTER M4-B는 별도 STEP으로 착수한다(이번 승인에는 포함되지 않음).
