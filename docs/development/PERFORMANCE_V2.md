## 1. 측정 방법과 중요한 함정

Production(`real-estate-app-phi-taupe.vercel.app`)에 GET만 보내 재는 스크립트를 만들었다
(`scripts/perf-journey-audit.ts`, READ ONLY, 유료 서비스 불필요).

**콜드 측정의 함정**: 서버리스 함수는 최근 호출되면 따뜻하다. 같은 스크립트를 연속으로
두 번 돌리면 두 번째 실행의 "first"는 이미 warm이라 훨씬 빠르게 나온다. 실제로 오늘
1회차와 2회차가 이렇게 갈렸다:

| 라우트 | 1회차 first (진짜 콜드) | 2회차 first (최근 사용됨) |
| --- | ---: | ---: |
| HOME | **1,234ms** | 652ms |
| SEARCH api | **1,390ms** | 216ms |
| APT DETAIL api | 1,285ms* | 56ms |
| FEED api 전체 | **1,313ms** | 1,448ms |
| OFFICETEL DETAIL page | **1,545ms** | 819ms |

\* 1회차 APT DETAIL api는 테스트 URL의 `dong`이 틀려(`서대신동3가`) 빈 응답을 잰 것이다.
검색이 반환하는 올바른 값은 `서대신동1가`이며, 바로잡은 뒤에는 74.7KB / 49ms warm이다.
**애플리케이션 버그가 아니라 측정 스크립트의 오류였다.**

→ 그래서 이 문서는 **cold와 warm을 절대 섞지 않고** 둘 다 보고한다.

## 2. 최상위 근본 원인 (순위)

### 1위 — 서버리스 **함수 초기화** ~570ms (콜드 지연의 대부분)

`/api/search?q=a`는 두 글자 미만이라 **DB에 접근하지 않고 즉시 반환**한다. 이 경로로
함수 오버헤드만 분리 측정했다:

| | 값 |
| --- | ---: |
| DB 미접근 warm 왕복 | **55ms** |
| DB 미접근 **콜드** 왕복 | **621ms** |
| DB 접근 warm 왕복 | 197ms |
| → DB + 쿼리 비용(warm) | **142ms** |
| → **순수 함수 초기화** | **≈ 570ms** |

즉 콜드 1.2~1.5s의 절반가량이 코드가 실행되기도 전의 런타임/Prisma 초기화다.
호스팅/플랜 변경 없이 앱 코드로 없앨 수 있는 부분이 아니다(§12 "provider 변경 금지").

### 2위 — 거래량 화면의 **기능 버그**(체감상 "느림"이 아니라 "고장")

아래 §4에서 근본 원인과 수정을 다룬다. 목록이 사라지는 화면은 사용자에게 "느리다"로
읽힌다 — 이번 STEP에서 가장 큰 실사용자 개선이다.

### 3위 — 오피스텔 상세의 **SSR → hydrate → fetch 워터폴**

서버가 상세를 그려 보낸 뒤, 클라이언트가 다시 `/transactions`를 불러야 목록이 찼다.
화면이 그려진 다음에도 목록 자리가 한 번 더 비어 있었다.

### 4위 — 콜드 상태의 **DB 커넥션 팬아웃**

`Promise.all`로 여러 쿼리를 동시에 쏘아도 풀에 데워진 연결이 없으면 각 쿼리가 따로
TCP+TLS 핸드셰이크를 해 병렬 이득이 사라진다(PERFORMANCE_V1.2에서 이미 실측된 성질).
`warmupConnections()` 헬퍼가 있었지만 **`/api/stats/dashboard` 한 곳에서만** 쓰이고 있었다.

### 순위에서 제외한 것 (측정 결과 병목 아님)

- **응답 크기**: 지도 마커 API가 비압축 387.9KB로 커 보였지만 **gzip 전송은 30.8KB**다.
  HOME 5.1KB, dashboard 4.5KB. 네트워크가 병목이 아니다.
- **warm API 지연**: 전 구간 27~250ms로 목표(500ms) 안이다.

## 4. P0 — 거래량 하단 목록 사라짐 (사용자 보고 버그)

### 재현 경로
`/stats/feed` 에서 `전체 → 매매 → 전체`, `전체 → 전세`, `매매 → 전세 → 전체`.
상단 지표는 바뀌는데 **하단 단지 목록만 사라진다.** 여러 지역에서 발생.

### 근본 원인

`TransactionFeedView`가 목록을 SWR의 `onSuccess` 안에서 상태로 **복사**하고 있었다.

```ts
onSuccess: (json) => { setAllTrades(offset === 0 ? flat : [...prev, ...flat]); }
```

`onSuccess`는 **실제 fetch가 일어났을 때만** 호출된다. `전체 → 매매 → 전체`로 돌아오면
첫 키가 이미 SWR 캐시에 있고 `dedupingInterval: 60_000` 때문에 재요청이 없다 →
`onSuccess`가 불리지 않는다. 그런데 필터 핸들러는 이미 `setAllTrades([])`를 해 둔 뒤다.

결과: `data`는 정상인데 목록 상태만 빈 배열. 상단 지표는 `data.summary`에서 **직접** 읽으므로
정상 갱신되고, 하단 목록만 사라진다 — 보고된 증상과 정확히 일치한다.

### 수정

목록을 이벤트로 복사하지 않고 **현재 응답에서 파생**시킨다. 페이지네이션(더보기)만
offset별로 누적하며, 누적본에 **그것을 만든 쿼리 키**를 함께 들고 다닌다
(`src/lib/stats/feed-accumulator.ts`, 순수 모듈 + 회귀 테스트 12개).

- `useEffect([data, queryKey, offset])`로 반영 → **캐시 히트에서도 실행된다**
- 쿼리 키에 `dealType`이 포함돼 필터 전환이 누적본을 정확히 가른다
- §16 체감 성능: 전환 중에는 이전 목록을 지우지 않고 **stale로 유지**해 깜빡임을 없앴다
- 빈 상태 판정은 "현재 키의 신선한 응답"일 때만 → 전환 중 빈 화면으로 튀지 않는다

### 검증 (로컬 Production 빌드, 실제 클릭)

| 조작 | 하단 목록 | 상단 지표 |
| --- | ---: | --- |
| 초기 전체 | 56 | 14/0/5/5 |
| → 매매 | 28 | 7/0/4/1 |
| → **전체** | **56** | 14/0/5/5 |
| → 전세 | 16 | 4/0/0/4 |
| → **전체** | **56** | 14/0/5/5 |
| → 매매 → 전세 → **전체** | 28 → 16 → **56** | 일치 |

다른 지역(해운대구)에서도 전 시나리오 통과: 200 → 100 → 200 → 140 → 200.
지역 변경 → 필터 변경 회귀도 통과.

## 5. P1 수정

### (1) 오피스텔 상세 워터폴 제거
서버가 **기본 탭의 첫 페이지를 함께 렌더**한다. 실측: SSR HTML에 거래 50행 포함,
hydrate 후 `/transactions` 호출 **0회**(이전에는 1회 필수).
탭/면적을 바꾸면 그때부터 클라이언트가 API를 쓴다 — 계약 변화 없음.

### (2) 콜드 커넥션 팬아웃 완화
`getOfficetelDetail`에서 master 조회(1쿼리)와 `warmupConnections(2)`를 **겹쳐서** 실행한다.
그 뒤 area/summary 4쿼리가 한꺼번에 나가는데, 콜드에서는 각자 핸드셰이크를 하느라
병렬 이득이 사라지던 구간이다. warm일 때는 추가 비용이 없다(겹치는 await가 있으므로).

### (3) SSR/클라이언트 페이지 크기 불일치 정리
서버는 50건을 프리로드하는데 클라이언트 페이지 크기는 20이라 첫 페이지 캐시 키와
`hasMore` 계산이 어긋날 수 있었다. `OFFICETEL_TX_PAGE_SIZE` 상수 하나로 통일했다.

## 7. 보류된 스키마/인덱스 권고 (이번 STEP에서 만들지 않음)

**`officetel_trade_histories` / `officetel_rent_histories` 의 `officetel_master_id` 인덱스**

- 현재 상태: FK지만 인덱스 없음(Postgres는 FK에 인덱스를 자동 생성하지 않는다)
- 영향 쿼리: `WHERE officetel_master_id = ?` 단독 조회
- 현재 회피책: 상세 읽기 경로는 `(canonical_key, deal_date)` 인덱스로 좁히고 masterId를
  교차 조건으로만 쓴다 → **지금은 필요 없다**(warm 37~93ms)
- 실측 근거: STEP 5A 감사 스크립트에서 master별 상관 서브쿼리를 쓰자
  **statement timeout**이 났고, GROUP BY 집계로 바꿔 해결했다
- 필요해지는 시점: master 기준 대량 집계(지역 랭킹 등)를 만들 때
- 예상 이득: 5,056 × seq scan(88,674 / 226,291행) 제거

**승인 없이 인덱스를 만들지 않았다.**

## 8. 성능 가드레일

새 기능이 조용히 속도를 갉아먹지 않도록 기준을 명시한다.

1. **핵심 라우트당 DB 쿼리 5개 이하**를 기본으로 한다. 넘으면 집계 SQL로 합칠 것.
2. **한 요청에서 동시 DB 쿼리 4개 초과 금지.** 오피스텔 상세가 9개를 동시에 쏘아
   Supabase pooler(`pool_size: 15`)를 `EMAXCONNSESSION`으로 죽인 실제 사고가 있었다
   → `LEFT JOIN LATERAL`로 9 → 2로 줄여 해결.
3. **핵심 상세 경로에서 런타임 지오코딩 금지.** 저장된 좌표만 읽는다.
4. **검색에 상한 없는 SELECT 금지.** 랭킹 후 상위 N만 응답한다.
5. **같은 데이터를 서버와 클라이언트가 중복으로 가져오지 않는다.** 첫 화면 데이터는
   서버에서 함께 내려 워터폴을 만들지 않는다.
6. **차트/지도 라이브러리는 기본 lazy.** 필요한 화면에서만 로드한다.
7. **새 핵심 라우트는 cold + warm 수치를 함께 보고**한다. warm만 보고하지 않는다.
8. 반복 **> 2s = P1**, 핵심 경로 **> 3s = FAIL**.
9. 배포 전후로 `scripts/perf-journey-audit.ts`를 돌려 비교한다(무료, READ ONLY).
