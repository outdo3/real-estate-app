## 1. 측정 방법과 중요한 함정

Production(`real-estate-app-phi-taupe.vercel.app`)에 GET만 보내 재는 스크립트를 만들었다
(`scripts/perf-journey-audit.ts`, READ ONLY, 유료 서비스 불필요).

**콜드 측정의 함정**: 서버리스 함수는 최근 호출되면 따뜻하다. 같은 스크립트를 연속으로
두 번 돌리면 두 번째 실행의 "first"는 이미 warm이라 훨씬 빠르게 나온다. 실제로 오늘
1회차와 2회차가 이렇게 갈렸다:

| 라우트 | 1회차 first (진짜 콜드) | 2회차 first (최근 사용됨) |
| --- | ---: | ---: |
| HOME | **1,234ms** | 652ms |
| SEARCH api | **1,390ms** | 216ms |
| APT DETAIL api | 1,285ms* | 56ms |
| FEED api 전체 | **1,313ms** | 1,448ms |
| OFFICETEL DETAIL page | **1,545ms** | 819ms |

\* 1회차 APT DETAIL api는 테스트 URL의 `dong`이 틀려(`서대신동3가`) 빈 응답을 잰 것이다.
검색이 반환하는 올바른 값은 `서대신동1가`이며, 바로잡은 뒤에는 74.7KB / 49ms warm이다.
**애플리케이션 버그가 아니라 측정 스크립트의 오류였다.**

→ 그래서 이 문서는 **cold와 warm을 절대 섞지 않고** 둘 다 보고한다.

## 2. 최상위 근본 원인 (순위)

### 1위 — 서버리스 **함수 초기화** ~570ms (콜드 지연의 대부분)

`/api/search?q=a`는 두 글자 미만이라 **DB에 접근하지 않고 즉시 반환**한다. 이 경로로
함수 오버헤드만 분리 측정했다:

| | 값 |
| --- | ---: |
| DB 미접근 warm 왕복 | **55ms** |
| DB 미접근 **콜드** 왕복 | **621ms** |
| DB 접근 warm 왕복 | 197ms |
| → DB + 쿼리 비용(warm) | **142ms** |
| → **순수 함수 초기화** | **≈ 570ms** |

즉 콜드 1.2~1.5s의 절반가량이 코드가 실행되기도 전의 런타임/Prisma 초기화다.
호스팅/플랜 변경 없이 앱 코드로 없앨 수 있는 부분이 아니다(§12 "provider 변경 금지").

### 2위 — 거래량 화면의 **기능 버그**(체감상 "느림"이 아니라 "고장")

아래 §4에서 근본 원인과 수정을 다룬다. 목록이 사라지는 화면은 사용자에게 "느리다"로
읽힌다 — 이번 STEP에서 가장 큰 실사용자 개선이다.

### 3위 — 오피스텔 상세의 **SSR → hydrate → fetch 워터폴**

서버가 상세를 그려 보낸 뒤, 클라이언트가 다시 `/transactions`를 불러야 목록이 찼다.
화면이 그려진 다음에도 목록 자리가 한 번 더 비어 있었다.

### 4위 — 콜드 상태의 **DB 커넥션 팬아웃**

`Promise.all`로 여러 쿼리를 동시에 쏘아도 풀에 데워진 연결이 없으면 각 쿼리가 따로
TCP+TLS 핸드셰이크를 해 병렬 이득이 사라진다(PERFORMANCE_V1.2에서 이미 실측된 성질).
`warmupConnections()` 헬퍼가 있었지만 **`/api/stats/dashboard` 한 곳에서만** 쓰이고 있었다.

### 순위에서 제외한 것 (측정 결과 병목 아님)

- **응답 크기**: 지도 마커 API가 비압축 387.9KB로 커 보였지만 **gzip 전송은 30.8KB**다.
  HOME 5.1KB, dashboard 4.5KB. 네트워크가 병목이 아니다.
- **warm API 지연**: 전 구간 27~250ms로 목표(500ms) 안이다.

## 4. P0 — 거래량 하단 목록 사라짐 (사용자 보고 버그)

### 재현 경로
`/stats/feed` 에서 `전체 → 매매 → 전체`, `전체 → 전세`, `매매 → 전세 → 전체`.
상단 지표는 바뀌는데 **하단 단지 목록만 사라진다.** 여러 지역에서 발생.

### 근본 원인

`TransactionFeedView`가 목록을 SWR의 `onSuccess` 안에서 상태로 **복사**하고 있었다.

```ts
onSuccess: (json) => { setAllTrades(offset === 0 ? flat : [...prev, ...flat]); }
```

`onSuccess`는 **실제 fetch가 일어났을 때만** 호출된다. `전체 → 매매 → 전체`로 돌아오면
첫 키가 이미 SWR 캐시에 있고 `dedupingInterval: 60_000` 때문에 재요청이 없다 →
`onSuccess`가 불리지 않는다. 그런데 필터 핸들러는 이미 `setAllTrades([])`를 해 둔 뒤다.

결과: `data`는 정상인데 목록 상태만 빈 배열. 상단 지표는 `data.summary`에서 **직접** 읽으므로
정상 갱신되고, 하단 목록만 사라진다 — 보고된 증상과 정확히 일치한다.

### 수정

목록을 이벤트로 복사하지 않고 **현재 응답에서 파생**시킨다. 페이지네이션(더보기)만
offset별로 누적하며, 누적본에 **그것을 만든 쿼리 키**를 함께 들고 다닌다
(`src/lib/stats/feed-accumulator.ts`, 순수 모듈 + 회귀 테스트 12개).

- `useEffect([data, queryKey, offset])`로 반영 → **캐시 히트에서도 실행된다**
- 쿼리 키에 `dealType`이 포함돼 필터 전환이 누적본을 정확히 가른다
- §16 체감 성능: 전환 중에는 이전 목록을 지우지 않고 **stale로 유지**해 깜빡임을 없앴다
- 빈 상태 판정은 "현재 키의 신선한 응답"일 때만 → 전환 중 빈 화면으로 튀지 않는다

## 8. 성능 가드레일

새 기능이 조용히 속도를 갉아먹지 않도록 기준을 명시한다.

1. **핵심 라우트당 DB 쿼리 5개 이하**를 기본으로 한다. 넘으면 집계 SQL로 합칠 것.
2. **한 요청에서 동시 DB 쿼리 4개 초과 금지.** 오피스텔 상세가 9개를 동시에 쏘아
   Supabase pooler(`pool_size: 15`)를 `EMAXCONNSESSION`으로 죽인 실제 사고가 있었다
   → `LEFT JOIN LATERAL`로 9 → 2로 줄여 해결.
3. **핵심 상세 경로에서 런타임 지오코딩 금지.** 저장된 좌표만 읽는다.
4. **검색에 상한 없는 SELECT 금지.** 랭킹 후 상위 N만 응답한다.
5. **같은 데이터를 서버와 클라이언트가 중복으로 가져오지 않는다.** 첫 화면 데이터는
   서버에서 함께 내려 워터폴을 만들지 않는다.
6. **차트/지도 라이브러리는 기본 lazy.** 필요한 화면에서만 로드한다.
7. **새 핵심 라우트는 cold + warm 수치를 함께 보고**한다. warm만 보고하지 않는다.
8. 반복 **> 2s = P1**, 핵심 경로 **> 3s = FAIL**.
9. 배포 전후로 `scripts/perf-journey-audit.ts`를 돌려 비교한다(무료, READ ONLY).

# PERFORMANCE V2.1 — 콜드 스타트 하드닝 / 첫 방문 최적화

V2가 "콜드 1.0~1.55s, 그 중 ~570ms는 플랫폼"이라고 결론지었다. V2.1에서 그 결론을
다시 측정했고, **일부는 측정 방법의 산물이었다.**

## 1. V2 콜드 결론의 정정

### (a) `cache: 'no-store'`로 쟀다 → CDN을 우회했다

V2 측정 스크립트는 `fetch(url, { cache: 'no-store' })`를 썼다. HOME은 실제로는
**정적 프리렌더 + CDN 캐시**로 서빙된다:

| 요청 방식 | 지연 | `x-vercel-cache` |
| --- | ---: | --- |
| `no-store` 첫 요청 | 373ms | HIT |
| `no-store` 두 번째 | 45ms | HIT |
| **기본(실사용자와 동일)** | **19~30ms** | **HIT** |

즉 V2가 보고한 **HOME 콜드 986ms는 "배포 직후 CDN MISS" 한 번**이고, 그 뒤의 모든
방문자는 20~30ms를 받는다. 일반 사용자의 첫 방문이 1초라는 뜻이 아니었다.

### (b) "~570ms 플랫폼 floor"는 균일하지 않다

한 번도 호출한 적 없는 라우트들의 첫 요청을 재 보면 **49ms ~ 1,105ms로 크게 흩어진다**:

| 라우트 | 첫 요청 | 2번째 |
| --- | ---: | ---: |
| `/api/apt/[name]/facilities` | **49ms** | 44ms |
| `/api/community/posts` | 162ms | 75ms |
| `/api/redevelopment` | 209ms | 91ms |
| `/presales` 페이지 | 275ms | 24ms |
| `/api/ledger`(의존성 1개, 즉시 400) | 900ms | 37ms |
| `/api/stats/yearly` | **6,678ms** | 42ms |

고정된 floor가 있다면 이렇게 흩어질 수 없다. 실제 성질은 **람다 인스턴스 단위 부팅**이고,
이미 부팅된 인스턴스에 라우팅되면 다른 라우트도 빠르다. 그래서 V2의
"모든 콜드 = 570ms 플랫폼" 서술은 **과잉 일반화였고, 이 문서로 정정한다.**

### (c) 남은 진짜 문제는 콜드가 아니라 **캐시 없는 외부 API 라우트**였다

전 라우트 warm 스윕에서 목표(500ms)를 넘는 라우트는 **딱 하나**였다.

## 2. 수정한 것

### P1 — `/api/school/stats` warm 1,105ms → 캐시 적용

요청마다 외부 API를 약 **7회** 불렀다: NEIS 학교목록을 **시도 전체**로 페이지네이션
전량 조회(부산 3페이지) + Kakao 주소 지오코딩 1회 + 학원 카테고리 검색 최대 3회.
**캐시가 전혀 없었다.**

`getOrSetCache(region, 6h)`로 감쌌다. 담기는 값은 거래/가격이 아니라 **학교 명부와
학원 개수**이고, 학교 명부는 학년도 단위로 바뀐다 — 실거래 신선도 계약과 무관하다.
되돌리려면 상수 하나만 바꾸면 된다.

로컬 실측: 2,520ms → **23ms** → 12ms. 지역별로 키가 분리되는 것도 확인
(해운대구 1,357ms → 9ms). 반환 값은 동일(서구 학교 23, 학원 45).

### P1 — Kakao 도메인 preconnect

검색창을 처음 쓰거나 지도를 열면 반드시 붙는 두 호스트에 대해 DNS+TLS를 미리 연다.
**SDK 스크립트를 전역 선로드하지는 않는다**(무거운 것을 미리 받지 않는다는 원칙 유지) —
연결만 미리 연다. 코드에서 실제 사용을 확인한 호스트만 넣었다
(`dapi.kakao.com` 25곳, `t1.daumcdn.net` 1곳).

## 3. 의도적으로 하지 않은 것

| 항목 | 이유 |
| --- | --- |
| `/stats`를 정적으로 전환 | `generateMetadata`가 `searchParams`를 읽어 동적이다. 지역별 공유 메타데이터(GLOBAL SHARE SYSTEM V1)를 위한 **의도된 기능**이고, 얻는 것은 warm 60ms → 25ms(약 35ms)로 §15 임계(100ms) 미만이다. 기능을 성능과 바꾸지 않는다 |
| `/api/stats/yearly` TTL 연장(10분) | 캐시 미스 시 MOLIT을 ~140회 불러 6.7s가 걸린다. TTL을 늘리면 개선되지만 그것은 **데이터 신선도 계약 변경**(STOP 조건 5)이라 임의로 하지 않는다 |
| `/api/stats/yearly` 전월세를 DB로 전환 | 코드 주석은 "전월세는 DB에 없다"고 하지만 이후 `RENT_TRADE_HISTORY_V1`이 `apartment_rent_histories`를 만들었다. 다만 **부산 전 기간 커버리지가 검증되지 않았고**(Phase C 이월), 검증 없이 소스를 바꾸면 거래 건수가 조용히 줄어든다 — 데이터 진실성 위험. `TRADE_DB_FIRST_V1`이 했던 커버리지 분석이 선행돼야 한다 |
| `/api/search` 조기반환 경로의 Prisma 지연 로딩 | 두 글자 미만 검색은 실사용자 경로가 아니다. 흔한 경로에 동적 import 비용만 얹는다 |
| 마커 응답 축소 / 번들 재구성 | V2에서 이미 측정: gzip 전송 30.8KB, warm 120ms. 병목이 아니다 |

## 4. 콜드 측정 방법론 (가드레일에 추가)

1. **`no-store`로 재면 CDN을 우회한다.** 실사용자 체감을 재려면 기본 `fetch`로 재고
   `x-vercel-cache` 헤더를 함께 기록한다.
2. **콜드는 인스턴스 단위**다. 한 번의 콜드 표본으로 개선/회귀를 주장하지 않는다
   (§14). 최소 min/median/max를 남긴다.
3. **배포 직후 측정 = 전 라우트 콜드**라 비교 기준으로 유용하다. 단 그것을
   "일반 사용자의 첫 방문"이라고 부르지 않는다.
4. warm은 median(+p95)으로 보고한다.

## 5. import-time / Prisma 규칙 (가드레일 추가)

- 라우트 모듈 최상위에서 **부작용 있는 초기화**를 하지 않는다(DB 호출, 파일 읽기 등).
- `prisma`는 반드시 `src/lib/prisma.ts` 싱글턴만 쓴다. 라우트에서 `new PrismaClient()` 금지.
- `warmupConnections()`는 **겹칠 await가 있을 때만** 쓴다. 단독으로 앞에 await하면
  콜드에 순수 비용만 더한다.
- 외부 API를 부르는 라우트는 **캐시를 기본으로** 한다. 캐시 없이 외부 API를 2회 이상
  부르는 라우트는 리뷰 대상이다(이번에 발견된 유일한 warm 목표 위반이 그 형태였다).

## 6. 정적/동적 판정 규칙 (가드레일 추가)

- `generateMetadata`에서 `searchParams`를 읽으면 그 라우트는 **동적**이 된다. 공유
  메타데이터가 필요해서 그렇게 한 것이라면 그대로 두고, 필요 없다면 정적으로 둔다.
- 정적 페이지는 CDN HIT(20~30ms)를 받는다. 새 페이지는 기본을 정적으로 두고,
  동적으로 만들 때는 **그 이유를 주석에 남긴다.**
- 거래 데이터는 현재 신선도 계약을 넘겨 캐시하지 않는다.
