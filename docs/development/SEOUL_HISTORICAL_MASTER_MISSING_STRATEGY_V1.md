## 7. 제품 동작 audit (runtime 변경 0)

master 없는 aptSeq의 거래가 각 기능에서 어떻게 보이는지 코드로 확인했다.

| 기능 | 데이터 소스 | 판정 |
|---|---|---|
| 지역 리포트 (`region-read.ts`) | `apartmentTradeHistory` 직접 집계, master는 **enrichment**만 | **(a) 정상 집계** |
| 통계 (stats) | 같은 거래 테이블 | **(a) 정상 집계** |
| 거래 많은 단지 / 최근 실거래 | 거래 테이블 | **(a) 정상 집계** |

### 지도 오귀속 — 실측 (STOP 조건)

`/api/transactions`는 거래의 `(dong, name)`을 `resolveApartmentCoords()`로 master에 연결한다. 1순위 `dong+name` 완전일치, 2순위 **같은 법정동 안에서 `aptNamesMatch()`**(양방향 부분포함 + 차수 가드). master가 없으면 1순위가 구조적으로 실패하므로 **항상 2순위가 돈다.**

운영 함수를 그대로 import해 실제 master·실제 이름으로 실행한 결과:

| | 조사 대상 | NO_MATCH | **오귀속** | 오귀속 행 |
|---|---|---|---|---|
| 서울(backfill 시) | 2,424 aptSeq | 2,086 | **338** | **11,766** |
| 부산(현재 상태) | 1,470 aptSeq | 1,372 | **98** | 2,879 |

실제 사례 — 전부 **다른 단지의 aptSeq와 좌표를 물려받는다**:

- 서울: 신반포**5**·**8**·**9**·**10**·**11**(잠원동, 합계 1,852행)이 전부 → **신반포청구(1998)** 하나로. 신동아(길동 1,133행) → 신동아4. 한신3차 → 한신서래. 우성1 → 우성아파트.
- 부산(현재): 대림타운**1**·**2**·**3**(화명동, 합계 909행) → 전부 **대림타운**. 장백 → 장백장미타워1. 서면 → 서면롯데캐슬스카이. 삼성아파트 → 삼성타운.

**현재 Production 실제 노출 범위**: 지도는 DB-first 경로에서 **최근 12개월**만 읽는다. 지금 그 창에 들어오는 부산 master-없는 행은 **9건**이고, 그중 **1건이 실제로 오귀속된다** — `주례일산맨션(26530-69)` → `주례(26530-72)`의 aptSeq·좌표를 받는다. 나머지 8건은 NO_MATCH(좌표 없음)로 안전하다.

즉 **오늘의 피해는 1행으로 작지만 경로는 열려 있고**, 서울 backfill이 들어오면 잠재 노출이 11,766행으로 커진다. 상세 페이지는 `resolveStrongIdentityAptSeqs` 덕분에 보호되지만 **지도에는 대응하는 보호 장치가 없다**(2순위가 무조건 돈다).

## 8. Backfill 안전성 (현재 master 6,843 그대로 적재할 때)

| 질문 | 답 |
|---|---|
| 73,275 historical 행을 저장할 수 있는가 | **가능** |
| FK 제약이 있는가 | **없음** — `apartment_trade_histories`에 FK **0개**, `apartment_masters`를 참조하는 제약도 0 |
| stats 집계가 되는가 | **된다** — 집계는 거래 테이블 직접, master는 enrichment |
| 상세가 잘못 연결될 위험 | 낮음 — STRONG_RESULT_PROTECTION |
| orphan-like semantics | `aptSeq`는 보존되고 `identityKey = id:{aptSeq}`가 유지된다. master가 없을 뿐 고아 행이 아니다 |
| **제품적으로 올바른가** | **아직 아니다** — §7 지도 오귀속 경로가 열려 있다 |

**저장 가능 ≠ 제품적으로 올바름.** 저장·집계는 안전하고 선례(부산 4.59%)도 있지만, 지도 경로를 닫기 전에는 서울 73,275행을 넣는 것이 오귀속 잠재 노출을 11,766행으로 키운다.

## 9. 권고 정책

**OPTION C(transaction-only)를 채택하고, 과거 단지 master를 만들지 않는다.**

근거는 §4·§5다 — MOLIT의 어떤 exact 증거도 "같은 물리 단지"를 증명하지 못하고, 같은 필지 32건 중 **강한 동일 단지 신호는 0건**이다. master를 만들면 반드시 "이 과거 단지를 어디에 잇는가"라는 판단이 따라오는데, 그 판단을 뒷받침할 증거가 없다.

| # | 항목 | 결정 |
|---|---|---|
| 1 | backfill 전 MASTER 확장 필수인가 | **아니오** |
| 2 | 필요하다면 몇 개인가 | **0** |
| 3 | 사용할 exact 기준 | 해당 없음(생성하지 않음) |
| 4 | transaction-only로 둘 항목 | **2,424 aptSeq / 73,275행 전부** |
| 5 | 같은 필지 32건 merge | **금지** — 강한 신호 0, 재건축 승계 8, 필지 공유 21, 모호 5 |
| 6 | 재건축 후보 처리 | 목록으로만 보존. 승계 관계를 데이터에 기록하지 않는다 |
| 7 | historical master 검색 노출 | 해당 없음(생성 안 함) → 검색 오염 0 |
| 8 | stats 집계 포함 | **포함** — 현재도 거래 테이블에서 집계되므로 추가 작업 없음 |
| 9 | sitemap/SEO | 제외(현재 sitemap이 단지를 싣지 않음) |
| 10 | detail page 접근 | 도달 경로 없음. 직접 URL은 STRONG_RESULT_PROTECTION로 보호 |

### `historicalOnly` 개념 모델 검토

제안된 `historicalOnly / searchVisible / seoIndex / statsIncluded` 플래그 모델은 **지금은 불필요**하다 — 생성하지 않으면 그 플래그가 표현하려던 상태(검색 숨김·SEO 제외·통계 포함)가 **이미 현재 동작과 같다**. 플래그를 도입하는 순간 schema 변경 + 모든 소비자 분기 + 과거 단지 identity 판단이 함께 따라온다. 훗날 재건축 이력을 제품 기능으로 보여주기로 결정하면 그때 별도 승인으로 설계한다(이번 STEP에서 schema 변경 제안은 하지 않는다).

### 선결 조건 (backfill 전)

**지도 2순위 이름 매칭에 상세와 같은 수준의 보호를 넣기 전에는 서울 매매 apply를 하지 않는다.** 방향(별도 승인·별도 STEP):
- `resolveApartmentCoords` 2순위를 **끄거나**, 매칭 성공 시에도 `aptSeq`를 부여하지 않고 좌표만 쓰거나(그 역시 위험), 상세의 `resolveStrongIdentityAptSeqs`와 같은 "더 강한 증거가 있으면 느슨한 매칭 배제" 규칙을 적용한다.
- 가장 보수적인 안: **master에 정확히 일치하지 않는 거래는 마커를 만들지 않는다**(NO_MATCH와 동일 취급). 현재 부산에서 이미 1,372/1,470이 그 상태라 회귀 폭이 작다.
- 이 변경은 지도 마커 동작을 바꾸므로 **사용자 승인 대상**이다. 부산 회귀(마커 수 변화)를 먼저 실측할 것.

## 10. 자연키 충돌 2건 재검증 — **PATCH_REQUIRED**

```
id:11590-3369::114.69::sale|106000|2025-03-15|4|0   → 11590:202503, 11620:202503
id:11590-3369::114.69::sale|105000|2025-08-08|10|0  → 11590:202508, 11620:202508
```

| 항목 | 값 |
|---|---|
| canonical lawdCd | **11590 (동작구)** — aptSeq 앞 5자리 |
| 원인 | 관악구(11620) 응답에 동작구 단지 행이 섞여 나온다(REVIEW_REQUIRED 33행과 같은 계열) |
| 자연키에 lawdCd | **없음** — `(group_key, deal_amount, deal_date, floor, occurrence_index)` |
| 예상 소유자 | **먼저 apply된 구**가 가져간다. 동작을 먼저 적재하면 정상(11590), 관악을 먼저 적재하면 **11620으로 저장돼 구 귀속이 틀어진다** |
| skip 되는 건수 | 나중 구에서 **2건** (`createMany skipDuplicates`) |

**패치가 필요한 지점**: `applyMatchesPlan()`(`scripts/backfill-seoul-sale-logic.ts:148`)은 `report.inserted === planned.inserts`를 요구한다. 충돌 행이 skip되면 실제 insert가 계획보다 2 작아져 **드라이버가 그 셀에서 불필요하게 정지**한다(데이터 손상이 아니라 오탐 정지).

권고(이번 STEP에서 **구현하지 않음**):
- **`sale-sync-core`는 건드리지 않는다.** 기존 행 조회를 lawdCd 없이 넓히면 취소 판정 경로 전체에 영향이 간다 — 위험 대비 이득이 없다.
- 드라이버 쪽에서만: dry-run 때 계획된 insert의 자연키를 **DB 전역 unique index로 조회**해 이미 존재하는 건수를 `expectedSkips`로 셀별 기록하고, `applyMatchesPlan`이 `report.inserted === planned.inserts - expectedSkips`를 보게 한다. 결정적이고 sale-sync-core 무변경이다.
- 적재 순서 권고: **동작(11590)을 관악(11620)보다 먼저** 적용하면 2행이 canonical 구에 저장된다.

## 14. Blockers · 다음

1. **STOP 조건 성립(§7)** — 지도 2순위 이름 매칭이 master 없는 거래를 다른 단지에 귀속시킨다. 서울 backfill 전에 닫아야 한다. **부산에도 이미 존재하는 결함**이며 현재 노출은 1행이다.
2. **PATCH_REQUIRED(§10)** — `applyMatchesPlan`의 skip 보정. 코드는 건드리지 않았다.
3. apply는 여전히 `DEFECT_A_GATE_PASS` 미설정으로 BLOCKED이고, false-cancel 28행 repair 결정도 미결이다.
4. 기존 46행 UPDATE 6건은 apply 승인 항목.
5. 같은 필지 UNRESOLVED 5건은 MOLIT 밖 증거가 필요하다 — 이번 정책(merge 금지)에서는 결정할 필요가 없다.
